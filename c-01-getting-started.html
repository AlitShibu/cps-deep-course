Getting Started with C

You already know how to program — Java gave you variables, loops, functions, objects. This chapter isn't about "how to think like a programmer," it's about the specific things C does differently: no safety net, no garbage collector, and a direct, visible path from your source code down to the machine. Coming from Java, the biggest shift is trust — C trusts you completely, which means it also won't stop you from making mistakes it would consider none of its business.

Section 1.1

What C is, and why it still matters in 2026

Compiled, not interpreted

Java code runs on the JVM — a virtual machine that interprets (or JIT-compiles) bytecode at runtime, giving you portability at the cost of a layer between your code and the real hardware. C is compiled directly to native machine code for a specific processor — no virtual machine, no bytecode, no runtime layer. Your compiled program IS the sequence of instructions the CPU executes, nothing standing in between.

Java runs through a virtual machine every time; C is compiled once into instructions the CPU runs natively.

No safety net — and why that's the point

Java protects you from yourself constantly: automatic memory management (a garbage collector reclaims unused objects), array bounds checking (accessing index 10 of a 5-element array throws an exception rather than silently corrupting memory), and strict typing enforced at compile time and runtime both. C provides none of this by default. You manage memory yourself (Chapters 6-7, 12), array bounds aren't checked at all (writing past the end of an array is legal-looking C that corrupts whatever memory happens to sit next to it), and the type system, while present, is far more permissive about letting you do questionable things without complaint.

Why this is a feature, not just a missing feature

Every safety mechanism costs performance and predictability — a garbage collector can pause your program unpredictably to reclaim memory, which is unacceptable when a motor control loop needs to run every 5 milliseconds without fail (recall the RTOS topic later in your roadmap). C's philosophy is: give the programmer complete control and complete responsibility, so that performance-critical and hardware-adjacent code (operating system kernels, device drivers, microcontroller firmware, real-time control loops) has a language that never does anything you didn't explicitly ask it to do. This is precisely why, decades after Java arrived, C remains the dominant language for embedded systems and everything in your Microcontrollers, RTOS, and ECU roadmap topics.

Where C sits in your roadmap

This course teaches standard C — the language itself, running on your laptop, compiling to a regular executable. Later, your Microcontrollers topic introduces embedded C — the same language, but targeting a microcontroller with far less memory, no operating system underneath it, and direct register-level hardware access. Chapter 13 of this course bridges the two explicitly, but everything through Chapter 12 is foundational C you'd need regardless of whether your final target is a laptop, a server, or a $2 microcontroller.

Section 1.2

The toolchain: from source code to running program

Java's javac does one visible step: source to bytecode. C's build process has four distinct stages, and understanding them now will make several later chapters (especially Chapter 9's preprocessor and header files) click immediately instead of feeling like arbitrary rules.

Four stages: preprocess, compile, assemble, link — gcc runs all four for you by default under one command.
  1. Preprocessing — handles anything starting with # (like #include) purely as text substitution, before any actual C syntax is understood. Chapter 9 covers this fully.
  2. Compilation — translates the preprocessed C code into assembly language — human-readable-ish CPU instructions, still not yet actual binary.
  3. Assembly — converts assembly into an object file (.o) — actual machine code, but not yet a runnable program (it might reference functions, like printf, that live elsewhere).
  4. Linking — combines your object file(s) with any needed libraries (like the C standard library, which provides printf) into one final, runnable executable.

The command gcc program.c -o program runs all four stages silently and produces a runnable file named program. You can also run stages individually — useful for understanding what's happening, and occasionally necessary for larger projects (Chapter 9 covers compiling multiple files separately and linking them together):

gcc -E program.c -o program.i    # preprocessing only -- see the expanded source
gcc -S program.c -o program.s    # compile to assembly, stop there
gcc -c program.c -o program.o    # compile+assemble to an object file, don't link yet
gcc program.o -o program          # link into a final executable
Section 1.3

Your first program, dissected line by line

#include <stdio.h>

int main(void) {
    printf("Hello, world!\n");
    return 0;
}

Every piece here matters, and nothing is decorative — unlike Java, where a "Hello World" carries several concepts (class declaration, static method, access modifiers) that don't matter yet, C's version is genuinely minimal.

LineWhat it does
#include <stdio.h>A preprocessor directive (Section 1.2) — pulls in declarations for standard input/output functions like printf, from the "standard I/O" header file.
int main(void)Every C program's execution begins here — main is not a convention, it's a requirement the linker enforces. int means main returns an integer (its exit code — how it reports success/failure to whatever launched it); void means it takes no arguments (there's a variant that does, covered when it becomes relevant).
printf("Hello, world!\n");Calls the standard library's print function. \n is an escape sequence for a newline character — not two characters, one.
return 0;Exits main, reporting exit code 0 — by strong Unix convention, 0 means "success," any non-zero value signals some kind of failure or specific error condition.
Why exit codes matter, even though Java rarely surfaces this

Command-line tools and scripts routinely check a program's exit code to decide what to do next (if program_ran_ok; then ...) — this is a core part of how Unix-style tooling (including your Git & GitHub track's CI pipelines) chains programs together reliably. It's worth building the habit of returning meaningful exit codes from day one, even in small programs, rather than treating return 0; as unexplained boilerplate.

Compiling and running it

$ gcc hello.c -o hello
$ ./hello
Hello, world!

Note the ./ before hello — unlike Windows, most Unix-like shells (Linux, macOS) don't automatically look in the current directory for executables, as a security precaution. You have to say explicitly "run the one right here."

Section 1.4

Program structure at a glance

A quick map of the pieces you'll flesh out over the next several chapters, so you have a mental skeleton before the details arrive:

#include <stdio.h>      // Section 1.2/1.3 -- preprocessor directives, usually at the top

int add(int a, int b);   // function prototype -- Chapter 4 covers this fully

int main(void) {          // every program's entry point
    int x = 5;             // variable declaration -- Chapter 2
    if (x > 0) {            // control flow -- Chapter 3
        printf("positive\n");
    }
    int result = add(x, 3); // function call -- Chapter 4
    return 0;
}

int add(int a, int b) {    // function definition -- Chapter 4
    return a + b;
}

Notice: every statement ends with a semicolon (Java habit that transfers directly), and code blocks are delimited with curly braces — also familiar from Java. What's different from Java: there's no enclosing class, no public static void boilerplate, and functions can exist freely at the top level of a file rather than needing to live inside a class.

A habit to unlearn immediately

Coming from Java, it's tempting to look for "the class" a C program's logic belongs to. There isn't one — C is not object-oriented. Functions and data are separate; there's no concept of a method "belonging" to a piece of data the way Java's instance methods do. This isn't a missing feature to route around — it's a genuinely different way of organizing a program, and Chapter 4 (Functions) and Chapter 8 (Structs) show you the C-idiomatic way of achieving similar organizational goals without classes.

Section 1.5

Basic input and output

Output with printf — format specifiers

printf takes a format string containing format specifiers — placeholders starting with % — followed by the values to substitute in, in matching order:

int age = 25;
float height = 1.75f;
char grade = 'A';

printf("Age: %d, Height: %f, Grade: %c\n", age, height, grade);
// Age: 25, Height: 1.750000, Grade: A
SpecifierType
%dint
%ffloat / double
%cchar (a single character)
%sstring (Chapter 5 explains what a C string actually is)
%pa pointer's address (Chapter 6)
%%a literal percent sign
A real, common danger — not just a style nitpick

Unlike Java, where a type mismatch is caught by the compiler or throws a runtime exception, mismatching a format specifier and the actual argument type in C is often not caught at all — printf("%d", 3.14) compiles and runs, but reads the wrong number of bytes off the argument list and prints garbage. Modern gcc/clang will warn about this with -Wall (worth always enabling), but it's not a hard compiler error the way it would be in Java. Get in the habit of double-checking format specifiers match your variable types exactly.

Input with scanf

int age;
printf("Enter your age: ");
scanf("%d", &age);
printf("You are %d years old.\n", age);

Notice the & before age — this is the "address-of" operator, and it's not optional decoration. scanf needs to know where in memory to write the value it reads, not just what type to expect — a small, early preview of the pointer concept that Chapter 6 covers in full depth. For now, treat "always put & before a variable name given to scanf" as a fixed rule; the full explanation of why is worth the wait until Chapter 6, where it will make complete sense.

Worked problem

Problem: Write a program that reads two integers from the user and prints their sum.

#include <stdio.h>

int main(void) {
    int a, b;
    printf("Enter two integers: ");
    scanf("%d %d", &a, &b);
    printf("Sum: %d\n", a + b);
    return 0;
}
$ gcc sum.c -o sum && ./sum
Enter two integers: 7 12
Sum: 19

What just happened: scanf("%d %d", ...) can read multiple values from one line, separated by whitespace (spaces, tabs, or newlines are all treated the same way by %d) — you don't need one scanf call per value.

Wrap-up

Recap

  1. C compiles directly to native machine code — no virtual machine layer like Java's JVM — which is exactly why it remains the standard for embedded and performance-critical systems.
  2. C provides no safety net by default (no garbage collection, no bounds checking) — a deliberate tradeoff favoring full control and predictable performance over convenience.
  3. The build process has four stages: preprocess → compile → assemble → link — gcc runs all four under one command by default.
  4. Every C program starts at main; unlike Java, there's no enclosing class — functions exist freely at the top level.
  5. printf/scanf use format specifiers that must match variable types exactly — a mismatch often compiles without error and produces garbage output, unlike Java's stricter type checking.
  6. scanf requires the address of a variable (via &) to know where to write — an early preview of pointers, fully explained in Chapter 6.
Check yourself

Quick check

Question 1

Why does C not need a virtual machine the way Java does?

C is compiled directly into native machine code for a specific processor, so the compiled program runs as actual CPU instructions with no interpretation layer in between — unlike Java, which compiles to bytecode that the JVM interprets/JIT-compiles at runtime.
Question 2

What are the four stages of building a C program, in order?

Preprocessing, compilation, assembly, and linking.
Question 3

Why is scanf("%d", &age) written with an & before age, and what would likely happen if you forgot it?

scanf needs the memory address of the variable to know where to write the value it reads, not just the variable's current value. Forgetting the & is a common bug that often compiles (possibly with a warning) but can crash or corrupt memory at runtime, since scanf would misinterpret age's current value as if it were an address.

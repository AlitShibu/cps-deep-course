Variables, Types & Operators

Java's types are a convenience layer with a lot of help from the runtime. C's types are a direct description of how many bytes of memory to reserve and how to interpret the bits inside them — nothing more, nothing hidden. This chapter builds exact, no-surprises fluency with C's type system, because half of Chapter 6 (pointers) and Chapter 12 (memory model) is really just this chapter applied to memory addresses instead of values.

Section 2.1

The basic types, and what they really are

In Java, int is always exactly 32 bits, everywhere, guaranteed by the language spec. In C, the exact size of a type can technically vary by platform (a holdover from C's history running on wildly different hardware) — but on essentially every modern desktop, laptop, and 32-bit+ microcontroller you'll touch, the sizes below are the practical reality.

TypeTypical sizeHolds
char1 byteA single byte — often a character, but really just an 8-bit number (range: -128 to 127, or 0-255 if unsigned)
int4 bytesA whole number, roughly ±2.1 billion
float4 bytesA decimal number, ~7 significant digits of precision
double8 bytesA decimal number, ~15-16 significant digits — the default choice for real engineering math
Why "typical" and not "guaranteed" — and why it matters for embedded work later

C's standard only guarantees minimum sizes and relative orderings (e.g., int is at least as large as short), not exact sizes — a historical decision that let C run efficiently on very different hardware. On a microcontroller (your later Microcontrollers topic), memory is scarce enough that this ambiguity actually matters: a library called <stdint.h> provides types with guaranteed exact sizes — int32_t (exactly 32 bits, always), uint8_t (exactly 8 bits, unsigned), and so on. Professional embedded C code almost always uses these explicit-width types instead of plain int/char, precisely to avoid depending on a platform's "typical" behavior. File this away now; Chapter 13 revisits it directly.

Signed vs. unsigned

Every integer type can be signed (can represent negative numbers, the default) or unsigned (only non-negative, but doubles the positive range since no bits are "spent" representing sign):

signed char c;     // -128 to 127 (the default, "signed" is often omitted)
unsigned char c;   // 0 to 255

signed int x;      // ~-2.1 billion to ~2.1 billion (the default, "signed" usually omitted)
unsigned int x;    // 0 to ~4.2 billion

Java has no unsigned types at all (a deliberate simplification) — this is a genuinely new concept, and it matters for embedded work: raw sensor readings, hardware register values, and byte-level protocol data (CAN bus frames, from your Motorsport track, are a direct example) are naturally unsigned, and mixing signed and unsigned incorrectly is a classic, hard-to-spot bug (Section 2.4 covers this).

In code — checking sizes on your own machine

#include <stdio.h>

int main(void) {
    printf("char:   %zu byte(s)\n", sizeof(char));
    printf("int:    %zu byte(s)\n", sizeof(int));
    printf("float:  %zu byte(s)\n", sizeof(float));
    printf("double: %zu byte(s)\n", sizeof(double));
    return 0;
}

sizeof is a compile-time operator (not a function call, despite the parentheses-looking syntax) that returns a type's size in bytes — worth running once on your own machine to confirm the "typical" sizes above actually hold there.

Section 2.2

Declaration, initialization, and a critical difference from Java

Declaring vs. initializing

int x;        // declaration only -- x exists, but its value is UNDEFINED (garbage!)
int y = 5;    // declaration + initialization -- y is guaranteed to start as 5
The single biggest "coming from Java" trap in this chapter

Java always initializes variables to a sensible default (0, null, false) automatically. C does not. An uninitialized local variable contains whatever bits happened to already be sitting in that memory location — leftover from whatever used that memory before, effectively random from your program's perspective. Reading an uninitialized variable is legal C (the compiler won't necessarily stop you, though -Wall often warns) and one of the most common sources of bugs that "work on my machine" and then fail mysteriously elsewhere — because the garbage value differs depending on what happened to be in memory beforehand. Always initialize variables when you declare them, as a hard personal rule, not just when it's convenient.

Multiple declarations and constants

int a = 1, b = 2, c = 3;      // multiple variables, one line

const double PI = 3.14159;    // 'const' -- cannot be reassigned after initialization
PI = 4.0;                      // COMPILE ERROR: assignment of read-only variable

const is C's equivalent of Java's final for variables — a compiler-enforced promise that a value won't change after being set. Unlike Java's final, const in C interacts with pointers in a genuinely subtle way (does the pointer itself not change, or does the thing it points to not change?) — this nuance is worth setting aside for now and returning to properly once Chapter 6 gives you pointers to reason about it with.

Section 2.3

Operators

Arithmetic — mostly familiar, one sharp edge

int a = 7, b = 2;
printf("%d\n", a + b);   // 9
printf("%d\n", a - b);   // 5
printf("%d\n", a * b);   // 14
printf("%d\n", a / b);   // 3   <-- integer division! Not 3.5
printf("%d\n", a % b);   // 1   <-- modulo (remainder)
Integer division — the single most common early bug in C

When both operands of / are integers, C performs integer division — the result is truncated toward zero, discarding any fractional part entirely, not rounded. 7 / 2 is 3, not 3.5, and not 4. To get a decimal result, at least one operand must be a floating-point type: 7.0 / 2 or (double)a / b (an explicit type cast, forcing a temporary conversion) both correctly produce 3.5. This single behavior surprises nearly everyone coming from a language with more automatic numeric promotion, and it's a very common source of subtly wrong calculations (e.g. computing an average and getting a truncated integer instead of the real decimal average).

Comparison and logical operators

a == b   // equal to
a != b   // not equal to
a < b, a > b, a <= b, a >= b

a && b   // logical AND
a || b   // logical OR
!a       // logical NOT

These behave like Java's, with one conceptual difference worth flagging: C has no true boolean type in older standards (a _Bool type and the more familiar bool keyword exist in modern C via <stdbool.h>, but historically, and still very commonly in real code) — comparisons and logical expressions evaluate to a plain int: 0 for false, 1 for true. This matters because in an if condition (Chapter 3), any non-zero value counts as true — not just literal 1 — a pattern that shows up constantly in idiomatic C code.

Assignment operators — compound shortcuts

x += 5;   // same as x = x + 5;
x -= 2;   // same as x = x - 2;
x *= 3;   // same as x = x * 3;
x /= 2;   // same as x = x / 2;
x++;      // same as x = x + 1; (post-increment)
++x;      // same as x = x + 1; (pre-increment)

These transfer directly from Java, including the pre/post-increment distinction (the difference only matters when the increment is embedded inside a larger expression, like arr[i++] — a pattern you'll see constantly once Chapter 5 introduces arrays).

Section 2.4

Type conversion — implicit and explicit

Implicit conversion (automatic, sometimes dangerously silent)

C automatically converts between compatible types in many situations — assigning an int to a double variable, or using a char in arithmetic (where it's automatically promoted to an int using its underlying numeric value). This is usually harmless and convenient. It becomes dangerous specifically when it loses information silently:

int big = 300;
char small = big;      // no error, no warning by default!
printf("%d\n", small); // 44 -- NOT 300! Data was silently truncated.

What happened: a char only holds 8 bits (range -128 to 127 if signed). 300 doesn't fit — only the lowest 8 bits of 300's binary representation survive, producing a different, "wrapped around" value. C performs this conversion without complaint by default; it's your responsibility to ensure a value actually fits its destination type.

The signed/unsigned trap

unsigned int u = 5;
int i = -1;
if (i < u) {
    printf("i is less than u\n");
} else {
    printf("i is NOT less than u\n");   // <-- this one actually prints!
}
Why this genuinely surprising result happens

When a signed and unsigned integer are compared directly, C converts the signed value to unsigned before comparing (a rule called the "usual arithmetic conversions"). -1, reinterpreted as unsigned, becomes an enormous positive number (the unsigned type's maximum value) — because negative numbers are stored as very large bit patterns under the hood (Chapter 10's bitwise chapter explains the "two's complement" representation fully). So -1 ends up "greater than" 5 once both are forced into unsigned form. This is a real, well-documented category of bug in production C code — mixing signed and unsigned types in comparisons or arithmetic without deliberate thought.

Explicit conversion — casting

A cast forces a conversion deliberately, making your intent visible in the code rather than relying on (or falling victim to) implicit rules:

double d = 3.99;
int i = (int)d;          // explicit cast -- i is 3 (truncated, not rounded)

int a = 7, b = 2;
double result = (double)a / b;   // cast BEFORE the division happens -- result is 3.5

Note the second example carefully: casting a to double before the division forces the entire division to happen in floating-point (since one operand is now a double, the other gets automatically promoted too) — this is the standard idiom for avoiding Section 2.3's integer-division pitfall.

Worked problem

Problem: Compute the average of 5 exam scores stored as integers, correctly producing a decimal result.

#include <stdio.h>

int main(void) {
    int scores[5] = {88, 92, 79, 95, 84};   // arrays properly covered in Chapter 5
    int sum = 0;
    for (int i = 0; i < 5; i++) {
        sum += scores[i];
    }
    double average = (double)sum / 5;    // cast BEFORE dividing
    printf("Average: %.2f\n", average);   // Average: 87.60
    return 0;
}

Without the cast, sum / 5 would compute as integer division (439 / 5 = 87, truncated), silently discarding the .6 — a realistic, easy-to-miss bug this cast prevents.

Wrap-up

Recap

  1. C's basic types (char, int, float, double) describe fixed-size memory layouts, not guaranteed-portable abstractions like Java's — <stdint.h> types (covered fully in Chapter 13) give exact, guaranteed widths when that matters.
  2. Unlike Java, local variables are not automatically initialized — reading one before assigning it is legal but produces garbage; always initialize on declaration as a hard rule.
  3. Integer division truncates toward zero rather than rounding; get a decimal result by casting at least one operand to a floating-point type before the division happens.
  4. Implicit type conversions can silently lose data (assigning a too-large int to a char) or produce surprising results (mixing signed and unsigned in a comparison) — C won't stop you by default.
  5. Explicit casts — (type)expression — make conversion intent visible and let you control exactly when and how a conversion happens, rather than relying on implicit rules.
Check yourself

Quick check

Question 1

What value does "int x; printf("%d", x);" print, and why is this different from Java?

An unpredictable "garbage" value — whatever bits happened to already be in that memory location. Unlike Java, C does not automatically initialize local variables to a default value.
Question 2

What does 9 / 4 evaluate to in C, and how would you get 2.25 instead?

9 / 4 evaluates to 2 (integer division, truncated). To get 2.25, cast at least one operand to a floating-point type first, e.g. (double)9 / 4.
Question 3

Why can comparing a signed int of -1 against an unsigned int produce a surprising result?

C converts the signed value to unsigned before comparing when the types are mixed. -1 reinterpreted as unsigned becomes a very large positive number, so it can end up appearing "greater than" a small unsigned value, which is the opposite of what you'd expect from the signed values alone.

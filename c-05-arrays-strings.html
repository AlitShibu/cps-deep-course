Arrays & Strings

Java's arrays are objects with built-in bounds checking and a .length property; Java's Strings are a rich, immutable class. C's arrays are raw, fixed-size blocks of contiguous memory with zero built-in protection, and C strings are just arrays of characters with one special convention holding them together. This chapter is where "C trusts you completely" starts to feel real.

Section 5.1

Arrays — fixed-size, contiguous, unprotected

Declaring and using an array

int scores[5];             // declares an array of 5 ints -- values are UNINITIALIZED (Ch.2)
int grades[5] = {90, 85, 77, 92, 68};   // declared and initialized together

scores[0] = 100;            // assign the first element (index 0!)
printf("%d\n", grades[2]);  // 77

Indexing starts at 0, exactly like Java. An array of 5 elements has valid indices 0 through 4 — there is no index 5.

What an array actually is in memory

Unlike Java, where an array is an object living on the heap with metadata (including its length) attached, a C array is simply a fixed block of contiguous memory, large enough to hold all its elements back-to-back, with absolutely no metadata stored alongside it — no length, no bounds information, nothing.

A C array is exactly this block, nothing more — the language itself has no idea how many elements it has once you're past its declaration.
The consequence — out-of-bounds access is not caught

In Java, grades[10] on a 5-element array throws ArrayIndexOutOfBoundsException — always, reliably. In C, grades[10] compiles and runs, silently reading (or, worse, writing to) whatever memory happens to sit past the array's end — memory that might belong to a completely different variable. This is called undefined behavior: the language makes no guarantee about what happens, and it might appear to "work" for a while before crashing unpredictably or corrupting unrelated data. Because there's no built-in length, you are responsible for tracking an array's size (often via a separate variable or a #define constant) and never indexing past it — the compiler will not help you.

sizeof and array length

int arr[10];
int length = sizeof(arr) / sizeof(arr[0]);   // 10 -- total bytes / bytes-per-element
printf("%d\n", length);

This is the standard idiom for computing an array's length within the same scope where it was declared — it stops working correctly once an array is passed into a function (Section 5.2 explains exactly why).

Section 5.2

Arrays and functions — the decay you need to know about

Pass an array to a function, and something subtle happens: the array decays into a pointer to its first element — the function receives only an address, not the array itself, and critically, not its size.

void print_array(int arr[], int length) {   // 'int arr[]' is really 'int *arr' underneath
    printf("Inside function, sizeof(arr) = %zu\n", sizeof(arr));   // prints 8 (a pointer's size!)
    for (int i = 0; i < length; i++) {
        printf("%d ", arr[i]);
    }
    printf("\n");
}

int main(void) {
    int nums[5] = {1,2,3,4,5};
    printf("In main, sizeof(nums) = %zu\n", sizeof(nums));   // 20 (5 ints x 4 bytes)
    print_array(nums, 5);
    return 0;
}
Why this is a genuinely common source of bugs

Section 5.1's sizeof(arr)/sizeof(arr[0]) trick to compute array length works perfectly inside main, where nums is a real, full-sized array. But inside print_array, arr is just a pointer (8 bytes on most modern systems) — sizeof(arr) returns 8, not 20, and computing "length" this way inside the function would silently give a wrong, tiny answer. This is exactly why print_array takes a separate length parameter — once an array decays to a pointer at a function boundary, the size information is genuinely gone, and there is no way to recover it from the pointer alone. Every C function that operates on an array you didn't just declare locally needs its size passed in explicitly, as a rule with no exceptions.

A first, gentle preview of Chapter 6

"Arrays decay into pointers" is your first real hint of how deeply connected arrays and pointers are in C — deep enough that Chapter 6 revisits this exact fact and builds on it directly. For now, the practical takeaway is simple: always pass an array's length alongside the array itself to any function that needs to work with it.

Section 5.3

Strings — just arrays of characters, with a convention

The core idea: null-termination

C has no dedicated string type. A C string is simply an array of char, with one crucial convention: it ends with a special null terminator character, written '\0' (the character with value 0 — not the digit '0', not a space, a genuinely distinct character), marking where the actual text stops.

char greeting[6] = {'H', 'e', 'l', 'l', 'o', '\0'};   // explicit, verbose form
char greeting2[] = "Hello";                             // equivalent, and idiomatic --
                                                          // the compiler adds '\0' automatically
"Hello" is 6 bytes in memory, not 5 — the null terminator is part of the string, always.
Why this matters so much

Every string-handling function in the standard library (printf's %s, strlen, strcpy, and so on) works by reading characters one at a time until it finds '\0' — that's genuinely the only way it knows where the string ends, since (per Section 5.1) a C array carries no length metadata of its own. If a "string" is missing its null terminator — through a bug, or a manually-built character array that forgot it — these functions will keep reading past the intended end, into whatever memory happens to follow, until they eventually (by luck) hit a zero byte or crash. A missing null terminator is one of the most classic C bugs there is.

Common string functions (from <string.h>)

#include <string.h>

char s1[20] = "Hello";
char s2[] = " World";

printf("%zu\n", strlen(s1));      // 5 -- length NOT including the '\0'
strcat(s1, s2);                    // appends s2 onto the end of s1 (s1 must have room!)
printf("%s\n", s1);                 // "Hello World"

char s3[20];
strcpy(s3, "Copy me");              // copies a string into s3 (s3 must have room!)

if (strcmp(s1, s3) == 0) {          // strcmp returns 0 when strings are EQUAL (not true/false!)
    printf("equal\n");
} else {
    printf("not equal\n");
}
Two sharp edges, both extremely common in real bugs

1. Buffer overflow: strcat and strcpy do not check whether the destination array is actually big enough — writing past a fixed-size array's end is undefined behavior (Section 5.1), and with strings, this specific mistake is common enough to be a notorious, decades-old category of security vulnerability. Prefer the safer strncat/strncpy variants, which take an explicit maximum length, whenever the input size isn't tightly controlled.

2. strcmp's return value is not a boolean the way you'd expect: it returns 0 when the strings are equal (not 1/true as many beginners assume), and a negative or positive number indicating alphabetical ordering otherwise. Writing if (strcmp(a,b)) — intending "if equal" — actually checks the opposite, since a non-zero result (meaning "not equal") is what counts as true in an if (Chapter 3, Section 3.1). Always write if (strcmp(a,b) == 0) explicitly.

Section 5.4

Multi-dimensional arrays

int grid[3][4];   // 3 rows, 4 columns -- 12 ints total, still one contiguous block

grid[1][2] = 99;   // row 1, column 2

int matrix[2][3] = {
    {1, 2, 3},
    {4, 5, 6}
};

Despite the double-bracket syntax, a 2D array in C is still just one single contiguous block of memory underneath — grid[3][4] is really 12 ints laid out back-to-back in row-major order (the entire first row, then the entire second row, and so on). This matters directly for your CPS/robotics work: a small 2D transformation matrix (recall the Linear Algebra roadmap topic) or a sensor's grid-shaped data (like a low-resolution depth camera frame) is often represented exactly this way in embedded C.

Worked problem

Problem: Given a 2D array representing sensor readings from a 3x3 grid, find the average reading.

#include <stdio.h>

int main(void) {
    float readings[3][3] = {
        {21.5, 22.0, 21.8},
        {23.1, 22.4, 21.9},
        {22.7, 23.0, 22.2}
    };

    float sum = 0;
    int count = 0;
    for (int row = 0; row < 3; row++) {
        for (int col = 0; col < 3; col++) {
            sum += readings[row][col];
            count++;
        }
    }
    printf("Average: %.2f\n", sum / count);   // Average: 22.29
    return 0;
}

Nested loops over a 2D array — the outer loop walks rows, the inner walks columns within each row — is the standard, idiomatic pattern, and it directly mirrors how the data is actually laid out in memory (row-major order), which also makes it the most cache-efficient traversal order on real hardware.

Wrap-up

Recap

  1. A C array is a fixed-size, contiguous block of memory with no built-in length metadata — unlike Java, out-of-bounds access is not caught and produces undefined behavior.
  2. Passing an array to a function makes it decay into a pointer to its first element, losing size information — always pass the length as a separate parameter.
  3. A C string is just a char array with a null terminator ('\0') marking its end — every standard string function relies on finding this terminator to know where a string stops.
  4. strcat/strcpy don't check destination buffer size (a classic overflow risk); strcmp returns 0 for equal, not a boolean true — both are common, sharp-edged pitfalls.
  5. Multi-dimensional arrays are still one contiguous block underneath, laid out in row-major order — relevant directly for matrix and grid-shaped sensor data in later roadmap topics.
Check yourself

Quick check

Question 1

Why does a C function that receives an array parameter also need a separate length parameter?

Because the array decays into a pointer at the function boundary, losing its size information entirely — sizeof on the parameter returns the pointer's size, not the original array's size, so there's no way to recover the length from inside the function without it being passed explicitly.
Question 2

How many bytes does the string "Cat" actually occupy in memory, and why?

4 bytes — 'C', 'a', 't', and the null terminator '\0', which is required and part of the string, not extra.
Question 3

What does strcmp(a, b) == 0 mean, and why is checking strcmp(a,b) alone (without ==0) a common bug?

strcmp returns 0 when the two strings are equal. Checking "if (strcmp(a,b))" alone treats any non-zero result as true — which is exactly the "not equal" case — so it silently does the opposite of what a beginner usually intends.

Pointers I — Fundamentals

Every chapter so far has been quietly setting this one up: Chapter 4 promised pointers were "how you opt out of pass-by-value," Chapter 5 showed arrays decaying into them, Chapter 1's scanf needed the & operator you're about to fully understand. Pointers are the single concept most responsible for both C's power and its reputation for danger — take this chapter slowly and it will pay off in every chapter after it.

Section 6.1

What a pointer actually is

Every variable, once created, lives at some specific location in memory — an address, usually shown as a hexadecimal number like 0x7ffee3a1b2c4. A pointer is simply a variable that stores an address instead of an ordinary value — a variable whose job is to say "the data I care about lives over there."

Analogy

A house's street address is not the house itself — it's information that tells you where to find the house. A pointer is exactly that: not the data, but the data's address. You can write that address on a sticky note (copy a pointer), hand the sticky note to someone else (pass a pointer to a function), or follow the address to actually visit the house (dereference the pointer) — but the sticky note itself is small and simple, regardless of how large or complex the house at that address is.

Declaring a pointer, and the two essential operators

int x = 42;
int *p = &x;    // p is a pointer to an int, holding the ADDRESS of x

printf("%d\n", x);     // 42 -- the value
printf("%p\n", (void*)&x);  // 0x7ffee3a1b2c4 (some address) -- x's location
printf("%p\n", (void*)p);   // the SAME address -- p stores exactly where x lives
printf("%d\n", *p);    // 42 -- dereference: "go to that address, get the value"
OperatorNameMeaning
&xAddress-of"Give me the address where x lives" — turns a variable into a pointer value.
*pDereference"Go to the address p holds, and give me the value stored there" — turns a pointer back into the value it points to.
int *pDeclarationHere, * means something different — "p is a pointer to an int," part of the type, not an operation. This dual meaning of * (type declaration vs. dereference operation) trips up beginners; context (is this a declaration or an expression?) tells you which one applies.
p doesn't hold 42 — it holds x's address. Dereferencing p ("*p") follows that address to retrieve 42.
Why pointers exist — solving Chapter 4's exact problem

Chapter 4 established that C passes arguments by value — a function only ever receives copies, so it can never modify the caller's original variable directly. Pointers are the deliberate escape hatch: if you pass a function the address of a variable (still passed by value — the address itself is copied — but that copied address still points at the original data), the function can dereference that address and modify the real, original variable. Section 6.3 makes this completely concrete.

Section 6.2

Pointer types, NULL, and sizes

Why a pointer's type matters

A pointer's declared type (int*, double*, char*) doesn't change what a pointer fundamentally is — an address is just an address — but it tells the compiler how many bytes to read when dereferencing, and how far to move when doing pointer arithmetic (Chapter 7 covers this fully). Dereferencing an int* reads 4 bytes starting at that address (Chapter 2's typical int size); dereferencing a double* reads 8. Get the type wrong (via an incorrect cast, for instance) and you'll read the right memory location but interpret its bits completely wrong.

NULL — the pointer that points nowhere

int *p = NULL;    // explicitly points to nothing -- a safe, deliberate "no address yet"

if (p == NULL) {
    printf("p doesn't point to anything valid\n");
}
Why NULL matters so much in practice

An uninitialized pointer (declared but never assigned) contains garbage — some random leftover address (echoing Chapter 2's uninitialized-variable pitfall, now at pointer scale) — and dereferencing it reads or writes to some unpredictable, possibly critical piece of memory, a serious and unpredictable bug. Dereferencing NULL specifically, by contrast, is a well-defined, immediate crash (a "segmentation fault" or "null pointer dereference") on virtually every real system — loud and immediate, not silent and unpredictable. This is exactly why initializing an unused pointer to NULL explicitly, and checking for NULL before dereferencing a pointer that might not have been set, is one of the most important defensive habits in all of C programming.

Pointer size is fixed, regardless of what it points to

int *pi;
double *pd;
char *pc;

printf("%zu\n", sizeof(pi));   // 8 (on a typical modern 64-bit system)
printf("%zu\n", sizeof(pd));   // 8 -- SAME size, even though double is bigger than int!
printf("%zu\n", sizeof(pc));   // 8 -- same again

A pointer's size depends only on the system's address width (8 bytes on a typical 64-bit machine — enough to represent any address in that system's memory space), never on the size of the type it points to. This is worth sitting with: pi, pd, and pc all store nothing but an address — the same kind of number, the same size, no matter what data type lives at that address.

Section 6.3

Pointers and functions — finally solving Chapter 4's problem

Recall Chapter 4's try_to_double, which couldn't modify main's variable because it only ever received a copy. Here's the fix, using everything from this chapter so far:

#include <stdio.h>

void double_it(int *x) {          // takes a POINTER to an int, not the int itself
    *x = *x * 2;                    // dereference: modify the value AT that address
}

int main(void) {
    int num = 10;
    double_it(&num);                // pass num's ADDRESS, not num itself
    printf("%d\n", num);            // 20 -- it actually changed this time!
    return 0;
}
x is still a copy (pass-by-value never stops being true) — but it's a copy OF AN ADDRESS, so dereferencing it reaches the real, original num.
Resolving the apparent contradiction

This does not violate Chapter 4's pass-by-value rule — x is genuinely still a copy, exactly as before. What's different is what's being copied: not the value 10, but the address 0x1000. Copying an address doesn't copy the data at that address — both the original num and the copied pointer x refer to the exact same memory location, so dereferencing x and modifying what's there genuinely changes num. This is the resolution to the tension Chapter 4 deliberately left open, and it's worth re-reading Chapter 4, Section 4.3 now that you have this piece — it should feel like a puzzle piece clicking into place.

Worked problem — swapping two values (impossible without pointers) 
#include <stdio.h>

void swap(int *a, int *b) {
    int temp = *a;   // save what a points to
    *a = *b;          // overwrite a's target with b's value
    *b = temp;        // overwrite b's target with the saved original a value
}

int main(void) {
    int x = 5, y = 10;
    swap(&x, &y);
    printf("x=%d, y=%d\n", x, y);   // x=10, y=5
    return 0;
}

Why this needs pointers: a swap(int a, int b) without pointers would only swap two local copies inside swap's own stack frame — utterly useless, since main's x and y would never be touched, per Chapter 4's pass-by-value rule. Passing addresses is the only way in standard C to let a function modify variables that belong to its caller.

Section 6.4

Pointers and arrays — making Chapter 5's "decay" concrete

Chapter 5, Section 5.2 stated that an array decays into a pointer to its first element when passed to a function. Now that you know what a pointer actually is, that sentence can be made completely literal:

int arr[5] = {10, 20, 30, 40, 50};

printf("%p\n", (void*)arr);      // the array's address...
printf("%p\n", (void*)&arr[0]);  // ...is EXACTLY the same as the address of its first element

int *p = arr;        // no & needed! an array's name, used like this, IS already an address
printf("%d\n", *p);       // 10 -- same as arr[0]
printf("%d\n", *(p+1));   // 20 -- same as arr[1]!
printf("%d\n", p[1]);      // 20 -- array indexing syntax works on pointers too!
The single fact this section exists to deliver

arr[i] and *(arr + i) are exactly the same operation — array indexing is really just pointer arithmetic plus a dereference, written with more convenient syntax. When you write p + 1 for an int*, C automatically advances the address by sizeof(int) bytes (not by 1 byte) — this is why pointer arithmetic "just works" to walk through an array element by element, and it's exactly the same trick used back in Chapter 1's early C-programming worked example, before you had the vocabulary to understand why it worked.

The one place arrays and pointers genuinely differ

Despite the deep equivalence above, an array name is not a variable that can be reassigned: arr = something_else; is a compile error, while p = something_else; is perfectly legal (pointers are ordinary variables; array names are not). And sizeof(arr) inside the scope where arr was actually declared gives the array's true total size (Chapter 5, Section 5.1) — but sizeof(p) always gives just the pointer's own size (Section 6.2), even if p currently points at that same array. The decay only happens when an array is used as a pointer (like being passed to a function, or assigned to a pointer variable) — the array itself, in its own declared scope, is still a real, full-sized array.

Rewriting Chapter 1's worked example, now fully explained

float average(float *data, int len) {
    float sum = 0.0f;
    float *end = data + len;         // address 'len' elements past the start
    for (float *p = data; p < end; p++) {   // p walks forward, one element at a time
        sum += *p;                    // dereference: read the value AT p's current address
    }
    return sum / len;
}

Every piece of this should now make complete sense: data is the decayed pointer to the array's first element, data + len is pointer arithmetic computing an address past the last valid element, and p++ advances the pointer by exactly one float's worth of bytes each iteration — all direct, mechanical consequences of what this chapter just covered.

Wrap-up

Recap

  1. A pointer is a variable that stores an address. &x gets a variable's address; *p dereferences a pointer, following its address to read/write the value there.
  2. A pointer's declared type controls how many bytes are read on dereference and how pointer arithmetic steps — but every pointer, regardless of type, is the same fixed size (the system's address width).
  3. NULL is an explicit "points to nothing" value — always initialize unused pointers to it, and check for it before dereferencing a pointer that might not be set; an uninitialized (not NULL) pointer is far more dangerous, since it fails unpredictably instead of immediately.
  4. Pointers resolve Chapter 4's pass-by-value limitation: passing an address (still by value) lets a function dereference its way back to modify the caller's original variable.
  5. Array indexing is pointer arithmetic in disguise — arr[i] and *(arr+i) are the exact same operation, which is the full, literal explanation of Chapter 5's "arrays decay into pointers."
Check yourself

Quick check

Question 1

What's the difference between &x and *p, in plain terms?

&x means "give me the address where x lives" (turns a value into a pointer). *p means "go to the address p holds and give me the value stored there" (turns a pointer back into a value) — they're opposite operations.
Question 2

Why does passing &num to a function let that function actually change num, when Chapter 4 established that C only ever passes copies?

The function does still only receive a copy — but it's a copy of num's address, not a copy of num's value. Since both the original num and the copied address refer to the same memory location, dereferencing the pointer inside the function reaches and modifies the real, original variable.
Question 3

Given int arr[5], what expression using pointer arithmetic and dereferencing is exactly equivalent to arr[3]?

*(arr + 3) — array indexing is pointer arithmetic plus a dereference, written with more convenient syntax; they compile to the exact same operation.

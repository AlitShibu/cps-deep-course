Pointers II — Dynamic Memory & Pointer Arithmetic

Chapter 6 gave you pointers as a way to reach existing variables. This chapter gives you memory that doesn't belong to any variable at all — memory you request, use, and must explicitly give back. It's also where Java's garbage collector's absence stops being an abstract fact and becomes something you have to actively manage, every time.

Chapter 7 of 13Standard CBuilds directly on Chapter 6
Section 7.1

Two kinds of memory: the stack and the heap

Chapter 4, Section 4.1 introduced the stack — fast, automatic memory tied to function calls, growing and shrinking as functions are entered and exited. There's a second region of memory, the heap, that works completely differently: it doesn't automatically grow or shrink with function calls — memory there is allocated and freed explicitly, on your command, and it stays reserved for as long as you want, independent of which function is currently running.

StackHeap
Managed byAutomatically, on function call/returnYou, explicitly (malloc/free)
LifetimeTied to the function call that created itUntil you explicitly free it — can outlive the function that created it
SpeedVery fast (just moving a pointer)Slower (the allocator has to find free space)
Size limitsSmall, fixed per-program (can overflow — Ch.4, recursion)Much larger, limited mainly by available system memory
Typical useOrdinary local variablesData whose size isn't known until runtime, or that must outlive its creating function
Why you need the heap at all

Recall Chapter 4's hard rule: never return the address of a local (stack) variable — its memory is reclaimed the instant the function returns. But sometimes you genuinely need to create data inside one function and have it survive after that function returns (build an array whose size isn't known until runtime, for instance — arrays on the stack need a fixed size known when the code is written, per Chapter 5). The heap is memory that doesn't disappear when a function returns — it disappears only when you say so, which is exactly what lets you solve this class of problem.

Section 7.2

malloc and free — requesting and returning heap memory

#include <stdlib.h>

int *p = malloc(sizeof(int));   // request enough heap memory for one int
if (p == NULL) {                 // malloc failed (out of memory) -- ALWAYS check
    printf("Allocation failed\n");
    return 1;
}
*p = 42;                          // use it, exactly like any other pointer
printf("%d\n", *p);               // 42

free(p);                          // give the memory back -- REQUIRED
p = NULL;                         // good practice: prevent accidental reuse (Section 7.4)

malloc (memory allocate) takes a number of bytes and returns a pointer to a freshly reserved block of that size on the heap — or NULL if the request couldn't be satisfied (Chapter 6, Section 6.2's NULL-checking habit is not optional here). sizeof(int) is the idiomatic way to request "enough space for one int," rather than hardcoding a byte count that might not match this system's actual int size (Chapter 2).

Allocating an array on the heap

int n = 10;   // suppose this came from user input -- unknown until runtime!
int *arr = malloc(n * sizeof(int));   // enough space for n ints
if (arr == NULL) { /* handle failure */ }

for (int i = 0; i < n; i++) {
    arr[i] = i * i;    // array-style indexing works fine on a malloc'd pointer
}

printf("%d\n", arr[5]);   // 25

free(arr);
arr = NULL;
This solves a real problem Chapter 5 couldn't

A stack-allocated array's size (Chapter 5, Section 5.1) must be a compile-time constant — the compiler needs to know exactly how much stack space to reserve when the code is written. malloc(n * sizeof(int)) can request a size based on n, a value only known while the program is actually running (read from user input, a sensor, a file). This is the standard, necessary technique any time an array's size genuinely isn't known in advance.

Section 7.3

The three classic heap bugs — and how to actually avoid them

Java's garbage collector exists specifically to make these three mistakes impossible. In C, avoiding them is entirely your responsibility, every single time you use malloc.

1. Memory leaks — forgetting to free

void leaky_function(void) {
    int *p = malloc(100 * sizeof(int));
    // ... use p ...
    // forgot to call free(p) before the function returns!
    // p (the pointer) is gone (it was a local stack variable) --
    // but the 100 ints it pointed to are still reserved on the heap,
    // and now NOTHING can reach them to free them. Leaked, forever
    // (until the program exits).
}
Why this is worse than it sounds

A single leak in a short-lived program is harmless — the operating system reclaims all its memory when the program exits regardless. But a leak inside a function called repeatedly in a long-running program (a control loop, a server, firmware that runs for weeks) steadily consumes more and more memory over time, eventually exhausting it entirely — a slow, creeping failure that can take hours or days to manifest, making it notoriously hard to diagnose after the fact.

2. Use-after-free — using memory you already gave back

int *p = malloc(sizeof(int));
*p = 42;
free(p);           // the memory is returned to the system
printf("%d\n", *p); // UNDEFINED BEHAVIOR -- p is a "dangling pointer" now
Why this is dangerous rather than just wrong

After free(p), p's address is no longer "yours" — the system is free to hand that same memory to a completely different, unrelated malloc call elsewhere in the program at any moment. Dereferencing p afterward might read old, stale data (appearing to "still work," misleadingly), or might read/corrupt someone else's actively-used data — and which of these happens can vary run to run, making this bug notoriously hard to reproduce and debug. The standard defense: set a pointer to NULL immediately after freeing it (as shown in Section 7.2) — dereferencing NULL crashes loudly and immediately (Chapter 6, Section 6.2), turning an unpredictable, silent bug into an obvious, easy-to-locate one.

3. Double-free — freeing the same memory twice

int *p = malloc(sizeof(int));
free(p);
free(p);   // undefined behavior -- can corrupt the heap's internal bookkeeping

This is a direct consequence of not following the free + NULL habit above — free(NULL) is explicitly safe and does nothing (a guarantee from the C standard), so if the first free is always immediately followed by setting the pointer to NULL, an accidental second free call becomes a harmless no-op instead of a heap-corrupting bug.

The single habit that prevents all three

Follow one consistent rule: every malloc gets exactly one matching free, and the pointer is set to NULL immediately after. This one habit — not a complex tool or technique — is what separates memory-safe C code from code riddled with these three bugs. Professional embedded and systems C code lives or dies by this discipline, since these categories of bugs are also, historically, among the most exploited security vulnerabilities in real-world software.

Section 7.4

Pointer arithmetic, in full

Chapter 6, Section 6.4 introduced p + 1 advancing by one full element's worth of bytes, not one byte. Here's the complete picture:

int arr[5] = {10, 20, 30, 40, 50};
int *p = arr;

p = p + 2;            // advances by 2 * sizeof(int) bytes -- now points at arr[2]
printf("%d\n", *p);   // 30

int *q = &arr[4];
int diff = q - p;      // POINTER SUBTRACTION -- gives a count of ELEMENTS between them, not bytes
printf("%d\n", diff);  // 2 (arr[4] is 2 elements past arr[2])
Why pointer subtraction gives element count, not bytes

This is deliberately symmetric with pointer addition — since p + 1 means "one element forward," q - p naturally means "how many elements apart are these two addresses," with the byte-level arithmetic (dividing by sizeof(the pointed-to type)) handled automatically by the compiler. This only produces a meaningful result when both pointers point into the same array — subtracting pointers into two unrelated allocations is undefined behavior, since there's no meaningful "number of elements" between two unrelated blocks of memory.

realloc — resizing a heap allocation

int *arr = malloc(5 * sizeof(int));
// ... arr fills up, need more room ...
int *new_arr = realloc(arr, 10 * sizeof(int));  // try to grow to 10 ints
if (new_arr == NULL) {
    // realloc failed -- IMPORTANT: the ORIGINAL arr is still valid and unfreed here
    free(arr);
    return 1;
}
arr = new_arr;   // only overwrite arr once we KNOW realloc succeeded
A subtle, common realloc bug

Writing arr = realloc(arr, ...) directly is a common mistake: if realloc fails, it returns NULL — and if you've already overwritten arr with that NULL, you've lost the only pointer to your original, still-valid, still-allocated memory, causing a leak (Section 7.3) at the exact moment you were trying to handle an error gracefully. Always assign realloc's result to a different variable first, check it, and only then update your original pointer, as shown above.

Section 7.5

Worked problem — a growable list from scratch

This problem ties Chapters 5, 6, and 7 together: build a simple dynamic array that grows as needed — conceptually the same idea behind Java's ArrayList, but built by hand, with every allocation decision explicit.

#include <stdio.h>
#include <stdlib.h>

typedef struct {          // previewing Chapter 8's struct syntax slightly early
    int *data;
    int size;               // how many elements are actually used
    int capacity;            // how many elements there's room for
} IntList;

void list_init(IntList *list) {
    list->capacity = 4;
    list->size = 0;
    list->data = malloc(list->capacity * sizeof(int));
}

void list_push(IntList *list, int value) {
    if (list->size == list->capacity) {          // out of room -- grow
        list->capacity *= 2;
        int *new_data = realloc(list->data, list->capacity * sizeof(int));
        if (new_data == NULL) { return; }          // handle failure -- Section 7.4's lesson
        list->data = new_data;
    }
    list->data[list->size] = value;
    list->size++;
}

void list_free(IntList *list) {
    free(list->data);
    list->data = NULL;
    list->size = list->capacity = 0;
}

int main(void) {
    IntList list;
    list_init(&list);
    for (int i = 0; i < 10; i++) {
        list_push(&list, i * i);
    }
    for (int i = 0; i < list.size; i++) {
        printf("%d ", list.data[i]);
    }
    printf("\n");
    list_free(&list);
    return 0;
}
// Output: 0 1 4 9 16 25 36 49 64 81

What just happened: the list starts with room for 4 elements. Every time list_push finds it's full, it doubles the capacity via realloc (following Section 7.4's safe pattern exactly) and keeps going — the array grows transparently as needed, with the caller never needing to know or manage the current capacity directly. This is a genuinely realistic, complete example of dynamic memory management as it's actually used in real C code, combining pointers (Ch.6), arrays (Ch.5), and heap allocation (this chapter) into one working tool.

Wrap-up

Recap

  1. The heap is memory you explicitly request (malloc) and return (free) — unlike the stack, it isn't tied to function calls, letting data outlive the function that created it or have a size only known at runtime.
  2. Always check malloc's return value for NULL before using it — allocation can fail.
  3. The three classic heap bugs — memory leaks (forgot to free), use-after-free (used memory after freeing it), and double-free — are all prevented by one consistent habit: every malloc gets exactly one free, immediately followed by setting the pointer to NULL.
  4. Pointer arithmetic moves by whole elements, not bytes; pointer subtraction gives an element count, and only makes sense between pointers into the same array.
  5. realloc can fail — always assign its result to a temporary variable first, check for NULL, and only then overwrite your original pointer, or you risk leaking the original allocation.
Check yourself

Quick check

Question 1

Why can't you always use a stack-allocated array (Chapter 5) instead of malloc when you need an array whose size depends on user input?

A stack array's size must be a compile-time constant, known when the code is written. malloc can request a size based on a runtime value (like user input), which a plain stack array cannot do.
Question 2

What single habit, consistently applied, prevents memory leaks, use-after-free, and double-free bugs?

Every malloc gets exactly one matching free, with the pointer immediately set to NULL afterward — this ensures memory isn't forgotten (leak), a stale pointer crashes loudly and immediately rather than silently corrupting data (use-after-free becomes a safe NULL dereference), and an accidental second free call on an already-NULL pointer is a safe no-op (double-free prevented).
Question 3

Why should you write "int *new_p = realloc(p, newsize); if (new_p == NULL) {...}" instead of "p = realloc(p, newsize);" directly?

If realloc fails, it returns NULL. Overwriting p directly with that NULL loses the only pointer to the original, still-valid allocation, causing a memory leak at the exact moment you were trying to handle the failure. Assigning to a separate variable first preserves the original pointer until you've confirmed the reallocation succeeded.

Structs, Unions & Typedefs

C has no classes — but it has structs, which group related data together without any of Java's methods, inheritance, or access modifiers. This chapter is how you'll model a sensor reading, a CAN bus frame, or an RTOS task control block later in your roadmap: as plain, transparent data, with functions operating on it separately.

Chapter 8 of 13Standard CBuilds on Chapters 4, 6
Section 8.1

What a struct is, and how it differs from a Java class

A struct groups several related variables (called members or fields) together under one name, so they can be treated as a single unit:

struct Point {
    double x;
    double y;
};

struct Point p1 = {3.0, 4.0};
printf("%f, %f\n", p1.x, p1.y);   // 3.000000, 4.000000

p1.x = 10.0;   // access and modify a member with the dot operator
The core difference from a Java class

A struct is purely data — no methods live inside it, no inheritance, no access modifiers (every member is always fully accessible, the equivalent of everything being public). C's philosophy is to keep data and the functions that operate on it as two separate, explicit things: you write ordinary functions that take a struct (usually via a pointer, Section 8.3) as a parameter, rather than attaching behavior to the data itself. This isn't a limitation to feel bad about — it's just a different, simpler organizational model, and it's exactly how you'll structure sensor data types, protocol frames, and hardware register layouts throughout the rest of your CPS roadmap.

Memory layout — a struct is just its members, back to back

A struct's memory layout is (almost always) its members laid out sequentially, in declaration order — directly analogous to how Chapter 5's arrays are one contiguous block, just with different-sized, differently-typed slots instead of identical ones.

A struct's members sit in contiguous memory, in the order they're declared — no hidden overhead, no vtables, nothing Java-style attached.
A subtlety worth knowing about: padding

The compiler is allowed to insert invisible padding bytes between members to keep each one aligned to a memory address efficient for the CPU to access (e.g., a 4-byte int often needs to start at an address divisible by 4). This means sizeof(struct Foo) isn't always exactly the sum of its members' individual sizes — it can be larger. This rarely matters for ordinary application code, but it matters a great deal once you're mapping a struct directly onto a hardware register layout or a network/CAN bus packet format (Motorsport track, later) — there, unexpected padding can silently misalign your data. Compilers provide a way to disable padding (#pragma pack or similar, compiler-specific) for exactly these situations.

Section 8.2

typedef — giving types a shorter name

Writing struct Point every single time you need the type is verbose. typedef creates an alias — a new name for an existing type:

typedef struct {
    double x;
    double y;
} Point;                    // now "Point" alone is the type name, no "struct" needed

Point p1 = {3.0, 4.0};       // much cleaner
Point p2 = {1.0, 1.0};

This combines the struct definition and the typedef into one statement — an extremely common idiom in real C code, including nearly everything you'll encounter in embedded libraries and headers. It also works for naming any type, not just structs:

typedef unsigned char byte;   // "byte" is now an alias for "unsigned char"
byte b = 255;

typedef int (*Comparator)(int, int);   // naming a function pointer type -- Chapter 12 territory,
                                          // shown here just to demonstrate typedef's full reach
Why this matters for embedded code specifically

Recall Chapter 2's note about <stdint.h>'s exact-width types (uint8_t, int32_t) — these are themselves just typedef'd aliases for whatever underlying type happens to be the right width on a given platform. typedef is the exact mechanism that lets the same embedded code compile correctly across different microcontrollers with different native type sizes, by aliasing a fixed, portable name to whatever the platform's actual matching type is underneath.

Section 8.3

Structs and pointers — the arrow operator

Passing a large struct to a function by value (Chapter 4) copies the entire struct — every member, all at once — which can be wasteful for a struct with many or large fields. The idiomatic fix, exactly like Chapter 6's solution for modifying a caller's variable, is to pass a pointer to the struct instead:

typedef struct {
    double x;
    double y;
} Point;

void move_point(Point *p, double dx, double dy) {
    (*p).x += dx;    // works, but awkward -- must dereference before accessing a member
    (*p).y += dy;
}

int main(void) {
    Point p1 = {0.0, 0.0};
    move_point(&p1, 3.0, 4.0);
    printf("%f, %f\n", p1.x, p1.y);   // 3.000000, 4.000000 -- actually modified!
    return 0;
}

The parentheses around *p are required — without them, *p.x would (due to operator precedence) try to access member x of p first (which doesn't type-check, since p is a pointer, not a struct) and only then dereference, the wrong order entirely. Because (*ptr).member is so common and the parentheses so easy to get wrong, C provides a dedicated shortcut:

void move_point(Point *p, double dx, double dy) {
    p->x += dx;    // exactly equivalent to (*p).x += dx, and far more readable
    p->y += dy;
}
The arrow operator, precisely

p->x is purely syntactic sugar for (*p).x — "dereference the pointer, then access this member" — with no other difference whatsoever. Real C code almost universally uses -> for pointer-to-struct member access and plain . only for a struct value you already hold directly (not through a pointer). Seeing -> in code is an instant, reliable signal that you're working with a pointer to a struct, not the struct itself.

Worked problem — modeling a sensor reading, CPS-relevant 
#include <stdio.h>

typedef struct {
    float temperature;
    float humidity;
    unsigned long timestamp_ms;
} SensorReading;

void print_reading(const SensorReading *r) {   // 'const' -- promises not to modify *r
    printf("[%lu ms] Temp: %.1fC, Humidity: %.1f%%\n",
           r->timestamp_ms, r->temperature, r->humidity);
}

void apply_calibration(SensorReading *r, float temp_offset) {
    r->temperature += temp_offset;   // DOES modify -- no const here, intentionally
}

int main(void) {
    SensorReading reading = {23.5f, 45.0f, 100200};
    print_reading(&reading);
    apply_calibration(&reading, -1.2f);
    print_reading(&reading);
    return 0;
}

Why const SensorReading *r in print_reading: this is a compiler-enforced promise that this function only reads the struct, never modifies it — attempting r->temperature = 0; inside a const-qualified function would be a compile error. This is standard, defensive practice in real C: mark a pointer parameter const whenever a function has no business changing what it points to, making the function's contract explicit and machine-checked rather than just a comment or a hope.

Section 8.4

Unions — one memory location, multiple interpretations

A union looks syntactically like a struct, but behaves completely differently: all its members share the exact same memory location, rather than each getting its own separate space. A union's total size is only as large as its largest member — because only one member's worth of data can be meaningfully stored at any given moment.

union Value {
    int i;
    float f;
    char bytes[4];
};

union Value v;
v.i = 65;
printf("%d\n", v.i);       // 65
printf("%c\n", v.bytes[0]); // 'A' -- the SAME 4 bytes, reinterpreted as characters!

v.f = 3.14f;
printf("%d\n", v.i);        // garbage-looking int -- NOT 65 anymore, NOT related to 3.14 either;
                              // it's just 3.14's raw bit pattern read AS an int
A union doesn't store three separate values — it stores one block of bytes, and each member is just a different lens for interpreting that same block.
Where you'd actually use this

Unions are the standard tool for interpreting the same raw bytes multiple ways — a common real need when parsing binary protocol data (a CAN bus frame's payload bytes, Motorsport track, might need to be read as a raw byte array for transmission but as a float or int for actual use) or when deliberately inspecting a value's underlying bit representation (as the example above does, peeking at a float's raw bytes). Chapter 10 (Bitwise Operations) revisits this exact "same bytes, different interpretation" idea from another angle.

The rule to hold onto

Only ever trust the union member you most recently wrote to — writing .f and then reading .i gives you a technically well-defined (the bytes are real, they exist) but almost never meaningful result, since you're reinterpreting one type's bit pattern as a completely different type. This is different from a struct, where every member holds independently meaningful data at all times.

Section 8.5

Nested and self-referential structs

Structs containing other structs

typedef struct {
    double x;
    double y;
} Point;

typedef struct {
    Point top_left;
    Point bottom_right;
} Rectangle;

Rectangle r = {{0.0, 0.0}, {10.0, 5.0}};
printf("%f\n", r.top_left.x);       // 0.000000 -- chain member access naturally

Nested access chains exactly as you'd expect — r.top_left.x reads left to right, "get top_left from r, then get x from that."

Self-referential structs — the foundation of linked data structures

typedef struct Node {
    int value;
    struct Node *next;   // a struct CANNOT contain itself directly (infinite size!)
                           // but it CAN contain a POINTER to itself -- pointers have
                           // a fixed size (Ch.6, Section 6.2) regardless of what they point to
} Node;
Why this must be a pointer, not a direct struct

struct Node next; (without the pointer) would require the compiler to know Node's size to compute Node's size — a circular, impossible requirement. struct Node *next; works because a pointer's size is always fixed (8 bytes on a typical 64-bit system, Chapter 6, Section 6.2) regardless of what type it points to — the compiler doesn't need to know Node's full size to know how big a pointer to a Node is. This exact pattern — a struct holding a pointer to another instance of itself — is the literal foundation of linked lists, trees, and graphs, all covered properly in your Data Structures & Algorithms roadmap topic; the mechanism explained here is precisely what makes those structures possible in C.

Wrap-up

Recap

  1. A struct groups related data together with no attached methods, inheritance, or access control — a deliberately simpler model than a Java class, where functions and data stay explicitly separate.
  2. typedef creates a type alias, most commonly combined directly with a struct definition — the standard idiom throughout real C code and libraries.
  3. Pass structs to functions by pointer to avoid copying the whole thing; the arrow operator (p->member) is shorthand for (*p).member.
  4. Mark a struct pointer parameter const when a function only reads it — a compiler-enforced, machine-checked promise not to modify the caller's data.
  5. A union makes all its members share one memory location — only the most recently written member gives a meaningful result; useful for reinterpreting the same raw bytes multiple ways.
  6. A struct can contain a pointer to its own type (never the type directly — that would require an impossible, circular size calculation) — the exact mechanism underlying linked lists, trees, and graphs.
Check yourself

Quick check

Question 1

What is p->x exactly equivalent to, and why does C provide -> as a shortcut?

p->x is exactly equivalent to (*p).x. The shortcut exists because the parentheses in (*p).x are easy to forget or get wrong (due to operator precedence, *p.x would try to access .x on p first, which fails to type-check), and this pattern is extremely common in real code.
Question 2

Why can't a struct contain a field of its own type directly, but it can contain a pointer to its own type?

Containing itself directly would require the compiler to know the struct's size in order to compute its size — a circular, impossible requirement. A pointer to the struct works because pointers always have a fixed size regardless of what type they point to, so the compiler doesn't need the struct's full size to know how big a pointer to it is.
Question 3

You write .f = 3.14 on a union, then read .i from the same union. What do you get, and why?

You get some integer value that is NOT 3 or 3.14 or otherwise meaningfully related — it's the raw bit pattern that represents 3.14 as a float, reinterpreted as if those same bits were an int. All union members share the same memory, so reading a different member than the one you last wrote just reinterprets the same bytes differently.

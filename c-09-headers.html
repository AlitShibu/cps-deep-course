Header Files & the Preprocessor

Every program so far in this course has lived in one file. Real programs — including everything you'll build in your CPS roadmap — span many files, and this chapter is how they share function prototypes, struct definitions, and constants without copy-pasting them everywhere. It's also a proper return to the preprocessor, first mentioned all the way back in Chapter 1.

Chapter 9 of 13Standard CBuilds on Chapters 1, 4, 8
Section 9.1

Why split a program across files at all

A single-file program becomes unwieldy past a certain size — hard to navigate, hard for multiple people to work on simultaneously (recall your Git & GitHub track's collaboration workflow), and slow to recompile entirely from scratch every time you change one small thing. C's answer, consistent with everything since Chapter 4's static functions, is to split code across multiple .c files, each independently compiled into its own object file (Chapter 1, Section 1.2), then linked together into one final program.

The immediate problem this creates: if math_utils.c defines a function square, how does main.c call it? Chapter 4, Section 4.5 already gave you half the answer — a prototype lets the compiler check a call before seeing the definition. The remaining question is: where do you put that prototype so both files can see it, without retyping it and risking the two copies drifting out of sync?

A header file is the single shared contract both .c files agree on.
Section 9.2

Header files — the shared contract

A header file (.h) holds declarations meant to be shared — function prototypes, struct/typedef definitions (Chapter 8), and constants — but never full function bodies (with rare, advanced exceptions not needed here). Any .c file that needs those declarations pulls them in with #include.

// math_utils.h
int square(int n);
int cube(int n);
// math_utils.c
#include "math_utils.h"      // note the quotes, not angle brackets -- Section 9.4

int square(int n) { return n * n; }
int cube(int n) { return n * n * n; }
// main.c
#include <stdio.h>
#include "math_utils.h"       // pulls in the prototypes -- now main.c can call them

int main(void) {
    printf("%d\n", square(4));   // 16
    printf("%d\n", cube(3));      // 27
    return 0;
}
$ gcc main.c math_utils.c -o program
$ ./program
16
27
Why this is more than just "avoiding retyping"

If square's signature ever changes (say, it now takes a double), you only edit math_utils.h once — every file that includes it automatically sees the update the next time it's compiled, and the compiler will immediately flag any call sites that no longer match. Without a shared header, two hand-copied prototypes could silently drift apart (one file updated, the other forgotten), producing bugs that are notoriously hard to track down since each individual file looks internally consistent.

What belongs in a .h file vs. a .c file

Goes in the .h (header)Goes in the .c (source)

Section 9.3

The preprocessor, properly — #define and macros

Chapter 1, Section 1.2 introduced the preprocessor as a pure text-substitution pass that runs before actual C compilation begins. #include is one preprocessor directive (it literally pastes the included file's text in place); #define is another, and it's worth understanding fully now.

Simple constants

#define MAX_SENSORS 8
#define PI 3.14159265

float readings[MAX_SENSORS];   // becomes: float readings[8]; before compilation even starts
#define vs. const — when to use which

Chapter 2 introduced const, which creates a real, typed variable the compiler tracks and type-checks. #define is pure text substitution with no type checking whatsoever — the preprocessor doesn't know or care about C syntax, it just swaps text. Modern C style generally prefers const for typed constant values specifically because of this type safety, reserving #define for things that are genuinely about the preprocessing stage itself — conditional compilation (Section 9.5) and include guards (Section 9.4) being the main legitimate remaining uses.

Function-like macros — powerful, and genuinely dangerous

#define SQUARE(x) ((x) * (x))

int result = SQUARE(5);        // becomes: ((5) * (5))  →  25
int result2 = SQUARE(2 + 3);   // becomes: ((2 + 3) * (2 + 3))  →  25 (correct, because of the parens!)
Why every part of that macro is wrapped in parentheses

Because #define is pure text substitution, every parameter and the whole expression must be individually parenthesized, or operator precedence can silently produce a wrong result. Without the inner parentheses: #define SQUARE(x) (x * x) applied to SQUARE(2+3) would expand to (2+3 * 2+3) — which, by normal operator precedence (multiplication before addition), evaluates to 2 + 6 + 3 = 11, not 25. This is a real, classic, and easy-to-miss macro bug — always fully parenthesize every parameter and the entire macro body as a hard rule.

A second real danger: macros can't protect against repeated side effects 
#define SQUARE(x) ((x) * (x))
int i = 5;
int result = SQUARE(i++);   // expands to ((i++) * (i++)) -- i is incremented TWICE,
                              // and the result is undefined behavior (modifying i twice
                              // between sequence points)!

A real function evaluates its argument exactly once, no matter how many times the parameter name appears in the body — a macro re-evaluates the raw text everywhere the parameter appears, silently duplicating any side effects. This is a genuine, well-known category of macro bug, and it's a strong reason modern C style generally prefers real functions over function-like macros wherever performance isn't a hard, measured requirement (an inline function, a topic in later, more advanced material, gets you macro-like performance with none of these hazards).

Section 9.4

Include guards — solving the double-inclusion problem

Since #include is literal text-pasting (Section 9.1), a real risk emerges once headers start including other headers: if the same header gets pasted into a file twice (directly or through a chain of other includes), every struct and typedef inside it gets defined twice — a compile error, since C doesn't allow redefining the same type in one translation unit.

// sensor.h -- WITHOUT protection
typedef struct {
    float value;
} Reading;   // if this header is accidentally included twice, this line
              // causes "redefinition of Reading" -- a compile error

The fix — an include guard

// sensor.h -- WITH protection
#ifndef SENSOR_H     // "if NOT already defined"
#define SENSOR_H      // define it now, so next time this is skipped entirely

typedef struct {
    float value;
} Reading;

#endif                 // matches the #ifndef above
Why this works, mechanically

The first time sensor.h is included anywhere in a build, SENSOR_H isn't yet defined, so #ifndef SENSOR_H is true, and everything down to #endif is processed — including the line that defines SENSOR_H. If the exact same header gets included again later (directly, or via some other header that also includes it), SENSOR_H is now already defined, so #ifndef SENSOR_H is false, and the preprocessor skips straight to #endif — the struct definition is never pasted in a second time. This three-line pattern (#ifndef / #define / #endif) is so universal that essentially every header file you write should start and end with it, no exceptions, as a hard habit.

A naming convention worth adopting

The guard name (SENSOR_H above) must be unique across your entire project — two different headers accidentally using the same guard name would cause the second one to be silently skipped entirely, a confusing bug. The standard convention is the filename, uppercased, with the dot replaced by an underscore: sensor.h → SENSOR_H, math_utils.h → MATH_UTILS_H. Some modern compilers also support a simpler, non-standard-but-nearly-universal alternative, #pragma once, placed once at the top of a header — functionally equivalent, less typing, but technically not part of the official C standard, so the #ifndef pattern remains the more portable, textbook-correct choice.

Section 9.5

Conditional compilation

Beyond include guards, #ifdef/#ifndef/#else/#endif let you include or exclude entire blocks of code at compile time — genuinely relevant for your embedded/CPS work, where the same codebase often needs to target different hardware or build configurations.

#define DEBUG_MODE   // comment this line out to disable all debug output at once

int main(void) {
    int sensor_value = 42;

#ifdef DEBUG_MODE
    printf("Debug: sensor_value = %d\n", sensor_value);
#endif

    // ... rest of program ...
    return 0;
}
Why this matters directly for your Microcontrollers roadmap topic

Real embedded projects routinely need to compile slightly different code depending on the target board, or strip out debug logging entirely for a final release build (debug printf calls cost real time and program space on a memory-constrained microcontroller). Since this is resolved entirely at compile time — before the program even exists as a runnable binary — code inside a false #ifdef block isn't just skipped at runtime, it's never compiled into the program at all, adding zero size and zero runtime cost. This is meaningfully different from an ordinary if statement (Chapter 3), which is a runtime check that still costs a small amount of compiled code and execution time even when the condition is false.

Wrap-up

Recap

  1. A header file holds shared declarations (prototypes, structs, constants) so multiple .c files can agree on one contract without duplicating or risking drifted-apart copies.
  2. #define is pure text substitution with no type checking — prefer typed const for constant values; reserve macros mainly for conditional compilation and include guards.
  3. Function-like macros need every parameter and the whole body parenthesized to avoid operator-precedence bugs, and can't safely take arguments with side effects (like i++), since the argument text is duplicated wherever it appears.
  4. Include guards (#ifndef/#define/#endif) prevent a header's contents from being pasted in twice, which would otherwise cause redefinition errors — every header you write should have one.
  5. Conditional compilation (#ifdef) resolves entirely at compile time, adding zero runtime cost to skipped code — genuinely useful for stripping debug code or targeting different hardware in embedded projects.
Check yourself

Quick check

Question 1

Why should a function's full body never go inside a header file that multiple .c files include?

If the header is included by multiple .c files, the function's definition would be pasted into each one, causing a "multiple definition" linker error. Headers should hold only the prototype (declaration); the actual definition belongs in exactly one .c file.
Question 2

What does #define SQUARE(x) (x * x) get wrong, and what's the fix?

Without parentheses around x and the whole expression, SQUARE(2+3) expands to (2+3 * 2+3), which due to operator precedence evaluates incorrectly (11, not 25). The fix is #define SQUARE(x) ((x) * (x)) — parenthesize every parameter occurrence and the entire macro body.
Question 3

What problem do include guards (#ifndef/#define/#endif) solve?

They prevent the same header's contents from being pasted into a file more than once (directly or via a chain of other includes), which would otherwise cause "redefinition" compile errors for any structs or typedefs in that header.

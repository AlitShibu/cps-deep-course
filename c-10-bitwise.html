Bitwise Operations

Every value you've used so far has been treated as a number. This chapter treats values as what they actually are underneath: raw sequences of bits. This is the exact skillset your Digital Logic Design and Microcontrollers roadmap topics assume — setting individual hardware register bits, packing sensor flags efficiently, and decoding raw protocol data all live here.

Section 10.1

Binary representation, and two's complement

Every value in memory is ultimately a sequence of bits — 1s and 0s. An unsigned char (8 bits) counts in binary exactly like decimal, just base 2: 00000101 is 5, 00001010 is 10. The value of each bit position doubles moving left, exactly like each decimal digit position is worth 10x the one to its right.

Negative numbers: two's complement

Chapter 2, Section 2.4 previewed this: negative numbers are stored using two's complement, a specific encoding where the most significant bit effectively represents "negative weight." To find -5's bit pattern (as an 8-bit signed value): write 5 in binary (00000101), flip every bit (11111010), then add 1 (11111011).

Two's complement: flip the bits, add 1 — this single rule makes addition/subtraction hardware work identically for positive and negative numbers.
Why two's complement, specifically, and not some simpler scheme

Two's complement's genuinely elegant property: ordinary binary addition, performed exactly the same way regardless of sign, produces correct results even when negative numbers are involved — 5 + (-5), added bit by bit the normal way, naturally produces all zeros (ignoring a final carry-out bit). This means CPU hardware needs only one addition circuit, not separate logic for signed and unsigned arithmetic — a direct, practical reason this specific encoding won out. It's also the precise explanation for Chapter 2's signed/unsigned comparison surprise: -1's two's-complement bit pattern is all 1s, which reinterpreted as unsigned is the largest possible value for that type — exactly the "very large positive number" behavior observed there.

Section 10.2

The bitwise operators

OperatorNameBehavior
&ANDEach result bit is 1 only if both corresponding input bits are 1.
|OREach result bit is 1 if either input bit is 1.
^XOREach result bit is 1 if the input bits differ.
~NOTFlips every bit (unary — one operand).
<<Left shiftShifts all bits left, filling with 0s — equivalent to multiplying by a power of 2.
>>Right shiftShifts all bits right — equivalent to dividing by a power of 2 (for unsigned/positive values).
The classic beginner mix-up

&/| (single character) are bitwise operators, working bit by bit. &&/|| (Chapter 2's logical operators) work on whole values' truthiness (Chapter 3, Section 3.1's zero/non-zero rule) and short-circuit. 5 & 3 gives 1 (bitwise AND of 0101 and 0011). 5 && 3 gives 1 too, but for a completely different reason — both operands are simply non-zero, so the logical AND is "true," represented as the int 1. These can coincidentally produce the same-looking result for small numbers, which is precisely what makes this mix-up dangerous to overlook — always be deliberate about which one you mean.

unsigned char a = 0b00001100;   // 12 (binary literals are a GCC/C23 extension, widely supported)
unsigned char b = 0b00001010;   // 10

printf("%d\n", a & b);   // 0b00001000 = 8
printf("%d\n", a | b);   // 0b00001110 = 14
printf("%d\n", a ^ b);   // 0b00000110 = 6
printf("%d\n", (unsigned char)~a);  // 0b11110011 = 243 (flips ALL 8 bits)
printf("%d\n", a << 2);   // 0b00110000 = 48 (12 * 4)
printf("%d\n", a >> 2);   // 0b00000011 = 3  (12 / 4)
Section 10.3

Bit flags and masks — the practical payoff

A single byte has 8 independent bits — which means it can store 8 independent true/false flags, far more compactly than 8 separate int variables (or even 8 separate bools). This is the standard technique for packing status flags, hardware register configuration, or permission sets efficiently — genuinely important on a memory-constrained microcontroller.

The three fundamental operations

#define FLAG_ENABLED   (1 << 0)   // 0b00000001
#define FLAG_ERROR     (1 << 1)   // 0b00000010
#define FLAG_LOW_POWER (1 << 2)   // 0b00000100

unsigned char status = 0;

// SET a bit -- turn it on, without touching any other bit
status |= FLAG_ENABLED;      // 0b00000001

// CHECK a bit -- is it currently on?
if (status & FLAG_ENABLED) {
    printf("Enabled!\n");
}

// CLEAR a bit -- turn it off, without touching any other bit
status &= ~FLAG_ERROR;        // ~FLAG_ERROR is 0b11111101 -- ANDing preserves every
                                // other bit and forces just this one to 0

// TOGGLE a bit -- flip it, whatever it currently is
status ^= FLAG_LOW_POWER;
Set (OR with the flag), clear (AND with its inverse), toggle (XOR) — each touches exactly one bit, leaving every other bit exactly as it was.
Why each operation is built the way it is

Setting uses OR because 0 | 1 = 1 (turns a bit on) and 1 | 1 = 1 (leaves an already-on bit unchanged) — OR-ing with 0 anywhere else in the byte leaves those bits completely untouched (x | 0 = x). Clearing uses AND with an inverted mask because 1 & 0 = 0 (forces the target bit off) while ANDing with 1 everywhere else leaves those bits unchanged (x & 1 = x). This is precisely why &, |, and ^ are the specific tools for this job — each has exactly the right "identity" behavior (the value that changes nothing) paired with exactly the right "forcing" behavior (the value that guarantees a specific outcome) needed to touch one bit in isolation.

Worked problem — directly modeling a hardware register

Problem: A microcontroller's GPIO configuration register uses bit 3 to enable a pin as output, and bits 4-5 as a 2-bit speed setting (0=slow, 1=medium, 2=fast, 3=max). Write code to enable output mode and set speed to "fast" (2), without disturbing any other bits in the register.

#define OUTPUT_ENABLE_BIT (1 << 3)          // bit 3
#define SPEED_MASK         (0b11 << 4)        // bits 4-5, as a 2-bit field

unsigned char config_register = 0b00000000;   // assume starting fresh for this example

// Enable output mode
config_register |= OUTPUT_ENABLE_BIT;

// Set speed to "fast" (2 = 0b10), placed at bits 4-5
config_register &= ~SPEED_MASK;              // clear the speed bits first (both to 0)
config_register |= (2 << 4);                  // then set them to the new value

printf("Register: 0b%d%d%d%d%d%d%d%d\n", /* ... print each bit ... */);
// Result: 0b00101000
//                 ^ bit 3: output enabled
//               ^^ bits 4-5: 10 = speed "fast"

Why the clear-then-set pattern for the speed field: since speed is a 2-bit field (not a single flag), simply OR-ing in the new value wouldn't work if the old value had bits set that the new value doesn't — leftover 1s from the old setting would corrupt the new one. Clearing the field first (AND with the field's inverted mask) guarantees a clean slate before OR-ing in the new value — this exact clear-then-set pattern is standard practice any time you're writing a multi-bit field, not just a single flag, directly into a hardware register.

Where this connects directly forward

Microcontroller GPIO/peripheral registers, CAN bus message flag bytes (Motorsport track), and TinyML's model quantization (packing 8-bit weights efficiently) all use exactly this bit-manipulation toolkit. This chapter is not academic — it's the literal syntax you'll type in your Microcontrollers roadmap topic.

Wrap-up

Recap

  1. Two's complement encodes negative numbers by flipping bits and adding 1 — it lets hardware use one addition circuit for both signed and unsigned arithmetic, and it's the direct explanation for Chapter 2's signed/unsigned comparison surprise.
  2. Bitwise &, |, ^, ~ operate bit-by-bit — not to be confused with the logical &&/||, which work on a whole value's truthiness.
  3. <</>> shift bits left/right, equivalent to multiplying/dividing by powers of 2.
  4. Set a bit with OR, clear a bit with AND-and-inverted-mask, toggle a bit with XOR — each touches exactly the intended bit(s) while leaving every other bit untouched.
  5. For multi-bit fields (not just single flags), use the clear-then-set pattern — clear the field first, then OR in the new value — to avoid leftover bits from a previous value corrupting the new one.
  6. This toolkit is the literal, practical syntax used for microcontroller register configuration, CAN bus flag bytes, and other bit-packed data throughout your later CPS roadmap topics.
Check yourself

Quick check

Question 1

What's the difference between & and &&, and why can they sometimes produce the same-looking result for small numbers?

& is bitwise AND (operates bit by bit on the operands' binary representations); && is logical AND (evaluates whether both operands are non-zero/"true" as whole values). They can coincidentally look similar for very small numbers (like 1 & 1 = 1 and 1 && 1 = 1) but are fundamentally different operations that diverge for most other values.
Question 2

Why does "status &= ~FLAG;" clear a bit without disturbing any other bits in status?

~FLAG inverts the flag's bit pattern, producing all 1s except a 0 at the target bit's position. ANDing status with this mask forces that one bit to 0 (since anything AND 0 is 0) while every other bit is ANDed with 1, which leaves it completely unchanged (x AND 1 = x).
Question 3

Why do you need to clear a multi-bit field before OR-ing in a new value, rather than just OR-ing the new value in directly?

If the field previously held a value with bits set that the new value doesn't have, simply OR-ing the new value in would leave those old 1-bits in place (since OR only ever turns bits on, never off), corrupting the result into something that isn't the intended new value. Clearing the field first guarantees a clean slate.

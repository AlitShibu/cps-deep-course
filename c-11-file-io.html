File I/O

Everything printed so far has gone to the screen. This chapter is about reading and writing actual files — logging sensor data, loading a configuration, saving telemetry — using the same standard library that's been quietly available since Chapter 1's stdio.h include.

Chapter 11 of 13Standard CBuilds on Chapters 1, 5, 6
Section 11.1

Opening, closing, and the FILE pointer

All file operations in C revolve around a FILE* — a pointer (Chapter 6) to an opaque structure the standard library uses to track everything about an open file (its position, buffering state, and more) that you don't need or want to see the details of.

#include <stdio.h>

int main(void) {
    FILE *fp = fopen("data.txt", "w");   // "w" = write mode (creates/overwrites)
    if (fp == NULL) {                     // ALWAYS check -- opening can fail
        printf("Could not open file\n");
        return 1;
    }

    fprintf(fp, "Sensor reading: %d\n", 42);   // just like printf, but writes to fp

    fclose(fp);   // ALWAYS close -- required to actually save data reliably
    return 0;
}
ModeMeaning
"r"Read — file must already exist, or fopen returns NULL.
"w"Write — creates a new file, or completely erases an existing one.
"a"Append — writes are added to the end of an existing file (or creates one if it doesn't exist).
"rb", "wb"Binary versions of read/write — Section 11.3 covers why this distinction matters.
Why fclose matters — not just tidiness

For performance, the standard library often buffers writes — holding recently written data in memory temporarily rather than sending every single byte to the disk immediately. fclose forces any buffered data to actually be written out (called flushing) before releasing the file. Forgetting to close a file risks losing the last chunk of buffered, unwritten data if the program exits unexpectedly — a genuinely common source of "the log file is missing its last few entries" bugs. This is directly analogous to Chapter 7's malloc/free discipline: every fopen should have exactly one matching fclose.

Reading a file back

FILE *fp = fopen("data.txt", "r");
if (fp == NULL) {
    printf("File not found\n");
    return 1;
}

char line[100];
while (fgets(line, sizeof(line), fp) != NULL) {   // reads one line at a time
    printf("Read: %s", line);                        // line already includes its own '\n'
}

fclose(fp);

fgets reads up to one line (or up to sizeof(line)-1 characters, whichever comes first — leaving room for the null terminator, Chapter 5, Section 5.3) and returns NULL once there's nothing left to read, which is exactly what makes it a clean loop condition.

Section 11.2

Formatted reading and writing

fscanf is to fgets/manual parsing what scanf (Chapter 1, Section 1.5) is to reading raw keyboard input — it reads directly into typed variables using format specifiers, following the exact same rules (including needing & for non-string types, Chapter 6's address-of operator).

// Writing structured data
FILE *fp = fopen("readings.csv", "w");
fprintf(fp, "%d,%.1f,%.1f\n", 1, 23.5, 45.0);   // id, temperature, humidity
fprintf(fp, "%d,%.1f,%.1f\n", 2, 24.1, 44.2);
fclose(fp);

// Reading it back
fp = fopen("readings.csv", "r");
int id;
float temp, humidity;
while (fscanf(fp, "%d,%f,%f\n", &id, &temp, &humidity) == 3) {
    printf("Reading %d: %.1fC, %.1f%%\n", id, temp, humidity);
}
fclose(fp);
Why checking fscanf's return value matters

fscanf returns the number of items it successfully matched and assigned — comparing this against the expected count (3 here) is the standard way to detect malformed or incomplete data, or to know when you've reached the end of the file (where it returns a special value, EOF, rather than a partial count). Ignoring this return value is a common source of bugs where a program silently reads garbage or stale values from previous iterations instead of noticing a file was malformed or ended early.

Section 11.3

Binary file I/O — reading and writing raw memory

Everything so far has been text mode — human-readable characters. Binary mode writes a value's actual in-memory bit pattern directly to disk, with no text formatting or conversion — significantly faster and more compact for large amounts of structured data (like telemetry logs, Motorsport track), at the cost of the file no longer being human-readable.

typedef struct {
    float temperature;
    float humidity;
    unsigned long timestamp_ms;
} SensorReading;   // recall this exact struct from Chapter 8

SensorReading readings[3] = {
    {23.5f, 45.0f, 1000},
    {23.7f, 44.8f, 2000},
    {24.1f, 44.2f, 3000}
};

FILE *fp = fopen("readings.bin", "wb");     // note "wb" -- binary write
fwrite(readings, sizeof(SensorReading), 3, fp);   // write 3 structs' worth of raw bytes
fclose(fp);

// Reading it back
SensorReading loaded[3];
fp = fopen("readings.bin", "rb");            // "rb" -- binary read
size_t count = fread(loaded, sizeof(SensorReading), 3, fp);
fclose(fp);
printf("Read %zu readings; first temp: %.1f\n", count, loaded[0].temperature);
What fwrite/fread actually do, and why this connects to Chapter 8

fwrite copies sizeof(SensorReading) * 3 bytes directly from memory to the file — exactly the same bytes that exist in the readings array right now, including any struct padding (Chapter 8, Section 8.1). fread does the reverse, copying bytes from the file straight back into memory. This is genuinely fast (no per-value text conversion happening), but it also means a binary file's format is tied to the exact struct layout, sizes, and byte-order of the system that wrote it — a file written on one system isn't guaranteed to read back correctly on a system with a different struct padding scheme or byte order. For portable data exchange across different systems, a defined text or well-specified binary protocol format (like the CAN bus frames in your Motorsport track) is generally preferred over raw fwrite of a struct; for a program logging and later reading its own data on the same system, this pattern is simple and fast.

A common oversight

Always check fread's return value (the actual number of complete items read) against what you expected — a file that's shorter than anticipated (truncated, corrupted, or simply ended early) will cause fread to return fewer items than requested, and code that assumes it always got exactly what it asked for will silently process uninitialized or stale data in the unfilled portion of its buffer.

Section 11.4

Worked problem — a simple data logger

A realistic pattern combining this chapter with earlier ones: log a series of sensor readings to a text file, appending to preserve history across multiple program runs.

#include <stdio.h>
#include <time.h>

void log_reading(const char *filename, float value) {   // const, Chapter 8's habit
    FILE *fp = fopen(filename, "a");    // "a" -- append, never overwrites past runs
    if (fp == NULL) {
        printf("Warning: could not open log file\n");
        return;
    }
    time_t now = time(NULL);
    fprintf(fp, "%ld,%.2f\n", (long)now, value);
    fclose(fp);
}

int main(void) {
    log_reading("sensor_log.csv", 23.5f);
    log_reading("sensor_log.csv", 24.1f);
    log_reading("sensor_log.csv", 23.8f);
    printf("Logged 3 readings\n");
    return 0;
}

Run this program multiple times, and sensor_log.csv keeps growing rather than being erased each time — exactly the behavior a real logging system needs, made possible entirely by choosing "a" instead of "w" as the file mode.

Wrap-up

Recap

  1. All file operations use a FILE* obtained from fopen — always check it against NULL, since opening a file can fail.
  2. Always fclose an opened file — this flushes buffered data to disk; forgetting it risks losing the last unwritten data if the program exits unexpectedly.
  3. File modes: "r" (read, must exist), "w" (write, erases existing content), "a" (append, preserves existing content).
  4. fscanf/fprintf work like their keyboard/screen counterparts (Chapter 1) but target a file — always check fscanf's return value to detect malformed or incomplete data.
  5. Binary mode (fread/fwrite) copies raw memory bytes directly, fast but tied to the exact struct layout and system that wrote it — text mode is more portable, binary mode is faster and more compact.
Check yourself

Quick check

Question 1

Why can forgetting to call fclose() cause data loss, even if all your fprintf calls appeared to succeed?

Writes are often buffered in memory for performance rather than being sent to disk immediately. fclose forces this buffered data to actually be flushed to disk. Without it, if the program exits unexpectedly, any data still sitting in the buffer (not yet flushed) can be lost.
Question 2

What's the difference between opening a file with "w" versus "a"?

"w" creates a new file or completely erases an existing one before writing. "a" preserves existing content and adds new writes to the end of the file — essential for a log file that should accumulate history across multiple program runs.
Question 3

Why is a binary file written with fwrite not guaranteed to read back correctly on a different system?

fwrite copies the exact in-memory bytes of a struct, including any compiler-inserted padding, which can differ between systems/compilers, and the raw bit representation of multi-byte values can differ in byte order across different hardware. A binary file's format is tied to the exact memory layout of the system that wrote it.

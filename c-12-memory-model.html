The C Memory Model

Every chapter since Chapter 2 has quietly referred to "the stack," "the heap," "global scope," and "static storage" as if they were separate, obvious places. This chapter draws the whole map at once — every piece of memory your program ever touches, in one unified picture, closing every loose thread the rest of this course left open.

Section 12.1

The four memory segments, all at once

A running C program's memory is divided into distinct regions, each with different rules about lifetime and management. You've met every one of these already, in isolation — here they are together.

Four segments, one address space: stack and heap typically grow toward each other from opposite ends; static/global and code are fixed in size from the moment the program starts.
SegmentWhat lives thereLifetimeManaged by

Why this unified view is worth having, explicitly

Nearly every C pitfall this course has covered is a violation of exactly one segment's rules: returning a stack address after the frame is popped (Ch.4) is treating stack memory as if it had heap-like persistent lifetime. A memory leak (Ch.7) is heap memory whose lifetime you failed to end deliberately. A buffer overflow (Ch.5) writes past a segment's allocated boundary into whatever happens to sit adjacent. Once you can place any given bug onto this one map, "why did this happen" usually becomes immediately clear from which segment's rule was broken.

Section 12.2

One program, all four segments, traced explicitly

#include <stdio.h>
#include <stdlib.h>

int global_counter = 0;              // STATIC/GLOBAL segment -- exists for the whole run

void track_calls(void) {
    static int call_count = 0;        // STATIC/GLOBAL segment too! (Ch.4, Sec.4.6) --
                                        // NOT the stack, despite being declared "inside" a function
    call_count++;
    global_counter++;
    printf("Call #%d (global: %d)\n", call_count, global_counter);
}

int main(void) {                      // main()'s own STACK frame begins here
    int local_var = 10;                 // STACK -- exists only during this call to main

    int *heap_data = malloc(5 * sizeof(int));   // HEAP -- persists until freed, regardless
                                                   // of which function is currently running
    for (int i = 0; i < 5; i++) {
        heap_data[i] = i * i;
    }

    track_calls();   // pushes a NEW stack frame for track_calls, on top of main's
    track_calls();
    track_calls();

    printf("local_var: %d\n", local_var);
    printf("heap_data[3]: %d\n", heap_data[3]);

    free(heap_data);   // HEAP memory explicitly released
    return 0;            // main's STACK frame is popped -- local_var ceases to exist
}
Walking through where everything actually lives

global_counter and call_count both live in the static/global segment — allocated once, before main even starts, and never moved or reclaimed until the program exits. This is exactly why call_count (Chapter 4's static-local pattern) can remember its value across the three separate calls to track_calls — it isn't part of any function's stack frame at all, despite the misleading visual impression that declaring it "inside" a function might give.

local_var lives in main's stack frame — created when main starts, destroyed the instant main returns. heap_data the pointer variable also lives on main's stack (it's a local variable itself!) — but the five integers it points to live on the heap, entirely independent of any function's stack frame, which is exactly why they'd still be valid even if a different function held a copy of that same pointer.

The subtlety worth sitting with: a pointer variable's own storage vs. what it points to

This is a distinction beginners often blur: where a pointer variable itself is stored (here, the stack, since heap_data is a local variable) is completely independent of where the memory it points to lives (here, the heap). A stack-allocated pointer can point to heap memory (as above), to another stack variable's address (Chapter 6's &x examples), or to static/global memory — the pointer's own storage location and its target's storage location are two entirely separate facts, and conflating them is a common source of confusion when reasoning about a program's memory behavior.

Section 12.3

Why this map matters even more on embedded hardware

On your laptop, these four segments live inside gigabytes of RAM, and the operating system quietly handles a great deal of complexity underneath (virtual memory, protection between programs) that makes running out of any single segment rare in ordinary use. A microcontroller (your next roadmap topic) typically has kilobytes, not gigabytes — sometimes as little as a few dozen kilobytes total, for every segment combined, with no operating system underneath cushioning the consequences of getting it wrong.

What changes, concretely, once memory is this scarce

Stack overflow (Chapter 4, recursion) becomes a real, everyday risk, not a theoretical edge case — a deeply nested function call chain or a large local array can exhaust a microcontroller's entire stack space in a way that's essentially impossible to trigger accidentally on a desktop. Heap fragmentation becomes a serious practical concern — repeated malloc/free cycles of varying sizes can leave the heap full of small, unusable gaps between allocated blocks, eventually causing an allocation to fail even though the total free memory would seem to be enough; many embedded projects avoid dynamic allocation (Chapter 7) entirely after initial setup, for exactly this reason, preferring pre-sized static/global buffers instead. Global and static memory (Section 12.1's third segment) is often the most heavily used segment in embedded C, specifically because its size is fixed and fully known at compile time — a predictability that matters enormously when there's no room for surprises.

This is precisely why Chapter 2's <stdint.h> exact-width types matter so much in practice: on a system with only a few kilobytes total, the difference between an int that happens to be 2 bytes versus 4 bytes on a given microcontroller is a meaningful fraction of your entire available memory, multiplied across every variable in your program.

Wrap-up

Recap

  1. Every piece of memory in a running C program belongs to one of four segments: stack (automatic, per-call), heap (manual, via malloc/free), static/global (fixed, whole-program lifetime), or text/code (your compiled instructions).
  2. Nearly every memory-related bug covered in this course is a violation of one segment's specific rules — recognizing which segment is involved usually makes the bug's cause immediately clear.
  3. A pointer variable's own storage location (often the stack) is completely independent from where the memory it points to lives (which could be heap, static, or another stack frame) — these are two separate facts that are easy to conflate.
  4. On memory-constrained embedded hardware, stack overflow and heap fragmentation become real everyday risks rather than rare edge cases — many embedded projects avoid dynamic allocation after startup entirely, favoring the predictability of static/global memory instead.
Check yourself

Quick check

Question 1

A static local variable is declared inside a function. Which memory segment does it actually live in, and why is this surprising to some beginners?

The static/global segment, not the stack — despite being declared "inside" a function, its static keyword gives it whole-program lifetime, which requires it to live in the same fixed, permanent segment as global variables, not in that function's temporary stack frame.
Question 2

A pointer variable p is declared as a local variable inside a function, and holds the address of some malloc'd memory. Where does p itself live, and where does the memory it points to live?

p itself (the pointer variable, storing an address) lives on the stack, since it's a local variable. The memory it points to lives on the heap, since it was obtained via malloc. These are two separate storage locations, and this distinction matters when reasoning about how long each piece of data actually remains valid.
Question 3

Why do many embedded projects avoid using malloc/free after initial setup, preferring static/global buffers instead?

Repeated allocation and freeing of different-sized blocks can fragment the heap, eventually causing allocations to fail even when enough total free memory technically exists. Static/global memory has a size that's fixed and fully known at compile time, which is far more predictable — a valuable property on hardware with only a few kilobytes of memory total and no room for surprises.

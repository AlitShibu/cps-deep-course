From C to Embedded C

Everything in this course ran on your laptop, with an operating system underneath cushioning every mistake. Embedded C is the same language, running on a microcontroller with no OS, direct hardware access, and none of that cushioning. This closing chapter names exactly what changes, and traces every earlier chapter forward to where it becomes essential in your Microcontrollers roadmap topic next.

Section 13.1

No operating system, and a much smaller standard library

Every program in this course has quietly relied on an operating system: fopen (Chapter 11) asked the OS for a file handle; malloc (Chapter 7) asked the OS's memory manager for heap space; even printf (Chapter 1) ultimately asked the OS to display characters on a screen. A microcontroller running bare-metal (no OS at all — the norm for small, simple embedded projects) has none of this machinery underneath it.

What this means concretely for the code you write

There's usually no file system, so Chapter 11's fopen/fread typically have no meaningful target at all. malloc may technically exist (via a minimal embedded C library) but is often avoided anyway, exactly per Chapter 12's fragmentation concerns — many embedded codebases use only static/global and stack memory, by disciplined choice, never touching the heap after startup. printf either doesn't exist, or has been specially reimplemented by the toolchain to send characters out a UART serial connection (your Serial Protocols roadmap topic) instead of to a screen that doesn't exist. None of the C language itself has changed — Chapters 1 through 10's core language rules apply identically — what's changed is which parts of the standard library (built on OS services you no longer have) remain available or meaningful.

What replaces main's normal "exit"

On your laptop, main returning ends the program and control returns to the operating system (Chapter 1, Section 1.3's exit codes). On bare-metal embedded hardware, there's no OS to return control to — main typically never returns at all, instead containing an infinite loop that runs for as long as the device has power:

int main(void) {
    setup_hardware();       // configure peripherals once, at startup

    while (1) {               // runs forever -- there's nowhere else to "return" to
        read_sensors();
        update_control_loop();
        // ... this loop IS the entire running life of the device
    }
    // unreachable -- and that's expected, not a bug
}
Section 13.2

Memory-mapped registers, and the volatile keyword

On a microcontroller, hardware peripherals (GPIO pins, timers, UART) are controlled by reading and writing specific, fixed memory addresses — writing the right bit pattern (Chapter 10) to the right address configures or triggers real physical hardware, not just ordinary program data.

#define GPIO_OUTPUT_REGISTER  (*(volatile unsigned int *)0x40020014)

GPIO_OUTPUT_REGISTER |= (1 << 5);    // set bit 5 -- Chapter 10's exact bit-flag pattern,
                                        // now physically turning on a real pin's voltage
Why volatile is required here, specifically

The compiler normally optimizes code aggressively — if it sees a variable written but never subsequently read (from its own point of view, reading the source code alone), it may eliminate that write entirely as "dead code," or cache a value in a CPU register instead of re-reading memory every time, assuming (reasonably, for ordinary variables) that nothing else could have changed it in the meantime. A hardware register's value can change due to the hardware itself — an incoming signal, a timer firing — completely outside anything the compiler can see in the C code. volatile is a direct instruction to the compiler: "never optimize away or cache accesses to this — always actually read/write the real memory location, every single time, exactly as written." Without it, a perfectly reasonable-looking optimization could silently break hardware interaction in a way that's notoriously difficult to debug, since the code looks completely correct on the page.

Connecting this directly back to Chapter 6

The line above is, underneath the macro, exactly Chapter 6's pointer machinery: (volatile unsigned int *)0x40020014 is a pointer, explicitly cast to point at a specific hardware address (rather than an address the compiler chose for an ordinary variable), and the outer *(...) dereferences it — reading or writing whatever is actually at that physical location. Registers, GPIO pins, and every other piece of a microcontroller's hardware are all, ultimately, just pointers to specific fixed addresses — the exact same dereference operation from Chapter 6, Section 6.1, now pointed at silicon instead of an ordinary stack variable.

Where this leaves you

You now have the complete standard-C foundation your Microcontrollers, RTOS, Serial Protocols, and ECU roadmap topics all assume. Nothing in embedded C is a new language — it's this exact language, applied under tighter constraints, with direct hardware access replacing the OS services you've relied on throughout this course. The next time you open a microcontroller's datasheet and see a register address and a bit layout table, you now have every piece of vocabulary needed to turn that table directly into working C code.

Wrap-up

Recap

  1. Bare-metal embedded C has no operating system underneath it — standard library functions relying on OS services (file I/O, often malloc) are unavailable or reimplemented; main typically never returns, running an infinite loop instead.
  2. Hardware peripherals are controlled via memory-mapped registers — specific fixed addresses that, when read or written, directly affect real hardware.
  3. volatile tells the compiler never to optimize away or cache accesses to a variable, since its value can change from outside the C code's visible control flow (hardware events) — essential for any register access.
  4. A hardware register access is, underneath, exactly Chapter 6's pointer dereference — just pointed at a fixed physical address instead of an ordinary variable.
  5. Every chapter in this course maps directly onto a specific embedded concern: exact-width types (Ch.2), stack discipline (Ch.4), pointers as the mechanism for register access (Ch.6-7), structs for modeling hardware/protocol layouts (Ch.8), conditional compilation for multi-board support (Ch.9), bitwise operations as daily register-configuration syntax (Ch.10), and the memory model (Ch.12) as the single most consequential concern for embedded reliability.
Check yourself

Quick check — final review across the whole C course

Question 1

Why does main() typically never return on bare-metal embedded hardware, unlike every program in this course so far?

There's no operating system to return control to — on a laptop, returning from main hands control back to the OS, but bare-metal hardware has no OS underneath, so main instead contains an infinite loop that constitutes the device's entire running life.
Question 2

Why is volatile necessary when accessing a hardware register, when it's never needed for an ordinary local variable?

The compiler normally assumes nothing outside the visible C code can change a variable's value, and may optimize away or cache accesses accordingly. A hardware register's value can change due to external hardware events invisible to the compiler, so volatile forces every access to actually read/write the real memory location, preventing the compiler from silently breaking hardware interaction through an otherwise-reasonable optimization.
Question 3

What single earlier chapter's concept is a memory-mapped register access an application of?

Chapter 6's pointer dereference — a register access is a pointer explicitly cast to point at a fixed hardware address, dereferenced to read or write whatever is actually at that physical location.

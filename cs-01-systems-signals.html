Systems, Signals & the Big Picture

Every CPS project so far has quietly used control in an ad-hoc way — Microcontrollers Chapter 7's capstone adjusted LED brightness based on a light reading, a direct if simple feedback response. This topic makes that idea rigorous: how do you formally describe a system's behavior, decide whether feedback is worth the complexity it adds, and design a controller with predictable, provable behavior rather than just "tune it until it looks right"? This chapter builds the vocabulary and intuition everything else in the topic sits on.

Section 1.1

What "a system" means here

In control engineering, a system (often called the plant) is anything with an input that produces an output whose behavior you want to influence or predict: a DC motor (input: applied voltage, output: shaft speed), a room (input: heater power, output: temperature), a car's cruise control (input: throttle, output: speed). The controller is the separate piece of logic that decides what input to apply to the plant, based on what outcome is actually wanted.

Why separating "plant" and "controller" as distinct concepts matters

The plant's behavior is fixed by physics — a given motor has whatever electrical and mechanical characteristics it has, and you generally can't change them. The controller is the part you actually get to design. Keeping this separation explicit is what allows the same general control techniques (this whole topic) to apply equally to a motor, a room's temperature, or a drone's altitude — the mathematical structure of "plant + controller" is the same in each case, even though the underlying physics is completely different.

Reference, error, and the goal of control

A control system exists to make a system's output track a desired value, the reference (or setpoint) — a thermostat's reference is the target temperature, a cruise control's reference is the desired speed. The error is simply reference minus actual output, and — as this whole topic will make precise — driving that error toward zero, reliably and without unwanted side effects like oscillation, is the entire point of control design.

Section 1.2

Open-loop vs. closed-loop control

An open-loop controller decides its output based only on the reference — it never checks what the plant's output actually did. A closed-loop (feedback) controller measures the actual output and adjusts its input based on the error between reference and measurement.

Open-loop: the controller has no idea whether the plant actually achieved the desired output.
Why open-loop control can fail silently

A microwave that runs for a fixed time based only on a dial setting is open-loop — it has no way to know if the food actually reached the intended temperature; it just trusts that "this much time at this power level" will work, based on an assumption that may not hold (different food mass, different starting temperature). Open-loop control works fine when the plant's behavior is well-understood and disturbances are minimal, but it has no mechanism to correct for anything unexpected — it simply can't detect that it failed.

Closed-loop: the feedback path continuously feeds the actual output back, letting the controller correct based on real error, not assumption.
This is exactly Electronics Chapter 6's op-amp negative feedback, generalized

An op-amp's negative feedback (Electronics Chapter 6) is a closed-loop control system in miniature: the "plant" is the op-amp's raw high gain, the "reference" is effectively set by the input and feedback resistor ratio, and feeding a portion of the output back to the inverting input is precisely the summing-junction feedback path shown above. The same core idea — measure the actual result, compare against what's wanted, correct the difference — appears at every scale from a single op-amp circuit to a full robotic control system, which is exactly why this topic generalizes a pattern you've already used, rather than introducing something unrelated.

Feedback isn't automatically better — it adds real complexity and new failure modes

A feedback loop needs a working sensor (adding cost, potential failure points, and measurement noise), and — as Chapters 4-5 will show rigorously — a poorly designed feedback controller can actually make a system's behavior worse than no control at all, oscillating or even growing unstable. The decision to use closed-loop control is a genuine engineering trade-off (added complexity and cost, for the ability to correct for disturbances and modeling errors), not an automatic "feedback is always the sophisticated, correct choice."

Section 1.3

Block diagrams: the standard notation

A block diagram represents a system as boxes (each representing a mathematical operation on its input to produce its output) connected by arrows (signal flow) — exactly the diagrams shown in Section 1.2. Three elements account for nearly everything: a block (transforms an input signal into an output signal — the transfer function, formalized in Chapter 2), a summing junction (adds or subtracts signals, shown as a circle with +/− labels), and a branch point (a signal splits to go to more than one place, without being altered).

Why block diagrams matter beyond just being a picture

A block diagram isn't merely illustrative — it's a precise mathematical statement about how signals combine, and (as Chapter 4 covers in depth) block diagrams can be algebraically simplified using formal rules, exactly like simplifying an algebraic expression. This is why control engineers draw and manipulate block diagrams constantly: the diagram itself is often the fastest path to deriving a system's overall input-output relationship, rather than working directly with the underlying differential equations every time.

Section 1.4

Why feedback matters: disturbance rejection and model uncertainty

Feedback earns its added complexity by solving two problems open-loop control fundamentally can't: disturbances (unpredictable external influences on the plant — wind gusts on a drone, road friction changes for a car's cruise control) and model uncertainty (your understanding of the plant's exact behavior is never perfect — a motor's true characteristics vary with temperature, load, and manufacturing tolerances).

Feedback corrects for what you didn't (and often couldn't) predict

An open-loop controller's output depends entirely on how accurately you modeled the plant in advance — if a cruise control simply sets throttle based on a fixed "speed vs. throttle" table, hitting a hill (a disturbance the table never accounted for) causes the car to slow down with no correction at all. A closed-loop cruise control measures actual speed and increases throttle specifically because the error (reference minus measured speed) grew — it doesn't need to have predicted the hill in advance; it only needs to notice the resulting error and respond to it, which is precisely what makes feedback so powerful for real-world systems that are never perfectly predictable.

Section 1.5

Worked problem — thermostat: open-loop vs. closed-loop

Problem

Compare two room-heating designs: (A) a heater that runs at a fixed power for a fixed duration once turned on, and (B) a thermostat that measures room temperature and turns the heater on/off based on whether the measured temperature is below or above a target. Someone opens a window partway through heating in both cases. Trace what happens in each.

Design A (open-loop):
  - Heater runs for the pre-set duration, delivering a fixed amount of heat energy
  - Window opens -> heat escapes faster than assumed -> room ends up colder
    than intended
  - Heater has NO WAY to detect this happened -- it simply finishes its
    programmed run and stops, regardless of actual room temperature

Design B (closed-loop / thermostat):
  - Heater runs, temperature sensor continuously measures actual room temp
  - Window opens -> room temp drops -> ERROR (target - measured) increases
  - Controller detects the increased error and keeps the heater on longer,
    specifically BECAUSE the measured temperature hasn't yet reached target
  - Heater turns off only once measured temperature actually reaches the target,
    regardless of how much extra heat the open window required

Why Design B "doesn't need to know about the window" to correct for it: this is exactly Section 1.4's point about disturbance rejection — the thermostat never needs a model of "how much colder does an open window make the room," because it's not working from a prediction at all; it's continuously reacting to the actual measured error, whatever caused it. This is the single most important practical advantage feedback provides over open-loop control, and it generalizes to essentially any disturbance the designer never explicitly anticipated.

Why Design A isn't simply "wrong" as an engineering choice: for a well-insulated, predictable room with no expected disturbances, open-loop heating (or a simple manual dial) can be perfectly adequate and considerably cheaper (no sensor, no controller logic) — the decision genuinely depends on how much disturbance and model uncertainty a specific application actually needs to tolerate, exactly Section 1.2's pitfall box point.

Wrap-up

Recap

  1. A plant is the fixed physical system being controlled; a controller is the designed logic deciding what input to apply. A reference is the desired output; error is reference minus actual output.
  2. Open-loop control decides its output from the reference alone, with no way to detect whether the plant actually achieved the desired result. Closed-loop (feedback) control measures the actual output and corrects based on the resulting error.
  3. A single op-amp's negative feedback circuit (Electronics Ch.6) is a miniature closed-loop control system — the same measure-compare-correct pattern scales from a simple circuit to a full robotic system.
  4. Feedback isn't automatically superior — it adds sensor cost, complexity, and (as later chapters show) new potential failure modes like instability. It earns its complexity specifically by handling disturbances and model uncertainty that open-loop control fundamentally cannot detect or correct.
  5. Block diagrams (blocks, summing junctions, branch points) are a precise, algebraically-manipulable notation for system structure — not just an illustration, but a real tool for deriving system behavior (formalized in Chapter 4).
Check yourself

Quick check

Question 1

Why can't an open-loop controller detect that a disturbance (like an opened window) has affected the plant's actual behavior?

An open-loop controller decides its output based only on the reference, with no measurement of the plant's actual output at all -- there's no feedback path carrying information about what actually happened back to the controller. Without measuring the real output, it has no way to detect any discrepancy between what it assumed would happen and what actually occurred.
Question 2

How is an op-amp circuit with negative feedback an example of closed-loop control?

The op-amp's raw output acts as the "plant," and feeding a portion of that output back to the inverting input is exactly a feedback path measuring the actual result. The op-amp continuously adjusts its output based on the difference between the two inputs (effectively an error signal), which is precisely the measure-compare-correct structure of closed-loop control, just implemented in a simple analog circuit rather than a full control system.
Question 3

Why isn't closed-loop control automatically the "better" choice for every system?

Closed-loop control requires a working sensor, which adds cost, complexity, and potential failure points (including measurement noise), and a poorly designed feedback controller can actually make behavior worse than no control at all -- including instability. The choice between open-loop and closed-loop is a genuine engineering trade-off based on how much disturbance and model uncertainty a specific application needs to tolerate, not an automatic preference for the more sophisticated option.

Putting It Together

Six chapters have covered modeling, transfer functions, poles, feedback, stability, and PID as separate ideas — each with its own worked problem in isolation. This closing chapter assembles them into a single, repeatable design process, addresses the practical gap between a continuous-time design and a microcontroller's inherently discrete implementation, and closes with one capstone project carried start to finish: physics, to transfer function, to stability check, to controller design, to working embedded code.

Section 7.1

The full control design process

1. MODEL the physical system  -- derive a differential equation from
   physical law (Chapter 2)
2. Convert to a TRANSFER FUNCTION using the Laplace transform (Chapter 2-3)
3. Analyze OPEN-LOOP behavior -- poles, expected response shape,
   is it already stable? (Chapter 3)
4. Choose a CONTROLLER STRUCTURE (commonly PID) and design/estimate
   initial gains (Chapter 6)
5. Derive the CLOSED-LOOP transfer function via block diagram
   reduction (Chapter 4)
6. Verify CLOSED-LOOP STABILITY, e.g. via Routh-Hurwitz, and check
   the design has adequate margin, not just barely-stable (Chapter 5)
7. IMPLEMENT the controller in discrete form on real hardware,
   including practical safeguards like anti-windup (Chapter 6)
8. TEST on the real system and iteratively TUNE, since the LTI
   model is always an approximation (Chapter 6)
Why this order specifically, and why skipping step 6 is a common, costly mistake

Each step depends on the output of the previous one — you can't meaningfully check closed-loop stability (step 6) before you have a closed-loop transfer function (step 5), which needs a controller design (step 4), which needs to know the open-loop behavior it's correcting (step 3). A genuinely common real-world mistake is designing a PID controller purely by intuition or by directly tuning gains on real hardware (jumping straight to steps 4 and 7-8), skipping the stability verification in step 6 entirely — this can work out fine for simple, forgiving systems, but risks discovering instability (Chapter 5) only once it's already happening on physical hardware, which is a far more expensive and sometimes dangerous way to find out than a five-minute Routh-Hurwitz check on paper first.

Section 7.2

From continuous design to discrete implementation

Every transfer function and stability analysis in this topic has assumed a continuous-time signal — but a microcontroller (Microcontrollers Chapter 3-4) samples its inputs at discrete time steps and updates its output only periodically, not continuously. This gap between the theory and the implementation is worth understanding, even briefly, before trusting a continuous-time design to behave identically once discretized.

Why sampling rate is a genuine design parameter, not just an implementation detail

A control loop that samples too infrequently relative to how fast the plant's dynamics actually change (its poles, from Chapter 3) effectively "misses" important behavior between samples — the discrete controller is reacting to stale information, degrading performance and, in extreme cases, destabilizing a system that would have been perfectly stable under truly continuous control. A common rule of thumb is sampling at least 10-20× faster than the system's fastest relevant time constant (Chapter 2-3) — directly connecting the abstract pole/time-constant values derived earlier in this topic to a concrete number: how many milliseconds Microcontrollers Chapter 4's millis()-based loop needs to run its PID update.

A design that's stable in continuous time can become unstable when discretized too slowly

This isn't a hypothetical concern — it's a well-documented, genuinely important effect: reducing sampling rate effectively introduces additional delay and approximation error into the loop, both of which can erode a design's stability margin (Chapter 5) or eliminate it entirely. A controller verified stable via Routh-Hurwitz on the continuous-time model should still be tested at its actual intended sampling rate on real (or simulated) hardware before being trusted — the continuous-time analysis is a necessary first check, not a substitute for verifying the final, actually-discretized implementation.

Section 7.3

Capstone project — full DC motor speed control design

Project spec

Design and verify a PID speed controller for a DC motor, from physical model through to working embedded code, following the Section 7.1 process end to end.

# --- Step 1-2: Model and transfer function (Chapter 2's exact motor example) ---
# J(dω/dt) + bω = KV  ->  G(s) = K/(Js+b)
# Using the same numeric example as Chapter 4's worked problem:
G(s) = 2/(s+2)

# --- Step 3: Open-loop analysis ---
# Single pole at s=-2 -> already stable on its own, first-order,
# time constant τ=0.5s, DC gain=1 (Chapter 2-3)
# But open-loop alone has no way to correct for load disturbances (Chapter 1) --
# closing the loop is still worthwhile even though the plant itself is stable

# --- Step 4: Controller design -- start with PI (integral to kill
# Chapter 4's steady-state error finding; skip D initially, motor
# speed measurements are often noisy -- Section 6.3's pitfall) ---
Kp = 5, Ki = 2   (starting estimates, to be tuned)

# --- Step 5: Closed-loop transfer function (Chapter 4's method) ---
# Controller in s-domain: C(s) = Kp + Ki/s = (Kp*s + Ki)/s
# Forward path: C(s)G(s) = (Kp*s+Ki)/s × 2/(s+2) = 2(Kp*s+Ki) / (s(s+2))
# Closed-loop, unity feedback: T(s) = C(s)G(s) / (1+C(s)G(s))
# Characteristic equation: s(s+2) + 2(Kp*s+Ki) = 0
#   s² + 2s + 2*Kp*s + 2*Ki = 0
#   s² + (2+2Kp)s + 2Ki = 0
# Substituting Kp=5, Ki=2:
s² + 12s + 4 = 0

# --- Step 6: Stability check (Routh-Hurwitz, Chapter 5) ---
# For a 2nd-order s²+a₁s+a₂: stable iff BOTH a₁>0 AND a₂>0 (a simpler
# special case of the full Routh array for this low an order)
a₁ = 12 > 0  ✓
a₂ = 4 > 0   ✓
# STABLE, with healthy positive margin on both coefficients

# --- Step 7: Discrete implementation (Chapter 6's pattern, PI only) ---
float Kp = 5.0, Ki = 2.0;
float integral = 0;
unsigned long lastTime = 0;

float computePI(float setpoint, float measuredSpeed) {
    unsigned long now = millis();
    float dt = (now - lastTime) / 1000.0;
    lastTime = now;

    float error = setpoint - measuredSpeed;
    integral += error * dt;
    integral = constrain(integral, -50, 50);   // anti-windup (Chapter 6)

    return Kp*error + Ki*integral;
}

// In loop(): read speed sensor, call computePI(), apply result via
// analogWrite() to the motor driver (Microcontrollers Chapter 3, PWM)

Why derivative was deliberately left out of this design, not merely forgotten: Section 6.3 flagged derivative action's sensitivity to noisy measurements, and shaft speed sensors (especially simple ones) are commonly noisy — a real engineer routinely makes exactly this judgment call, starting with PI and only adding D later if overshoot genuinely proves to be a problem in practice, rather than including all three terms by default. This mirrors Section 7.1's step 8 directly: the design isn't finished at the paper stage, it's refined based on how the real system actually behaves.

Why the characteristic equation's coefficients directly show the design has real margin, not just barely-passing stability: both coefficients (12 and 4) are comfortably positive, not close to zero — recalling Chapter 5's worked problem, where the boundary of instability was a coefficient hitting exactly zero, having both coefficients well clear of that boundary gives confidence this design tolerates some real-world model imperfection (Chapter 2's LTI limitations) without becoming marginally stable or unstable in practice.

The complete chain, one more time: a physical law (Chapter 2) became a differential equation, became a transfer function, was combined with a designed PI controller via block diagram algebra (Chapter 4), was verified stable via Routh-Hurwitz (Chapter 5), and was finally implemented as real, running C code using exactly the non-blocking timing pattern from Microcontrollers Chapter 4 and PWM output from Microcontrollers Chapter 3 — this is genuinely the entire discipline of control systems engineering, compressed into one worked example, and it's exactly the process a real embedded controls engineer follows for a real project.

Wrap-up

Recap

  1. The full control design process: model → transfer function → open-loop analysis → controller design → closed-loop derivation → stability verification → discrete implementation → real-system tuning. Skipping stability verification before hardware testing is a common, costly shortcut to avoid.
  2. A continuous-time design must eventually run on a sampled, discrete-time microcontroller — sampling rate is a real design parameter, not an implementation afterthought, with "10-20× the fastest relevant time constant" as a practical rule of thumb.
  3. A design verified stable in continuous time can lose that stability margin, or become genuinely unstable, if implemented with too slow a sampling rate — always verify the actual discretized implementation, not just the continuous-time model.
  4. Real controller design routinely makes deliberate trade-offs (like omitting the derivative term when sensor noise is a known issue) rather than mechanically including every available term — good engineering judgment, not incompleteness.
  5. Coefficients well clear of a stability boundary (not just barely passing) indicate genuine design margin, providing confidence against the LTI model's inevitable real-world imperfections.
Check yourself

Quick check

Question 1

Why is skipping the closed-loop stability verification step (before testing on real hardware) considered a costly shortcut, even for a system that seems to be working during testing?

A stability check like Routh-Hurwitz can be done on paper in minutes and definitively rules out instability across the full range of conditions the model captures. Skipping it means instability, if present, is only discovered once it actually happens on physical hardware -- which can be more expensive, slower to diagnose, and in some applications genuinely dangerous, compared to catching the issue analytically beforehand.
Question 2

Why can a controller that's proven stable using a continuous-time model still become unstable once implemented on a microcontroller?

A microcontroller samples and updates at discrete time intervals rather than continuously. Sampling too slowly relative to the system's actual dynamics introduces effective delay and approximation error into the control loop, which can erode or entirely eliminate the stability margin that was verified using the idealized continuous-time model -- the continuous-time analysis doesn't automatically guarantee the same result once the control loop is actually discretized.
Question 3

In the capstone project, why was the derivative term deliberately left out of the initial PID design?

Derivative action is highly sensitive to measurement noise, and motor shaft speed sensors are commonly noisy. Rather than including all three PID terms automatically, the design started with just proportional and integral, planning to add derivative later only if overshoot proved to be an actual problem once tested on the real system -- a deliberate engineering trade-off based on a known practical limitation, not an oversight.

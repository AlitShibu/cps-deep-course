Finite State Machines

Counters (Chapter 5) advance through a fixed, unchanging sequence. Real control systems need more — a traffic light's next color depends on more than just "what came before," and a system's behavior often needs to branch based on external inputs. A finite state machine is the formal, systematic way to design exactly this kind of logic — and it's the direct blueprint for an adaptive traffic signal controller.

Chapter 6 of 7Builds on Chapters 3-5Directly relevant to adaptive traffic-signal control
Section 6.1

What a finite state machine actually is

A finite state machine (FSM) is a system that exists, at any given moment, in exactly one of a fixed, finite set of states — and moves between states according to defined transitions, usually triggered by inputs and/or the passage of clock edges. A traffic light is a perfect everyday example: it's always in exactly one state (Red, Yellow, or Green), and it moves through a defined sequence of transitions over time.

A state diagram: circles are states, arrows are transitions, labels describe what triggers each transition.
Why "finite" is the key word, and why this generalizes Chapter 5's counters

A counter is actually a special, simple case of an FSM — each count value is a "state," and the transition rule is always the same ("go to the next number on every clock edge," Section 5.2). An FSM generalizes this by allowing the next state to depend on more than just the current state — it can also depend on external inputs (a pedestrian button press, a sensor reading), letting the system's behavior branch and respond to the outside world, not just march through a fixed sequence blindly.

Section 6.2

Moore vs. Mealy machines

FSMs come in two standard flavors, distinguished by exactly one thing: what determines the output.

TypeOutput depends on
Moore machineThe current state only — the output is a fixed property of being in that state.
Mealy machineThe current state and the current input, together — the output can change instantly in response to an input, without waiting for the next state transition.
A concrete way to feel the difference

In a Moore traffic light, "Green" always means the same output (go) regardless of anything else happening right now — the output is entirely defined by which state you're in. In a Mealy version of a similar system, imagine a state "Waiting for pedestrian" whose output changes immediately the instant a pedestrian button is pressed, without needing to first transition into a whole new "state" — the output reacts directly and immediately to the input, layered on top of whatever state the system happens to be in. Moore machines tend to be simpler to reason about and are more common in straightforward sequencing tasks (like a basic traffic light); Mealy machines can react faster to inputs (no need to wait for a clock edge and a state change) but are correspondingly trickier to design and verify correctly.

Section 6.3

The general FSM design process, and how it maps to hardware

Every FSM, once designed, is built from exactly two pieces you already know: a state register (Chapter 5 — a register holding a code representing "which state am I in right now") and combinational logic (Chapter 3 — computing the next state and the output, based on the current state and any inputs).

Every FSM is this same three-block structure: next-state logic decides where to go, a state register remembers where you are, output logic decides what to do while there.

The design process, in order:

  1. Draw the state diagram (Section 6.1's traffic light circles-and-arrows) directly from the English description of desired behavior.
  2. Build a state table — a formal table listing, for every state and every possible input, exactly what the next state and output should be (directly analogous to Chapter 2's truth tables, but for states instead of individual bits).
  3. Assign binary codes to each state — e.g., Red=00, Yellow=01, Green=10 — since the state register (Chapter 5) can only store binary values.
  4. Derive the next-state and output logic from the state table, using Chapter 2-3's Boolean simplification and Karnaugh map techniques directly.
  5. Build it from a register (Chapter 5) plus the derived combinational logic (Chapter 3).
Section 6.4

Worked problem — a basic adaptive traffic light FSM

A simplified version of exactly the kind of system an adaptive traffic signal controller builds on: a traffic light that normally cycles Red→Green→Yellow→Red on fixed timers, but can be interrupted by a "sensor detects heavy cross-traffic" input that forces an early transition to Red, extending the cross street's green time.

Step 1: State diagram (in words, since we can't draw a full interactive diagram here) 
States: RED, GREEN, YELLOW  (2 bits needed: 00, 01, 10)

RED    --[fixed timer expires]--> GREEN
GREEN  --[fixed timer expires]--> YELLOW
GREEN  --[cross-traffic sensor input=1, EARLY]--> YELLOW   (Mealy-style: input causes an
                                                               immediate transition, not
                                                               waiting for the normal timer)
YELLOW --[fixed timer expires]--> RED
Step 2: State table (partial, showing the GREEN state's two possible transitions) 
Current State | Sensor Input | Next State | Output (light color)
   GREEN      |      0       |   GREEN*   |   Green
   GREEN      |      1       |   YELLOW   |   Green   (Mealy: output still shows Green
                                                          right now, but next-state logic
                                                          already reacts to the sensor)

*GREEN stays GREEN only while the fixed timer hasn't yet expired --
 a real implementation ANDs this with a separate timer-counter's "expired" signal
Why this is a Mealy machine, specifically — and why that choice matters here

The sensor input directly influences the next-state decision, allowing an immediate reaction (cutting green time short) rather than waiting for the state to naturally finish its normal timer first — this responsiveness is precisely why a Mealy-style design (or a Moore design with careful extra states) is the right choice for an adaptive system, as opposed to a simple Moore machine that would only ever follow its fixed, pre-timed sequence regardless of real traffic conditions. This is the exact conceptual leap from "fixed-timer traffic light" to "adaptive traffic light" — the entire premise of an adaptive traffic signal project — expressed in FSM terms: adding sensor inputs that can alter transitions, not just relying on time alone.

Wrap-up

Recap

  1. A finite state machine exists in exactly one of a fixed set of states at a time, moving between them via defined transitions — a generalization of Chapter 5's counters that allows inputs, not just time, to influence what happens next.
  2. Moore machines produce output based on state alone; Mealy machines let output (or the next transition) react directly to inputs, enabling faster, more adaptive responses at the cost of more complex design and verification.
  3. Every FSM is built from the same three-block architecture: next-state logic and output logic (both combinational, Chapter 3), wrapped around a state register (Chapter 5) that remembers the current state.
  4. The design process — state diagram, state table, binary state encoding, derive logic, build — is systematic and repeatable for any sequencing/control problem, not just traffic lights.
  5. Adding sensor inputs that can alter an FSM's transitions (not just relying on fixed timers) is the exact conceptual step from a simple sequencer to an adaptive control system — directly the premise of an adaptive traffic signal project.
Check yourself

Quick check

Question 1

How is a Chapter 5 counter actually a special case of a finite state machine?

Each count value is a state, and the transition rule is fixed and simple: always advance to the next value on every clock edge, with no dependence on external inputs. An FSM generalizes this by allowing the next state to also depend on inputs, not just the passage of clock edges alone.
Question 2

What's the key difference between a Moore machine and a Mealy machine?

A Moore machine's output depends only on the current state. A Mealy machine's output (or next-state decision) depends on both the current state AND the current input, allowing it to react to inputs immediately rather than waiting for a state transition to complete first.
Question 3

What are the three architectural blocks every FSM is built from, and which earlier chapters do they come from?

Next-state logic and output logic, both built from combinational logic (Chapter 3); and a state register, built from flip-flops (Chapters 4-5) that remembers the current state between clock edges.

Section 7.1

Two paths from a diagram to real hardware

Once you've designed a circuit — even something as simple as Chapter 3's full adder — there are two fundamentally different ways to make it physically real:

Fixed-function ICs — gates already baked into silicon

Decades-old chip families (the "74xx series") package a handful of gates each — a single chip might contain four independent NAND gates, wired to external pins, and nothing else. Building a circuit means physically wiring several such chips together on a breadboard or PCB (recall your PCB Design roadmap topic). This is simple to understand and still used for small, fixed designs, but genuinely impractical for anything with more than a modest number of gates — you'd need dozens of chips and enormous amounts of wiring for a real FSM or counter of useful size.

Programmable logic — an FPGA reconfigures itself to BE your circuit

An FPGA (Field-Programmable Gate Array — the exact device your later FPGA roadmap topic covers in depth) contains thousands of tiny, generic, reconfigurable logic blocks. Instead of wiring separate fixed-function chips together, you describe your entire circuit — every gate, every flip-flop, every FSM from this course — in a text file, and specialized software configures the FPGA's internal blocks and interconnections to physically become that exact circuit.

Why this matters for everything you just learned

Every single concept from Chapters 1-6 — gates, truth tables, flip-flops, counters, FSMs — is not just theory you'll leave behind. It's the literal vocabulary you need to read and write the text description that configures an FPGA. The next section shows you exactly what that text description looks like, and how directly it maps onto what you've already learned.

Section 7.2

Hardware Description Languages — describing circuits, not writing programs

VHDL and Verilog are the two dominant Hardware Description Languages (HDLs) — text formats that look superficially like programming code, but describe hardware structure and timing, not a sequence of instructions to execute. This distinction is worth taking seriously, because it's the single biggest mental adjustment coming from C or Python.

The critical mental shift: concurrent, not sequential

In C (Chapter 4 of the C course), statements execute one after another, in order — line 2 waits for line 1 to finish. In an HDL, every line describing a signal assignment can, in principle, happen simultaneously — you're describing physically separate pieces of hardware (Chapter 2's gates, Chapter 4's flip-flops) that all exist and operate at the same time, not a sequence of steps a single processor works through one at a time. A block like process(clk) in VHDL doesn't mean "run this function when called" — it describes a piece of hardware (a register, Chapter 5) that updates only on a clock edge, exactly like Chapter 4's edge-triggered flip-flops.

A full adder (Chapter 3, Section 3.1), described in Verilog

module full_adder(
    input  a, b, cin,
    output sum, cout
);
    assign sum  = a ^ b ^ cin;        // XOR chain -- Chapter 2's XOR gate, Chapter 3's Sum logic
    assign cout = (a & b) | (b & cin) | (a & cin);  // Chapter 3's carry-out logic, directly
endmodule
Why this should look almost readable already

^ is XOR, & is AND, | is OR — exactly Chapter 2's gate symbols and exactly C Chapter 10's bitwise operators, now describing real hardware structure instead of a software bit-manipulation operation on a variable. The assign statements aren't sequential instructions — both lines describe genuinely separate, simultaneously-existing pieces of combinational logic (Chapter 3), computing continuously and in parallel, exactly like the real full-adder circuit diagram from Chapter 3 you already understand.

A D flip-flop (Chapter 4), described in Verilog

module d_flipflop(
    input  clk, d,
    output reg q
);
    always @(posedge clk)    // "posedge" = positive/rising edge -- Chapter 4's edge-triggering
        q <= d;                // capture d's value into q, exactly at the clock edge, nothing more
endmodule

always @(posedge clk) is a direct, literal statement of Chapter 4's central idea: this hardware only updates at the instant of a rising clock edge — everything between edges is irrelevant, exactly as Section 4.3's worked problem demonstrated by hand.

Wrap-up

Recap

  1. Circuits become physical hardware either through fixed-function ICs (simple, but impractical past small designs) or FPGAs (reconfigurable logic blocks that physically become your described circuit).
  2. Hardware Description Languages (VHDL, Verilog) describe circuit structure and timing, not sequential instructions — every line can represent simultaneously-existing, parallel hardware, a genuine mental shift from software.
  3. HDL operators (&, |, ^) are exactly this course's gates and exactly C's bitwise operators — the same underlying concept in a third notation.
  4. always @(posedge clk)-style blocks directly implement Chapter 4's edge-triggered flip-flop behavior — HDL doesn't introduce a new timing concept, it gives you syntax for one you already understand.
  5. Every chapter in this course maps to a specific, concrete need later in the roadmap: Microcontroller timers (Ch.5), memory-mapped registers (Ch.1, Ch.3), RTOS/protocol logic and traffic-signal controllers (Ch.6), and the FPGA topic's entire syntax (Ch.7).

Quick check — final review across the whole Digital Logic course

Question 1

Why is it misleading to think of an HDL description as "code that runs," the way a C program does?

An HDL describes physically separate pieces of hardware that exist and operate simultaneously, not a sequence of instructions executed one after another by a single processor. Multiple assign/always blocks in the same file all represent concurrently-existing circuitry, not a step-by-step sequence.
Question 2

What does "always @(posedge clk) q <= d;" directly correspond to from Chapter 4?

An edge-triggered D flip-flop -- this HDL block describes hardware that captures d's value into q only at the instant of a rising clock edge, exactly matching Chapter 4's core concept, just expressed in HDL syntax instead of a truth table or diagram.

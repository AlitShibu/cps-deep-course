Complexity & Big-O

Every later chapter in this topic ends with the same question: how much does this cost, and how does that cost grow as the data grows? This chapter builds the language for answering it. You will learn to count operations instead of seconds, to read the growth of a function off a piece of code, to use Big-O notation precisely (including its formal definition), to account for memory as well as time, and to recognize the cases where the textbook answer and the real answer on a microcontroller disagree. Code appears in C, the main language of this course, with Python alongside where it makes an idea clearer.

Section 1.1

Why we measure cost, and why not in seconds

Two programs solve the same problem. Which is better? The obvious test is to run both and time them, but that answer is fragile: it depends on the processor, the compiler's optimization level, what else is running, and above all on the particular input you happened to try. A program that is instant on 100 items may be unusable on 100,000, and a stopwatch on the small case will never tell you.

Algorithm analysis replaces the stopwatch with two questions that do not depend on the machine:

ResourceThe questionName
TimeHow many basic operations does the algorithm perform, as a function of the input size n?Time complexity
MemoryHow much extra storage does it need, as a function of n?Space complexity

The input size n is whatever grows: the number of elements in an array, the number of characters in a string, the number of nodes in a graph. What counts as a basic operation is a deliberate simplification: one comparison, one addition, one array access, one assignment. Each is treated as costing the same single unit. Real machines differ (a division is slower than an addition), but the simplification is justified because the quantity we care about, how the total scales with n, is not changed by constant factors.

Why this matters more on a microcontroller than on a laptop

On a laptop, a wasteful algorithm often hides behind a fast processor and gigabytes of memory. On an ESP32 or an AVR-based Arduino you have kilobytes of RAM, no operating system to rescue you, and often a hard deadline (a control loop that must finish every millisecond, a UART buffer that overflows if you are slow, as in Serial Protocols Chapter 2). A choice between an O(n) and an O(n²) approach can be the difference between meeting and missing a real-time deadline, and an algorithm that needs O(n) extra memory can simply not fit.

Section 1.2

Counting operations

Start with the most honest method: count exactly. Here is a function that sums an array.

int sum(const int a[], int n) {
    int total = 0;              // 1 assignment
    for (int i = 0; i < n; i++) {   // 1 assignment, n+1 comparisons, n increments
        total += a[i];          // n additions (each also reads a[i])
    }
    return total;               // 1 return
}

The exact count is something like 3n + 4 operations, depending on how finely you count. Now consider a function that checks whether any two elements of an array are equal.

int has_duplicate(const int a[], int n) {
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            if (a[i] == a[j]) return 1;
        }
    }
    return 0;
}

In the worst case (no duplicates) the inner comparison runs (n−1) + (n−2) + … + 1 + 0 times:

Total comparisons = n(n − 1) / 2

n = 10     →        45 comparisons
n = 1,000  →   499,500 comparisons
n = 100,000 → 4,999,950,000 comparisons

Notice what dominates. For large n the formula n(n−1)/2 = n²/2 − n/2 is essentially n²/2: the n/2 term is negligible next to it, and the 1/2 is just a constant. What matters is that doubling n roughly quadruples the work. That growth rate is the real fingerprint of the algorithm, and the next section gives it a name.

Suppose a slow device performs 1,000,000 simple operations per second. An O(n) pass over a million items takes 1 second. An O(n log n) algorithm takes about 20 seconds. An O(n²) algorithm needs 10¹² operations, which is 10⁶ seconds, about 11.6 days. An O(log n) algorithm needs about 20 operations: twenty millionths of a second. The same problem, four algorithms, and a spread from microseconds to weeks. This is why the notation exists.

Section 1.3

Big-O notation, precisely

Big-O captures "how the cost grows" by deliberately throwing away two kinds of detail: constant factors, and everything except the fastest-growing term.

The formal definition

f(n) = O(g(n))   means:

    there exist constants c > 0 and n₀ such that
    f(n) ≤ c · g(n)   for every n ≥ n₀

In words: beyond some starting size n₀, f never grows faster than a constant multiple of g. The function g is an upper bound on growth. Check it on a real example: is 3n² + 20n + 500 = O(n²)?

Try c = 4. We need 3n² + 20n + 500 ≤ 4n²,  i.e.  n² ≥ 20n + 500.

n = 34:  1,156 ≥ 1,180 ?  No.
n = 35:  1,225 ≥ 1,200 ?  Yes.

For every n ≥ 35 the gap n² − 20n − 500 keeps growing, so the inequality
holds from then on. With c = 4 and n₀ = 35 the definition is satisfied.
Therefore 3n² + 20n + 500 = O(n²).

The three simplification rules

RuleExample
Drop constant factors5n → O(n); n²/2 → O(n²)
Drop lower-order termsn² + 100n + 7 → O(n²)
Sequential steps add; nested steps multiplyA loop of n followed by a loop of n² → O(n + n²) = O(n²). A loop of n containing a loop of n → O(n · n) = O(n²)

Big-O is an upper bound, and it comes with relatives

NotationMeaningInformal reading
O(g(n))f grows no faster than g (upper bound)"at most this bad"
Ω(g(n))f grows at least as fast as g (lower bound)"at least this bad"
Θ(g(n))both O(g) and Ω(g): a tight bound"exactly this rate"

In everyday engineering conversation people say "O(n)" when they strictly mean Θ(n), the tight bound. It is worth knowing the difference: saying an algorithm is O(n²) is technically true of a linear algorithm too, since linear growth is also bounded above by n². When precision matters, say Θ.

Best, worst, and average case

The same algorithm can behave differently on different inputs of the same size n. Linear search shows this clearly:

CaseSituationComparisons
BestTarget is the first element1 → O(1)
WorstTarget is last, or absentn → O(n)
AverageTarget equally likely at any positionabout n/2 → O(n)

Unless stated otherwise, "the complexity" means the worst case. That is the right default for engineers: a guarantee that holds for every input is what you need when a deadline depends on it.

Big-O does not say "this takes n steps"

It says the cost grows proportionally to n for large n. Two O(n) algorithms can differ by a factor of 100 in real speed, and an O(n) algorithm with a large constant can lose to an O(n²) one on small inputs. Big-O compares how algorithms scale, not which is faster at a given n. Section 1.6 returns to this.

Section 1.4

The common complexity classes, with code

O(1): constant time

The cost does not depend on n at all. Reading a[i] is O(1) because an array is contiguous memory: the address is computed directly as base + i × element_size, with no searching.

int first(const int a[]) { return a[0]; }        // C: O(1)
def first(a): return a[0]                          # Python: O(1)

O(n): linear time

One pass over the data. Linear search is the model example.

int linear_search(const int a[], int n, int target) {
    for (int i = 0; i < n; i++) {
        if (a[i] == target) return i;
    }
    return -1;
}
def linear_search(a, target):
    for i, x in enumerate(a):
        if x == target:
            return i
    return -1

O(log n): logarithmic time

The problem size is cut by a constant factor (usually half) at every step. Binary search on a sorted array is the model example: compare with the middle element, discard the half that cannot contain the target, repeat.

int binary_search(const int a[], int n, int target) {
    int lo = 0, hi = n - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;   // not (lo+hi)/2: that can overflow
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1;
        else                  hi = mid - 1;
    }
    return -1;
}
def binary_search(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2           # Python integers do not overflow
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

How many steps? Each iteration halves the remaining range, so at most ⌊log₂ n⌋ + 1 comparisons are needed. For n = 1,000,000 that is ⌊19.93⌋ + 1 = 20 comparisons, against up to 1,000,000 for linear search. Doubling the data adds just one more step.

The (lo + hi) overflow bug, a real classic

In C, int mid = (lo + hi) / 2 breaks when lo + hi exceeds the largest int. The fix lo + (hi − lo) / 2 never overflows. A version of this bug sat undetected for years in widely used library code, because it only appears with arrays of more than a billion elements. On a 16-bit microcontroller, where int tops out at 32,767, the same bug appears at arrays of only about 16,000 elements.

O(n log n): linearithmic time

The signature of efficient sorting (Chapter 6): split the problem in half repeatedly (log n levels), doing O(n) work at each level. You will meet it again in merge sort and heap sort.

O(n²): quadratic time

Typically two nested loops over the same data, like has_duplicate in Section 1.2. Fine for tiny inputs, painful beyond a few thousand elements.

O(2ⁿ): exponential time

The cost doubles with every extra element. The classic example is naive recursive Fibonacci, because each call spawns two more calls that recompute the same values over and over.

long fib(int n) {                       // C
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);
}
def fib(n):                             # Python
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

The number of calls for fib(n) is 2·fib(n+1) − 1. For fib(5) that is 15 calls; for fib(30) it is 2,692,537 calls, all to compute one number. Strictly the growth is about 1.618ⁿ (the golden ratio), which is O(2ⁿ) as an upper bound. The fix is to stop recomputing: remember results (memoization) or build up from the bottom.

long fib_fast(int n) {                  // C: O(n) time, O(1) space
    long a = 0, b = 1;
    for (int i = 0; i < n; i++) {
        long next = a + b;
        a = b;
        b = next;
    }
    return a;
}
from functools import lru_cache

@lru_cache(maxsize=None)                # Python: memoized, O(n) time and space
def fib(n):
    return n if n <= 1 else fib(n - 1) + fib(n - 2)

The same function drops from exponential to linear time. Chapter 10 (Dynamic Programming) turns this trick into a general method.

Section 1.5

Space complexity, the stack, and amortized cost

Space complexity

Space complexity counts the extra memory an algorithm needs beyond its input, again as a function of n. The two versions of Fibonacci differ in time and in space: fib_fast uses three variables however large n is (O(1) space), while memoized Fibonacci stores n results (O(n) space). An algorithm that works in place, modifying the input array without a second copy, has O(1) extra space; one that builds a full copy has O(n).

ExampleTimeExtra space
Reverse an array in place by swapping endsO(n)O(1)
Reverse an array by copying into a new oneO(n)O(n)
Iterative FibonacciO(n)O(1)
Memoized FibonacciO(n)O(n)

The hidden cost: recursion uses stack memory

Each active function call occupies a stack frame (return address, saved registers, local variables). A recursion that goes n levels deep therefore uses O(n) stack space even if it allocates nothing explicitly. The frame size is typically a few tens of bytes, though it varies with compiler and chip. On a laptop with megabytes of stack that is irrelevant; on a microcontroller with a stack of a couple of kilobytes, a recursion a few hundred levels deep can overflow it and corrupt memory silently, with no error message. This is why embedded coding standards often forbid recursion outright, and why iterative versions of algorithms matter in this course.

Amortized analysis: the cost of an average operation over a sequence

Some operations are usually cheap but occasionally expensive. The standard example is appending to a growable array. When the array is full, a new one of double the size is allocated and every element is copied across.

typedef struct { int *data; int len, cap; } IntVec;

int vec_push(IntVec *v, int x) {
    if (v->len == v->cap) {                       // full: grow
        int new_cap = v->cap ? v->cap * 2 : 1;
        int *p = realloc(v->data, new_cap * sizeof *p);
        if (!p) return -1;                          // allocation failed
        v->data = p;
        v->cap = new_cap;
    }
    v->data[v->len++] = x;
    return 0;
}

A single push can cost O(n) when it triggers a copy, so is push O(n)? In the worst single case, yes; but the expensive copies are rare and the capacity doubles each time. Appending n items from capacity 1 copies 1 + 2 + 4 + … + n/2 elements in total, which is less than n. So the total work for n appends is under 2n, and the amortized cost per append is O(1).

Appending 1,000 items, starting from capacity 1:
resizes copy 1, 2, 4, 8, 16, 32, 64, 128, 256, 512 elements
total copies = 1,023   →   about 1.02 copies per append

Python's list.append is the same idea: a growable array with amortized O(1) appends. Note the contrast with real-time work: amortized O(1) guarantees the average, not that no single call is slow. A control loop with a hard deadline cannot tolerate an occasional O(n) pause, which is why embedded code usually pre-allocates a fixed-size buffer instead of growing one.

Preview: the ring buffer from Serial Protocols

A UART driver's receive buffer is a fixed-size array used as a ring, giving O(1) worst-case insertion and removal and no allocation at all. It trades flexibility (it can overflow) for a guaranteed constant cost. Chapter 4 builds exactly this structure.

Section 1.6

Measuring in practice, and where Big-O misleads

Theory tells you how an algorithm scales; measurement tells you what it costs on your hardware. Use both.

#include <stdio.h>
#include <time.h>

clock_t start = clock();
run_the_algorithm(data, n);
clock_t end = clock();
printf("%.3f ms\n", 1000.0 * (end - start) / CLOCKS_PER_SEC);
import timeit
t = timeit.timeit(lambda: linear_search(data, -1), number=100)
print(f"{t / 100 * 1000:.3f} ms per call")

To check the growth rate empirically, time the algorithm at n, 2n, 4n, and 8n. For O(n) the time roughly doubles each step; for O(n²) it roughly quadruples; for O(log n) it barely moves. On a microcontroller use a hardware timer (such as micros() on Arduino-style cores) instead of clock().

Four ways the textbook answer and reality disagree

EffectWhat happens
Constant factorsA well-written O(n) loop can beat a clumsy O(log n) routine until n is large; Big-O ignores the multiplier but you pay it.
Small nFor n = 20, a simple linear scan is usually faster than binary search plus the work of keeping the array sorted. Simplicity wins at small scale.
Memory access patternOn processors with caches, scanning a contiguous array is far cheaper per element than following pointers through scattered memory, so array-based O(n) can beat pointer-based O(log n) well past toy sizes.
Worst case versus typical caseAn algorithm with a bad worst case may be excellent on realistic data, and the reverse. Know which your application needs.
The practical rule

Choose by Big-O when n can grow large or is unbounded. When n is small and known (a lookup table of 50 entries, a menu of 8 items), choose the simplest correct code and do not pay in complexity for scalability you will never use. Premature optimization is cost without benefit; ignoring growth is the opposite mistake. The skill is knowing which regime you are in.

What to take away: part (a) is the mechanical skill of this chapter: read loops as counts, and let the dominating term decide the class. Part (b) is the judgment: Big-O tells you which algorithm scales better, but the engineering decision also weighs how large n really is, how the data is maintained, and how much complexity the code can afford.

Wrap-up

Recap

  1. Algorithms are compared by counting basic operations as a function of input size n (time complexity) and extra memory used (space complexity), not by stopwatch time, which depends on the machine and the particular input.
  2. Big-O is defined precisely: f(n) = O(g(n)) if there are constants c and n₀ with f(n) ≤ c·g(n) for all n ≥ n₀. In practice, drop constant factors and lower-order terms; sequential steps add, nested steps multiply. Ω is a lower bound and Θ a tight bound; "the complexity" normally means the worst case.
  3. The classes to recognize on sight: O(1) array index; O(log n) halving, as in binary search (20 comparisons for a million items); O(n) a single pass; O(n log n) efficient sorting; O(n²) nested loops; O(2ⁿ) naive overlapping recursion (fib(30) makes 2,692,537 calls).
  4. Space matters as much as time on a microcontroller: in-place algorithms use O(1) extra space, and recursion silently costs O(depth) stack, which is why embedded code often avoids it.
  5. Amortized analysis averages an occasionally expensive operation over a whole sequence: doubling a growable array makes append O(1) amortized (about 1.02 copies per append for 1,000 items), but a hard real-time deadline still needs a worst-case guarantee, such as a pre-allocated ring buffer.
  6. Big-O describes scaling, not speed at a given n. Constant factors, small n, and memory access patterns can reverse the textbook ranking, so use Big-O to choose when n is large or unbounded, and prefer the simplest correct code when n is small and fixed.
Check yourself

Quick check

Question 1

Show that 3n² + 20n + 500 is O(n²) by giving explicit constants c and n₀ that satisfy the definition.

Choose c = 4 and n₀ = 35. We need 3n² + 20n + 500 ≤ 4n², which simplifies to n² ≥ 20n + 500. At n = 35: 1,225 ≥ 700 + 500 = 1,200, so it holds (and at n = 34 it fails, which is why n₀ is 35). For larger n the difference n² − 20n − 500 only grows, so the inequality holds for every n ≥ 35. Other valid pairs exist (for example a larger c with a smaller n₀); the definition only requires that some pair works.
Question 2

A function first runs a loop of n iterations, then separately runs a pair of nested loops of n iterations each. What is its time complexity, and how would the answer change if the nested loops were instead inside the first loop?

Sequential steps add: O(n) + O(n²) = O(n²), because the lower-order term is dropped. If the nested loops were inside the first loop, the costs multiply: n × n² = O(n³). The distinction is exactly the rule from Section 1.3: sequential adds, nested multiplies.
Question 3

A growable array starts at capacity 1 and doubles whenever it is full. How many element copies happen in total while appending 1,000 items, and what does that say about the cost per append?

Resizes happen when the array holds 1, 2, 4, 8, 16, 32, 64, 128, 256, and 512 elements, copying that many each time: 1 + 2 + 4 + … + 512 = 1,023 copies. Over 1,000 appends that is about 1.02 copies per append, so the amortized cost per append is O(1), even though one particular append (the 513th) copies 512 elements at once. The caveat for embedded work is that the worst single call is still O(n), which a hard real-time loop may not tolerate.
Question 4

Why can a simple O(n) scan through a small array of 20 elements beat an O(log n) search structure in practice?

Big-O ignores constant factors and only describes scaling for large n. At n = 20 the log₂ n advantage is a handful of comparisons at most, while the more elaborate structure adds fixed overhead: extra code, maintaining sort order or pointers, and, on processors with a cache, scattered memory accesses that cost far more per step than reading a contiguous array. The simple scan has almost no overhead and reads memory in order, so its larger step count costs little. The crossover point depends on the hardware, which is why measuring matters when n is small.
Question 5

Why does naive recursive fib(30) make about 2.7 million calls, and what are two ways to bring the cost down to linear time?

Each call to fib(n) spawns two more calls, and the two sub-trees recompute the same values repeatedly (fib(28) is computed from both fib(30) and fib(29), and so on), so the number of calls grows exponentially: 2·fib(31) − 1 = 2,692,537 for n = 30. Two fixes: memoization (store each result the first time it is computed, so each of the 31 values is computed once, giving O(n) time and O(n) space), or an iterative loop that keeps only the previous two values (O(n) time and O(1) space), which is also the better choice on a memory-limited microcontroller since it avoids recursion's stack usage.

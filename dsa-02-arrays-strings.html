Arrays & Strings

The array is the structure everything else is built on, and the string is the array you will misuse most often. This chapter applies Chapter 1's cost-counting to both. You will see exactly why an array gives O(1) access but O(n) insertion, learn the three techniques that solve most array problems (two pointers, prefix sums, sliding windows), find out why a harmless-looking strlen in a loop condition can turn O(n) code into O(n²), see how two-dimensional arrays are laid out in memory, and finish with the safe-string habits that keep firmware from corrupting its own RAM. C is the main language; Python appears where the contrast teaches something.

Section 2.1

Arrays in memory, and what they cost

An array is a block of equally sized elements stored one after another in memory. That single fact explains every cost in this section. If a starts at address base and each element takes size bytes, then element i lives at:

address of a[i] = base + i × size

Computing that is one multiplication and one addition, however large the array is, so reading or writing a[i] is O(1). This is called random access. Nothing has to be searched or followed.

Fig 2.1 — Contiguous layout: the address of any element is computed, never searched for.

The cost of each operation

OperationCostWhy
Read or write a[i]O(1)Address arithmetic, as above
Search an unsorted arrayO(n)No shortcut: look at each element (Chapter 1's linear search)
Search a sorted arrayO(log n)Binary search; the layout makes jumping to the middle O(1)
Append at the end (space available)O(1)Write to a[len] and increase len
Insert at index iO(n)Everything from i onward must shift one slot right to open a gap
Delete at index iO(n)Everything after i must shift one slot left to close the gap

The array's strength and weakness come from the same property. Elements are packed with no gaps, so locating one is instant, but you cannot make room for a new one without moving its neighbors. Chapter 3 introduces linked lists, which make the opposite trade.

Capacity versus length

In C an array has a fixed capacity set when it is declared. What your program actually stores is the length, the number of slots in use. C does not track either for you: sizeof a / sizeof a[0] gives the capacity only where a is a true array (not after it decays to a pointer, C Chapter 5), and the length is a separate variable you maintain. A fixed array plus a len counter is the basic pattern behind nearly every embedded buffer.

Why arrays are fast in practice, beyond Big-O

Because elements are adjacent, a processor with a cache loads several neighbors in one memory fetch, so a loop over an array runs close to the hardware's best speed. This is the "memory access pattern" effect from Chapter 1, Section 1.6. On a small microcontroller with no cache the effect is weaker, but arrays still win on the thing that matters most there: no per-element overhead. An int16_t array of 100 readings costs exactly 200 bytes; a pointer-linked structure would add a pointer to every element.

Section 2.2

Insertion, deletion, reversal and rotation

Insert and delete by shifting

To insert at index idx, move the elements from idx to the end one slot right, then write the new value. memmove is the right tool because the source and destination ranges overlap (memcpy with overlapping ranges is undefined behavior).

#include <string.h>

// Returns 0 on success, -1 if full or idx out of range.
int insert_at(int a[], int *len, int cap, int idx, int val) {
    if (*len >= cap || idx < 0 || idx > *len) return -1;
    memmove(&a[idx + 1], &a[idx], (*len - idx) * sizeof a[0]);
    a[idx] = val;
    (*len)++;
    return 0;
}

int delete_at(int a[], int *len, int idx) {
    if (idx < 0 || idx >= *len) return -1;
    memmove(&a[idx], &a[idx + 1], (*len - idx - 1) * sizeof a[0]);
    (*len)--;
    return 0;
}

The number of elements moved by an insert at index idx is len − idx. Inserting at the front of a 1,000-element array moves all 1,000; inserting at the end moves none. Averaged over all positions that is about n/2 moves, so insertion is O(n). The bounds checks matter: C will happily write past the end of an array and corrupt whatever sits next to it.

Trace: insert 99 at index 2 of a six-element array 
capacity 10, len 6:   [5, 6, 7, 8, 9, 10, _, _, _, _]
shift a[2..5] right:  [5, 6, 7, 7, 8, 9, 10, _, _, _]     (len - idx = 6 - 2 = 4 elements moved)
write a[2] = 99:      [5, 6, 99, 7, 8, 9, 10, _, _, _]    len is now 7

One cheap trick: if the order of elements does not matter, delete in O(1) by overwriting the removed slot with the last element (a[idx] = a[len-1]; len--;). It is a common pattern in embedded code, for example when removing a finished task from an unordered task list.

Reverse in place

Swap the two ends and move inward. Each swap fixes two elements, so n/2 swaps in total: O(n) time, O(1) extra space (the in-place case from Chapter 1's space table).

void reverse(int a[], int lo, int hi) {      // reverses a[lo..hi] inclusive
    while (lo < hi) {
        int t = a[lo]; a[lo] = a[hi]; a[hi] = t;
        lo++; hi--;
    }
}
a[lo:hi+1] = a[lo:hi+1][::-1]       # Python: reverse a slice in place (the slice is copied internally)

Rotate with three reversals

Rotating left by k turns [1,2,3,4,5,6,7,8] with k = 3 into [4,5,6,7,8,1,2,3]. The obvious way uses a second array (O(n) extra space) or shifts everything one step, k times (O(n·k) time). There is a neat third way that is O(n) time and O(1) space: reverse the first k elements, reverse the rest, then reverse the whole array.

void rotate_left(int a[], int n, int k) {
    k %= n;                      // k = n means "rotate by a full turn": nothing to do
    if (k == 0) return;
    reverse(a, 0, k - 1);
    reverse(a, k, n - 1);
    reverse(a, 0, n - 1);
}
Trace: rotate [1..8] left by 3 
start:                    [1, 2, 3, 4, 5, 6, 7, 8]
reverse a[0..2]:          [3, 2, 1, 4, 5, 6, 7, 8]
reverse a[3..7]:          [3, 2, 1, 8, 7, 6, 5, 4]
reverse a[0..7]:          [4, 5, 6, 7, 8, 1, 2, 3]   ✓

swaps: 3/2 + 5/2 + 8/2 (integer division) = 1 + 2 + 4 = 7

Why it works: write the array as two blocks A B (here A = 1 2 3, B = 4 5 6 7 8). Reversing each block gives Aᴿ Bᴿ, and reversing that whole thing gives B A, the rotation. In general the total swaps are about n/2 in the last pass plus (k/2 + (n−k)/2) = n/2 in the first two, so roughly n swaps, linear in n regardless of k.

Section 2.3

Three techniques that solve most array problems

Many array problems have an obvious O(n²) solution with two nested loops. The three techniques below are the standard ways to bring them down to O(n). Learn to recognize the shape of the problem; the code is short once you do.

Technique 1: two pointers

Keep two indices and move them according to a rule, so that each element is visited a bounded number of times. Two common shapes:

Reader and writer (same direction). Remove duplicates from a sorted array in place. The writer w marks where the next kept element goes; the reader r scans ahead.

// Returns the new length. Requires a sorted array.
int dedup_sorted(int a[], int n) {
    if (n == 0) return 0;
    int w = 1;                              // a[0] is always kept
    for (int r = 1; r < n; r++) {
        if (a[r] != a[w - 1]) a[w++] = a[r];   // new value: keep it
    }
    return w;
}
Input  [1, 1, 2, 2, 2, 3, 5, 5]   →   first 4 slots become [1, 2, 3, 5], returns 4

Two ends moving inward. Given a sorted array, find two elements that add to a target. Start with the smallest and largest. If the sum is too small, only moving the left pointer right can increase it; if too large, only moving the right pointer left can decrease it. So every step discards one candidate for good.

int two_sum_sorted(const int a[], int n, int target, int *i, int *j) {
    int lo = 0, hi = n - 1;
    while (lo < hi) {
        int s = a[lo] + a[hi];
        if (s == target) { *i = lo; *j = hi; return 1; }
        if (s < target) lo++;
        else            hi--;
    }
    return 0;                               // no such pair
}
Trace: a = [1, 3, 4, 6, 8, 11], target = 10 
lo=0 hi=5:  1 + 11 = 12  > 10  → hi--
lo=0 hi=4:  1 +  8 =  9  < 10  → lo++
lo=1 hi=4:  3 +  8 = 11  > 10  → hi--
lo=1 hi=3:  3 +  6 =  9  < 10  → lo++
lo=2 hi=3:  4 +  6 = 10  = 10  → found (indices 2 and 3)     5 iterations

The two pointers together travel at most n−1 steps, so this is O(n) time and O(1) space, against O(n²) for checking every pair. The sorted order is what justifies discarding candidates; on an unsorted array this exact method is wrong.

Technique 2: prefix sums

Suppose you must answer many questions of the form "what is the sum of readings from index i to j?". Summing each time costs O(n) per query. Instead, spend O(n) once to build P, where P[k] is the sum of the first k elements (so P[0] = 0). Then any range sum is one subtraction:

sum of a[i..j] (inclusive) = P[j + 1] − P[i]

void build_prefix(const int a[], int n, long p[]) {   // p must have n + 1 slots
    p[0] = 0;
    for (int i = 0; i < n; i++) p[i + 1] = p[i] + a[i];
}
a = [12, 15, 11, 18, 20, 14, 9, 17]
P = [0, 12, 27, 38, 56, 76, 90, 99, 116]

sum of a[2..5] = P[6] − P[2] = 90 − 27 = 63        (check: 11 + 18 + 20 + 14 = 63)

Build once at O(n) cost, then each query is O(1). It uses O(n) extra space, which is the price. The extra leading zero (P[0] = 0) is what lets a range that starts at index 0 work without a special case.

Technique 3: the sliding window

When the question is about every block of k consecutive elements (the maximum sum of 3 consecutive readings, say), do not re-add each block from scratch. When the window slides one step right, one element enters and one leaves, so update the running sum with one addition and one subtraction.

// Largest sum of any k consecutive elements; *start receives where it begins.
long best_window(const int a[], int n, int k, int *start) {
    long sum = 0;
    for (int i = 0; i < k; i++) sum += a[i];          // first window
    long best = sum;  *start = 0;
    for (int i = k; i < n; i++) {
        sum += a[i] - a[i - k];                         // slide: add newest, drop oldest
        if (sum > best) { best = sum; *start = i - k + 1; }
    }
    return best;
}
a = [12, 15, 11, 18, 20, 14, 9, 17], k = 3
window sums: 38, 44, 49, 52, 43, 40      → best = 52, starting at index 3 (18 + 20 + 14)

The naive version re-reads k elements for each of the n−k+1 windows: (n−k+1)·k reads. The sliding version reads k elements once, then two per step: k + 2(n−k). For the eight readings above that is 18 against 13. For a sensor stream of n = 1,000,000 with k = 1,000 it is 999,001,000 reads against 1,999,000, about 500 times fewer. This is the same idea as a moving-average filter, which you will meet again in firmware.

Which technique when

Two pointers: sorted data, pairs, in-place compaction. Prefix sums: many range-sum queries over data that does not change. Sliding window: a statistic over every block of k consecutive items. The shared pattern: find the redundant work in the nested-loop version (re-adding numbers already added, re-checking pairs already ruled out) and carry that information forward instead of recomputing it.

Section 2.4

Strings: the hidden costs in C and in Python

A C string is a char array whose end is marked by a zero byte ('\0'), as C Chapter 5 covered. Python's str is a different object entirely: immutable, with its length stored. That difference decides which operations are cheap.

OperationC (null-terminated)Python (str)
Lengthstrlen: O(n), it walks to the terminatorlen(s): O(1), stored
Compare two stringsstrcmp: O(n), stops at first difference==: O(n) worst case, same idea
Append a characterO(1) if you know the end and have roomCreates a new string: O(n) in general
Index s[i]O(1)O(1)

Pitfall 1: strlen in a loop condition

// Looks O(n). May be O(n²).
for (size_t i = 0; i < strlen(s); i++) {
    if (s[i] == ',') count++;
}

The condition is evaluated before every iteration, and strlen(s) scans the whole string each time. For a string of length n the condition runs n + 1 times, and each call examines n + 1 bytes (n characters plus the terminator): (n+1)² bytes in total. For n = 100,000 that is 10,000,200,001 byte reads, about ten billion, to count commas in a 100 KB line. The fix is to compute the length once, or to test for the terminator directly:

size_t n = strlen(s);                    // once: O(n)
for (size_t i = 0; i < n; i++) { ... }

for (const char *p = s; *p != '\0'; p++) { ... }    // no length needed at all

An honest caveat: an optimizing compiler can sometimes hoist strlen out of the loop when it can prove the string is not modified inside it. You should not depend on that. It does not happen when the loop body writes through any pointer that might alias s, and it is not guaranteed at all at low optimization levels, which is where embedded debug builds often run.

Pitfall 2: repeated strcat

strcat(dest, src) must first find the end of dest, which means scanning it. Building a long string by calling it in a loop rescans the growing result each time.

char out[10001] = "";
for (int i = 0; i < 1000; i++) strcat(out, "0123456789");   // append 10 chars, 1000 times

Before append number i the result holds 10·i characters, so the scans cost 10·(0 + 1 + … + 999) = 10 · 999 · 1000 / 2 = 4,995,000 byte reads, on top of the 10,000 bytes actually copied (plus one terminator byte read per scan). That is the O(n²) pattern: n/10 appends, each costing O(current length). The fix is to remember where the end is and copy there:

char out[10001];
char *end = out;
for (int i = 0; i < 1000; i++) {
    size_t len = 10;
    memcpy(end, "0123456789", len);       // copy at the known end
    end += len;                          // advance it
}
*end = '\0';                             // terminate once

Total work is the 10,000 bytes copied: O(n). This is a classic case where the library function, not your loop, hides the extra pass.

Python: strings are immutable

Python strings cannot be modified, so s += "x" builds a new string. In a loop that appears to be O(n²) copying. CPython contains an optimization that sometimes resizes the string in place and hides the cost, but it is an implementation detail that does not apply on every interpreter (MicroPython, PyPy) or in every situation, so do not rely on it. The portable idiom collects pieces in a list and joins once:

parts = []
for i in range(1000):
    parts.append("0123456789")         # amortized O(1) per append (Chapter 1)
out = "".join(parts)                   # one pass: O(total length)

Naive substring search

To find a pattern of length m in a text of length n, try each starting position and compare character by character, stopping at the first mismatch:

// Returns the index of the first match, or -1.
int find(const char *text, int n, const char *pat, int m) {
    for (int s = 0; s + m <= n; s++) {          // each alignment
        int q = 0;
        while (q < m && text[s + q] == pat[q]) q++;
        if (q == m) return s;
    }
    return -1;
}

There are n − m + 1 alignments and each costs up to m comparisons, so the worst case is O((n−m+1)·m), roughly O(n·m). On typical text mismatches come early and the real cost is near n. The bad case is repetitive data: searching for "aaab" in twenty 'a' characters tries all 17 alignments, and each matches three characters before failing on the fourth, so 17 × 4 = 68 comparisons for a 20-character text. Smarter algorithms (Knuth–Morris–Pratt and others) guarantee linear time, but the naive method is what strstr implementations often use for short patterns, and it is perfectly good for the short strings firmware deals with. In practice you call the library: strstr in C, the in operator or str.find in Python.

Section 2.5

Two-dimensional arrays: row-major order

Memory is a single line of bytes, so a 2D array must be flattened. C stores it row-major: all of row 0, then all of row 1, and so on. For int a[ROWS][COLS], element a[i][j] is at:

address of a[i][j] = base + (i × COLS + j) × sizeof(int)
Fig 2.2 — Row-major layout: each row is a contiguous run; the next row begins right after.

If this array starts at address 0x1000, then a[2][1] is at 0x1000 + 36 = 0x1024. The 36 was confirmed by taking the pointer difference (char*)&a[2][1] − (char*)a in a test build.

Why traversal order matters

// Row by row: visits memory in address order
for (int i = 0; i < ROWS; i++)
    for (int j = 0; j < COLS; j++)
        total += a[i][j];

// Column by column: jumps COLS × sizeof(int) bytes each step
for (int j = 0; j < COLS; j++)
    for (int i = 0; i < ROWS; i++)
        total += a[i][j];

Both are O(ROWS × COLS), and both produce the same answer. But the first reads memory sequentially while the second leaps a whole row at a time. On a processor with a cache, the second pattern loses most of the benefit of each cache fetch, and on large arrays it can be several times slower; the exact ratio depends on the hardware, so measure rather than assume. The rule is simple: make the inner loop run over the last index. (NumPy arrays from Python Chapter 4 are also row-major by default, which is why summing along the last axis is the fast direction there too.)

Passing a 2D array to a function

When a 2D array decays to a pointer, the compiler needs every dimension except the first to compute i × COLS + j. The parameter must therefore be written int a[][COLS] or int (*a)[COLS], with COLS a known constant (or, in C99, an earlier parameter: void f(int rows, int cols, int a[rows][cols])). Writing int **a is a different type, an array of pointers, and passing a true 2D array to it compiles with a warning at best and crashes at worst.

Section 2.6

Fixed buffers and safe strings in firmware

Embedded code usually avoids malloc (C Chapter 7 and Section 1.5 of this topic explained why), so strings live in fixed-size arrays. The danger is then simple and severe: write past the end of the array and you overwrite a neighbor, which on a microcontroller can be another variable, a saved return address, or a hardware-related RAM region. There is no operating system to stop you and often no error message at all. Three habits prevent most of it.

Habit 1: know the capacity and pass it along

Any function that writes into a buffer takes the buffer's size as a parameter. A function that receives only a char * cannot know how much room there is.

Habit 2: prefer snprintf to strcpy and strncpy

strcpy copies until it meets a terminator in the source and never checks the destination size, so a long source overflows. strncpy looks like the safe version but has a trap: if the source is as long as or longer than the limit, it does not write a terminator. In a test with a 4-byte buffer and the 11-character source "temperature", strncpy(buf, "temperature", sizeof buf) left the buffer holding the four characters temp with no '\0', and the next printf("%s", buf) would run on into whatever follows. snprintf always terminates (for a non-zero size) and tells you whether it truncated:

char buf[4];
int needed = snprintf(buf, sizeof buf, "%s", "temperature");
// buf holds "tem" followed by '\0'.  needed == 11, the length it WOULD have written.
if (needed >= (int)sizeof buf) {
    /* truncated: handle it - log, reject, or use a bigger buffer */
}

The return value is the key: a result that is greater than or equal to the buffer size means the output was cut off. On AVR-based Arduino boards snprintf exists but pulls in noticeable code size and, in the default libc build, does not support %f for floating-point numbers. Check your toolchain. When you cannot afford it, write a small bounded copy routine yourself, with the same contract: always terminate, report truncation.

Habit 3: keep the length, do not recompute it

For a buffer you fill piece by piece (a log line, a UART message), track len as you go and check len + piece_length < capacity before each append. That is both the safe version and the O(n) version from Section 2.4: one habit prevents the overflow and the quadratic scan.

typedef struct { char data[32]; size_t len; } Line;     // capacity 32, always terminated

int line_append(Line *l, const char *s) {
    size_t n = strlen(s);
    if (l->len + n + 1 > sizeof l->data) return -1;     // +1 for the terminator
    memcpy(l->data + l->len, s, n + 1);                 // copies the terminator too
    l->len += n;
    return 0;
}

Be clear about what this is: a structural sketch showing the bounded-append pattern, not a complete string library. It assumes l->data starts as an empty terminated string (len = 0, data[0] = '\0') and it does not handle a NULL argument.

Where this leads: the ring buffer

A fixed array with a len works until the data never stops arriving, as with a UART receiver or a sensor sampled forever. Then you need an array that reuses its oldest slots. That is the ring buffer, built from exactly the index arithmetic in this chapter plus a wraparound, and it is the centerpiece of Chapter 4.

Section 2.7

Worked problem — a sensor log, three ways

Problem

A node stores eight temperature readings (in tenths of a degree) in an array: [12, 15, 11, 18, 20, 14, 9, 17]. (a) Build a prefix-sum array and use it to find the average of readings 2 through 5 (inclusive, zero-based). (b) Find the three-reading window with the largest sum, and compare the number of element reads with the naive approach. (c) A display needs the readings rotated left by 3 so the oldest shown reading is the 4th stored. Show the rotation using three reversals and count the swaps. (d) A different task needs "does any pair of these readings add to 29?". State the cost of the naive method, and give a faster method with its requirement.

(a) Prefix sums P = [0, 12, 27, 38, 56, 76, 90, 99, 116]
        sum of a[2..5] = P[6] − P[2] = 90 − 27 = 63
        count = 5 − 2 + 1 = 4 readings, average = 63 / 4 = 15.75 (i.e. 1.575 degrees)
        Check by hand: 11 + 18 + 20 + 14 = 63 ✓

(b) Window sums (k = 3), starting at index 0..5:
        12+15+11 = 38,  15+11+18 = 44,  11+18+20 = 49,
        18+20+14 = 52,  20+14+9 = 43,   14+9+17 = 40
        Largest: 52, starting at index 3 (readings 18, 20, 14).
        Naive element reads: (n − k + 1) × k = 6 × 3 = 18
        Sliding window reads: k + 2(n − k) = 3 + 2 × 5 = 13
        (The saving is small at n = 8 but grows with n: at n = 1,000,000
        and k = 1,000 it is 999,001,000 against 1,999,000 reads.)

(c) Rotate left by k = 3:
        readings:           [12, 15, 11, 18, 20, 14, 9, 17]
        reverse a[0..2]:    [11, 15, 12, 18, 20, 14, 9, 17]     1 swap
        reverse a[3..7]:    [11, 15, 12, 17, 9, 14, 20, 18]     2 swaps
        reverse a[0..7]:    [18, 20, 14, 9, 17, 12, 15, 11]     4 swaps
        Total swaps = 1 + 2 + 4 = 7. The array now begins with the
        old a[3], as required: [18, 20, 14, 9, 17, 12, 15, 11].

(d) Naive: check every pair, n(n − 1)/2 = 28 comparisons for n = 8, O(n²) in
        general. Faster: sort the array first (O(n log n), Chapter 6), then
        run the two-pointer scan (O(n)). Requirement: the array must be
        sorted, and the two-pointer scan then needs at most n − 1 steps.
        Total O(n log n) beats O(n²) once n is large. Here the sorted array
        is [9, 11, 12, 14, 15, 17, 18, 20]: pair 9 + 20 = 29 is found on the
        very first step.

What to take away: parts (a) and (b) are the same idea in two forms: carry forward the work you have already done instead of redoing it. Part (c) shows an O(1)-space operation built from a primitive you already have (reverse). Part (d) shows the usual shape of an optimization: spend time once on preparation (sorting) so each later question becomes cheap, a trade you should always weigh against how many questions you will actually ask.

Wrap-up

Recap

  1. An array stores equal-sized elements contiguously, so a[i] is at base + i × size and access is O(1). The price is that insertion and deletion at an arbitrary index must shift the elements after it: O(n), exactly len − idx elements moved for an insert.
  2. Reversal swaps from both ends (n/2 swaps, O(1) space), and rotation by k is three reversals (reverse the first k, reverse the rest, reverse everything): O(n) time and O(1) extra space, with no second array.
  3. Three techniques remove redundant work from nested-loop solutions: two pointers (sorted data, pairs, in-place compaction), prefix sums (O(n) build, then O(1) per range sum via P[j+1] − P[i]), and sliding windows (update a running statistic by adding the entering element and dropping the leaving one).
  4. C strings are null-terminated, so strlen is O(n). Calling it in a loop condition can make a loop O(n²) (about ten billion byte reads for a 100,000-character string), and repeated strcat rescans its growing result each time. Track the length or the end pointer instead. Python strings store their length and are immutable, so build large strings with "".join.
  5. Naive substring search is O((n−m+1)·m) in the worst case, which repetitive data triggers; it is fine for short strings, and library routines or smarter algorithms exist for the rest.
  6. C stores 2D arrays row-major, with a[i][j] at base + (i × COLS + j) × size. Keep the inner loop over the last index so memory is read in order, and declare 2D array parameters with every dimension but the first.
  7. In firmware, strings live in fixed buffers, so pass capacities, prefer snprintf (which terminates and reports truncation) over strcpy/strncpy (strncpy may leave no terminator), and keep a running length. These are the foundations the ring buffer in Chapter 4 builds on.
Check yourself

Quick check

Question 1

An array holds 6 elements with capacity 10. You insert a new value at index 2. How many existing elements are moved, and how many would be moved if you inserted at index 0 instead? What would the count be for a 1,000-element array when inserting at the front?

The number moved is len − idx. At index 2 with len 6 that is 6 − 2 = 4 elements (the ones at indices 2 through 5). At index 0 it is 6 − 0 = 6, all of them. For a 1,000-element array inserting at the front moves all 1,000. Inserting at the end moves none, which is why appending is O(1) while insertion in general is O(n).
Question 2

A loop for (i = 0; i < strlen(s); i++) runs over a string of length 50,000. Roughly how many bytes does strlen examine in total, and what are two ways to fix the loop?

The condition is evaluated 50,001 times (for i = 0 through 50,000), and each call scans the 50,000 characters plus the terminator, 50,001 bytes. Total (50,001)² = 2,500,100,001 byte reads, about 2.5 billion, for what should be a 50,000-step loop. Fixes: compute size_t n = strlen(s); once before the loop and compare against n, or loop with for (const char *p = s; *p; p++) so no length is needed. A compiler may sometimes hoist the call itself, but that is not something to rely on.
Question 3

For a = [4, 8, 15, 16, 23, 42], write the prefix-sum array and use it to find the sum of a[1..4]. What is the cost of each additional range query once the array is built?

P = [0, 4, 12, 27, 43, 66, 108]. The sum of a[1..4] is P[5] − P[1] = 66 − 4 = 62, and by hand 8 + 15 + 16 + 23 = 62 ✓. After the one-time O(n) build, each range query is a single subtraction: O(1). The price is O(n) extra memory for P, and the technique assumes the underlying data does not change between queries (if it does, P must be rebuilt or updated).
Question 4

An int a[4][5] array starts at address 2000, with 4-byte ints. At what address is a[1][2]? Why must a function that takes this array declare int a[][5] and not just int a[][]?

Address = 2000 + (1 × 5 + 2) × 4 = 2000 + 28 = 2028. To compute that formula the compiler must know the row width (5), because moving down one row means skipping 5 elements. Only the first dimension can be omitted, since it is not used in the address calculation (it only bounds how far you may go). int a[][] would leave the row width unknown, so the compiler could not turn a[i][j] into an address.
Question 5

You call strncpy(buf, "temperature", 4) on a 4-byte buffer. What is in buf afterward, why is that dangerous, and what does snprintf(buf, sizeof buf, "%s", "temperature") do differently?

strncpy copies exactly 4 characters, temp, and because the source is at least as long as the limit it writes no terminator. The buffer is therefore not a valid C string; any later strlen, printf("%s"), or strcpy from it reads past the end into adjacent memory. snprintf writes at most size − 1 characters and always adds the terminator for a non-zero size, so buf holds tem plus '\0'. It also returns 11, the length it would have written, so comparing the return value with the buffer size (11 ≥ 4) tells you the output was truncated.

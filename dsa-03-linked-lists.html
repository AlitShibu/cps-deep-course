Linked Lists

Chapter 2 ended on the array's weakness: opening a gap means shifting everything after it. A linked list makes the opposite trade. Each element lives in its own node and points to the next one, so inserting or removing at a known position is a pointer rewrite, but reaching the k-th element means walking k links. This chapter builds singly and doubly linked lists in C with every pointer step shown, solves the classic pointer problems (reversal, finding the middle, detecting a cycle), and then asks the honest question: when is a linked list actually the right tool? On a microcontroller the answer is more nuanced than the textbook suggests, and the chapter ends with the fixed-pool technique that gets the benefits without malloc.

Section 3.1

What a linked list is, and what it costs

A node holds one value and a pointer to the next node. The list itself is just a pointer to the first node, called the head; the last node's pointer is NULL, which marks the end.

typedef struct Node {
    int data;
    struct Node *next;      // the link: address of the next node, or NULL
} Node;
Fig 3.1 — A singly linked list: nodes can sit anywhere in memory; only the links give them an order.

The cost of each operation

OperationCostWhy
Access the k-th elementO(n)No address arithmetic: start at head and follow k links
Search by valueO(n)Walk the list, same as an unsorted array
Insert or delete at the headO(1)Rewrite one or two pointers; nothing moves
Insert after a node you already holdO(1)Same: two pointer writes
Append at the tailO(n) without a tail pointer, O(1) with oneOtherwise you must walk to the last node first
Delete a node (singly linked) given only that nodeO(n)You need the previous node, and nothing points backward

Compare with Chapter 2's table: the array is O(1) at access and O(n) at insertion, and the list is the mirror image. Neither is better in general; each pays where the other is cheap. The important detail is the last row. Inserting is cheap when you already hold the position. Finding that position still costs a walk.

"Linked lists have O(1) insertion" is only half a sentence

Inserting at a node you already have a pointer to is O(1). Inserting "at index 500" is O(n), because you must walk 500 links to get there. An array inserting at index 500 pays O(n) in shifting; the list pays O(n) in walking. Insertion at the head or at a remembered position is where lists win, and a program that mostly works at one end (a queue, a stack) is the natural fit.

Memory overhead

Each node stores a pointer in addition to the value. On the 64-bit machine used to test this chapter, sizeof(Node) is 16 bytes for a 4-byte int: 4 bytes of data, 4 bytes of alignment padding so the pointer sits on an 8-byte boundary, and 8 bytes of pointer. A 1,000-element list therefore takes 16,000 bytes against 4,000 for an array of the same ints, and that is before the allocator's own bookkeeping, which typically adds more per malloc call (the exact amount depends on the C library). On a 16-bit AVR, where an int and a pointer are both 2 bytes, a node is roughly twice the size of its value, so the overhead ratio is smaller there, but the absolute RAM budget is far tighter. Section 3.5 returns to this.

The same idea in Python

class Node:
    def __init__(self, data, next=None):
        self.data = data
        self.next = next

head = Node(4, Node(9, Node(13, Node(21))))      # 4 -> 9 -> 13 -> 21

This works, but note that a Python list is not a linked list; it is a growable array of references (Chapter 1's amortized append). You build linked structures by hand in Python to learn the idea or for specific needs; day to day, list and collections.deque are the tools. deque gives O(1) appends and pops at both ends, which is the use case people usually want a linked list for.

Section 3.2

The core operations in C, pointer by pointer

The list below keeps a head, a tail and a length. The tail pointer is what makes appending O(1); the cost is that every operation that might remove or add the last node must keep it correct, which is where most linked-list bugs live.

#include <stdlib.h>

typedef struct { Node *head; Node *tail; size_t len; } List;   // List l = {0}; is an empty list

int push_front(List *l, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return -1;                  // always check: malloc can fail
    n->data = v;
    n->next = l->head;                  // 1. new node points at the old first node
    l->head = n;                        // 2. head now points at the new node
    if (!l->tail) l->tail = n;          // first node of an empty list is also the last
    l->len++;
    return 0;
}

int push_back(List *l, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return -1;
    n->data = v;
    n->next = NULL;
    if (l->tail) l->tail->next = n;     // old last node points at the new one
    else           l->head = n;         // empty list: the new node is the head
    l->tail = n;
    l->len++;
    return 0;
}

int insert_after(List *l, Node *pos, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return -1;
    n->data = v;
    n->next = pos->next;                // 1. new node takes over pos's old successor
    pos->next = n;                      // 2. pos now points at the new node
    if (l->tail == pos) l->tail = n;
    l->len++;
    return 0;
}
Fig 3.2 — Inserting after a node: two pointer writes, no element moves.
Do the two writes in the right order

If you did step ② first (pos->next = n), the only pointer to the rest of the list (13 → 21 → …) would be overwritten, and the new node's next would have nothing correct to copy. The remaining nodes become unreachable: a memory leak and lost data in one line. Rule of thumb: connect the new node to the rest first, then splice it in. The same ordering matters in push_front.

Search and delete

Node *find(const List *l, int v) {
    for (Node *p = l->head; p; p = p->next)
        if (p->data == v) return p;
    return NULL;
}

Deleting by value must reach the node before the victim to rewrite its link, and the head is a special case because nothing precedes it. The usual way to avoid that special case is to walk with a pointer to a pointer: pp holds the address of whichever pointer currently points at the node being examined (first &l->head, then the next field of each node in turn). Rewriting *pp then works identically for the head and for a middle node.

int delete_value(List *l, int v) {                 // returns 1 if something was deleted
    Node **pp = &l->head;
    Node *prev = NULL;                             // tracked only to repair tail
    while (*pp && (*pp)->data != v) {
        prev = *pp;
        pp = &(*pp)->next;
    }
    if (!*pp) return 0;                            // not found
    Node *dead = *pp;
    *pp = dead->next;                              // unlink: previous pointer skips the victim
    if (l->tail == dead) l->tail = prev;          // deleted the last node: tail steps back
    free(dead);
    l->len--;
    return 1;
}

void free_list(List *l) {
    Node *p = l->head;
    while (p) {
        Node *nx = p->next;                        // save the link BEFORE freeing the node
        free(p);
        p = nx;
    }
    l->head = l->tail = NULL;
    l->len = 0;
}

Two details deserve attention. In delete_value, when the victim is the tail, the new tail is the previous node, which is why prev is tracked. This also shows why deleting the last node of a singly linked list is O(n) even with a tail pointer: the tail pointer tells you where the last node is, but not which node precedes it, so you walk from the head to find out. In free_list, reading p->next after free(p) is a use-after-free (C Chapter 7), so the link is saved first.

Trace: building and editing a list (each line is the list after the call) 
push_back 4, 9, 13, 21, 30        4 → 9 → 13 → 21 → 30        len 5
push_front(1)                      1 → 4 → 9 → 13 → 21 → 30    len 6
delete_value(13)                   1 → 4 → 9 → 21 → 30         len 5
delete_value(30)  (the tail)       1 → 4 → 9 → 21              len 4, tail now 21

This code was compiled and run under AddressSanitizer and UndefinedBehaviorSanitizer with no errors and no leaks. Two honesty notes. First, it is a clear teaching implementation, not a hardened library: for example, insert_after assumes pos really belongs to this list. Second, on a microcontroller you would think hard before calling malloc for every node, as Section 3.5 explains.

Section 3.3

Three classic pointer problems

These appear in interviews and in real code for the same reason: they exercise exactly the skill of tracking several pointers at once. Each is O(n) time and O(1) extra space, with no copying of data.

Reverse a list in place

Walk the list once and flip each link to point backward. You need three pointers: the node being processed (cur), the one behind it (prev), and the one ahead, saved before you overwrite the link (nx).

void reverse_list(List *l) {
    Node *prev = NULL, *cur = l->head;
    l->tail = l->head;                  // the old first node becomes the last
    while (cur) {
        Node *nx = cur->next;           // 1. remember the rest BEFORE breaking the link
        cur->next = prev;               // 2. flip this link backward
        prev = cur;                     // 3. advance both pointers
        cur = nx;
    }
    l->head = prev;                     // prev ends on the old last node: the new head
}
Trace: reverse 1 → 4 → 9 → 21 → 30 
start:         prev=NULL  cur=1       1 → 4 → 9 → 21 → 30
after node 1:  prev=1     cur=4       1 → ∅        (4 → 9 → 21 → 30 still intact via nx)
after node 4:  prev=4     cur=9       4 → 1 → ∅
after node 9:  prev=9     cur=21      9 → 4 → 1 → ∅
after node 21: prev=21    cur=30      21 → 9 → 4 → 1 → ∅
after node 30: prev=30    cur=NULL    30 → 21 → 9 → 4 → 1 → ∅
head = prev = 30.   5 loop iterations for 5 nodes: O(n) time, O(1) space.

Notice that no node is allocated or freed and no value is copied; only links change. Compare with reversing an array (Chapter 2), which swaps n/2 pairs of values. The step nx = cur->next is the one that beginners forget, and it is fatal: without it the rest of the list is lost the moment the link is flipped.

Find the middle: slow and fast pointers

You cannot jump to index n/2 (no random access), and you may not know n. The trick: advance one pointer by one node per step and another by two. When the fast one reaches the end, the slow one is at the middle.

Node *middle(Node *head) {
    Node *slow = head, *fast = head;
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
    }
    return slow;
}

For the 5-node list 30 → 21 → 9 → 4 → 1 the loop runs twice (slow lands on 21, then on 9; fast lands on 9, then on 1, whose next is NULL), so the result is the node holding 9, the exact middle. For an even count the function returns the second of the two middle nodes: on 10 → 20 → 30 → 40 → 50 → 60 it returns 40. It makes one pass (about n/2 loop iterations) instead of the two passes (count, then walk) you would otherwise need.

Detect a cycle: Floyd's tortoise and hare

If a list's last node points back into the list (a bug, or a deliberately circular structure), a plain traversal never ends. The same slow/fast pair detects this with O(1) memory: if there is a cycle, the fast pointer eventually laps the slow one and they meet; if there is none, fast reaches NULL.

int has_cycle(Node *head) {
    Node *slow = head, *fast = head;
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) return 1;      // compare ADDRESSES, not data
    }
    return 0;
}
Trace: nodes 1 → 2 → … → 7, with node 7's next pointing back to node 3 
step 1:  slow=2  fast=3
step 2:  slow=3  fast=5
step 3:  slow=4  fast=7
step 4:  slow=5  fast=4      (7 → 3 → 4: fast went around the loop)
step 5:  slow=6  fast=6      same node: cycle detected after 5 steps

The comparison must be between pointers (slow == fast); comparing data would trigger on any two nodes holding equal values. The alternative, remembering every visited node, needs O(n) memory, which is exactly what a microcontroller cannot spare.

Section 3.4

Doubly linked lists, circular lists and sentinel nodes

Doubly linked lists

The weakness of the singly linked list is that it cannot go backward, so removing a node needs its predecessor. A doubly linked list adds a prev pointer to every node, so a node can unlink itself in O(1) with no search:

typedef struct DNode {
    int data;
    struct DNode *prev, *next;
} DNode;

The costs: one more pointer per node (24 bytes per node on the test machine against 16, for an int payload) and more pointer writes per operation, so more chances for error. The benefit is O(1) removal given the node, and traversal in both directions.

Sentinel nodes remove the special cases

Almost every bug in the code of Section 3.2 comes from edge cases: empty list, head, tail. A sentinel (dummy) node removes them. Make the list circular with one permanent node that holds no data and whose next and prev point to itself when the list is empty. Now every real node has a real neighbor on both sides, always, and the same two functions handle every case:

void d_init(DNode *s)                  { s->prev = s->next = s; }      // empty list

void d_insert_after(DNode *pos, DNode *n) {
    n->prev = pos;
    n->next = pos->next;
    pos->next->prev = n;
    pos->next = n;
}

void d_remove(DNode *n) {
    n->prev->next = n->next;
    n->next->prev = n->prev;
}

// Walk the whole list:  for (DNode *p = s.next; p != &s; p = p->next) { ... }

Inserting at the front is d_insert_after(&s, n), inserting at the back is d_insert_after(s.prev, n), and removal never checks for head or tail. In a test with a sentinel and nodes 10, 20, 30, removing the node holding 20 left the traversal printing exactly 10 30. This is the layout the Linux kernel uses for its intrusive lists, which is why you will see this circular, sentinel-based design in real systems code. The caller owns the nodes here (they can live in static memory), so there is no malloc at all.

Why you will meet circular lists again

A circular structure is a natural fit for anything that repeats: a round-robin scheduler cycling through tasks, a playlist that loops. In Chapter 4 you will see the array-based version of the same idea, the ring buffer, which gives the wraparound behavior with none of the pointer overhead.

Section 3.5

Lists versus arrays, and the fixed node pool

Here is the honest comparison. Big-O alone would suggest lists for insertion-heavy work. Reality is more mixed.

FactorArrayLinked list
Access by indexO(1)O(n)
Insert/delete at a known positionO(n) shiftingO(1) pointer writes
Memory per elementJust the valueValue + one or two pointers (+ allocator overhead if malloc'd)
Memory layoutContiguous: cache-friendlyScattered: each step may be a cache miss
GrowthFixed capacity, or copy on resizeOne node at a time, no copying
Failure modeOverflow past capacitymalloc failure, fragmentation, dangling pointers

The cache row matters more than it looks. Following a pointer to a node allocated somewhere else usually costs far more than reading the next array slot, so for moderate n a plain array with shifting often beats a linked list even where the list wins on paper. This is the "memory access pattern" effect from Chapter 1. Lists earn their place when elements are large (shifting is expensive and a pointer is cheap by comparison), when you hold pointers to elements that must stay valid as others are inserted and removed (array elements move on insertion, nodes do not), or when you constantly insert and remove at known positions.

The embedded problem with malloc

Chapter 1 noted that embedded code often pre-allocates instead of growing. For linked lists the sharper issue is that malloc and free on a small heap cause fragmentation: after many allocations and frees of different sizes, free memory can be split into small pieces so that a request fails even though the total free bytes would suffice. Their timing is also not deterministic, which is awkward in real-time code, and on a device with a couple of kilobytes the allocator's per-block bookkeeping is a visible tax. Many embedded coding standards forbid dynamic allocation after startup for exactly these reasons.

The fix: a fixed node pool

Keep the linked-list idea, drop malloc. Declare an array of nodes at compile time, and instead of pointers use array indices as links. Unused nodes are chained into their own list, the free list; allocating means taking the first free node, and freeing means pushing it back. Both are O(1) and neither can fragment, because every node is the same size.

#include <stdint.h>

#define POOL_N 4
#define NIL    255                       // "no node": an index that can never be valid

typedef struct { int16_t value; uint8_t next; } PNode;

static PNode   pool[POOL_N];
static uint8_t free_head;

void pool_init(void) {
    for (uint8_t i = 0; i < POOL_N; i++)
        pool[i].next = (i + 1 < POOL_N) ? i + 1 : NIL;   // chain: 0→1→2→3→NIL
    free_head = 0;
}

uint8_t pool_alloc(void) {               // returns NIL if the pool is exhausted
    uint8_t i = free_head;
    if (i != NIL) free_head = pool[i].next;
    return i;
}

void pool_free(uint8_t i) {              // push node i back onto the free list
    pool[i].next = free_head;
    free_head = i;
}

In a test with POOL_N = 4, five calls to pool_alloc returned 0, 1, 2, 3 and then NIL: a clean, checkable failure instead of a crash or a silent heap corruption. After pool_free(1), the next allocation returned 1 again. The pool occupies 16 bytes here (each PNode is 4 bytes after padding on the test machine: a 2-byte value, a 1-byte index and one padding byte), and its size is known at compile time, which is what a linker map or a memory budget wants to see. Using a one-byte index for next instead of a pointer also saves RAM on small chips (1 byte against 2 on AVR, 4 or 8 elsewhere). The price is a hard capacity: when the pool is empty, the caller must handle failure.

This is a structural sketch of the technique, not a drop-in library: it is not safe to call from both main code and an interrupt handler without protecting the shared free_head (Microcontrollers Chapter 4, race conditions), and it does not guard against freeing the same index twice.

The practical rule

On a PC, use arrays (or dynamic arrays) by default and reach for a linked list when its specific strengths apply. On a microcontroller, if you need a list at all, size it for the worst case, put the nodes in a static pool, and treat "pool empty" as a normal condition your code handles. When the data is simply "the last N readings", skip lists entirely: Chapter 4's ring buffer is simpler and smaller still.

Worked problem — editing, reversing and sizing a list

Problem

What to take away: parts (a) to (d) are the mechanical skill: track the pointers, keep the order of the writes, and let the trace tell you the result. Part (e) is the judgment: a linked list's advantages are real but specific, its memory costs are real too, and on a microcontroller the right form of it is usually a bounded one.

Wrap-up

Recap

  1. A linked list is a chain of nodes, each holding a value and a pointer to the next; the list is a pointer to the first node and the last next is NULL. It mirrors the array: no random access (the k-th element costs k link hops, O(n)), but insertion and deletion at a position you already hold are a couple of pointer writes, O(1).
  2. Appending is O(n) unless you keep a tail pointer, and keeping the tail correct (on push, insert-after and delete) is where bugs concentrate. Deleting the last node of a singly linked list is O(n) even with a tail pointer, because you need its predecessor.
  3. Pointer order matters: connect the new node to the rest first, then splice it in; save cur->next before overwriting it; read p->next before free(p). The pointer-to-pointer walk (Node **pp) removes the special case for deleting the head.
  4. Three O(n)-time, O(1)-space classics: in-place reversal (three pointers: prev, cur, nx), the middle via slow and fast pointers (returns the second middle for even lengths), and cycle detection via the same pair, comparing addresses (in the traced example they meet after 5 steps).
  5. A doubly linked list adds a prev pointer so a node can be removed in O(1) given only that node, at the cost of an extra pointer per node. A circular list with a sentinel node eliminates empty/head/tail special cases, and the same two functions handle every position.
  6. Compared with arrays, lists cost more memory per element (16 bytes against 4 for an int on the 64-bit test machine, before allocator overhead) and are less cache-friendly, so they win in specific situations, not by default.
  7. On microcontrollers, malloc/free bring fragmentation, non-deterministic timing and bookkeeping overhead. A fixed node pool with index links and a free list gives O(1) allocation with no fragmentation and a known size, at the cost of a hard capacity that the code must handle.
Check yourself

Quick check

Question 1

In the list 1 → 4 → 9 → 21 → 30, how many link hops does it take to reach the node at index 3 starting from the head, and why can this not be made O(1) the way a[3] is in an array?

Three hops: the head node 1 is index 0, then following next three times reaches 4 (index 1), 9 (index 2) and 21 (index 3). In general the k-th node costs k hops, O(n) in the worst case. An array can jump because its elements are contiguous and equal-sized, so the address is base + i × size. List nodes are allocated separately and can sit anywhere, so the only way to learn where node k is, is to follow the chain of links from a node you already know.
Question 2

Your list has 1,000 nodes and no tail pointer. How many link hops does push_back need to find the last node, and how does that change with a tail pointer? What extra work must every delete do once you maintain a tail pointer?

Without a tail pointer you start at the head and follow links until a node's next is NULL: 999 hops for 1,000 nodes (O(n)). With a tail pointer you go straight to tail->next, so appending is O(1). The extra work on delete: if the node being removed is the tail, the tail pointer must be moved back to the previous node (or set to NULL if the list becomes empty), otherwise it dangles and the next append writes into freed memory. In a singly linked list, finding that previous node is itself an O(n) walk.
Question 3

Trace reverse_list on 7 → 8 → 9, giving the values of prev and cur after each iteration. What goes wrong if the line Node *nx = cur->next; is removed and cur = cur->next is used instead after the link is flipped?

Start: prev = NULL, cur = 7. After node 7: prev = 7, cur = 8 (list so far 7 → ∅). After node 8: prev = 8, cur = 9 (8 → 7 → ∅). After node 9: prev = 9, cur = NULL (9 → 8 → 7 → ∅). The loop ends and head = prev = 9, giving 9 → 8 → 7. If you use cur->next after executing cur->next = prev, you are reading the link you just overwrote: on the first iteration cur would become prev (NULL), the loop would end immediately, and nodes 8 and 9 would be lost (leaked) with the list reduced to just 7. That is why the next pointer must be saved before the link is flipped.
Question 4

For the cyclic list in Section 3.3 (nodes 1 to 7, with node 7 pointing back to node 3), the tortoise and hare meet after 5 steps at node 6. Why is the comparison written slow == fast on the pointers and not on the data fields, and why is this method better than remembering every node you have visited?

Comparing data would report a "cycle" whenever two different nodes happen to hold the same value, which is common (a list of sensor readings may repeat values). Only pointer equality means "the very same node." Remembering visited nodes would need up to n stored addresses, O(n) memory, and a search through them at each step unless you add a hash table (Chapter 7). Floyd's method uses just two pointers: O(1) extra space and O(n) time. If there is no cycle the fast pointer reaches NULL and the loop simply ends.
Question 5

On a 64-bit machine, sizeof(Node) is 16 for a node with an int and a next pointer. Where do the 16 bytes come from, and what would you use instead of malloc on a small microcontroller?

4 bytes for the int, 4 bytes of padding (the 8-byte pointer must start on an 8-byte boundary), and 8 bytes for the pointer: 4 + 4 + 8 = 16. A 1,000-node list is therefore 16,000 bytes against 4,000 for an int array, before the allocator's own per-block overhead. On a small microcontroller, use a statically allocated node pool: an array of nodes at compile time, array indices as links, and a free list for allocation and release. That keeps allocation O(1) and fragmentation-free, makes the RAM cost known at build time, and turns "out of nodes" into an explicit return value (NIL) instead of a heap failure. The cost is a fixed maximum size.

Stacks & Queues

Stacks and queues are not new storage, they are rules about access: a stack only touches the most recently added item, a queue only touches the oldest. Those restrictions are what make both O(1) for every operation, and what make them match real problems so well: matching brackets, evaluating expressions, undoing actions, buffering a UART stream, handing samples from an interrupt to the main loop. This chapter builds both in C on top of Chapters 2 and 3, then spends most of its time on the ring buffer, the single most useful data structure in embedded firmware. It ends with the honest limits of the interrupt-safe version: what the sketch shows, and what you must still check on your own hardware.

Section 4.1

The stack: last in, first out

A stack is a collection where you can only add (push), remove (pop) and look at (peek) the item on top. Think of a stack of plates: you never pull one from the middle. The last item pushed is the first one popped, hence LIFO (last in, first out).

Fig 4.1 — An array-based stack is an array plus one integer, top.

An array-based stack in C

The simplest implementation is the one from Chapter 2's pattern of a fixed array plus a counter. Here top holds the number of items, which is also the index of the next free slot.

#define STACK_CAP 8

typedef struct {
    int data[STACK_CAP];
    int top;                                   // number of items in the stack
} Stack;                                       // Stack s = {0}; is an empty stack

int stack_push(Stack *s, int v) {
    if (s->top == STACK_CAP) return -1;        // overflow: refuse, don't write past the array
    s->data[s->top++] = v;
    return 0;
}

int stack_pop(Stack *s, int *out) {
    if (s->top == 0) return -1;                // underflow: nothing to pop
    *out = s->data[--s->top];
    return 0;
}

int stack_peek(const Stack *s, int *out) {
    if (s->top == 0) return -1;
    *out = s->data[s->top - 1];
    return 0;
}

Two design choices are worth noticing. The functions return a status and pass the value through a pointer, because every int is a legitimate stack value, so there is no spare "error" value to return directly. And both failure cases are checked rather than assumed away: pushing onto a full stack and popping an empty one are the two classic stack bugs (overflow and underflow), and in C an unchecked version silently corrupts memory instead of raising an error.

Trace: push 1, 2, 3 · pop · push 4 · pop · pop · pop · pop 
push 1, 2, 3        stack (bottom→top): [1, 2, 3]    top = 3
pop      → 3        [1, 2]
push 4              [1, 2, 4]
pop      → 4        [1, 2]
pop      → 2        [1]
pop      → 1        []
pop      → fails (returns −1): the stack is empty

Notice the order that came out: 3, 4, 2, 1. Not the order in which items arrived; the most recent one is always served first.

The same thing in Python

stack = []
stack.append(1); stack.append(2); stack.append(3)     # push: amortized O(1)
top = stack.pop()                                    # pop:  O(1); raises IndexError if empty
peek = stack[-1]                                     # peek: O(1)

A Python list already is a growable array (Chapter 2), so it makes a fine stack as long as you only use append and pop() at the end. A stack can also be built on a linked list (Chapter 3) by pushing and popping at the head, which gives O(1) with no capacity limit, at the cost of a node allocation per push.

You already use a stack: the call stack

Every function call pushes a frame (return address, parameters, locals) and every return pops it. That is why recursion "costs O(depth) stack space" (Chapter 1, Section 1.5) and why a runaway recursion is called a stack overflow. On a microcontroller this stack is a region of RAM of fixed size, typically growing toward the heap or other data; run past its end and you silently overwrite variables. Chapter 5 returns to this when it turns recursion into explicit stacks.

Section 4.2

What stacks are good for: matching and evaluating

A stack is the right tool whenever the most recently opened thing must be the first one closed. Two classic problems show the pattern.

Balanced brackets

Is {[()]} well formed? Is ([)]? Scan left to right: push every opening bracket; on a closing bracket, the top of the stack must be its matching opener, which you pop. At the end the stack must be empty.

// Returns 1 if balanced, 0 if not, -1 if nesting is deeper than the buffer allows.
int balanced(const char *str) {
    char st[32];
    int top = 0;
    for (const char *p = str; *p; p++) {
        char c = *p;
        if (c == '(' || c == '[' || c == '{') {
            if (top == (int)sizeof st) return -1;
            st[top++] = c;
        } else if (c == ')' || c == ']' || c == '}') {
            if (top == 0) return 0;                       // closer with nothing open
            char o = st[--top];
            if ((c == ')' && o != '(') || (c == ']' && o != '[') || (c == '}' && o != '{'))
                return 0;                                 // wrong kind of opener
        }
    }
    return top == 0;                                      // anything left open is unbalanced
}

Run on a set of test strings, it returned: {[()]} → balanced; ([)] → not balanced (when the ) arrives, the top of the stack is [, not (); ((a+b)*c → not balanced (one ( is still on the stack at the end); a+b) → not balanced (a closer with an empty stack); the empty string → balanced. It is O(n) time, with O(depth) space; a counter alone would not be enough, because with several bracket kinds you must remember which opener is outstanding, and in what order.

Evaluating postfix (RPN) expressions

In postfix notation the operator comes after its operands: 3 4 + means 3 + 4. There are no parentheses and no precedence rules, and evaluating is a stack exercise: push numbers; on an operator, pop two operands (the second one popped is the left operand), apply the operator, push the result.

// Space-separated tokens, non-negative integer operands, + - * /.  Returns 0 on success.
int eval_rpn(const char *expr, long *result) {
    long st[16];
    int top = 0;
    const char *p = expr;
    while (*p) {
        if (*p == ' ') { p++; continue; }
        if (*p >= '0' && *p <= '9') {
            char *end;
            long v = strtol(p, &end, 10);
            if (top == 16) return -1;                    // stack full
            st[top++] = v;
            p = end;
        } else {
            if (top < 2) return -1;                      // operator needs two operands
            long b = st[--top];                          // right operand comes off first
            long a = st[--top];
            long r;
            switch (*p) {
                case '+': r = a + b; break;
                case '-': r = a - b; break;
                case '*': r = a * b; break;
                case '/': if (b == 0) return -1; r = a / b; break;
                default:  return -1;                     // unknown operator
            }
            st[top++] = r;
            p++;
        }
    }
    if (top != 1) return -1;                             // leftover operands: malformed
    *result = st[0];
    return 0;
}
Trace: 5 1 2 + 4 * + 3 - (this is (5 + ((1 + 2) × 4)) − 3 in ordinary notation) 
token   action                  stack (bottom→top)
5       push                    [5]
1       push                    [5, 1]
2       push                    [5, 1, 2]
+       pop 2, 1 → 1+2 = 3      [5, 3]
4       push                    [5, 3, 4]
*       pop 4, 3 → 3×4 = 12     [5, 12]
+       pop 12, 5 → 5+12 = 17   [17]
3       push                    [17, 3]
-       pop 3, 17 → 17−3 = 14   [14]       result: 14

In testing, 3 4 + 2 * 7 - gave 7 and the sample above gave 14, while 4 0 / (division by zero), 1 + (too few operands) and 2 3 (two values left over) were each rejected. This is a sketch of the technique: it handles only non-negative integer literals and does not detect overflow in long arithmetic. The same stack discipline is how calculators and compilers evaluate expressions; converting ordinary infix notation to postfix uses a second stack (the shunting-yard algorithm), which is worth looking up once you are comfortable with this one.

The pattern to recognize

Whenever a problem says "the most recent unfinished thing must be dealt with first" (nested brackets, nested function calls, undo history, backtracking through a maze, depth-first search in Chapter 9), reach for a stack.

Section 4.3

The queue: first in, first out

A queue serves items in the order they arrived, like people at a counter: enqueue adds at the back, dequeue removes from the front. That is FIFO (first in, first out). It is the natural structure for anything where fairness or arrival order matters: tasks waiting for a processor, characters arriving on a serial line, messages between two parts of a program.

The difficulty is implementation, because a queue touches both ends of its storage. Let us look at the two obvious approaches and what is wrong with each.

Attempt 1: a plain array, shifting on dequeue

Enqueue at the end of an array, and on dequeue remove element 0 and shift everything left. This is correct and wasteful: every dequeue moves n − 1 elements, O(n). Draining a 1,000-element queue this way costs 999 + 998 + … + 0 = 499,500 element moves, the same quadratic pattern as Chapter 2's insertion at the front. (Python's list.pop(0) does exactly this, which is why collections.deque and its popleft(), O(1), is the right queue in Python.)

Attempt 2: a linked list with head and tail pointers

Chapter 3 gave the cure: enqueue at the tail (O(1) because you keep a tail pointer) and dequeue at the head (O(1)). Both ends are cheap, because you never need to walk or to find a predecessor.

typedef struct QNode { int data; struct QNode *next; } QNode;
typedef struct { QNode *head, *tail; } LQueue;           // LQueue q = {0}; is empty

int lq_enqueue(LQueue *q, int v) {
    QNode *n = malloc(sizeof *n);
    if (!n) return -1;
    n->data = v; n->next = NULL;
    if (q->tail) q->tail->next = n; else q->head = n;
    q->tail = n;
    return 0;
}

int lq_dequeue(LQueue *q, int *out) {
    QNode *n = q->head;
    if (!n) return -1;                                   // empty
    *out = n->data;
    q->head = n->next;
    if (!q->head) q->tail = NULL;                      // queue became empty: reset tail too
    free(n);
    return 0;
}

Enqueuing 1, 2, 3 and dequeuing three times returned 1, 2, 3, and a fourth dequeue failed cleanly with the tail pointer reset to NULL; forgetting that reset is the classic bug (the next enqueue then writes through a freed node). This works and has no capacity limit, but it carries all the costs Chapter 3 listed for embedded use: a malloc and free per item, a pointer of overhead per element, and fragmentation risk. For an unbounded general-purpose queue on a PC it is a fine answer. For firmware there is a better one.

Attempt 3: a circular array, the ring buffer

Keep the array, but instead of shifting, move two indices: head (where the next item will be read from) and tail (where the next item will be written). When an index reaches the end of the array it wraps back to 0. Nothing ever moves, dequeue and enqueue are both O(1), memory is a fixed block, and there is no allocation. The next section builds it carefully.

Section 4.4

The ring buffer in depth

A ring buffer (also called a circular buffer or circular queue) is a fixed array treated as if its last slot were followed by its first. Writing advances tail; reading advances head; both wrap around using modular arithmetic: index = (index + 1) % N.

#define RB_N 4

typedef struct {
    int    buf[RB_N];
    size_t head;          // index of the next item to read (the oldest)
    size_t tail;          // index of the next free slot to write
    size_t count;         // number of items currently stored
} RingBuf;                // RingBuf r = {0}; is empty

int rb_push(RingBuf *r, int v) {
    if (r->count == RB_N) return -1;               // full: reject the new item
    r->buf[r->tail] = v;
    r->tail = (r->tail + 1) % RB_N;                // advance and wrap
    r->count++;
    return 0;
}

int rb_pop(RingBuf *r, int *out) {
    if (r->count == 0) return -1;                  // empty
    *out = r->buf[r->head];
    r->head = (r->head + 1) % RB_N;
    r->count--;
    return 0;
}
Fig 4.2 — The state after pushing 10, 20, 30, popping, then pushing 40 and 50: head and tail are equal even though the buffer is full.
Trace: capacity 4 (this is the output of the code above) 
operation          buf             head tail count
push 10, 20, 30    [10, 20, 30, _]   0    3     3
pop → 10           [10, 20, 30, _]   1    3     2      (10 is still in memory, but no longer "in" the queue)
push 40            [10, 20, 30, 40]  1    0     3      tail wrapped from 3 to 0
push 50            [50, 20, 30, 40]  1    1     4      overwrote the stale 10; buffer is full
push 60            rejected (returns −1): full
pop → 20           [50, 20, 30, 40]  2    1     3

The order out is exactly the order in (10, 20, then 30, 40, 50 would follow), and no element was ever moved. That is the whole point.

The full-versus-empty ambiguity

Look at the trace row after push 50: head = 1 and tail = 1, and the buffer is full. In an empty buffer head == tail as well. With only the two indices, a full and an empty ring look identical. There are two standard remedies:

RemedyHowTrade-off
Keep a count (as above)Full when count == N, empty when count == 0Uses all N slots, but count is shared state written by both the reader and the writer, which complicates the interrupt-safe version (Section 4.5)
Always leave one slot emptyEmpty when head == tail, full when (tail + 1) % N == headHolds only N − 1 items, but each index is written by exactly one side, which is what makes the lock-free version possible

Modulo versus a bit mask

The wrap (i + 1) % N needs a division on processors that lack a hardware divide instruction (many small ones, including classic AVR, do their division in software, which is slow). If N is a power of two, (i + 1) & (N - 1) gives the same result with a single AND, because N − 1 is all ones in binary (for N = 8, the mask is 0b111). This was checked for every index from 0 to 63 with N = 8. Compilers will often make this substitution themselves for an unsigned index and a constant power-of-two N, so write whichever is clearer and use a power-of-two size on purpose.

The mask only works for powers of two

With N = 6 the "mask" would be 5 = 0b101, and (5 + 1) & 5 is 4, not 0, so the index lands on the wrong slot and skips slot 5 forever. Modulo gives (5 + 1) % 6 = 0, correct. If the buffer size is not a power of two, use % (or a compare-and-reset: if (++i == N) i = 0;).

When the buffer fills: reject or overwrite?

Full is a normal condition for a ring buffer and the code must choose a policy. Reject (as rb_push does) keeps the oldest data and drops the newest: right for a command or message queue where order and completeness matter. Overwrite keeps the newest data and drops the oldest: right for "the last N readings", where stale data is worthless. Overwrite just advances head to discard the oldest before writing:

void rb_push_overwrite(RingBuf *r, int v) {
    if (r->count == RB_N) {                        // full: discard the oldest
        r->head = (r->head + 1) % RB_N;
        r->count--;
    }
    r->buf[r->tail] = v;
    r->tail = (r->tail + 1) % RB_N;
    r->count++;
}

Pushing 1 through 6 into a 4-slot buffer this way leaves the items 3, 4, 5, 6, read out oldest first. In Python, collections.deque(maxlen=4) behaves exactly like this: appending past the limit silently discards from the other end, and after appending 1 to 6 it holds [3, 4, 5, 6].

Section 4.5

The ring buffer between an interrupt and the main loop

Here is the problem the ring buffer was made for. A UART receives bytes at its own pace, and the hardware raises an interrupt for each one (Serial Protocols Chapter 2). The interrupt service routine (ISR) must be quick, so it just drops the byte into a buffer. The main loop picks bytes up whenever it gets to them. If the main loop is busy for a few milliseconds, the buffer absorbs the burst; if it is busy for too long, the buffer overflows and bytes are lost. This is exactly how serial-port receive buffers in Arduino-style cores work: a small power-of-two ring buffer filled by the receive interrupt and drained by Serial.read() (commonly 64 bytes on AVR boards and 16 on those with very little RAM; check your core's source for your board).

The structure here is single-producer, single-consumer (SPSC): exactly one writer (the ISR) and exactly one reader (the main loop). That restriction allows a very simple design, in which each index is modified by only one side: the producer owns tail, the consumer owns head, and each only reads the other's index. This is the "leave one slot empty" variant, with no shared count.

#include <stdint.h>

#define N 16                                   // power of two, so the mask works
static uint8_t          buf[N];
static volatile uint8_t head;                  // written only by the consumer (main loop)
static volatile uint8_t tail;                  // written only by the producer (ISR)

// Called from the ISR. Returns -1 if full (the byte is dropped).
int rx_put(uint8_t b) {
    uint8_t next = (tail + 1) & (N - 1);
    if (next == head) return -1;               // full: one slot is always left empty
    buf[tail] = b;                             // write the data FIRST...
    tail = next;                               // ...then publish it by moving tail
    return 0;
}

// Called from the main loop. Returns -1 if empty.
int rx_get(uint8_t *b) {
    if (head == tail) return -1;               // empty
    *b = buf[head];                            // read the data FIRST...
    head = (head + 1) & (N - 1);               // ...then release the slot by moving head
    return 0;
}

The order inside each function is the key idea: the producer writes the data before it moves tail, so the consumer can never see an updated tail that points at a slot whose data has not been written yet; the consumer finishes reading before it moves head, so the producer cannot reuse a slot that is still being read. In single-threaded testing with N = 16, 20 attempted rx_put calls accepted 15 bytes (capacity N − 1) and rejected 5, 15 were read back, and 40 put/get pairs through the wrap point all returned the right byte.

What the sketch does NOT guarantee: read this before using it

The logic above was tested only in a single thread. Whether it is safe between an ISR and a main loop on your chip depends on things the code cannot show:

  • Index width and atomicity. On an 8-bit AVR a 16-bit variable is read and written in two instructions, and an interrupt can land between them. This sketch uses uint8_t indices (so capacity is limited to 256) precisely so each index access is one instruction. With larger buffers, disable interrupts around the access or use a type your platform guarantees is atomic.
  • volatile is not synchronization. It stops the compiler from caching an index in a register, but it does not order accesses to the non-volatile buf relative to the indices. Strictly, a compiler may reorder them, so portable code adds a compiler barrier or makes the buffer accesses volatile too.
  • Multiple cores. On a dual-core chip such as the ESP32, the producer and consumer may run on different cores with caches and write buffers, and volatile is not enough. Use C11 atomics with acquire/release ordering, or the RTOS's own queue or ring-buffer primitives, which exist for this purpose.
  • More than one producer or consumer. The "each index has one owner" argument fails as soon as two ISRs or two tasks write the same index. Then you need a lock or a different design.

Those caveats are the honest limit of this section: it teaches why the structure works and what its invariant is; it is not a drop-in driver. When you reach the Real-Time Operating Systems topic, you will meet queues that package this pattern with the synchronization done properly.

Section 4.6

Deques, and choosing a structure

A deque (double-ended queue, pronounced "deck") allows push and pop at both ends. A ring buffer supports this directly: pushing at the front means decrementing head (with wraparound) and writing there, and popping at the back means decrementing tail. Every operation stays O(1). Stacks and queues are both special cases of it, and Python's collections.deque is one. A fourth relative, the priority queue, serves items by importance rather than arrival order; it needs a different structure (the heap, Chapter 8).

One more use: the moving average

Chapter 2's sliding window computed a statistic over fixed-size blocks of a stored array. On a live sensor stream the data is not stored; you keep only the most recent W readings, and that is a ring buffer with overwrite. Keep a running sum: when the buffer is full, subtract the reading about to be overwritten, then add the new one. Each update is O(1) no matter how large W is.

#define W 4
typedef struct { int buf[W]; size_t idx, count; long sum; } MovAvg;     // MovAvg m = {0};

double ma_update(MovAvg *m, int x) {
    if (m->count == W) m->sum -= m->buf[m->idx];    // full: drop the oldest reading's contribution
    else                m->count++;
    m->buf[m->idx] = x;                              // overwrite the oldest slot
    m->sum += x;
    m->idx = (m->idx + 1) % W;
    return (double)m->sum / m->count;                // average of what is stored so far
}

Here a single index serves as both head and tail, because the buffer is always read in full and the oldest slot is exactly the next one to write. The cost is O(1) time per sample and O(W) memory, whether W is 4 or 4,000. (Because sum is a long of exact integers, there is no drift; a floating-point running sum can accumulate rounding error, a point Linear Algebra Chapter 8 explained.)

What to take away: parts (a) and (b) are the stack discipline: push on open or operand, pop on close or operator, and check the end state. Part (c) is the ring buffer used as a window onto a stream. Part (d) is the decision the data structure forces on you: what should happen when it is full, and what does shifting versus wrapping cost?

Wrap-up

Recap

  1. A stack is LIFO: push, pop and peek all touch only the top, so all are O(1). An array plus a top counter implements it (full when top == CAP, empty when top == 0); always check for overflow and underflow, because in C an unchecked version silently corrupts memory. The call stack is a stack of frames, which is why recursion costs O(depth) memory.
  2. Stacks suit problems where the most recent unfinished item is handled first. Balanced brackets push openers and match closers (a counter is not enough with several bracket kinds); postfix evaluation pushes operands and pops two for each operator, with the second pop as the left operand (5 1 2 + 4 * + 3 - evaluates to 14).
  3. A queue is FIFO. A plain array that shifts on every dequeue costs O(n) per dequeue (499,500 moves to drain 1,000 items); a linked list with head and tail pointers is O(1) but needs allocation per item; a ring buffer gives O(1) with a fixed block and no allocation.
  4. A ring buffer keeps head (next read) and tail (next write) and wraps with (i + 1) % N. Equal indices mean either full or empty, so you must either keep a count (all N slots usable) or always leave one slot empty (N − 1 usable, each index written by one side only).
  5. For power-of-two N, i & (N − 1) replaces the modulo with a single AND; for other N it is wrong (with N = 6, (5 + 1) & 5 gives 4, not 0). Choose a full-buffer policy deliberately: reject keeps the oldest data (commands), overwrite keeps the newest (recent readings).
  6. The single-producer single-consumer ring buffer lets an ISR hand bytes to the main loop: the producer owns tail, the consumer owns head, and each writes the data before moving its index. The sketch is not production-safe by itself: it depends on atomic index access, compiler ordering, a single producer and consumer, and on multi-core chips needs atomics or RTOS primitives.
  7. A deque allows O(1) push and pop at both ends (a ring buffer with two-way indices); a moving average over the last W readings is an overwrite ring buffer plus a running sum, O(1) per sample regardless of W. Priority queues need the heap of Chapter 8.
Check yourself

Quick check

Question 1

Starting from an empty stack, perform: push 1, push 2, push 3, pop, push 4, pop, pop. What values are returned by the three pops, and what does the stack contain at the end?

The pops return 3, then 4, then 2. After push 1, 2, 3 the stack is [1, 2, 3]; the first pop returns 3 leaving [1, 2]; push 4 gives [1, 2, 4]; the next pop returns 4 leaving [1, 2]; the last pop returns 2 leaving [1]. The final stack holds just 1. The most recently pushed item is always returned first, which is why the output order (3, 4, 2) differs from the arrival order (1, 2, 3, 4).
Question 2

Evaluate the postfix expression 5 1 2 + 4 * + 3 -, listing the stack after each token. Why is the order of the two popped operands important for - and /?

Stacks after each token: 5 → [5]; 1 → [5, 1]; 2 → [5, 1, 2]; + → [5, 3]; 4 → [5, 3, 4]; * → [5, 12]; + → [17]; 3 → [17, 3]; - → [14]. The result is 14. For a non-commutative operator the first value popped is the right operand and the second popped is the left one: at the final - the pops give 3 then 17, and the result must be 17 − 3 = 14, not 3 − 17 = −14. Getting the order backward silently produces wrong answers for subtraction and division.
Question 3

A ring buffer of capacity 8 uses a count. Currently head = 6 and count = 3. Which slots hold the data, where will the next item be written, and what is tail after that write?

The three items occupy slots 6, 7 and 0 (the data wraps around the end of the array). The next write goes to tail = (head + count) % 8 = (6 + 3) % 8 = 1, so slot 1. After writing there, tail advances to 2 and count becomes 4. The oldest item (the next one read) is still at slot 6, because only a read moves head.
Question 4

Why can head == tail mean either "empty" or "full" in a ring buffer, and what are the two standard ways to tell them apart? Which one suits an ISR-to-main-loop buffer, and why?

Both indices wrap around the same array, so after enough writes the tail has caught up with the head: the same pair of values arises when nothing is stored (head and tail start equal) and when every slot is occupied (tail wrapped all the way round to head). The two fixes are (1) a separate count, giving full when count == N and empty when count == 0, with all N slots usable; and (2) always leaving one slot empty, giving empty when head == tail and full when (tail + 1) % N == head, with only N − 1 usable. The second suits an ISR and a main loop because each index is then written by exactly one side (the ISR owns tail, the main loop owns head), so no shared variable needs to be updated atomically by both; a shared count would be modified by both contexts and would need protection.
Question 5

For N = 8, show that (i + 1) & 7 wraps correctly at i = 7. Then show why the same trick fails for a buffer of N = 6 using the mask 5.

For N = 8 the mask 7 is 0b0111. At i = 7, i + 1 = 8 = 0b1000, and 0b1000 & 0b0111 = 0, which is the correct wrap back to slot 0; for every other i from 0 to 6, i + 1 is below 8 and the mask leaves it unchanged. For N = 6 the "mask" N − 1 = 5 = 0b101 has a zero bit, so the AND clears bits of valid indices: at i = 5, i + 1 = 6 = 0b110 and 0b110 & 0b101 = 0b100 = 4, but the correct wrapped index is 0 (6 % 6). Slot 5 would never be used again and the buffer would behave wrongly. Masking works only when N is a power of two, because only then is N − 1 a run of all ones.

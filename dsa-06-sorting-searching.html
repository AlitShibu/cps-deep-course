Sorting & Searching

Sorting is the most studied problem in computing, and for a good reason: a sorted array turns an O(n) search into an O(log n) one, makes duplicates and medians trivial to find, and lets you merge data sets in a single pass. This chapter builds the main sorting algorithms from scratch (insertion, selection, merge, quicksort), counts their comparisons on real inputs rather than just quoting formulas, and explains the vocabulary that decides which to use: stability, in-place, adaptive, and worst case versus average case. It then turns to searching, including the lookup-table-with-interpolation technique that converts raw ADC readings into temperatures, and ends with how to choose a sort when you have a few hundred bytes of RAM and a deadline.

Section 6.1

What sorting is, and the vocabulary for comparing sorts

To sort is to rearrange a collection into non-decreasing order. Most algorithms in this chapter are comparison sorts: the only thing they learn about the data is the result of asking "is a[i] less than a[j]?". That restriction matters, because it gives a hard limit on how fast any of them can be.

A lower bound: no comparison sort beats n log n

Sorting n distinct items means finding which of the n! possible orderings the input is in. Each comparison has two outcomes, so k comparisons can distinguish at most 2k orderings. To tell all n! orderings apart you need 2k ≥ n!, so k ≥ log₂(n!). Concretely, log₂(8!) = log₂(40,320) ≈ 15.3, so sorting 8 items needs at least 16 comparisons in the worst case, whatever the algorithm; for 10 items, log₂(3,628,800) ≈ 21.8, so at least 22. For large n, log₂(n!) grows like n log₂ n, which is why O(n log n) is the best a comparison sort can do. (Sorts that are faster, like counting sort in Section 6.5, work by not using comparisons, and pay for it with restrictions on the data.)

The properties that distinguish sorts

PropertyMeaningWhy you care
Time: best / average / worstCost on the luckiest, typical and unluckiest input of size nA real-time deadline depends on the worst case (Chapter 1)

No algorithm wins on all four, which is why this chapter teaches several. In the code below, every sort orders an int array ascending and the comparison counts quoted in the text were measured by instrumenting these exact routines.

Section 6.2

The simple sorts: selection and insertion

Selection sort

Repeatedly find the smallest remaining element and swap it into the next position. After pass i, the first i + 1 positions hold their final values.

void selection_sort(int a[], int n) {
    for (int i = 0; i < n - 1; i++) {
        int m = i;                              // index of the smallest seen so far
        for (int j = i + 1; j < n; j++)
            if (a[j] < a[m]) m = j;
        if (m != i) { int t = a[i]; a[i] = a[m]; a[m] = t; }
    }
}

The inner loop always scans everything that remains, so the number of comparisons is (n−1) + (n−2) + … + 1 = n(n−1)/2 regardless of the input: 28 for n = 8, whether the array is sorted or reversed, and 499,500 for n = 1,000. It is not adaptive. Its one virtue is that it makes at most n − 1 swaps: sorting 8 reversed items took just 4 swaps. That matters only when writing is far more expensive than reading, as with some flash memory. Selection sort is also not stable: on the records (2,a), (2,b), (1,c), the first swap moves (1,c) to the front by exchanging it with (2,a), leaving (1,c), (2,b), (2,a) with the two 2s in reversed order.

Insertion sort

Treat the left part of the array as already sorted. Take the next element (the key), shift larger sorted elements one place right to open a gap, and drop the key into it. It is how most people sort a hand of playing cards.

void insertion_sort(int a[], int n) {
    for (int i = 1; i < n; i++) {
        int key = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > key) {      // shift bigger elements right
            a[j + 1] = a[j];
            j--;
        }
        a[j + 1] = key;                       // drop the key into the gap
    }
}

The work depends on the input. On an already sorted array each key is compared once and nothing shifts: n − 1 = 7 comparisons for n = 8, which is O(n). On a reversed array every key travels all the way to the front: 28 comparisons and 28 shifts for n = 8, O(n²). Over all 40,320 orderings of 8 items the comparison count ranged from 7 to 28, and on a random array of 1,000 numbers it took 245,781 comparisons, close to n²/4 = 250,000. So insertion sort is adaptive (its cost tracks how disordered the input is), stable (it only shifts elements strictly greater than the key, so equal items never pass each other: on the same three records it kept (2,a) before (2,b)), and in place. That combination is why it is the right choice for small arrays and nearly sorted data, and why fast production sorts switch to it for small pieces.

Bubble sort (repeatedly swap adjacent out-of-order pairs) is also O(n²) and is mentioned only so you recognize it: it makes more writes than insertion sort for the same result and has no advantage worth its place in firmware.

Section 6.3

Merge sort: divide and conquer with a guarantee

Chapter 5's recurrence T(n) = 2T(n/2) + O(n) is merge sort. Split the array in half, sort each half recursively, then merge the two sorted halves into one sorted whole. Merging is the heart of it: with two sorted runs, repeatedly take the smaller of the two front elements. Each element is moved once, so a merge of n elements costs O(n) and at most n − 1 comparisons.

#include <string.h>

// Merge the sorted runs a[lo..mid) and a[mid..hi) using tmp as scratch space.
static void merge(int a[], int tmp[], int lo, int mid, int hi) {
    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi)
        tmp[k++] = (a[j] < a[i]) ? a[j++] : a[i++];   // take LEFT on ties: this is what makes it stable
    while (i < mid) tmp[k++] = a[i++];                // one run is empty; copy the rest of the other
    while (j < hi)  tmp[k++] = a[j++];
    memcpy(&a[lo], &tmp[lo], (size_t)(hi - lo) * sizeof a[0]);
}

static void msort(int a[], int tmp[], int lo, int hi) {
    if (hi - lo < 2) return;                 // base case: 0 or 1 element is already sorted
    int mid = lo + (hi - lo) / 2;
    msort(a, tmp, lo, mid);
    msort(a, tmp, mid, hi);
    merge(a, tmp, lo, mid, hi);
}

// The caller supplies the scratch array: no malloc inside the sort.
void merge_sort(int a[], int tmp[], int n) { msort(a, tmp, 0, n); }

Two design decisions are deliberate. The scratch buffer is passed in by the caller, so the function itself never calls malloc and the extra memory is visible and countable (n integers). And on a tie the left element is taken first, which keeps equal items in their original order.

Fig 6.1 — Merge sort on 8 numbers: three levels (log₂ 8), each doing at most n − (number of merges) comparisons.

Cost

The recursion tree of Chapter 5 applies directly: log₂ n levels, with at most n comparisons of merging work at each, so O(n log n) in every case, best, average and worst. On 8 items the measured comparison count over all 40,320 orderings ranged from 12 (already sorted) to 17 (the worst case, the example in Fig 6.1 happens to hit it), against the theoretical minimum of 16 from Section 6.1: merge sort is within one comparison of optimal at n = 8. On a random array of 1,000 numbers it used 8,702 comparisons, below the n log₂ n ≈ 9,966 estimate (which is an upper-bound shape, not an exact count). The recursion depth is only log₂ n, so its stack use is small (Chapter 5).

The price is memory: the scratch array makes it O(n) extra space, not in place. On a 2 KB microcontroller, sorting 500 sixteen-bit readings with merge sort needs another 1,000 bytes. That is exactly the situation where the next algorithm, or insertion sort, is preferred. Merge sort is stable, needs no random access beyond sequential passes (which is why it dominates for sorting linked lists and external data on disk or flash), and has a guaranteed worst case, which is its selling point for real-time work if you can spare the buffer.

Section 6.4

Quicksort: fast on average, dangerous in the worst case

Quicksort also divides and conquers, but does its work before the recursive calls instead of after. Pick a pivot, rearrange the array so everything smaller than the pivot is to its left and everything else to its right (partition), put the pivot in its final position, then sort the two sides recursively. There is nothing to combine at the end.

// Lomuto partition: pivot is the last element a[hi]. Returns the pivot's final index.
static int partition(int a[], int lo, int hi) {
    int pivot = a[hi];
    int i = lo;                                   // a[lo..i-1] holds elements < pivot
    for (int j = lo; j < hi; j++) {
        if (a[j] < pivot) {
            int t = a[i]; a[i] = a[j]; a[j] = t;  // move the small element into the "small" zone
            i++;
        }
    }
    int t = a[i]; a[i] = a[hi]; a[hi] = t;        // place the pivot between the zones
    return i;
}

Partitioning n elements takes n − 1 comparisons.
void quicksort(int a[], int lo, int hi) {
    while (lo < hi) {
        int p = partition(a, lo, hi);
        if (p - lo < hi - p) {              // left side is smaller:
            quicksort(a, lo, p - 1);        //   recurse on it...
            lo = p + 1;                     //   ...and loop on the larger right side
        } else {
            quicksort(a, p + 1, hi);
            hi = p - 1;
        }
    }
}

The cost, and the worst case

If every pivot lands near the middle, the recursion is T(n) = 2T(n/2) + O(n): O(n log n). On a random array of 1,000 numbers it used 10,471 comparisons, comparable to merge sort's 8,702, in place and without a scratch buffer. That is why quicksort is the standard general-purpose sort. But the pivot is a gamble. If it is always the smallest or largest element, one side is empty and the other holds n − 1 elements: T(n) = T(n − 1) + O(n), which is O(n²). With the last element as pivot, that happens on already sorted input, the very case Section 6.2 said sensors often produce. Measured: sorting 1,000 already-sorted numbers took 499,500 comparisons, the same as selection sort, and over all 8-item orderings the comparison count ranged from 13 to 28.

The stack-depth trap, and the fix in the code above

A worst-case split also makes the recursion n levels deep. The simple form (recurse into both sides) reached a depth of 999 on that sorted input. On a microcontroller that is a stack overflow waiting to happen (Chapter 5, Section 5.7). The version given above recurses into the smaller side and loops on the larger side. Each recursive call then handles at most half the elements, so the depth is at most log₂ n no matter how bad the pivots are. On the same sorted input of 1,000 numbers the depth stayed at 1, and on the random input it reached 6 (the bound is ⌊log₂ 1000⌋ = 9). The time is still O(n²) on a bad input, but the stack stays small. This fixes the memory risk, not the time risk.

Ways to make bad pivots unlikely: choose the median of the first, middle and last elements (which handles sorted and reverse-sorted input well), or pick a random pivot (which makes a deliberately hostile input practically impossible). Production implementations go further: some quicksort variants such as introsort switch to heap sort (Chapter 8) when the recursion gets too deep, giving a guaranteed O(n log n). Quicksort is not stable (partitioning swaps distant elements).

Section 6.5

Library sorts, a comparator bug, and sorting without comparing

Use the library, but write the comparator carefully

In practice you usually call qsort from C's standard library (the ordering algorithm is up to the implementation) or sorted() in Python, which uses Timsort, a stable merge/insertion hybrid that is very fast on partly sorted data. qsort asks you for a comparison function that returns a negative, zero or positive number. The tempting way to write it has a classic bug:

int cmp_bad(const void *pa, const void *pb) {
    return *(const int *)pa - *(const int *)pb;       // BUG: the subtraction can overflow
}

int cmp_good(const void *pa, const void *pb) {
    int a = *(const int *)pa, b = *(const int *)pb;
    return (a > b) - (a < b);                          // -1, 0 or +1, never overflows
}

qsort(arr, n, sizeof arr[0], cmp_good);

With a = 2,000,000,000 and b = −2,000,000,000 the true difference is 4,000,000,000, which exceeds the largest 32-bit int. When wrapped into 32 bits the result is −294,967,296, which would claim that a is less than b. (Signed overflow is formally undefined behavior in C; the wrapped value shown is what a typical two's-complement machine produces.) The comparison form (a > b) - (a < b) is the safe habit. In Python, sorted(data, key=...) avoids comparators entirely, and because the sort is stable, sorting by two fields means sorting by the secondary key first, then by the primary key: on [(2,'a'), (2,'b'), (1,'c')] sorting by the number gives [(1,'c'), (2,'a'), (2,'b')], keeping a before b.

Counting sort: beating n log n by not comparing

The n log n bound only applies to comparison sorts. If the values are small integers in a known range 0..K−1 (ADC readings, byte values, grades), you can count how many times each value occurs, then write the values out in order:

void counting_sort(int a[], int n, int K, int count[]) {    // count[] has K entries
    for (int k = 0; k < K; k++) count[k] = 0;
    for (int i = 0; i < n; i++) count[a[i]]++;             // histogram: one pass
    int w = 0;
    for (int k = 0; k < K; k++)                            // write each value count[k] times
        for (int c = 0; c < count[k]; c++) a[w++] = k;
}

On [3, 1, 3, 0, 2, 1, 3] with K = 4 it produced [0, 1, 1, 2, 3, 3, 3]. The time is O(n + K), linear if K is not much bigger than n. The catch is memory and range: the count array needs K entries, so sorting 10-bit ADC values (K = 1,024) needs 1,024 counters, 2 KB with 16-bit counters, which is no bargain for sorting 20 samples. It is a histogram, so it applies to plain integers, not to records carrying other data; the record-preserving, stable variant needs an extra pass and an output array.

Section 6.6

Searching sorted data: lower bound and table interpolation

Chapter 1 gave you binary search for finding a value. In real code you often want a more general question answered: where would this value go? The answer is the lower bound: the index of the first element that is greater than or equal to the target (or n if there is none). It works whether or not the target is present, and with duplicates it finds the first one.

int lower_bound(const int a[], int n, int target) {
    int lo = 0, hi = n;                      // search the half-open range [lo, hi)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1;   // everything up to mid is too small
        else                  hi = mid;      // a[mid] could be the answer: keep it
    }
    return lo;
}

On [2, 5, 5, 5, 8, 12, 16] it returned 1 for the target 5 (the first 5), 4 for the target 6 (where it would be inserted to keep order), 0 for 1, and 7 (past the end) for 99. This is the same O(log n) loop as Chapter 1, with the loop invariant "the answer lies in [lo, hi]" made explicit. Getting the boundary updates right (mid + 1 versus mid) is the usual source of off-by-one errors, and stating the invariant is how you avoid them.

Embedded use: ADC to temperature with a calibration table

Many sensors are not linear. A common firmware technique is to store a short table of calibration points (raw reading, true value) and compute any reading in between by linear interpolation between the two neighboring points. Finding the neighboring points is a binary search over the sorted raw-reading column. The table below is illustrative (not data from a real sensor), with temperature in tenths of a degree so everything stays in integer arithmetic.

static const int adc_pts[6] = {   0, 205, 410, 614, 819, 1023};   // sorted raw readings
static const int temp10[6]  = {-100,  50, 180, 300, 420,  600};   // tenths of a degree C

int adc_to_temp10(int adc) {
    const int n = 6;
    if (adc <= adc_pts[0])     return temp10[0];        // clamp below the table
    if (adc >= adc_pts[n - 1]) return temp10[n - 1];    // clamp above the table
    int lo = 0, hi = n - 1;                              // invariant: adc_pts[lo] <= adc < adc_pts[hi]
    while (hi - lo > 1) {
        int mid = lo + (hi - lo) / 2;
        if (adc_pts[mid] <= adc) lo = mid; else hi = mid;
    }
    long dx = adc_pts[lo + 1] - adc_pts[lo];
    long dy = temp10[lo + 1]  - temp10[lo];
    return temp10[lo] + (int)((long)(adc - adc_pts[lo]) * dy / dx);
}

With six points the binary search only saves a couple of steps over a linear scan, and a linear scan would be just as good here. The binary search earns its place when the table has dozens or hundreds of entries (a thermistor lookup table, a gamma-correction curve), because the cost then stays at ⌈log₂ n⌉ comparisons plus one multiplication and one division. Two details matter in the code: the multiplication is done in long so (adc − adc_pts[lo]) × dy cannot overflow a 16-bit int, and the clamping handles readings outside the calibrated range explicitly rather than extrapolating wildly. The truncation in integer division is a small systematic error (here up to one tenth of a degree) that you can accept or remove by rounding.

Section 6.7

Choosing a sort on a microcontroller, and a real use: the median filter

The decision for firmware comes down to four questions, in order:

  1. How big is n? For n up to a few dozen, insertion sort is usually the right answer: tiny code, no extra memory, no recursion, stable, and fast on nearly sorted data. Chapter 1's rule applies: do not pay in complexity for scalability you will never use.
  2. Do you need a guaranteed time? Merge sort (if you can spare an n-element buffer) or heap sort (Chapter 8, in place) give O(n log n) in the worst case. Quicksort's O(n²) worst case is unacceptable under a hard deadline unless pivots are controlled.
  3. Is memory the binding constraint? Insertion sort and heap sort need O(1) extra; quicksort with the smaller-side-first loop needs O(log n) stack; merge sort needs O(n).
  4. Do you need to sort at all? Often not. A running maximum needs no sort; the median of a small window needs only a partial one; keeping an array sorted as items arrive (insertion into a sorted buffer) costs O(n) per item instead of re-sorting from scratch.

The median filter: sorting five numbers to reject a spike

A moving average (Chapter 4) is badly thrown off by a single spurious reading: one glitch drags the mean up. The median of a small window ignores such outliers. For a window of 5, copy the five most recent readings, sort the copy, and take the middle element:

int median5(const int in[5]) {
    int w[5];
    memcpy(w, in, sizeof w);          // sort a COPY: the original stays in arrival order
    insertion_sort(w, 5);             // n = 5: insertion sort is the right tool
    return w[2];                      // the middle of five
}

For the readings 20, 21, 95, 22, 21, where 95 is an electrical glitch, the sorted copy is 20, 21, 21, 22, 95 and the median is 21, while the mean is 35.8, far from any real reading. At n = 5 the insertion sort needs at most 10 comparisons, so this runs comfortably inside a control loop. Feed it from the ring buffer of Chapter 4 (which keeps the last five readings in arrival order) and you have a complete, allocation-free spike filter. For larger windows, insertion sort's O(w²) starts to hurt and there are cleverer structures, but for windows of 3 to 9 it is hard to beat.

Part (e) is the judgment: for small n the best algorithm is the simplest one whose worst case you can bound, and the algorithm with the best asymptotics is not automatically the right one.

Wrap-up

Recap

  1. Comparison sorts must distinguish n! orderings, so they need at least log₂(n!) comparisons: 16 for 8 items, 22 for 10, and about n log₂ n for large n. Sorts are compared by best/average/worst time, extra space (in place or not), stability (equal items keep their order) and adaptivity (faster on nearly sorted input).
  2. Selection sort makes n(n−1)/2 comparisons on any input (28 for n = 8) but at most n − 1 swaps, and is not stable. Insertion sort is adaptive (7 comparisons on sorted input of 8, 28 on reversed), stable and in place, and is the right choice for small or nearly sorted arrays.
  3. Merge sort splits, sorts each half, and merges: O(n log n) in every case, stable, with O(log n) recursion depth, but it needs an O(n) scratch buffer (pass it in rather than calling malloc). For n = 8 its comparison count ranged from 12 to 17 across all orderings; for 1,000 random numbers it used 8,702.
  4. Quicksort partitions around a pivot and recurses on both sides: O(n log n) on average (10,471 comparisons for 1,000 random numbers), in place, not stable, but O(n²) when pivots are bad (499,500 comparisons on 1,000 already-sorted numbers with a last-element pivot). Recursing on the smaller side and looping on the larger bounds the stack depth to log₂ n (depth 1 on that sorted input, against 999 for the plain version), though not the time. Median-of-three or random pivots make bad cases unlikely.
  5. Use library sorts when you can, and write comparators with (a > b) - (a < b) rather than subtraction, which overflows (2,000,000,000 − (−2,000,000,000) wraps to −294,967,296 in 32 bits). Counting sort beats n log n for small-range integers in O(n + K) time and O(K) memory by not comparing at all; Python's sorted is stable, so sort by the secondary key first.
  6. The lower bound is the index of the first element ≥ the target and works for absent and duplicate values; state the invariant (the answer lies in [lo, hi]) to get the boundaries right. A sorted calibration table plus binary search plus linear interpolation converts a raw ADC reading to a value in integer arithmetic (adc 500 → 23.2 °C in the illustrative table), using long for the product and clamping at the ends.
  7. On a microcontroller choose by n first (insertion sort for a few dozen items), then by whether you need a worst-case guarantee, then by memory. A median of a small sorted window rejects glitches that wreck a mean (median 21 against mean 35.8 for 20, 21, 95, 22, 21), and often you do not need a full sort at all.
Check yourself

Quick check

Question 1

Why can no comparison-based sort use fewer than log₂(n!) comparisons in the worst case? What does that give for n = 8?

A sort must identify which of the n! possible orderings the input is in. Each comparison has two outcomes, so after k comparisons the algorithm can have distinguished at most 2k cases. To cover all orderings, 2k ≥ n!, so k ≥ log₂(n!). For n = 8, 8! = 40,320 and log₂ 40,320 ≈ 15.3, so at least 16 comparisons are needed in the worst case (and merge sort needed at most 17 on 8 items). The argument only covers sorts that learn about the data by comparing; counting sort avoids the bound by indexing into an array instead.
Question 2

Trace insertion sort on [3, 1, 4, 2]. How many comparisons does it make, and how many on [1, 2, 3, 4]? Which property of insertion sort does the difference illustrate?

On [3, 1, 4, 2]: inserting 1 takes 1 comparison (it shifts 3 and reaches the front); inserting 4 takes 1 (3 ≤ 4, stop); inserting 2 takes 3 (shifts 4, shifts 3, then 1 ≤ 2 stops). Total 5 comparisons. On the already sorted [1, 2, 3, 4] each key stops after one comparison: n − 1 = 3. The difference illustrates that insertion sort is adaptive: its work tracks how far out of order the input is, from O(n) for sorted input to O(n²) for reversed input. Selection sort, by contrast, always makes n(n−1)/2 = 6 comparisons for n = 4.
Question 3

Merge the sorted runs [1, 4, 8] and [2, 3, 9]. How many comparisons are made and what is the output? What is the largest possible number of comparisons for merging runs of lengths p and q?

1 vs 2 → take 1; 4 vs 2 → take 2; 4 vs 3 → take 3; 4 vs 9 → take 4; 8 vs 9 → take 8; the left run is now empty, so 9 is copied without a comparison. That is 5 comparisons and the output [1, 2, 3, 4, 8, 9]. In general each comparison places one element, and the last element left in one run is copied for free, so merging runs of length p and q needs at most p + q − 1 comparisons (here 3 + 3 − 1 = 5); it can need fewer, as little as min(p, q) if one run is entirely smaller than the other.
Question 4

Quicksort with the last element as pivot is run on an already sorted array of 1,000 numbers. What happens to its time and to its recursion depth, and how does the "recurse on the smaller side" version change each?

With a sorted array the last element is the largest, so every partition puts all other elements on one side and leaves the other side empty. The recurrence becomes T(n) = T(n − 1) + O(n), which is O(n²): 499,500 comparisons for 1,000 elements (the same as selection sort). The plain recursive version also goes about n levels deep (measured: 999), which risks overflowing a small stack. Recursing only into the smaller side and looping on the larger side bounds the recursion depth by log₂ n (measured: depth 1 on this input), but the time remains 499,500 comparisons. To fix the time you must also choose pivots better, for example median-of-three or a random pivot.
Question 5

For the calibration table in Section 6.6, compute the interpolated temperature (in tenths of a degree) for adc = 700, using the segment with points (614, 300) and (819, 420). Why is the multiplication done in long?

The segment is [614, 819): dx = 819 − 614 = 205 and dy = 420 − 300 = 120. The value is 300 + (700 − 614) × 120 / 205 = 300 + 86 × 120 / 205 = 300 + 10,320 / 205 = 300 + 50 (10,320 / 205 = 50.34, truncated) = 350, i.e. 35.0 °C. The product (adc − adc_pts[lo]) × dy can exceed 32,767, the largest value of a 16-bit int on small microcontrollers (here 10,320 is below it, but a table with larger spans or finer units would not be), so doing the multiplication in long prevents silent overflow before the division brings the value back down.

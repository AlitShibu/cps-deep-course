Hash Tables

Binary search finds a key in O(log n), but only in sorted data, and keeping data sorted costs you on every insertion. A hash table aims for something better: look up, insert and delete a key in O(1) on average, with no ordering at all. It does this by turning the key into an array index with a hash function, and the whole difficulty of the topic is what happens when two keys want the same slot. This chapter builds the idea from direct addressing, derives the hash functions you will actually use, builds both standard collision strategies (chaining and open addressing) as fixed-memory C code with no malloc, measures how they behave as the table fills, and finishes with the honest answer to when a hash table is the wrong choice, which on a microcontroller is more often than a PC programmer expects.

Section 7.1

From direct addressing to hashing

Suppose a node reads sensors identified by a small number, and you want to find a sensor's latest value given its ID. If the IDs run from 0 to 99, the answer is trivial: an array int16_t value[100], indexed directly by ID. Lookup, insert and delete are each one array access, O(1) in the worst case, no search at all. This is direct addressing, and it is the fastest possible lookup structure.

It breaks when the keys come from a much bigger space than the keys you actually store. If the IDs are 16-bit numbers, a direct-address table needs 65,536 entries. With 2-byte values that is 131,072 bytes, far more RAM than most microcontrollers have, to store perhaps twenty sensors. If the keys are strings (a command name, a variable name), direct addressing is impossible: there is no sensible array index for the word "humidity".

The hash table's idea is to shrink the key space onto a small array. A hash function h maps any key to an integer; reduce that to an array index with h(key) mod m (or a bit mask when m is a power of two), where m is the table size. Now a table of m = 32 slots can serve 16-bit keys or strings. The price is that many different keys must share the same slots, and the next sections deal with that.

Section 7.2

Hash functions

A good hash function has three properties. It is deterministic (the same key always gives the same value, or lookups would fail), fast (it runs on every operation), and well spread (different keys should land on different indices as evenly as possible, even when the keys follow a pattern). The third property is the hard one.

Strings: djb2 and FNV-1a

Two short hash functions for strings are in wide use because they are tiny and decent. Both fold each character into a running 32-bit value:

#include <stdint.h>

uint32_t djb2(const char *s) {
    uint32_t h = 5381;
    while (*s) h = h * 33 + (unsigned char)*s++;        // h = h*33 + c
    return h;
}

uint32_t fnv1a(const char *s) {
    uint32_t h = 2166136261u;                           // FNV offset basis (32-bit)
    while (*s) {
        h ^= (unsigned char)*s++;                       // mix in the character...
        h *= 16777619u;                                 // ...then multiply by the FNV prime
    }
    return h;
}

Hand-check djb2 on the one-letter string "a": 5381 × 33 + 97 = 177,670, which is what the code returned, and fnv1a("a") returned 0xE40C292C, the published value for that input. Reduced to a table of 8 slots with % 8, these eight sensor names land as follows:

Eight keys into eight slots, and both functions produce collisions: djb2 sends pressure and speed to slot 6 and voltage and gps to slot 7; FNV-1a sends humidity and speed to slot 0 and pressure and current to slot 2. That is not a defect of either function. It is what even a well-spread hash does when the table is this full, and Section 7.3 quantifies it. Neither function is suitable where an attacker chooses the keys; they are fast mixing functions, not cryptographic hashes.

Integers: avoid the trap of "key mod table size"

For integer keys the obvious choice is key % m. It is fine for keys that are scattered, and disastrous for keys that share a pattern with m. Sensor IDs that are all multiples of 8 and a table of m = 8 send every key to slot 0, one long chain. A cheap, much better choice for a power-of-two table is multiplicative hashing: multiply by a large odd constant and keep the top bits of the 32-bit product:

#define HT_BITS 3                                        // table size m = 2^3 = 8

static uint8_t hash_idx(uint16_t key) {
    return (uint8_t)(((uint32_t)key * 2654435769u) >> (32 - HT_BITS));
}

The constant 2,654,435,769 (0x9E3779B9) is 232 divided by the golden ratio, the classic choice (Knuth's multiplicative method). Keeping the top bits matters: the high bits of the product depend on all the bits of the key, whereas the low bits depend only on the low bits of the key. Measured on the same eight slots:

keys 100..109            key % 8:         4 5 6 7 0 1 2 3 4 5
                         multiplicative:  6 3 0 5 2 7 4 1 5 2     (first 8 keys fill all 8 slots)
keys 8, 16, 24, ..., 64  key % 8:         0 0 0 0 0 0 0 0         (all eight in one slot)
                         multiplicative:  7 7 6 6 5 5 4 4         (four slots, at most 2 per slot)

Be honest about what this shows. Multiplicative hashing is far better than % 8 on patterned keys, but it is not perfect (the multiples of 8 still pair up), and consecutive keys spread well under both methods. Nothing spreads every possible key set perfectly, and the next section shows why.

Why not just use a prime for m?

With key % m, a prime m avoids most patterns: keys 10, 20, 30, 40, 50 all land in slot 0 with m = 10 but in slots 10, 9, 8, 7, 6 with m = 11. The cost is a division on every operation, which is slow on microcontrollers without a hardware divider, and a table size that is no longer a power of two. Multiplicative hashing with a power-of-two table gets most of the benefit with a multiply and a shift. Either is a legitimate engineering choice; the wrong choice is a power-of-two key % m with keys you know are patterned.

Section 7.3

Collisions are unavoidable, and arrive early

A collision is two different keys hashing to the same slot. When there are more possible keys than slots they are guaranteed (the pigeonhole principle), but they happen far earlier than intuition suggests. This is the birthday problem: with 23 people in a room, the chance that two share a birthday (365 possible days) is already about 50.7% (the chance of no match is 0.4927). Replace days with table slots:

Table size mKeys insertedChance of at least one collision
3652350.7%
1,024104.3%
1,0242017.0%
1,0244053.8%

(Computed as 1 minus the product of (m − i)/m for i from 0 to n − 1, assuming each key is equally likely to land in any slot.) A rule of thumb: the first collision is expected after about √(π·m/2) keys, which is about 40 for m = 1,024. So a table that is less than 4% full will usually already have a collision. A hash table is therefore not a structure that avoids collisions. It is a structure that handles them cheaply, and the two standard ways to do so are the next two sections.

"O(1)" hides the worst case

If every key hashes to the same slot, a hash table degenerates into a single linked list or a long probe sequence and every operation becomes O(n). That is the worst case of Chapter 1 returning. It happens by accident with patterned keys and a poor hash (the multiples-of-8 example), and on purpose when an attacker can choose keys that collide, which is why some languages randomize their string hashing: in CPython the hash of a string differs from one run of the interpreter to the next (hash('a') printed two different values in two separate runs). For a real-time system, "O(1) on average" is not a guarantee, and Section 7.7 returns to that.

Section 7.4

Collision strategy 1: chaining

In chaining each slot (called a bucket) holds the head of a linked list (Chapter 3) of all the entries that hash to it. Insert by adding a node at the head of the bucket's list, look up by hashing to the bucket and walking its list, delete by unlinking the node.

Fig 7.1 — Chaining: every bucket is a linked list. Patterned keys can pile into one chain.

Cost and the load factor

The quantity that governs performance is the load factor α = n / m, the number of stored entries divided by the number of buckets. The average chain holds α entries. With a well-spread hash, a lookup that finds its key examines on average about 1 + α/2 entries, and an unsuccessful lookup examines about α entries, plus the constant work of hashing. For α = 1 (as many entries as buckets) that is about 1.5 and 1.0 steps: still O(1) as long as α is kept bounded. With n = 100 keys in m = 64 buckets, α = 1.5625, about 1.78 entries examined for a hit. Chaining degrades gracefully: even at α > 1 it keeps working, just slower, since each bucket can hold any number of entries. Random spread still leaves some unevenness: in one simulation of 1,000 random keys into 1,000 buckets, the average chain length was 1 but the longest chain was 6.

A fixed-memory implementation: no malloc

On a microcontroller you do not want a malloc per entry (Chapter 3, Section 3.5). The node pool technique fits perfectly: all entries live in a fixed array, links are one-byte indices, and a free list hands out unused entries. The keys here are 16-bit sensor IDs and the values 16-bit readings.

#define HT_BITS 3
#define HT_M    (1u << HT_BITS)         // 8 buckets
#define HT_N    6                        // pool capacity: at most 6 entries stored
#define NIL     255

typedef struct { uint16_t key; int16_t val; uint8_t next; } Entry;

typedef struct {
    uint8_t bucket[HT_M];                // index of the first entry in each chain, or NIL
    Entry   pool[HT_N];                  // all entries live here
    uint8_t free_head;                   // free list of unused pool entries
    uint8_t count;
} HTable;

void ht_init(HTable *t) {
    for (unsigned b = 0; b < HT_M; b++) t->bucket[b] = NIL;
    for (uint8_t i = 0; i < HT_N; i++)
        t->pool[i].next = (i + 1 < HT_N) ? i + 1 : NIL;     // chain the free entries
    t->free_head = 0;
    t->count = 0;
}

// Insert or update. Returns 0 on success, -1 if the pool is exhausted.
int ht_put(HTable *t, uint16_t key, int16_t val) {
    uint8_t b = hash_idx(key);
    for (uint8_t i = t->bucket[b]; i != NIL; i = t->pool[i].next)
        if (t->pool[i].key == key) { t->pool[i].val = val; return 0; }   // key exists: update
    uint8_t n = t->free_head;
    if (n == NIL) return -1;                                  // no free entry
    t->free_head = t->pool[n].next;
    t->pool[n].key = key;
    t->pool[n].val = val;
    t->pool[n].next = t->bucket[b];                           // new entry goes at the head
    t->bucket[b] = n;
    t->count++;
    return 0;
}

int ht_get(const HTable *t, uint16_t key, int16_t *out) {
    for (uint8_t i = t->bucket[hash_idx(key)]; i != NIL; i = t->pool[i].next)
        if (t->pool[i].key == key) { *out = t->pool[i].val; return 0; }
    return -1;                                                // not found
}

int ht_remove(HTable *t, uint16_t key) {
    uint8_t b = hash_idx(key), prev = NIL;
    for (uint8_t i = t->bucket[b]; i != NIL; prev = i, i = t->pool[i].next) {
        if (t->pool[i].key == key) {
            if (prev == NIL) t->bucket[b] = t->pool[i].next;   // removing the head of the chain
            else             t->pool[prev].next = t->pool[i].next;
            t->pool[i].next = t->free_head;                   // return the entry to the free list
            t->free_head = i;
            t->count--;
            return 0;
        }
    }
    return -1;
}

Tested under AddressSanitizer and UndefinedBehaviorSanitizer: inserting keys 100 to 105 (values twice the key) filled the 6-entry pool, and a further insert of key 200 failed with −1 rather than writing out of bounds. A lookup of 103 returned its value 206 and a lookup of the absent key 999 returned −1; putting 103 again updated the value in place (count unchanged at 6). Removing 102 freed an entry (count 5), after which inserting 200 succeeded, and removing the absent key 555 returned −1. The whole structure is 46 bytes on the test machine (an 8-byte bucket array, six 6-byte entries after padding, and two bytes of bookkeeping), fixed at compile time. As in Chapter 3, this is a structural sketch: it has no protection against use from both an interrupt and the main loop, and the one-byte indices limit the pool to 255 entries.

Section 7.5

Collision strategy 2: open addressing

Chaining needs a link in every entry and a second structure (the pool). Open addressing stores the entries directly in the table array and resolves a collision by probing: if the home slot is taken, try another until a free slot appears. The simplest rule is linear probing: try the home slot h, then h + 1, h + 2, … wrapping around at the end.

Lookup follows the same path: start at the home slot and move forward until you find the key (success) or reach an empty slot (the key is absent, because if it were present the insert would have placed it before the first empty slot). Memory is one flat array with no pointers, which is compact and cache-friendly, but there is a hard limit: at most m entries, and performance collapses as the table fills.

#define OA_M 8
enum { EMPTY = 0, USED = 1, DELETED = 2 };

typedef struct { uint16_t key; int16_t val; uint8_t state; } Slot;
typedef struct { Slot s[OA_M]; } OATable;                 // zero-initialize: all slots EMPTY

int oa_put(OATable *t, uint16_t key, int16_t val) {
    unsigned h = key % OA_M;                              // simple hash for this demo
    int first_del = -1;                                   // first tombstone seen along the probe path
    for (unsigned i = 0; i < OA_M; i++) {
        unsigned k = (h + i) % OA_M;
        if (t->s[k].state == USED && t->s[k].key == key) { t->s[k].val = val; return 0; }
        if (t->s[k].state == DELETED && first_del < 0) first_del = (int)k;
        if (t->s[k].state == EMPTY) {                     // key is not present: insert now
            unsigned dst = (first_del >= 0) ? (unsigned)first_del : k;   // reuse a tombstone if seen
            t->s[dst].key = key; t->s[dst].val = val; t->s[dst].state = USED;
            return 0;
        }
    }
    if (first_del >= 0) {                                 // table has no EMPTY slot, but has a tombstone
        t->s[first_del].key = key; t->s[first_del].val = val; t->s[first_del].state = USED;
        return 0;
    }
    return -1;                                            // completely full
}

int oa_get(const OATable *t, uint16_t key, int16_t *out) {
    unsigned h = key % OA_M;
    for (unsigned i = 0; i < OA_M; i++) {
        unsigned k = (h + i) % OA_M;
        if (t->s[k].state == EMPTY) return -1;            // reached a gap: key is absent
        if (t->s[k].state == USED && t->s[k].key == key) { *out = t->s[k].val; return 0; }
    }
    return -1;
}

int oa_remove(OATable *t, uint16_t key) {
    unsigned h = key % OA_M;
    for (unsigned i = 0; i < OA_M; i++) {
        unsigned k = (h + i) % OA_M;
        if (t->s[k].state == EMPTY) return -1;
        if (t->s[k].state == USED && t->s[k].key == key) {
            t->s[k].state = DELETED;                      // a TOMBSTONE, not EMPTY
            return 0;
        }
    }
    return -1;
}

Deletion needs tombstones

You cannot delete by simply marking the slot EMPTY. Another key may have been pushed past this slot during its own probe, and a lookup for it stops at the first empty slot, so it would wrongly report "not found". Instead, mark the slot DELETED (a tombstone): lookups continue past it, and a later insert may reuse it. The cost is that tombstones accumulate and slow lookups until the table is rebuilt.

Fig 7.2 — Linear probing with h = key mod 8: colliding keys occupy the next free slots, forming a cluster.

Run on this exact sequence, the inserts of 15, 23, 31, 7 (all with home slot 7) and 42 (home slot 2) took 1, 2, 3, 4 and 2 probes, leaving 23, 31, 7 and 42 in slots 0 to 3 and 15 in slot 7. The measured behavior afterward: looking up 31 took 3 probes (slots 7, 0, 1). Looking up the absent key 99 (home slot 3) took 2 (slot 3 is occupied, slot 4 is empty); the absent key 50 (home slot 2) took 3. After oa_remove(23), looking up 31 still succeeded in 3 probes, because the tombstone in slot 0 did not stop the search; looking up the now-deleted 23 returned not-found only after 6 probes, because it had to scan to the first truly empty slot (slot 4). Inserting 55 (home 7) then reused the tombstone at slot 0, but only after 6 probes, since the code must continue to an empty slot to confirm 55 is not already stored further along.

Primary clustering

The weakness of linear probing is clustering: occupied slots form contiguous runs, and any key whose home slot lands in a run must probe to its end, which then makes the run longer. The cost therefore rises sharply with the load factor α. For linear probing with a well-spread hash, the standard analysis gives about ½(1 + 1/(1 − α)) probes for a successful lookup and about ½(1 + 1/(1 − α)²) for an unsuccessful one. A simulation on a 100,000-slot table with random hash values agreed closely:

The lesson: an open-addressing table that is half full costs about 1.5 to 2.5 probes, but at 90% full a miss costs about 50. In practice you size an open-addressing table so that α stays below about 0.5 to 0.7, which means paying for roughly twice as many slots as entries. Chaining, by contrast, has no such cliff (a miss at α = 1 examines about 1 entry) and its entry pool is shared by all buckets, so memory is used evenly however the keys happen to spread.

Section 7.6

Load factor, resizing, and Python's dict

Because performance depends on α, a hash table that can grow does so before α gets too high. The standard method is to allocate a bigger array (typically double the size) and rehash every entry into it: the hash index depends on m, so entries cannot simply be copied across. A rehash costs O(n), but if the table doubles each time, the cost spreads across the insertions that triggered it and the amortized cost of an insert stays O(1), the same argument as the growable array of Chapter 1, Section 1.5. Like that array, a single insert occasionally costs O(n), which is the kind of pause a hard real-time loop cannot tolerate.

On a microcontroller the table is almost always fixed size, chosen from a known maximum number of entries, and "full" is a condition you handle (the pool-exhausted return in ht_put). That also means the load factor is bounded by design rather than by resizing, which turns the O(1) average into something you can reason about.

Python: dict and set

Python's dict and set are hash tables (Python Chapter 2), written in C, resizing automatically, with O(1) average lookup, insert and delete. Their rules follow directly from this chapter: keys must be hashable, which means immutable and consistently hashable (a list as a key raises TypeError because it could change after being stored and would then be in the wrong bucket; a tuple of hashable items works). Since Python 3.7 a dict also remembers insertion order, a language guarantee but a property of Python's design, not of hash tables in general. The classic uses: counting occurrences, removing duplicates, and fast membership tests.

counts = {}
for word in ["temp", "rpm", "temp", "gps", "temp"]:
    counts[word] = counts.get(word, 0) + 1          # O(1) average per word
# counts == {'temp': 3, 'rpm': 1, 'gps': 1}

seen = set()
unique = [x for x in [4, 2, 4, 7, 2] if not (x in seen or seen.add(x))]   # [4, 2, 7]

Compare with a list: x in some_list scans in O(n), while x in some_set is O(1) on average. Replacing a list with a set for repeated membership tests is one of the most common easy speedups in Python.

Section 7.7

When to use a hash table, and when not to

SituationBetter choiceWhy

Keys must be visited in sorted order, or range queries ("all readings between 40 and 60")Sorted array or a tree (Chapter 8)A hash table scatters keys; it has no order

An embedded use that suits a hash table well is a dispatch table: a received CAN or sensor message carries an ID, and you need to find the handler for that ID. With few IDs, a sorted array and binary search is simplest and has a guaranteed bound; with many sparse IDs, a hash table with a fixed pool is faster on average. If the set of IDs is fixed at build time you can often eliminate the problem entirely by choosing a hash (or a small direct-address table) that is collision-free for that exact set.

The practical rule

Reach for a hash table when you need exact-key lookup over many items and can tolerate "average" O(1). In firmware, size it from a known maximum, keep the load factor bounded, and handle "full" explicitly. Do not use it when order matters, when n is tiny, or when a missed deadline is not acceptable. In those cases a sorted array or direct addressing is the safer tool.

What to take away: parts (a) and (b) show that the hash function and table size matter as much as the collision strategy: the same five keys give chains of 4 or of 2. Part (c) is the open-addressing mechanics, including why deletion needs a tombstone. Part (d) is the engineering decision: for a small, known number of entries, a chained table on a static pool or an open-addressing table at half load costs a few hundred bytes, while direct addressing wastes the RAM and a naive growable table is unavailable.

Wrap-up

Recap

  1. A hash table maps a key to an array index with a hash function (h(key) mod m, or a bit mask for power-of-two m), giving O(1) average lookup, insert and delete. Direct addressing is the special case where the key itself is the index; it needs a slot per possible key (131,072 bytes for 16-bit keys with 2-byte values) and is impossible for strings.
  2. A good hash is deterministic, fast and well spread. djb2 (h = h*33 + c from 5381) and FNV-1a (xor then multiply by 16777619 from 2166136261) are short string hashes; multiplicative hashing (multiply by 0x9E3779B9 and keep the top bits) is a cheap integer hash that spreads patterned keys far better than key % 8 (keys 8 to 64 fall into 4 slots instead of 1), though not perfectly.
  3. Collisions are unavoidable and early (birthday problem): 23 keys in 365 slots give a 50.7% chance of one; 40 keys in 1,024 slots give 53.8%. A hash table handles collisions rather than avoiding them, and if all keys collide every operation degrades to O(n), which poor hashes and adversarial keys can trigger.
  4. Chaining keeps a linked list per bucket. With load factor α = n/m, a hit examines about 1 + α/2 entries and a miss about α, and it degrades gracefully even above α = 1. A fixed pool of entries with one-byte index links gives it with no malloc (46 bytes for 8 buckets and 6 entries on the test machine), at the price of a hard capacity.
  5. Open addressing stores entries in the table itself and probes on collision (linear probing: h, h+1, h+2, …). Deletion must leave a tombstone, not an empty slot, or later lookups stop too early. Clustering makes cost rise steeply with load: about 1.5 and 2.5 probes for a hit and a miss at α = 0.5, but about 5.5 and 50 at α = 0.9, so keep α below roughly 0.5 to 0.7.
  6. Growable tables rehash into a bigger array (O(n), amortized O(1) per insert, with occasional pauses); embedded tables are usually fixed size with "full" handled explicitly. Python's dict and set are hash tables: keys must be hashable (immutable), and x in some_set is O(1) on average against O(n) for a list.
  7. Use a hash table for exact-key lookup, counting and deduplication over many items. Avoid it when order or range queries matter (use a sorted array or tree), when n is tiny (a linear scan wins), when the key set is fixed (perfect hashing or a sorted table), or when a hard worst-case deadline applies (it only guarantees an average).
Check yourself

Quick check

Question 1

Compute djb2("ab") by hand from djb2("a") = 177,670, and give its bucket in a table of m = 8.

Each character updates h to h × 33 + c. After "a", h = 177,670. Adding 'b' (ASCII 98): 177,670 × 33 + 98 = 5,863,110 + 98 = 5,863,208. Then 5,863,208 mod 8 = 0 (5,863,208 / 8 = 732,901 exactly), so the key goes to bucket 0. (The value fits in 32 bits, so no wraparound occurred here; for longer strings the multiplication wraps modulo 232, which is intended and harmless in an unsigned type.)
Question 2

A chained table holds 100 entries in 64 buckets. What is the load factor, and about how many entries does a successful lookup examine on average? An unsuccessful one?

The load factor is α = 100 / 64 = 1.5625. A successful lookup examines about 1 + α/2 = 1 + 0.78 = 1.78 entries; an unsuccessful lookup examines about α = 1.56 entries (it walks the whole chain of its bucket). Both assume a well-spread hash. Chaining continues to work above α = 1 because each bucket can hold any number of entries, only the chains get longer; open addressing could not hold 100 entries in 64 slots at all.
Question 3

You insert 40 random keys into a table with 1,024 slots, which is under 4% full. Why is it still more likely than not that at least one collision has already happened?

This is the birthday problem. The chance that all 40 keys land in distinct slots is the product of (1024 − i)/1024 for i = 0 to 39, which is about 0.462, so the chance of at least one collision is about 53.8%. There are 40 × 39 / 2 = 780 pairs of keys, and each pair has a 1/1024 chance of colliding, so collisions arise from the sheer number of pairs, not from the table being full. The first collision is expected after about √(π·m/2) ≈ 40 keys for m = 1,024. Collisions are therefore normal and must be handled by design, not treated as a rare failure.
Question 4

In the open-addressing example, 31 sits in slot 1 although its home slot is 7. If oa_remove(23) simply marked slot 0 as EMPTY, what would a lookup of 31 do, and how does a tombstone fix it?

The lookup of 31 starts at its home slot 7 (occupied by 15, not a match), then goes to slot 0. If slot 0 had been marked EMPTY, the search would stop there, because an empty slot means "the key would have been placed before this point if it were present", and it would wrongly report 31 as absent even though it is in slot 1. With a tombstone (state DELETED) in slot 0, the lookup knows the slot was once occupied, continues to slot 1, and finds 31 (still 3 probes). The cost is that tombstones lengthen later searches, and a lookup for the deleted key itself must scan all the way to the first truly empty slot (6 probes in the example).
Question 5

Sensor IDs 10, 20, 30, 40, 50 are stored with h = key mod m. Show where they land for m = 10 and for m = 11, and explain what this says about choosing the table size.

With m = 10 the slots are 0, 0, 0, 0, 0: every key shares a factor with m, so all five fall into slot 0 and form one chain (O(n) lookup). With the prime m = 11 the slots are 10, 9, 8, 7, 6: all distinct. When keys follow a regular pattern (multiples of a number), a table size sharing factors with that number makes collisions systematic. A prime size avoids most such patterns, at the cost of a division per operation and a non-power-of-two size. The alternative for power-of-two tables is multiplicative hashing, which mixes the bits of the key before taking the index, spreading patterned keys far better than a plain modulo (though not perfectly).

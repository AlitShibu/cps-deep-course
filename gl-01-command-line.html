The Command Line & Linux Fundamentals

Nearly every tool in your CPS roadmap — compiling C, running Python scripts, flashing microcontrollers, working with Git — happens through a terminal, on Linux or a Linux-like environment. This chapter builds real comfort with the command line itself, not just a list of commands to memorize.

Section 1.1

Why the terminal, when a mouse exists

A graphical interface is great for browsing and clicking — but it's slow for repeating an action, awkward for automating anything, and often simply unavailable: a microcontroller flashing tool, a remote server, or a CI pipeline (recall the Git track's GitHub Actions) has no mouse to click at all. The terminal is a text-based way to tell your computer exactly what to do, and critically, every command you type can be saved, repeated, and automated — the foundation of Chapter 3's shell scripting.

The "everything is a file" philosophy

Linux treats almost everything — regular files, folders, hardware devices, even running processes' information — as something you can read, write, or list using the same small set of tools. This uniform design is exactly why a small number of commands (this chapter's focus) go remarkably far: you don't need a different tool for every different kind of "thing" on the system.

Section 1.2

Navigating the filesystem

pwd                  # print working directory -- "where am I right now?"
ls                     # list files in the current directory
ls -la                  # list ALL files (including hidden ones, starting with '.'), with details
cd folder_name           # change directory -- move INTO folder_name
cd ..                     # move UP one level, to the parent directory
cd ~                       # jump straight to your home directory
cd -                        # jump back to whichever directory you were just in
A filesystem is a tree — cd moves you between nodes, pwd tells you exactly where in the tree you currently are.

Absolute vs. relative paths

An absolute path (starting with /) describes a location from the filesystem's root, unambiguous no matter where you currently are: /home/dev/projects. A relative path describes a location relative to your current directory: if you're already in /home/dev, just projects gets you there. Relative paths are shorter to type but only correct from the specific directory you're currently in — a script using relative paths behaves differently depending on where it's run from, a genuinely common source of "works on my machine" bugs.

Section 1.3

Basic file operations

mkdir new_folder         # create a new folder
touch file.txt             # create a new, empty file (or update its timestamp if it exists)
cp source.txt dest.txt       # copy a file
cp -r source_folder dest       # copy a FOLDER (and everything inside it) -- '-r' means recursive
mv old_name.txt new_name.txt    # move OR rename -- same command does both
rm file.txt                      # delete a file -- NO trash bin, this is permanent
rm -r folder_name                  # delete a folder and everything inside it -- also permanent
cat file.txt                        # print a file's entire contents to the screen
less file.txt                        # view a file's contents, one screen at a time (for big files)
rm has no undo — a genuine, common source of real disasters

Unlike deleting a file through a graphical file manager (which usually goes to a recoverable trash/recycle bin), rm deletes immediately and permanently — there is no built-in "restore from trash." rm -rf folder_name (recursive, force) deleting the wrong folder is one of the most infamous, genuinely career-story-worthy mistakes in computing. Before running rm -r on anything, it's worth the extra second to run ls on that exact path first and confirm you're about to delete exactly what you think you are.

Getting help without leaving the terminal

man ls          # the full manual page for a command -- press 'q' to quit
ls --help        # a shorter usage summary, for most commands
which python      # shows exactly which installed program a command name refers to
Section 1.4

A first taste of pipes — the Unix philosophy in action

Every command you've seen so far does one focused job. The real power of the command line comes from combining small tools — feeding one command's output directly into another command's input, using the pipe operator |.

ls -la | grep ".txt"       # list all files, but only show lines containing ".txt"
ls | wc -l                    # list files, then COUNT how many lines that produced
                                 # (i.e., "how many files are in this folder?")
This is the Unix philosophy: small, focused tools, chained together, rather than one giant tool trying to do everything.
Why this matters beyond convenience

This isn't just a shortcut — it's the design principle underlying most serious command-line work: grep doesn't know or care what produced its input, and ls doesn't know or care what happens to its output. Each tool is small, well-tested, and does one job well, and pipes let you compose them into exactly the specific tool you need for a given task, on the fly, without writing new software. Chapter 3 goes much deeper into this exact idea with more powerful text-processing tools.

Section 1.5

Worked problem — finding the largest log file in a project

Problem

You have a folder full of telemetry log files with a mix of extensions, and need to find which one is largest, without opening a file manager.

# Navigate to the folder
cd ~/projects/telemetry_logs

# List files with details, including size, sorted by size (largest first)
ls -la
# Add -S to sort by size:
ls -laS

# The first line of output (after the "total" line) is now the largest file

Why -S specifically: most commands' flags (the dash-prefixed options) modify behavior in small, composable ways — -l for "long/detailed format," -a for "all, including hidden," -S for "sort by size." These can be combined into one flag group (-laS) rather than needing three separate command invocations — a small habit worth building, since real terminal work involves constantly combining a handful of well-known flags rather than memorizing entirely separate commands for each variation.

Wrap-up

Recap

  1. The terminal matters because commands can be saved, repeated, and automated — essential for tools with no GUI at all (flashing microcontrollers, remote servers, CI pipelines) and for anything you'll do more than once.
  2. Absolute paths (starting with /) work from anywhere; relative paths depend on your current directory — a common source of scripts that "work on my machine" but fail elsewhere.
  3. rm has no undo — always double-check the target path, especially with -r (recursive folder deletion).
  4. Pipes (|) chain small, focused tools together — the Unix philosophy of composing simple tools rather than building one tool that does everything.
  5. Command flags (like -l, -a, -S) combine into groups (-laS) — a small, well-known set of flags covers the overwhelming majority of real terminal work.
Check yourself

Quick check

Question 1

Why might a script using relative paths work fine when run from one directory but fail when run from another?

A relative path is interpreted relative to whatever the current working directory happens to be at the time the script runs. If the script is run from a different directory than the one it was designed for, the relative paths inside it will point to the wrong (or nonexistent) locations.
Question 2

Why is extra caution warranted before running "rm -r" on any path, compared to deleting a file through a graphical file manager?

rm deletes immediately and permanently, with no trash/recycle bin to recover from -- unlike most graphical file managers, which typically move deleted items to a recoverable trash folder first.
Question 3

What does "ls | wc -l" accomplish, and why does this demonstrate the Unix philosophy?

It counts how many files/folders are in the current directory -- ls lists them, and piping that output into wc -l (word count, counting lines) counts how many lines (i.e., entries) were listed. Neither tool was designed specifically for "counting files" -- combining two small, general-purpose tools via a pipe achieves a specific result neither tool provides on its own.

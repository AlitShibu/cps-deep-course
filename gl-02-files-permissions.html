Files, Permissions & Processes

Two ideas that come up constantly once you start doing real work in a terminal: who's allowed to do what to a file, and what's actually running on the system right now. Both matter directly for embedded work — flashing a microcontroller often fails with a permission error before it fails for any interesting reason, and a stuck serial connection needs a process killed to free it up.

Section 2.1

The permissions model — read, write, execute

$ ls -l script.sh
-rwxr-xr-- 1 dev users 220 Jan 5 10:30 script.sh

That first, cryptic-looking string breaks down into four parts, each carrying real meaning:

Three permission triplets, each independently controlling read/write/execute for a different group of users.

The leading character (- for a regular file, d for a directory) is the file type; the next nine characters are three groups of three: what the owner can do, what the group can do, and what everyone else can do. Each triplet is read (r), write (w), execute (x) — a dash means that permission is absent.

chmod — changing permissions

chmod +x script.sh          # add execute permission for everyone
chmod u+w file.txt            # add write permission for the owner (u) specifically
chmod 755 script.sh             # the numeric form: owner=7(rwx), group=5(r-x), other=5(r-x)
Where the numbers come from

Each permission has a fixed numeric weight — read=4, write=2, execute=1 — and you add them: rwx = 4+2+1 = 7, r-x = 4+0+1 = 5. This is exactly Chapter 10 of the C course's bit-flag pattern (Digital Logic's Boolean algebra, one level removed) — three independent yes/no permissions, packed into one number by treating each as an independent bit. 755 is genuinely just three separate 3-bit values written next to each other.

The single most common "permission denied" cause for beginners

A freshly created or downloaded script almost never has execute permission by default — attempting ./my_script.sh fails with "Permission denied" until you run chmod +x my_script.sh once. This is one of the most common early command-line frustrations, and it's rarely a sign anything is actually wrong with the script's content — just that its permission bits don't yet allow execution.

Section 2.2

Processes — what's actually running

Every running program is a process, identified by a unique PID (Process ID). Managing processes — seeing what's running, stopping something stuck — is a routine part of real terminal work, especially embedded development where a serial monitor or flashing tool can hang and block a port other tools need.

ps aux                # list every running process on the system
ps aux | grep python    # combine with Chapter 1's pipes: only show Python-related processes

top                       # a live, continuously updating view of running processes
                             # (press 'q' to quit)

kill 4521                  # ask process 4521 to stop gracefully (by PID)
kill -9 4521                 # force-kill it immediately -- use only if a graceful kill doesn't work
Why kill has two distinct forms, and why that matters

A plain kill sends a polite "please shut down" signal, giving the process a chance to save its state and exit cleanly. kill -9 (SIGKILL) is an unconditional, immediate termination the process cannot ignore or clean up after — appropriate as a last resort for a genuinely stuck process, but risky for anything mid-write to a file (an interrupted write can leave a corrupted, half-written file behind). Always try a plain kill first; reach for -9 only when that doesn't work.

Foreground and background jobs

python long_analysis.py &     # the '&' runs it in the BACKGROUND -- your terminal is
                                 # immediately free to keep typing other commands

jobs                             # list background jobs running in this terminal session
fg %1                              # bring job 1 back to the FOREGROUND
Ctrl+Z                              # pause (suspend) the current foreground job
bg %1                                # resume a paused job, but in the background
Why this matters for real embedded/data work

A long-running data analysis script (Python Chapter 8's SciPy processing on a large telemetry file) or a serial monitor watching microcontroller output doesn't need to block your entire terminal session — running it in the background lets you keep working, checking logs, or running other commands in the same window, rather than needing a separate terminal window for every long-running task.

Section 2.3

Environment variables and PATH

An environment variable is a named value available to every program running in your terminal session — a shared, global-ish configuration space (loosely echoing C Chapter 4's caution about globals, but here it's a deliberate, standard mechanism for passing configuration around).

echo $HOME              # print the value of the HOME variable -- your home directory
export MY_API_KEY="abc123"     # set a new environment variable for this session
echo $MY_API_KEY                 # abc123

echo $PATH                        # a colon-separated LIST of folders the shell searches
                                     # whenever you type a command name
Why "command not found" happens, precisely

When you type python or gcc, the shell doesn't magically know where that program lives — it searches every folder listed in $PATH, in order, until it finds a matching executable file. "Command not found" means the shell searched every folder in $PATH and found nothing matching that name — often because a newly installed tool's folder was never added to $PATH in the first place. This is precisely the mechanism behind Python Chapter 9's virtual environments "activating" — activation temporarily modifies $PATH so that typing python or pip finds the virtual environment's own copies first, ahead of the system-wide ones.

Section 2.4

Worked problem — freeing a stuck serial port

Problem

A serial monitor program is holding open the connection to a microcontroller, and a flashing tool now fails with "port busy" — a genuinely common embedded workflow annoyance.

# Find what's using the serial port
ps aux | grep ttyUSB

# Output shows something like:
# dev    4832  0.1  0.5  ...  python serial_monitor.py

# The PID is 4832 -- ask it to stop gracefully
kill 4832

# Verify it's actually gone
ps aux | grep ttyUSB
# (no matching output now -- the process is confirmed stopped)

# Now the flashing tool can claim the port successfully

Why the verification step matters: kill (without -9) requests termination but doesn't guarantee it happens instantly — a process could ignore or delay handling the signal briefly. Re-running ps aux | grep confirms the process actually stopped before you retry the flashing tool, rather than assuming success and hitting the exact same "port busy" error a second time.

Wrap-up

Recap

  1. File permissions (rwx for owner, group, and everyone else) are packed into a single number using the same bit-weight pattern as C's bit flags — chmod +x is the standard fix for a script that fails with "Permission denied."
  2. Every running program is a process with a PID; ps/top show what's running, and kill stops a process — try a plain kill before kill -9, which forces immediate termination with no cleanup.
  3. Running a command with a trailing & puts it in the background, freeing your terminal for other work — jobs, fg, and bg manage background/foreground jobs.
  4. Environment variables (like $PATH) are shared configuration values available to every program in a session — $PATH specifically is the list of folders searched when you type a command name, and "command not found" means the search came up empty.
  5. Python's virtual environments (Python Chapter 9) work by temporarily modifying $PATH — this chapter's mechanism is the literal explanation for that earlier chapter's "activation" behavior.
Check yourself

Quick check

Question 1

A freshly downloaded script fails with "Permission denied" when run as ./script.sh. What's the most likely cause and fix?

The script most likely lacks execute permission. The fix is chmod +x script.sh, which adds execute permission so the file can actually be run as a program.
Question 2

Why should you generally try a plain kill before kill -9 on a stuck process?

A plain kill sends a signal the process can respond to gracefully, allowing it to save state or clean up before exiting. kill -9 terminates immediately and unconditionally, which can leave files mid-write in a corrupted state if the process was actively writing to disk when killed.
Question 3

What does the shell actually do when you type a command name like "python", and what does "command not found" mean precisely?

The shell searches every folder listed in the $PATH environment variable, in order, looking for a matching executable file. "Command not found" means it searched every folder in $PATH and found no match -- often because the tool exists but its containing folder was never added to $PATH.

Text Processing, Pipes & Scripting

Chapter 1 introduced pipes as a preview. This chapter is where they become a real tool: chaining small, single-purpose programs together to filter, transform, and summarize text — then wrapping repeated command sequences into shell scripts so you never have to retype them. This is the chapter that turns the terminal from "a place to run one command at a time" into an actual automation environment, which matters directly for parsing sensor logs, batch-processing data files, and automating build/flash workflows.

Section 3.1

Redirection and pipes, properly

Every running program has three standard I/O streams open by default: stdin (input, normally your keyboard), stdout (normal output, normally your screen), and stderr (error output, also normally your screen, but a separate stream from stdout). Redirection operators let you rewire these streams to files or to other programs.

command > file.txt        # redirect stdout to file.txt, OVERWRITING it
command >> file.txt       # redirect stdout to file.txt, APPENDING to it
command < file.txt        # feed file.txt in as stdin, instead of the keyboard
command 2> errors.txt     # redirect ONLY stderr to errors.txt (stdout still prints)
command > out.txt 2>&1   # redirect BOTH stdout and stderr into out.txt
stdout and stderr both land on your screen by default, but they are two independent streams — which is why you can redirect one without touching the other.
Why stdout/stderr being separate actually matters

If a program's normal output and its error messages were the same stream, you couldn't save "just the results" to a file without also capturing every warning mixed into it. Because they're separate, ./flash_firmware > log.txt saves only the normal progress output to log.txt while errors still show up immediately on your screen — exactly what you want when watching a flashing tool run.

Pipes: connecting one program's stdout to another's stdin

cat sensor_log.txt | grep "ERROR" | wc -l
# cat prints the file -> grep filters to only ERROR lines -> wc -l counts them

A pipe (|) takes the stdout of the command on its left and feeds it in as the stdin of the command on its right. Each command in the chain is small and does exactly one job — the power comes from chaining several of them together, which is the same "small, composable pieces" philosophy that shows up in well-structured C functions (Chapter 4) and clean Python (Python Chapter 9).

A pipe connects stdout, not stderr

Errors in the first command of a pipe do not flow into the second command by default — only stdout does. A command that fails and only prints to stderr will make the pipe silently receive nothing, which can look like "no results" instead of an obvious error. If a pipeline seems to be silently doing nothing, run the first command alone first to check it's actually succeeding.

Section 3.2

The core text-processing toolkit

A handful of small programs, combined with pipes, cover the large majority of everyday text filtering and summarizing needs. Each does one job well.

grep — search for a pattern

grep "ERROR" sensor_log.txt        # print every line containing "ERROR"
grep -i "error" sensor_log.txt       # case-INsensitive match
grep -v "DEBUG" sensor_log.txt        # invert match: print lines that DON'T contain "DEBUG"
grep -c "ERROR" sensor_log.txt         # print a COUNT of matching lines, not the lines themselves
grep -n "ERROR" sensor_log.txt          # show line NUMBERS alongside matches
grep -r "TODO" ./src                     # search RECURSIVELY through every file in a folder

cut — extract columns

# A CSV line: 2024-01-05,14:32:01,sensor_3,23.6,ERROR
cut -d',' -f3 readings.csv       # -d sets the delimiter, -f picks field(s) -> "sensor_3"
cut -d',' -f1,4 readings.csv      # multiple fields, comma-separated in the output

sort and uniq — order and deduplicate

sort names.txt                   # sort lines alphabetically
sort -n numbers.txt                # sort NUMERICALLY instead of as text (10 comes after 2)
sort -r names.txt                    # reverse order
sort names.txt | uniq                 # uniq removes ADJACENT duplicate lines
                                          # -- which is why sorting first matters: uniq only
                                          # catches duplicates that are next to each other
sort names.txt | uniq -c                  # count how many times each line appears
uniq without sort silently misses duplicates

uniq only collapses duplicate lines that are directly adjacent to each other. Running uniq on an unsorted file will leave separated duplicates untouched, which looks like a bug in uniq but is actually just a misunderstanding of what it does. The standard fix is always sort file | uniq, never uniq alone on unsorted input.

wc — count lines, words, characters

wc -l file.txt      # count LINES
wc -w file.txt        # count WORDS
wc -c file.txt          # count BYTES/characters

head and tail — peek at the start or end

head -n 5 sensor_log.txt      # first 5 lines
tail -n 5 sensor_log.txt        # last 5 lines
tail -f sensor_log.txt            # FOLLOW the file live -- keeps printing new lines as
                                     # they're appended, which is exactly how you watch a
                                     # log file that a running program is actively writing to
tail -f is the standard way to watch a live log

If a data-logging script is writing sensor readings to a file while it runs, tail -f readings.log lets you watch new readings appear in real time without repeatedly re-opening the file. This is a genuinely common embedded/data-work pattern: start the logger in the background (Chapter 2's &), then tail -f its output file in the same terminal to monitor progress.

Section 3.3

sed and awk — pattern-based editing and column processing

grep finds lines; sed and awk go a step further and transform them. Both have huge feature sets — this section covers the handful of patterns that account for most real-world use.

sed — stream editor, mainly for find-and-replace

sed 's/DEBUG/INFO/' log.txt          # replace the FIRST match of DEBUG with INFO, per line
sed 's/DEBUG/INFO/g' log.txt           # 'g' = replace ALL matches per line, not just the first
sed -i 's/DEBUG/INFO/g' log.txt          # -i edits the file IN PLACE instead of just printing
sed -n '5,10p' log.txt                     # print only lines 5 through 10
sed -i overwrites the file with no undo

Without -i, sed just prints the transformed text to your screen — the original file is untouched, and you can inspect the result before committing to it. With -i, the file is rewritten immediately with no confirmation and no backup. The safe habit: run the command without -i first, check the output looks right, then add -i once you're confident.

awk — column-aware text processing

awk treats each line as a row split into fields (by whitespace, by default), referred to as $1, $2, etc., with $0 meaning the whole line.

# readings.csv: 2024-01-05,14:32:01,sensor_3,23.6,ERROR
awk -F',' '{print $3, $4}' readings.csv        # -F sets the field separator; print fields 3 & 4

awk -F',' '$5 == "ERROR" {print $1, $2}' readings.csv
# print only rows where field 5 is exactly "ERROR" -- filtering AND extracting in one step

awk -F',' '{sum += $4} END {print sum}' readings.csv
# accumulate field 4 across every line, then print the total once, after all lines are read
Why awk's sum pattern works: END runs once, after everything else

The {sum += $4} block runs once per line, building up a running total in the variable sum. The END {print sum} block runs exactly once, after the last line has been processed — so it prints the final accumulated total rather than a running count printed on every line. This "process each line, then do one final thing" shape is the same idea as a loop with an accumulator variable in C or Python, just built into awk's structure directly.

When to reach for which tool

Rough rule of thumb: grep to find lines matching a pattern, cut for simple fixed-column extraction, sed for find-and-replace or printing a line range, awk once you need conditions, math, or multiple fields combined. Real pipelines often chain several: grep "ERROR" log.csv | awk -F',' '{print $1}' | sort | uniq -c — filter to errors, extract the date field, then count occurrences per date.

Section 3.4

Shell scripting — variables, conditionals, loops, functions

A shell script is just a text file containing a sequence of commands you'd otherwise type by hand — saved so it can be run as a single unit, repeatedly, without retyping. This is where Chapter 2's chmod +x becomes essential: a script needs execute permission before it can be run directly.

#!/bin/bash
# ^ the "shebang" line -- tells the system which interpreter should run this file

echo "Starting build..."
gcc main.c -o program
echo "Build complete."
What the shebang line actually does

#!/bin/bash isn't a comment in the usual sense — the operating system specifically checks a script's first line for this pattern and uses it to decide which program should interpret the rest of the file. Without it, running ./script.sh may fail or get interpreted by the wrong shell. It must be the literal first line of the file, with no blank line before it.

Variables

NAME="sensor_data"
echo "Processing $NAME"       # $NAME expands to the variable's value: "Processing sensor_data"

COUNT=$(wc -l < readings.csv)   # $(...) captures a COMMAND'S OUTPUT into a variable
echo "File has $COUNT lines"
No spaces around = in variable assignment

NAME = "sensor_data" (with spaces) fails in bash — the shell interprets it as trying to run a command called NAME with arguments = and "sensor_data", not as an assignment. It must be written exactly as NAME="sensor_data", with no space on either side of =.

Conditionals

if [ -f "readings.csv" ]; then
    echo "File exists"
else
    echo "File not found"
fi

if [ "$COUNT" -gt 1000 ]; then
    echo "Large dataset"
fi
The test operators are their own small vocabulary

Inside [ ... ], bash uses word-based operators rather than symbols for most comparisons: -f tests "is this a regular file", -d tests "is this a directory", -eq/-gt/-lt compare numbers, and == compares strings. This looks unfamiliar coming from C or Python's >/</==, but [ ... ] is itself a program (historically a separate command, test) with its own argument syntax, not a language-level construct like an if in C.

Loops

for f in *.csv; do
    echo "Processing $f"
    wc -l "$f"
done

for i in 1 2 3 4 5; do
    echo "Reading $i"
done

count=0
while [ $count -lt 5 ]; do
    echo "Count is $count"
    count=$((count + 1))
done
Why "$f" is quoted in the loop

Without quotes, a filename containing a space (sensor data.csv) would be split into two separate words by the shell, breaking the command. Quoting "$f" keeps the variable's value together as one argument regardless of spaces inside it. This is a real, common source of shell script bugs — the general habit is to quote variable expansions unless you specifically need word-splitting.

Functions and script arguments

#!/bin/bash

process_file() {
    local filename=$1          # $1 = first argument passed to the FUNCTION
    echo "Processing $filename"
    wc -l "$filename"
}

process_file "readings.csv"

# Arguments passed to the SCRIPT itself, e.g. `./script.sh readings.csv 3`:
echo "Script name: $0"
echo "First arg: $1"
echo "Second arg: $2"
echo "All args: $@"
echo "Number of args: $#"
local keeps a function's variables from leaking out

Without local, a variable assigned inside a bash function is global by default — it persists and can silently clash with a variable of the same name used elsewhere in the script. local filename=$1 confines that variable to the function it's declared in, which is the same motivation as C's preference for local variables over globals (C Chapter 4) — smaller, more predictable scope.

Section 3.5

Worked problem — a log-summary script

Problem

You have a growing sensor log file, sensor_log.csv, with rows like 2024-01-05,14:32:01,sensor_3,23.6,OK (date, time, sensor id, reading, status). Write a script that reports the total number of readings, the number of ERROR rows, and which sensor produced the most errors.

#!/bin/bash
# summarize_log.sh -- usage: ./summarize_log.sh sensor_log.csv

LOGFILE=$1

if [ ! -f "$LOGFILE" ]; then
    echo "Error: file '$LOGFILE' not found."
    exit 1
fi

TOTAL=$(wc -l < "$LOGFILE")
ERRORS=$(grep -c "ERROR" "$LOGFILE")

echo "Total readings: $TOTAL"
echo "Error readings: $ERRORS"

echo "Errors by sensor:"
grep "ERROR" "$LOGFILE" | cut -d',' -f3 | sort | uniq -c | sort -rn | head -n 1

Reading it piece by piece: the -f "$LOGFILE" check (Section 3.4) fails fast with a clear message if the file doesn't exist, rather than letting later commands fail with a more confusing error. wc -l and grep -c (Sections 3.1–3.2) give the two headline counts directly. The final pipeline is the chapter in miniature: grep filters to error rows, cut extracts just the sensor-id column, sort groups identical ids together, uniq -c counts occurrences of each, sort -rn puts the largest count first, and head -n 1 keeps only that top line.

Why exit 1 matters: returning a non-zero exit code on failure is how a script signals "something went wrong" to whatever called it — a build system, another script, or a human checking $? after the fact. exit 0 (or no explicit exit) signals success; any non-zero value conventionally signals failure.

Wrap-up

Recap

  1. Every program has three standard streams: stdin, stdout, and stderr — >/>> redirect stdout, 2> redirects stderr specifically, and | connects one command's stdout to the next command's stdin.
  2. Core text tools: grep finds matching lines, cut extracts columns, sort/uniq order and deduplicate (uniq only catches adjacent duplicates, so sort first), wc counts, and tail -f follows a live-growing file.
  3. sed does pattern-based find-and-replace (-i edits in place, with no undo); awk processes text by column, with conditions and running totals ({...} runs per line, END {...} runs once at the end).
  4. A shell script is a saved sequence of commands, starting with a shebang (#!/bin/bash) and needing execute permission (chmod +x) to run directly. Variables (NAME="value", no spaces around =), conditionals (if [ ... ]; then), and loops (for/while) give it real logic.
  5. Functions take arguments as $1, $2, etc.; local keeps a function's variables from leaking into the rest of the script. A script's own arguments are available the same way, plus $@ (all arguments) and $# (argument count).
Check yourself

Quick check

Question 1

Why does `uniq` sometimes fail to remove duplicate lines even though they clearly appear more than once in the file?

uniq only removes duplicate lines that are directly adjacent to each other. If the duplicates are scattered through the file rather than next to each other, they won't be collapsed. The fix is to sort the file first (sort file | uniq), which groups identical lines together before uniq processes them.
Question 2

What's the risk of running `sed -i 's/old/new/g' file.txt` compared to running it without -i first?

-i rewrites the file in place immediately, with no confirmation and no backup of the original content. Without -i, sed just prints the transformed result to the screen, leaving the file untouched so you can check the output is correct before committing to it. The safer habit is to test without -i first.
Question 3

In a bash for-loop like `for f in *.csv; do ... "$f" ... done`, why is $f wrapped in quotes?

Without quotes, a filename containing a space would be split into multiple separate arguments by the shell, breaking the command. Quoting "$f" preserves the variable's full value as a single argument regardless of spaces or other special characters inside it.

Git Fundamentals

Every serious codebase — a CPS coursework repo, a hackathon project, an open-source embedded library — is managed with version control, and Git is the tool nearly everyone uses. This chapter builds the mental model of what Git is actually doing under the hood (not just a list of commands to memorize), then walks through the everyday workflow: saving snapshots, branching to work on something without breaking the main codebase, and syncing with a remote like GitHub.

Section 4.1

Why version control, and Git's core idea

Without version control, "keeping track of changes" usually means files named project_final.c, project_final_v2.c, project_final_ACTUAL.c — a scheme that breaks down almost immediately once more than one person is involved, or once you need to know why something changed, not just that it changed. Version control solves this by recording a complete history of a project: every saved point can be inspected, compared, or returned to.

Git's core idea: snapshots, not differences

A common misconception is that Git stores a list of line-by-line differences between versions. It doesn't — every time you save a version (a commit), Git stores a complete snapshot of every tracked file at that moment (efficiently, by reusing unchanged files rather than re-storing them). This matters because it means Git can reconstruct the exact, complete state of the project at any past commit directly, without replaying a long chain of incremental patches.

Each commit points back to its parent, but each one also holds a complete, independent snapshot of the whole project at that point in time.

Setting up Git for the first time

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git init                    # turns the current folder into a Git repository

git init creates a hidden .git folder in the current directory — that folder is the entire repository: every commit, every branch, the full history. Deleting .git deletes the entire project history, even though the actual files on disk remain untouched.

Section 4.2

The three areas: working directory, staging area, repository

A file in a Git-tracked project is always in one of three places, and understanding this is the single biggest unlock for actually understanding Git's commands rather than just memorizing them.

git add moves changes from the working directory to the staging area; git commit moves staged changes into permanent history.
git status              # shows what's changed, and which of the three areas it's in
git add file.c            # stage a specific file
git add .                   # stage EVERYTHING that's changed in the current folder
git commit -m "Add sensor calibration function"    # save staged changes as a permanent commit
Why staging is a separate step from committing

The staging area lets you build a commit out of only some of your current changes — you might have edited three files, but only two of those edits are actually related and ready to be described by one commit message. Without staging, every commit would be forced to include literally everything currently changed, making it much harder to keep commits small and focused on one logical change each.

git commit without -m opens an editor

Running git commit alone drops you into a text editor (often Vim, which itself surprises beginners — see the box below) to write a commit message. git commit -m "message" supplies the message directly on the command line and skips the editor entirely, which is what you want for short, single-line commit messages.

.gitignore — telling Git what to never track

# .gitignore
build/
*.o
*.log
__pycache__/

A .gitignore file lists patterns for files Git should never stage or track — compiled binaries, log files, virtual environment folders. This keeps generated, machine-specific, or bulky files out of the repository's history, where they'd otherwise clutter every git status and bloat the repository size for no benefit.

Section 4.3

Viewing history: log, diff, and show

git log                    # full commit history: hash, author, date, message
git log --oneline            # condensed: one line per commit, easier to scan
git log --oneline --graph      # add a text-based branch graph alongside the log

git diff                         # show UNSTAGED changes (working dir vs staging area)
git diff --staged                  # show STAGED changes (staging area vs last commit)

git show a1b2c3d                     # show exactly what a specific commit changed
Why git diff has two modes

Because staging is a separate step, "what's changed" is genuinely ambiguous without specifying which comparison you mean. Plain git diff answers "what have I edited but not yet staged?"; git diff --staged answers "what's staged and about to be committed?" — the second is exactly what's worth reviewing right before running git commit, to catch a mistaken or incomplete stage before it becomes permanent history.

Commit hashes

Every commit has a unique identifier — a long hexadecimal hash like a1b2c3d4e5f6... — generated from the commit's content (its snapshot, message, timestamp, and parent). You'll usually only need the first 6–8 characters, since Git accepts any unambiguous prefix. This is directly related to hashing concepts that show up elsewhere in CS (and loosely echoes Digital Logic's bit-pattern thinking): the same content always produces the same hash, and even a tiny change produces a completely different one.

Section 4.4

Branching and merging

A branch is an independent line of development — a way to work on a new feature or experiment without touching the stable, working code on the main branch until you're ready.

git branch                       # list all branches (current one marked with *)
git branch feature-calibration     # create a new branch (doesn't switch to it yet)
git switch feature-calibration       # switch to that branch
git switch -c feature-calibration      # create AND switch in one step (-c = create)

# ... make commits on the feature branch ...

git switch main                          # switch back to the main branch
git merge feature-calibration              # bring the feature branch's commits into main
The feature branch develops independently; merging brings its commits back into main via a merge commit that has two parents.
Why branch instead of just editing main directly

If main always reflects a working, tested state of the project, anyone else using or building on it (a teammate, a hackathon collaborator, your own future self) can trust it. Doing exploratory or half-finished work on a separate branch means main never briefly contains broken code — you only merge once the feature branch is actually working.

Merge conflicts

If both main and the feature branch changed the same lines of the same file differently, Git can't automatically decide which version is correct — this is a merge conflict. Git marks the conflicting section directly in the file:

<<<<<<< HEAD
float threshold = 25.0;
=======
float threshold = 30.0;
>>>>>>> feature-calibration

You manually edit the file to keep the correct version (or some combination), delete the <<<<<<</=======/>>>>>>> marker lines, then git add the resolved file and git commit to complete the merge. A conflict is not an error to be afraid of — it's Git correctly refusing to guess at a decision only you can make.

Section 4.5

Working with remotes (GitHub)

Everything so far has been local — history stored only in your own .git folder. A remote is a copy of the repository hosted elsewhere (GitHub being the overwhelmingly common choice), which is what enables backup, collaboration, and sharing.

git clone https://github.com/user/project.git    # copy an existing remote repo to your machine

git remote add origin https://github.com/user/project.git   # link a LOCAL repo to a remote
                                                                # "origin" is just the conventional name

git push origin main         # upload your local commits on 'main' to the remote
git pull origin main            # download and merge the remote's commits into your local branch
git fetch origin                  # download remote commits WITHOUT merging them yet -- lets you
                                     # inspect what's new before deciding to integrate it
pull is really fetch + merge

git pull is shorthand for two steps done together: git fetch (download the remote's new commits) followed immediately by git merge (integrate them into your current branch). Using fetch alone is useful when you want to see what changed remotely — via git log origin/main — before committing to merging it into your own work.

Pushing to a branch someone else has also pushed to

If a remote branch has commits you don't have locally (a teammate pushed since you last pulled), git push is rejected rather than silently overwriting their work. The fix is to git pull first — merging their commits into yours locally — and only then push the combined result. This rejection is a deliberate safety feature, not a bug.

Typical collaborative workflow

git clone <url>                      # get the project
git switch -c my-feature                # create a branch for your change
# ... edit files ...
git add .
git commit -m "Implement calibration routine"
git push origin my-feature                 # push YOUR branch (not main) to the remote
# then open a Pull Request on GitHub to propose merging my-feature into main

A Pull Request (GitHub's term; GitLab calls it a Merge Request) is a request to merge one branch into another, opened through GitHub's web interface rather than the command line — it gives teammates a place to review the changes, comment, and discuss before the merge actually happens. This is standard practice for any team project, including hackathon repos.

Section 4.6

Undoing things safely

git restore file.c                # discard UNSTAGED changes to a file, reverting to last commit
git restore --staged file.c         # unstage a file (keeps the edits, just removes from staging)

git commit --amend -m "New message"   # rewrite the MOST RECENT commit's message (or add more changes)

git revert a1b2c3d                      # create a NEW commit that undoes a1b2c3d's changes --
                                           # history is preserved, nothing is deleted

git reset --soft a1b2c3d                  # move the branch pointer back, KEEPING changes staged
git reset --hard a1b2c3d                    # move the branch pointer back, DISCARDING changes entirely
git reset --hard is genuinely destructive

--hard discards uncommitted changes and moves history backward with no confirmation — any work only present in the discarded commits or as uncommitted edits is gone. git revert is the safer default for undoing something that's already been pushed or shared: it adds a new commit that cancels out the old one, rather than rewriting history that others may already have a copy of.

revert vs reset: preserving history vs rewriting it

Once commits are pushed to a shared remote, rewriting them with reset and force-pushing creates a mismatch with everyone else's copy of history, breaking their local repos in confusing ways. revert instead adds a normal new commit on top — safe to push and pull normally, because nothing that already existed is altered or removed, only added to.

Section 4.7

Worked problem — recovering from a bad commit on a shared branch

Problem

You pushed a commit to a shared main branch on GitHub that accidentally breaks the build. A teammate has already pulled it. How do you fix this without breaking their local copy?

# First, confirm which commit is the problem
git log --oneline
# a1b2c3d  Fix sensor threshold      <- looks fine
# e4f5g6h  Update calibration logic    <- this one broke the build
# 9i8h7g6  Add initial sensor code

# Since it's already been pushed AND pulled by someone else,
# reset --hard + force-push would corrupt their local history. Use revert instead:
git revert e4f5g6h
# Git creates a NEW commit that undoes exactly what e4f5g6h changed,
# opens the editor for a message (default is fine: "Revert 'Update calibration logic'")

git push origin main
# teammate runs a normal `git pull` -- no conflict, no rewritten history,
# their local repo picks up the revert commit like any other new commit

Why revert is the only safe option here: the moment a commit is shared (pushed, and especially once someone else has pulled it), rewriting it with reset requires a force-push that overwrites the remote's history — anyone who already pulled the old history now has a branch that's diverged in a way git pull can't cleanly reconcile. revert avoids this entirely by only ever adding new commits, never rewriting old ones — the one general rule worth remembering: never rewrite history that's already been shared.

Wrap-up

Recap

  1. Git stores complete snapshots at each commit, not diffs — commits form a chain, each pointing to its parent, which is why any past state can be reconstructed directly.
  2. Files move through three areas: working directory → (git add) → staging area → (git commit) → repository history. Staging lets you build a commit from only some of your current changes.
  3. git log/git diff/git show inspect history; git diff vs git diff --staged answer two different "what's changed" questions.
  4. A branch is an independent line of development; git switch -c creates and switches in one step, git merge brings a branch's commits back into another. A merge conflict happens when the same lines were changed differently on both sides — resolved by manually editing the marked section.
  5. A remote (e.g. GitHub) is a hosted copy of the repo — clone/push/pull/fetch sync with it. pull is fetch + merge combined. A Pull Request proposes merging one branch into another with review, before the merge happens.
  6. To undo: git revert adds a new commit that cancels an old one (safe for shared history); git reset --hard rewrites history and discards changes (destructive — never use on commits already shared with others).
Check yourself

Quick check

Question 1

What does each Git commit actually store — a diff from the previous commit, or something else?

Each commit stores a complete snapshot of every tracked file at that point in time (efficiently, reusing storage for unchanged files), not a line-by-line diff. This is why Git can reconstruct any past state directly, without replaying a chain of patches.
Question 2

What's the difference between `git diff` and `git diff --staged`?

git diff shows changes in the working directory that have NOT yet been staged. git diff --staged shows changes that ARE staged and about to become part of the next commit. They answer two different questions about what's currently different from the last commit.
Question 3

Why is `git revert` generally safer than `git reset --hard` for undoing a commit that's already been pushed and pulled by a teammate?

git revert adds a new commit that cancels out the old one, leaving history intact -- teammates can pull this new commit normally with no conflict. git reset --hard rewrites history and discards changes, which requires a force-push that can corrupt the history of anyone who already pulled the original commits. The general rule is to never rewrite history that has already been shared.

Numerical Linear Algebra in Practice

Every chapter so far has worked with exact numbers on paper. Real code runs on floating-point hardware, which is not exact — and some matrices amplify tiny numerical errors into large, dangerous ones. This chapter is what separates "I understand the math" from "I can trust code built on this math in a real engineering system."

Section 8.1

Floating-point numbers aren't exact

Computers represent real numbers using a fixed, finite number of bits (typically 64 bits for a "double" — the default in Python/NumPy). Most decimal numbers simply cannot be represented exactly in this format, the same way 1/3 can't be written exactly as a finite decimal.

import numpy as np
print(0.1 + 0.2)          # 0.30000000000000004 -- not exactly 0.3!
print(0.1 + 0.2 == 0.3)   # False
Why this matters for everything in this course

Every calculation this course has covered — Gaussian elimination (Chapter 3), matrix inversion (Chapter 4), eigenvalue computation (Chapter 6) — involves many chained floating-point operations. Each individual operation introduces a tiny rounding error, typically far too small to notice on its own. The real question this chapter answers is: under what conditions do these tiny errors compound into a large, untrustworthy final answer — and how do you recognize and avoid those conditions in real engineering code?

The practical rule this teaches immediately

Never compare floating-point numbers with == in real code — always check if they're within a small tolerance of each other instead: np.isclose(a, b) or abs(a-b) < 1e-9. This single habit prevents an entire category of bugs where mathematically-equal quantities fail an exact equality check purely due to floating-point representation, not due to any actual error in your logic.

Section 8.2

Ill-conditioning — when small input errors become large output errors

The core idea

Some matrices are numerically "delicate" — a tiny change in the input (from measurement noise, or just floating-point rounding) produces a wildly disproportionate change in the solution when you solve Ax=b or invert A. Such a matrix is called ill-conditioned. This is a distinct concept from singularity (Chapter 4) — an ill-conditioned matrix is technically still invertible (non-zero determinant), but sits dangerously close to being singular.

A concrete, dramatic example

Matrix: A = [[1, 1], [1, 1.0001]]. This is invertible (det = 0.0001, non-zero) — but only just barely.

import numpy as np
A = np.array([[1, 1], [1, 1.0001]])
b1 = np.array([2, 2])
b2 = np.array([2, 2.0001])   # b changed by only 0.0001

x1 = np.linalg.solve(A, b1)
x2 = np.linalg.solve(A, b2)
print(x1)   # [2. 0.]
print(x2)   # [1. 1.]  -- a TINY change in b caused a HUGE change in the solution!

A change of just 0.0001 in one entry of b caused the solution to shift by an entire unit — wildly disproportionate. If b came from real sensor measurements (which always carry some noise), this system would produce a dangerously unreliable answer, even though nothing about your code is "wrong."

The condition number — measuring this delicacy directly

The condition number of a matrix quantifies exactly this sensitivity, as a single number. A condition number near 1 means the matrix is well-behaved — errors don't get amplified. A very large condition number (thousands, millions) is a direct warning sign of the exact fragility demonstrated above.

import numpy as np
A = np.array([[1, 1], [1, 1.0001]])
print(np.linalg.cond(A))   # a very large number -- confirms severe ill-conditioning

A_good = np.array([[2, 0], [0, 3]])   # a well-behaved diagonal matrix, Chapter 2
print(np.linalg.cond(A_good))          # close to 1 -- well-conditioned
Connecting this back to eigenvalues, Chapter 6

For symmetric matrices, the condition number is exactly the ratio of the largest to smallest eigenvalue magnitude. A matrix with eigenvalues very close to zero (nearly singular, Chapter 4/5) alongside much larger ones has a huge condition number — this is the precise numerical signature of "this matrix is dangerously close to collapsing a dimension," tying Chapters 4, 5, 6, and 8 together into one coherent picture: singularity, low rank, near-zero eigenvalues, and ill-conditioning are all describing degrees of the exact same underlying fragility.

Section 8.3

Practical guidelines for real engineering code

Bringing together everything from this course into a short, concrete checklist for writing numerically trustworthy linear algebra code:

1. Never compute a matrix inverse just to solve a system

This was Chapter 4, Section 4.4's lesson, worth repeating as a hard rule: np.linalg.solve(A, b), never np.linalg.inv(A) @ b. Elimination-based solving is both faster and meaningfully more numerically stable.

2. Check the condition number before trusting a critical result

import numpy as np

def solve_safely(A, b, cond_threshold=1e10):
    cond = np.linalg.cond(A)
    if cond > cond_threshold:
        print(f"Warning: matrix is ill-conditioned (cond={cond:.2e}). "
              f"Solution may be unreliable.")
    return np.linalg.solve(A, b)

This kind of defensive check is standard practice in any control system, sensor fusion, or simulation code where a bad or misleading numerical answer could translate directly into a bad or dangerous physical action.

3. Use functions specialized for your matrix's structure

Section 6.5 already introduced this: prefer np.linalg.eigh over the general eig when you know a matrix is symmetric. The same principle generalizes — NumPy and SciPy have specialized, more accurate/faster routines for triangular, banded, and sparse matrices too. Exploiting known structure isn't just a performance optimization; it often meaningfully improves numerical accuracy as well.

4. Never test floating-point equality directly

Reiterating Section 8.1's rule, since it's the single most common numerical bug in beginner code: use np.isclose() or an explicit tolerance check, never bare ==, when comparing computed floating-point results.

5. Prefer well-scaled units

A subtle but real practical tip

If your matrix mixes wildly different magnitude quantities in the same system — say, one variable measured in meters (~1-10) and another in micrometers (~0.000001) — that mismatch itself tends to worsen conditioning. Where practical, scale your variables so they occupy similar numerical ranges (e.g., work in consistent SI base units) before assembling a matrix. This is a real, common cause of unexpectedly poor numerical behavior in engineering code that has nothing to do with the underlying physics being unstable — it's purely a units/scaling artifact.

Wrap-up

Recap

  1. Floating-point numbers are not exact — every arithmetic operation can introduce tiny rounding error, and never compare floats with ==.
  2. An ill-conditioned matrix amplifies small input errors (from noise or rounding) into large, unreliable output errors — distinct from singularity, but dangerously close to it.
  3. The condition number quantifies this sensitivity as a single number; large values are a direct, checkable warning sign.
  4. Ill-conditioning connects directly back to eigenvalues (Ch.6), rank (Ch.5), and singularity (Ch.4) — they're all describing degrees of the same underlying "close to collapsing a dimension" fragility.
  5. Practical rules: always solve() instead of computing an explicit inverse, check condition numbers on critical systems, use structure-specialized functions (like eigh for symmetric matrices), and keep variables in well-scaled, consistent units.
Check yourself

Quick check

Question 1

What's the difference between a singular matrix and an ill-conditioned matrix?

A singular matrix has determinant exactly zero and no inverse at all. An ill-conditioned matrix IS invertible (non-zero determinant) but is numerically "close" to singular, meaning small input errors get amplified into large, unreliable output errors.
Question 2

Why should you never write "if computed_value == 0.3" when checking a floating-point result in code?

Floating-point arithmetic accumulates tiny rounding errors, so a mathematically-correct result might come out as something like 0.30000000000000004 instead of exactly 0.3, causing an exact equality check to fail even though the answer is correct for practical purposes. Use a tolerance-based comparison instead.
Question 3

You're about to solve Ax=b for a safety-critical control system. What's one concrete check you should run before trusting the result?

Check A's condition number (np.linalg.cond(A)) — a very large value warns that the solution may be unreliable even if the solver returns an answer without error.

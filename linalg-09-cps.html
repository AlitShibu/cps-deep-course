Section 9.1

State-space representation, worked completely

Chapter 1 previewed the equation ẋ = Ax + Bu before you had the tools to use it. Now you have every piece: vectors (the state), matrices as transformations (Ch.2), and eigenvalues determining stability (Ch.6). Let's build one from scratch.

The physical system: a simple DC motor

Model a motor's state using two quantities: angular velocity ω and current i. The physics (from basic motor equations) gives:

ω̇ = -(b/J)*ω + (K/J)*i
i̇  = -(K/L)*ω - (R/L)*i + (1/L)*V

where b=friction, J=inertia, K=motor constant, R=resistance, L=inductance, and V is the applied voltage (our control input). This is already secretly a linear system — rewrite it as a state vector x = (ω, i) and control input u = V:

A = [ -b/J    K/J  ]      B = [  0  ]
    [ -K/L   -R/L  ]          [ 1/L ]

Plugging in example values (b=0.1, J=0.02, K=0.5, R=2, L=0.5):

A = [ -5     25   ]      B = [ 0 ]
    [ -1    -4    ]          [ 2 ]

Step 1: Is this system stable on its own (with no control input)?

Directly apply Chapter 6: find A's eigenvalues.

import numpy as np
A = np.array([[-5, 25], [-1, -4]])
eigvals = np.linalg.eigvals(A)
print(eigvals)   # complex pair, real part negative

The eigenvalues come out complex with negative real parts — per Chapter 6, Section 6.4, this means the motor's natural (uncontrolled) behavior is a damped oscillation: given a disturbance, it will spiral back toward rest rather than either blowing up or oscillating forever. Physically this matches intuition — friction (the b term) naturally damps the motor's motion.

Step 2: Simulating the system's response over time

import numpy as np

A = np.array([[-5, 25], [-1, -4]])
B = np.array([[0], [2]])

def simulate(A, B, x0, u_sequence, dt=0.01):
    x = x0.copy()
    history = [x.copy()]
    for u in u_sequence:
        x_dot = A @ x + (B.flatten() * u)
        x = x + x_dot * dt   # simple Euler integration step
        history.append(x.copy())
    return np.array(history)

x0 = np.array([0.0, 0.0])          # motor starts at rest
u_sequence = [12.0] * 200           # apply constant 12V for 200 steps
history = simulate(A, B, x0, u_sequence)
print("Final state (omega, current):", history[-1])

This loop is doing nothing more than Chapter 1's core stack-frame-style repeated operation, applied to physics: at every timestep, matrix-vector multiplication (Ch.2) computes how the state is currently changing, and that change gets accumulated into the state for the next step — the exact repeated-matrix-application idea from Chapter 6's stability discussion, just now with an added control input B*u pushing the system as well.

Why this is the payoff of the whole course, not just Chapter 6

Notice how many chapters this one example actually used: vectors to represent state (Ch.1), a matrix as the "rule" governing how state evolves (Ch.2), eigenvalues to assess stability before ever running a simulation (Ch.6), and — if you wanted to design a controller to change this behavior rather than just observe it — you'd reach for the pole-placement technique previewed in Ch.6's stability section, which is exactly what Control Systems II, later in your roadmap, teaches in full. This is precisely the kind of problem this entire course was built to prepare you for.

Section 9.2

Rotation matrices in robotics — tracking orientation

Chapter 2, Section 2.3 introduced the 2D rotation matrix R(θ) as one named transformation among several. In robotics, rotation matrices aren't just one example — they're a constant, central tool: every robot arm joint, every drone's orientation, every camera's viewing angle is tracked using exactly this machinery, extended to 3D.

3D rotation — building on the 2D case

A 3D rotation around the z-axis looks exactly like the 2D case, with an extra row/column that leaves the z-coordinate untouched:

Rz(θ) = [ cos θ   -sin θ   0 ]
        [ sin θ    cos θ   0 ]
        [   0        0     1 ]

Similarly, Rx(θ) and Ry(θ) rotate around the x- and y-axes respectively, leaving that axis's coordinate untouched. A robot arm's full orientation is typically built by composing several of these — directly applying Chapter 2, Section 2.4's lesson about matrix multiplication representing sequential transformations, and Section 2.4's specific warning that order matters now has real physical consequences: rotating around x then z gives a genuinely different final orientation than z then x.

Worked problem — tracking a drone's orientation through two rotations

Problem: A drone's onboard axis starts aligned with the world axes. It yaws (rotates around z) by 90°, then pitches (rotates around x) by 45°. Find its final orientation matrix, and where its original "forward" direction (1,0,0) now points.

import numpy as np

def Rz(theta):
    c, s = np.cos(theta), np.sin(theta)
    return np.array([[c, -s, 0], [s, c, 0], [0, 0, 1]])

def Rx(theta):
    c, s = np.cos(theta), np.sin(theta)
    return np.array([[1, 0, 0], [0, c, -s], [0, s, c]])

yaw = Rz(np.pi/2)     # 90 degrees
pitch = Rx(np.pi/4)   # 45 degrees

# Yaw happens first, then pitch is applied on top -- so pitch goes on the LEFT
# (Section 2.4: rightmost transformation acts first)
R_total = pitch @ yaw

forward = np.array([1, 0, 0])
new_forward = R_total @ forward
print(new_forward)   # direction the drone's nose now points, in world coordinates

Why the multiplication order here matters physically: if you'd written yaw @ pitch instead, you'd be describing "pitch first, then yaw" — a physically different sequence of motions producing a different final orientation, exactly the non-commutativity demonstrated concretely back in Chapter 2, Section 2.4. Getting this order backward is one of the most common real bugs in robotics kinematics code, and it's directly traceable to this course's Chapter 2 material.

Why this matters going forward in your roadmap

ROS2 (Year 3) represents every robot's pose using exactly this rotation-matrix machinery (often packaged as quaternions, a more compact representation with the same underlying rotational meaning). Computer Vision's camera projection matrices, Sensor Fusion's coordinate-frame alignment between different sensors, and Autonomous Racing's localization stack all depend on correctly composing rotations — this section is the direct mathematical seed for all of them.

Section 9.3

Closing the loop — how this course's nine chapters connect

The full thread, traced end to end

Vectors (Ch.1) represent quantities with magnitude and direction — including a system's entire state. Matrices (Ch.2) transform those vectors, and composing matrices models sequences of physical operations. Systems of equations (Ch.3) let you solve for unknowns a physical model implies, and inverses/determinants (Ch.4) tell you when a unique solution even exists — a question rank and linear independence (Ch.5) answer more deeply. Eigenvalues (Ch.6) reveal a matrix's "natural" behavior, most importantly whether a system is stable. Diagonalization (Ch.7) makes that natural behavior fully explicit and computationally cheap. Numerical practice (Ch.8) is what keeps all of the above trustworthy once you leave pen-and-paper for real floating-point code. And this final chapter showed both threads — state evolution and rotation — fully assembled into the kind of problem you'll actually solve in Control Systems II, ROS2, Sensor Fusion, and the Autonomous Racing stack.

You compose two 3D rotations as R2 @ R1 to rotate a vector. Which rotation is applied to the vector first?

R1 — the rightmost matrix in a product acts on the vector first (Chapter 2, Section 2.4), so R2 @ R1 @ v means "apply R1, then apply R2 to that result."

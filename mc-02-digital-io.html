Digital I/O

Chapter 1's blink sketch used one GPIO pin as an output. This chapter covers GPIO properly: configuring pins as input or output, reading a button press correctly (which is far less trivial than it first appears), and understanding pull-up/pull-down resistors and switch debouncing — both of which are direct, practical applications of ideas from Basic Electronics Chapters 2 and 3.

Chapter 2 of 7Builds on Chapter 1, Electronics Ch.2–3Reading and writing digital pins correctly
Section 2.1

GPIO pins and pin modes

A GPIO (General-Purpose Input/Output) pin can be configured, in software, as either a digital input or a digital output — the same physical pin, doing a completely different job depending on how pinMode() sets it up.

pinMode(pin, OUTPUT);        // the pin actively drives HIGH (5V/3.3V) or LOW (0V)
pinMode(pin, INPUT);           // the pin reads an externally-applied voltage
pinMode(pin, INPUT_PULLUP);      // the pin reads input, with an internal pull-up
                                     // resistor enabled (Section 2.3 explains why this matters)
What pinMode() is actually configuring, at the hardware level

Internally, each GPIO pin connects to a small piece of dedicated hardware that can either act as a voltage source driving the pin (output mode) or as a high-impedance voltmeter-like input reading whatever voltage is already present (input mode) — directly analogous to Electronics Chapter 7's voltmeter-vs-ammeter distinction: an input pin, like a voltmeter, is designed to disturb the circuit it's reading as little as possible.

Section 2.2

digitalWrite() and digitalRead()

digitalWrite(pin, HIGH);    // drive the pin to logic HIGH (5V or 3.3V, board-dependent)
digitalWrite(pin, LOW);       // drive the pin to logic LOW (0V)

int state = digitalRead(pin);   // returns HIGH (1) or LOW (0), based on the
                                    // voltage currently present on that pin
This is Digital Logic Chapter 1's binary abstraction, made physical

HIGH and LOW aren't exact voltages so much as voltage ranges the MCU interprets as a binary 1 or 0 — directly the same abstraction Digital Logic Design Chapter 1 introduced when explaining why real analog voltages get treated as clean binary values. A voltage that falls in an ambiguous zone between the two ranges (a genuinely possible real-world situation with a noisy or poorly-driven signal) can read unpredictably — part of why clean, well-defined HIGH/LOW signal sources matter in practice, not just in theory.

Section 2.3

Pull-up and pull-down resistors: fixing the "floating pin" problem

A simple push-button, wired naively (one side to the MCU pin, the other to ground, nothing else), leaves the pin's voltage completely undefined whenever the button isn't pressed — this is a floating pin, and it reads unpredictably (sometimes HIGH, sometimes LOW, sometimes flickering) due to tiny stray electrical noise.

A pull-up resistor holds the pin HIGH by default; pressing the button connects it directly to ground, pulling it LOW.
This is exactly Electronics Chapter 2's voltage divider, applied here

A pull-up resistor connects the pin to the supply voltage through a resistor, so with the button open, the pin sits firmly at a known HIGH (current draw is nearly zero into the high-impedance GPIO input, so almost no voltage drops across the resistor — Electronics Chapter 7's voltmeter-impedance reasoning again). Pressing the button connects the pin directly to ground, overpowering the pull-up and pulling the pin firmly LOW. A pull-down resistor is the mirror image: pin normally LOW, pulled HIGH when pressed. Either way, the pin now has a well-defined voltage in every button state — no floating, no ambiguity.

INPUT_PULLUP inverts your button logic — a very common beginner bug

Most MCUs have a built-in pull-up resistor enabled via pinMode(pin, INPUT_PULLUP), saving you from wiring an external one — but this means the pin reads HIGH when the button is not pressed, and LOW when it is pressed, the opposite of what many beginners intuitively expect. Code that checks if (digitalRead(pin) == HIGH) expecting that to mean "pressed" will have exactly backwards logic when using INPUT_PULLUP — always double check which state corresponds to "pressed" for your specific wiring.

Section 2.4

Debouncing mechanical switches

A mechanical button's metal contacts don't close cleanly in one clean instant — they physically bounce, making and breaking contact rapidly several times over a few milliseconds before settling. Read naively, a single human button press can register as multiple rapid presses in code.

This is exactly the RC transient physics from Electronics Chapter 3

A hardware debounce solution places a small capacitor across the switch, forming an RC low-pass filter (Electronics Chapter 4) that smooths out the rapid voltage chattering during the bounce period — the capacitor's charge/discharge time constant (τ=RC, Chapter 3) is chosen to be longer than the bounce duration but much shorter than any real button press, filtering out the noise while still responding quickly to genuine presses.

Software debouncing (the more common approach in practice)

unsigned long lastPressTime = 0;
const unsigned long debounceDelay = 50;   // milliseconds

void loop() {
    if (digitalRead(buttonPin) == LOW) {           // button pressed (INPUT_PULLUP wiring)
        if (millis() - lastPressTime > debounceDelay) {
            // genuine new press -- handle it here
            lastPressTime = millis();
        }
    }
}
Why a software debounce is usually preferred over adding a hardware capacitor

A capacitor and resistor per button adds board space, cost, and one more thing that can be wired wrong — a purely software debounce (simply ignoring any additional press events within a short window after the first) achieves the same practical result using only a timing check, at zero extra hardware cost. This is a genuinely common real-world trade-off in embedded design: solving a problem in software when it's cheap and reliable enough to do so, reserving hardware solutions for cases software genuinely can't handle (like Chapter 3's inductive flyback diode, which really must be a physical component).

Section 2.5

Worked problem — a debounced button-controlled LED toggle

Problem

Wire a button (using INPUT_PULLUP, so no external resistor is needed) to toggle an LED on and off with each distinct press — a naive digitalRead() check would register several toggles per single physical press due to bounce.

const int buttonPin = 2;
const int ledPin = 13;
bool ledState = false;
bool lastButtonReading = HIGH;      // HIGH = not pressed, with INPUT_PULLUP
unsigned long lastDebounceTime = 0;
const unsigned long debounceDelay = 50;

void setup() {
    pinMode(buttonPin, INPUT_PULLUP);
    pinMode(ledPin, OUTPUT);
}

void loop() {
    bool reading = digitalRead(buttonPin);

    if (reading != lastButtonReading) {
        lastDebounceTime = millis();     // reading changed -- reset the debounce timer
    }

    if (millis() - lastDebounceTime > debounceDelay) {
        // reading has been STABLE for longer than the debounce window --
        // it's a genuine state, not bounce noise
        if (reading == LOW) {              // genuine press detected (LOW = pressed)
            ledState = !ledState;
            digitalWrite(ledPin, ledState);
        }
    }

    lastButtonReading = reading;
}

Why this checks for stability rather than just timing since the last press: this version resets its timer every time the raw reading changes, and only treats a value as "real" once it's stayed constant longer than the debounce window — correctly handling the actual bounce pattern (rapid HIGH/LOW flickering) rather than just blocking a fixed time after the first detected edge, which can still misfire if bounce continues past a naive fixed delay.

Why toggling happens only once per press despite loop() running thousands of times per second: the toggle only fires the instant a debounced reading equals LOW while it's newly considered stable — combined with the state-change check, this naturally fires once per physical press-and-release cycle rather than continuously while the button remains held, since the reading itself doesn't keep "changing" while held steady.

Wrap-up

Recap

  1. A GPIO pin's job (drive vs. read voltage) is set by pinMode(); digitalWrite()/digitalRead() set/read its HIGH or LOW state — the same binary voltage-range abstraction from Digital Logic Chapter 1.
  2. An unconnected input pin floats and reads unpredictably. A pull-up or pull-down resistor (a direct application of Electronics Chapter 2's voltage divider) gives it a well-defined default state.
  3. INPUT_PULLUP uses the MCU's built-in pull-up, saving external wiring — but inverts button logic (HIGH=not pressed, LOW=pressed), a common source of bugs.
  4. Mechanical switches physically bounce, causing spurious multiple reads per press. Debouncing can be done in hardware (an RC filter, Electronics Ch.3–4) or in software (a timing check ignoring changes within a short window) — software is usually preferred for its zero extra hardware cost.
  5. A robust debounce implementation tracks how long a reading has been stable, not just time since the first detected change, to correctly reject continued bounce noise.
Check yourself

Quick check

Question 1

Why does an unconnected (floating) digital input pin read unpredictable, noisy values?

With nothing actively driving the pin to a known voltage, its voltage is left undefined and highly sensitive to tiny stray electrical noise nearby, causing it to read as HIGH or LOW unpredictably or flicker between them. A pull-up or pull-down resistor gives the pin a well-defined default voltage in every switch state, eliminating this ambiguity.
Question 2

If a button is wired with INPUT_PULLUP, what does digitalRead() return when the button is NOT pressed, and why is this often a source of bugs?

It returns HIGH when not pressed (the internal pull-up holds the pin high by default) and LOW when pressed (pressing connects the pin to ground). This is the opposite of many people's intuitive expectation that "pressed" should mean HIGH, so code that doesn't account for this inversion will have backwards logic.
Question 3

Why does a mechanical button press need debouncing at all?

A mechanical switch's contacts don't close in one clean instant -- they physically bounce, making and breaking contact rapidly several times over a few milliseconds before settling into a stable state. Read naively at full speed, this bounce can register as several rapid presses in code from what was physically a single press.

Analog I/O

Chapter 2's GPIO pins only understood two voltage states, HIGH and LOW. Most real-world sensors — temperature, light, position, pressure — produce a continuously varying voltage, not a clean binary signal. This chapter covers the ADC (analog-to-digital converter) that reads these continuous signals into digital numbers, and PWM, the standard trick for producing an analog-like output from a purely digital pin.

Section 3.1

The ADC: converting a continuous voltage into a number

An ADC (Analog-to-Digital Converter) measures an input voltage and reports it as a digital number, with a resolution that determines how many discrete levels that number can take.

10-bit ADC (Arduino Uno)   -> 2^10 = 1024 possible values (0 to 1023)
12-bit ADC (ESP32, typical) -> 2^12 = 4096 possible values (0 to 4095)
This is Digital Logic's binary representation, applied to a real continuous quantity

The ADC divides its full input voltage range (0V to a fixed reference voltage, often the board's own supply voltage) into evenly spaced discrete steps, then reports which step the actual input voltage falls closest to, as an ordinary binary number — directly the same binary-representation idea from Digital Logic Design Chapter 1, now applied to represent a genuinely continuous, real-world quantity rather than an inherently discrete one.

Voltage represented by reading = (reading / max_reading) × reference_voltage

# Example, Arduino Uno (10-bit, 5V reference):
reading = 512   ->   voltage = (512 / 1023) × 5V ≈ 2.5V
Why higher resolution matters: smaller voltage steps, more precision

A 10-bit ADC on a 5V reference resolves roughly 5V/1024 ≈ 4.9mV per step — any real voltage difference smaller than this is invisible to the ADC, rounded to the nearest available step. A 12-bit ADC on the same reference range resolves roughly 5V/4096 ≈ 1.2mV per step, four times finer. This directly matters for reading small or slowly-varying signals, where a coarser resolution can hide meaningful changes entirely inside a single ADC step.

The ESP32's ADC is notoriously non-linear near the extremes of its range

Unlike the Arduino Uno's comparatively clean ADC, the ESP32's built-in ADC has known non-linearity, particularly near 0V and near its upper reference voltage — readings there can deviate noticeably from the true voltage. For projects needing accurate absolute voltage readings from the ESP32, either restrict sensor output to the ADC's more linear middle range, or apply a calibration correction referencing the manufacturer's characterization data. This is a genuine, commonly-encountered hardware quirk, not a coding mistake.

Section 3.2

analogRead() in practice

int reading = analogRead(A0);   // reads pin A0, returns 0-1023 (Uno) or 0-4095 (ESP32)

void setup() {
    Serial.begin(9600);
}

void loop() {
    int sensorValue = analogRead(A0);
    float voltage = sensorValue * (5.0 / 1023.0);   // convert to actual volts, Uno reference
    Serial.println(voltage);
    delay(100);
}
Why the conversion uses 5.0/1023.0 as floats, not integer division

This is precisely C Programming's integer-vs-floating-point division pitfall — 5/1023 in C performs integer division and truncates to 0, silently destroying the entire calculation. Writing 5.0/1023.0 (or casting one operand to float) forces genuine floating-point division, exactly the fix covered when this same issue first appeared in C Programming's arithmetic chapter. This is one of the single most common bugs in beginner sensor-reading code, precisely because it compiles and runs with no error — it just silently produces zero.

A typical analog sensor circuit: the voltage divider, again

Many simple analog sensors (photoresistors/LDRs, some temperature sensors, potentiometers) don't output a voltage directly — they change resistance in response to the physical quantity being measured. Reading them requires forming a voltage divider (Electronics Chapter 2) with a known fixed resistor, then measuring the voltage at the midpoint with the ADC.

Why this is exactly Electronics Chapter 2's voltage divider, not a new concept

A photoresistor's resistance changes with light level; paired with a fixed resistor in series between supply voltage and ground, the midpoint voltage (read by the ADC) shifts as the photoresistor's resistance changes — precisely V_out = V_supply × (R_fixed/(R_fixed+R_sensor)) from Chapter 2's divider formula. Nothing new is happening electrically; the ADC is just the tool now reading that midpoint voltage as a number instead of a multimeter reading it as a display value.

Section 3.3

PWM and analogWrite(): faking an analog output

Most GPIO pins can only be fully HIGH or fully LOW — there's no true "analog output" pin capable of holding, say, exactly 2.5V indefinitely. PWM (Pulse-Width Modulation) works around this by switching the pin HIGH and LOW very rapidly, controlling the proportion of time spent HIGH (the duty cycle) to approximate an average voltage.

analogWrite(pin, value);   // value: 0 (always LOW) to 255 (always HIGH), 8-bit duty cycle
                              // 127 ≈ 50% duty cycle ≈ roughly half the average voltage
Higher duty cycle (more time HIGH per cycle) produces a higher effective average voltage — dimmer LED at low duty cycle, brighter at high duty cycle.
Why PWM works: the load's own physical response time smooths it out

PWM switches fast enough (typically hundreds of Hz to tens of kHz) that an LED's brightness, a motor's speed, or a heating element's temperature can't physically respond to the individual on/off pulses — they respond only to the average power delivered over many cycles, which is exactly this duty cycle relationship. This connects directly to Electronics Chapter 3's RC time constants: if the "smoothing" happens too slowly relative to the PWM frequency (or too quickly, for very low PWM frequencies), visible flicker or audible whine can result — PWM frequency choice is a genuine, practical design consideration, not an arbitrary detail.

Not every GPIO pin supports PWM

Only pins connected to the MCU's internal PWM-capable hardware timers (Chapter 4 covers timers directly) can run analogWrite() — on an Arduino Uno, this is a specific subset of pins, usually marked with a "~" symbol on the board's silkscreen. Calling analogWrite() on a non-PWM pin either does nothing useful or falls back to plain digitalWrite()-style behavior, depending on the specific board — always check the pinout diagram for PWM capability before wiring an analog-output-dependent circuit.

Section 3.4

Mapping and scaling values

ADC readings (0-1023 or 0-4095) and PWM duty cycles (0-255) rarely match the range a program actually wants to work with — the map() function linearly rescales a value from one range to another.

long map(long value, long fromLow, long fromHigh, long toLow, long toHigh)

int sensorValue = analogRead(A0);              // 0 to 1023
int brightness = map(sensorValue, 0, 1023, 0, 255);   // rescale to PWM's 0-255 range
analogWrite(ledPin, brightness);
map() is just the same linear-scaling math from earlier topics, packaged as a utility

Internally, map() performs exactly the kind of linear interpolation formula covered in Linear Algebra's early chapters — finding where a value sits proportionally within its source range, then placing it at the same proportional position within the target range. It's genuinely just arithmetic (and worth knowing it's integer arithmetic internally — inputs and outputs are long, so intermediate rounding can occur, occasionally worth watching for in precision-sensitive code).

Section 3.5

Worked problem — potentiometer-controlled LED brightness

Problem

A potentiometer (a 3-terminal variable resistor, wired as a voltage divider between supply and ground, with the wiper connected to an ADC pin) should control an LED's brightness via PWM, smoothly from off to full brightness as the knob turns.

const int potPin = A0;
const int ledPin = 9;    // must be a PWM-capable pin

void setup() {
    pinMode(ledPin, OUTPUT);   // analogWrite doesn't strictly require this, but it's good practice
}

void loop() {
    int potValue = analogRead(potPin);              // 0 to 1023 (Uno)
    int brightness = map(potValue, 0, 1023, 0, 255);  // rescale to PWM's 0-255 range
    analogWrite(ledPin, brightness);
    delay(10);   // brief delay -- smooths rapid ADC noise slightly, not strictly required
}

Why the potentiometer itself needs no additional circuitry: a potentiometer, wired with its two outer terminals across the supply and ground, is already a physical voltage divider (Electronics Chapter 2) whose ratio changes continuously as the wiper (middle terminal) moves — reading the wiper directly with the ADC captures exactly the divider's output voltage at whatever position the knob is currently in, with no extra fixed resistor needed since the potentiometer already provides both halves of the divider internally.

Why the resolution mismatch (0-1023 vs. 0-255) matters here specifically: without the map() call, feeding a raw ADC value up to 1023 directly into analogWrite() (which only accepts 0-255) would produce meaningless results for any potValue above 255 — the value would need to be interpreted modulo 256 or simply misbehave, since analogWrite() has no defined behavior for out-of-range inputs. The rescale is not optional here; it's required for the circuit to work at all.

Wrap-up

Recap

  1. An ADC converts a continuous voltage into a discrete digital number, with resolution (10-bit, 12-bit, etc.) setting how many distinct voltage steps it can distinguish — the same binary-representation idea from Digital Logic, applied to a real continuous quantity.
  2. Many analog sensors are resistance-based and need a voltage divider (Electronics Ch.2) to produce a readable voltage; analogRead() then reads that divider's midpoint, exactly as a multimeter would.
  3. Converting a raw ADC reading to actual volts requires floating-point division — the same integer-division pitfall from C Programming applies directly and silently if forgotten.
  4. PWM approximates an analog output by rapidly switching a pin, using duty cycle to control the effective average voltage — this only works because the driven load's own physical response is too slow to react to individual pulses. Not all pins support PWM.
  5. map() linearly rescales a value between two ranges — necessary whenever an ADC's resolution (e.g. 0-1023) doesn't match a target range (e.g. PWM's 0-255).
Check yourself

Quick check

Question 1

Why does a 12-bit ADC resolve smaller voltage differences than a 10-bit ADC, for the same reference voltage?

A 12-bit ADC has 4096 possible discrete steps across its voltage range, versus 1024 for a 10-bit ADC -- four times as many steps means each step corresponds to a smaller voltage difference, allowing the ADC to distinguish finer changes in the input voltage.
Question 2

Why does writing `voltage = sensorValue * (5/1023)` in C silently produce 0 instead of the intended conversion?

5/1023 with both operands as integers performs integer division in C, which truncates the true result (about 0.0049) down to 0. Multiplying sensorValue by 0 gives 0 regardless of the reading. Writing it as 5.0/1023.0 (or casting to float) forces floating-point division and produces the correct result.
Question 3

Why does PWM successfully make an LED appear to dim smoothly, even though the pin is only ever fully HIGH or fully LOW?

PWM switches the pin on and off fast enough that the LED (and the human eye) can't respond to the individual pulses -- what's perceived is the average power delivered over many cycles, which is controlled by the duty cycle (the proportion of time spent HIGH). A higher duty cycle delivers more average power, appearing brighter, even though the pin itself never holds an intermediate voltage.

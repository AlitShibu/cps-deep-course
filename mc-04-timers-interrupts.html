Timers & Interrupts

Chapter 1 flagged that delay() blocks everything. This chapter delivers the fix: millis()-based non-blocking timing, hardware timers running independently of your main code, and interrupts — a mechanism for responding to an event the instant it happens, rather than only when loop() happens to check for it. Together these are what let an embedded program genuinely do several things "at once."

Section 4.1

millis(): non-blocking timing

millis() returns the number of milliseconds since the MCU last started up — a continuously increasing counter your code can read at any time, without ever blocking.

unsigned long lastBlinkTime = 0;
const unsigned long blinkInterval = 500;
bool ledState = false;

void loop() {
    if (millis() - lastBlinkTime >= blinkInterval) {
        lastBlinkTime = millis();
        ledState = !ledState;
        digitalWrite(13, ledState);
    }
    // loop() keeps running immediately, free to do other work here too --
    // completely unlike delay(), which would have frozen everything for 500ms
}
The pattern: "has enough time passed?" instead of "wait until enough time passes"

This is the same underlying idea as C Programming's polling-loop patterns, applied to timing specifically: rather than pausing execution (delay()'s approach), the code checks, on every single pass through loop(), whether the target interval has elapsed yet — and if not, simply continues on to whatever else loop() needs to do, checking again next pass. loop() might run this check thousands of times before the interval actually elapses, and that's entirely fine; the check itself costs almost no time.

millis() overflows — and subtraction handles it correctly, but only if done right

millis() is stored as an unsigned long (32-bit), which overflows back to 0 after about 49.7 days of continuous uptime. Writing the comparison as millis() - lastBlinkTime >= blinkInterval (subtraction first, compared to the interval) handles this overflow correctly due to how unsigned integer wraparound arithmetic works — but writing it the seemingly-equivalent way, millis() >= lastBlinkTime + blinkInterval, breaks exactly at the overflow point. This subtle correctness detail is genuinely easy to get backwards, and worth remembering as a fixed idiom rather than re-deriving each time.

Section 4.2

Hardware timers

Beyond millis()'s software-level counting, MCUs contain dedicated hardware timer peripherals — independent circuits that count clock pulses entirely on their own, without any CPU involvement, and can be configured to trigger an action (like an interrupt, Section 4.3) at a precise, repeatable interval.

Why a hardware timer is more precise than a millis()-based software check

A millis()-based check only fires as often as loop() happens to reach that line of code — if loop() is busy doing something else (a slow sensor read, a long calculation), the check might run late, introducing timing jitter. A hardware timer counts independently in the background regardless of what the CPU is doing elsewhere, and can be set to fire an action at an exact, guaranteed interval — this is precisely why PWM (Chapter 3) is itself implemented using a hardware timer internally: the precise, jitter-free timing PWM needs simply isn't achievable through software polling alone.

Configuring hardware timers directly (rather than through the higher-level analogWrite()/millis() abstractions) involves setting specific timer registers — directly the "registers" concept from C Programming Chapter 13, now applied to a peripheral built specifically for precise timekeeping rather than general I/O.

Section 4.3

Interrupts: responding the instant something happens

An interrupt pauses whatever the CPU is currently doing, the instant a specified event occurs (a pin changing state, a timer reaching a count, data arriving on a communication line), runs a small dedicated function called an Interrupt Service Routine (ISR), then resumes exactly where the main program left off.

volatile bool buttonPressed = false;

void handleButtonPress() {       // this is the ISR
    buttonPressed = true;          // keep ISRs SHORT -- just flag it and return
}

void setup() {
    pinMode(2, INPUT_PULLUP);
    attachInterrupt(digitalPinToInterrupt(2), handleButtonPress, FALLING);
    // FALLING = trigger when the pin transitions from HIGH to LOW
}

void loop() {
    if (buttonPressed) {
        buttonPressed = false;
        // handle the actual button-press logic here, OUTSIDE the ISR
    }
}
Why the variable is declared volatile — a genuinely critical detail

C Programming Chapter 13 introduced volatile as telling the compiler "this value can change unexpectedly, don't optimize away repeated reads of it." An ISR can modify a shared variable at literally any instant, completely outside the normal flow of loop() — without volatile, the compiler might cache buttonPressed's value in a CPU register during loop(), never noticing the ISR changed the actual memory location, and the check would silently never see the update. This is not a theoretical concern; forgetting volatile on an interrupt-shared variable is one of the most notorious, hard-to-diagnose embedded bugs, precisely because the code often appears to work in testing and fails unpredictably.

Keep ISRs short — no delay(), no Serial.print(), minimal work

While an ISR runs, the CPU generally can't respond to most other interrupts (and on many platforms, normal timekeeping like millis() itself is paused) — a long-running ISR can cause other genuinely time-critical events to be missed entirely. The standard, disciplined pattern is exactly what the code above shows: the ISR does the absolute minimum (set a flag, store a value), and all the real handling logic happens back in loop(), checking that flag on its own schedule.

Section 4.4

Race conditions with shared data

Because an ISR can interrupt loop() at literally any point in its execution — including in the middle of reading or writing a multi-byte variable — code that reads a variable shared with an ISR needs to guard against reading it in a partially-updated, inconsistent state.

Why a multi-byte variable can be read "half-updated"

On an 8-bit AVR MCU, updating a 32-bit unsigned long actually takes several separate machine instructions to write each byte. If an interrupt fires between those instructions, loop() (running again after the interrupt returns, or even the ISR itself if it modifies the same variable) could observe a value that's part-old, part-new — neither the value before nor after the intended update, and simply wrong. Briefly disabling interrupts (noInterrupts() ... interrupts()) around the smallest possible section of code that reads or writes such a shared variable prevents this exact inconsistency, at the cost of a very brief window where new interrupts are delayed.

unsigned long safeCopy;
noInterrupts();          // briefly disable interrupts
safeCopy = sharedTimerValue;  // read the shared value safely, guaranteed consistent
interrupts();               // re-enable interrupts immediately after
Section 4.5

Worked problem — non-blocking blink alongside interrupt-driven button counting

Problem

Blink an LED every 500ms using millis() (not delay()), while simultaneously counting button presses via an interrupt — demonstrating both non-blocking timing and interrupts working together, something delay() alone could never achieve.

const int ledPin = 13;
const int buttonPin = 2;
unsigned long lastBlinkTime = 0;
const unsigned long blinkInterval = 500;
bool ledState = false;

volatile unsigned int pressCount = 0;

void countPress() {
    pressCount++;      // short, simple ISR -- just increments a counter
}

void setup() {
    pinMode(ledPin, OUTPUT);
    pinMode(buttonPin, INPUT_PULLUP);
    attachInterrupt(digitalPinToInterrupt(buttonPin), countPress, FALLING);
    Serial.begin(9600);
}

void loop() {
    // Non-blocking blink -- runs on its own schedule, never freezing loop()
    if (millis() - lastBlinkTime >= blinkInterval) {
        lastBlinkTime = millis();
        ledState = !ledState;
        digitalWrite(ledPin, ledState);
    }

    // Safely read the interrupt-updated counter
    noInterrupts();
    unsigned int currentCount = pressCount;
    interrupts();

    Serial.println(currentCount);
    // loop() keeps cycling continuously -- the LED keeps blinking on schedule
    // REGARDLESS of how many times the button is pressed in between
}

Why this couldn't be done with delay() and digitalRead() polling alone: a delay()-based blink would freeze loop() for up to 500ms at a time, during which any button press could be entirely missed if it happened to occur mid-delay — the interrupt approach guarantees the press is captured the instant it happens, completely independent of whatever loop() is doing at that moment, which is precisely the problem interrupts exist to solve.

Why noInterrupts()/interrupts() wraps only the single-line read, not the whole loop(): disabling interrupts for longer than strictly necessary risks missing a rapid follow-up button press during that window — keeping the disabled window as small as possible (just the one variable read) minimizes this risk while still guaranteeing a consistent read of the shared counter.

Wrap-up

Recap

  1. millis() enables non-blocking timing: check "has enough time passed?" on every loop() pass instead of blocking with delay(). Use the millis() - lastTime >= interval subtraction form specifically, to handle the ~49.7-day overflow correctly.
  2. Hardware timers count independently of the CPU, giving jitter-free precise timing (used internally by PWM) that a busy loop()'s millis() checks can't guarantee.
  3. An interrupt pauses the main program the instant a specified event occurs, runs a short ISR, then resumes exactly where it left off — enabling instant response regardless of what loop() is doing.
  4. Variables shared between an ISR and the main program MUST be declared volatile, or the compiler may cache a stale value and never notice the ISR's update — a classic, hard-to-diagnose embedded bug.
  5. ISRs should be kept as short as possible; multi-byte variables shared with an ISR should be read inside a brief noInterrupts()/interrupts() block to avoid reading a partially-updated, inconsistent value.
Check yourself

Quick check

Question 1

Why is `millis() - lastTime >= interval` the correct way to check elapsed time, rather than `millis() >= lastTime + interval`?

millis() overflows back to 0 after about 49.7 days. The subtraction form (millis() - lastTime) handles this overflow correctly due to how unsigned integer wraparound arithmetic works, while the addition form (lastTime + interval) breaks exactly at the point of overflow. The subtraction form should be used as a fixed idiom.
Question 2

Why must a variable shared between an ISR and the main loop() be declared volatile?

An ISR can change the variable at any instant, completely outside the normal flow of loop(). Without volatile, the compiler might optimize by caching the variable's value in a CPU register during loop() and never re-read the actual memory location the ISR modified, so the code would silently never see the interrupt's update.
Question 3

Why should an ISR do as little work as possible, deferring the real handling logic to loop()?

While an ISR runs, the CPU generally can't respond to most other interrupts, and normal timekeeping can be paused on many platforms. A long-running ISR risks missing other time-critical events entirely. The standard pattern is for the ISR to just set a flag or update a simple value, with all substantial handling logic done back in loop() on its own schedule.

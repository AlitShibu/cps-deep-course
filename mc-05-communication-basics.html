Communication Basics (Preview)

Every project so far has used one MCU talking to simple discrete components — an LED, a button, a potentiometer. Real projects usually need the MCU talking to other digital devices: sensors with their own onboard chips, displays, other microcontrollers. This chapter is a conceptual preview of the three protocols you'll encounter constantly — UART, I2C, and SPI — enough to use them confidently in a project immediately. The full byte-level protocol details, timing diagrams, and multi-device bus arbitration get their own dedicated treatment in the Serial Protocols topic later in this course.

Section 5.1

Serial/UART: the one you'll use immediately

UART (Universal Asynchronous Receiver-Transmitter) is the simplest communication method — two wires (TX: transmit, RX: receive), one device's TX connects to the other's RX and vice versa, and both sides must agree in advance on a baud rate (bits per second) since there's no shared clock signal telling the receiver when to sample each bit.

void setup() {
    Serial.begin(9600);         // start UART communication at 9600 baud
}

void loop() {
    Serial.println("Hello!");     // send text out over UART (usually to your computer)
    if (Serial.available() > 0) {   // check if incoming data has arrived
        int value = Serial.parseInt();  // read and parse a number from incoming data
    }
    delay(500);
}
The Serial Monitor is UART, viewed from the computer's side

When you open the Arduino IDE's Serial Monitor, you're using your computer's own UART-over-USB connection to the board — every Serial.print() in your sketch is literally the same UART protocol you'd use to talk to any other UART device, just happening to have your computer as the receiving end this time. This is why debugging with Serial.println() statements works at all: it's a real communication channel, not a special debugging-only feature.

Both sides must agree on the exact same baud rate

Since UART has no shared clock, a mismatched baud rate (the sketch uses 9600 but the Serial Monitor is set to 115200, for instance) causes the receiver to sample bits at the wrong moments, producing garbled, unreadable characters — not a clean error message, just visual noise. If a Serial Monitor shows gibberish, checking that the monitor's baud rate matches the sketch's Serial.begin() value is the very first thing to check.

Section 5.2

I2C: many devices, two shared wires

I2C (Inter-Integrated Circuit) uses just two shared wires — SDA (data) and SCL (clock) — that multiple devices can all connect to simultaneously, unlike UART's dedicated point-to-point pair. Each device on the bus has a unique address, so the MCU can direct communication to a specific device even though every device physically shares the same two wires.

#include <Wire.h>

void setup() {
    Wire.begin();                  // join the I2C bus as the controller ("master")
    Wire.beginTransmission(0x68);    // 0x68 -- the target device's I2C address
    Wire.write(0x00);                  // send a byte (often a register address to read/write)
    Wire.endTransmission();
}
Why a shared clock line (SCL) matters, compared to UART's baud-rate agreement

Because I2C provides an actual shared clock signal (SCL) that all devices see simultaneously, there's no need for a pre-agreed timing rate the way UART requires — every device just samples data relative to the clock edges it can directly observe. This is why I2C is often preferred for connecting several sensors or peripherals at once: adding a new device just means giving it a unique address and connecting it to the same two shared wires, rather than needing a whole new dedicated pair of wires per device as UART would.

I2C as a two-wire "party line" with named recipients

Think of I2C like a shared phone line multiple people can hear at once, where every message starts with a specific person's name — everyone hears everything, but only the addressed device responds or acts. This addressing scheme is exactly what lets a single MCU manage a temperature sensor, a display, and a real-time clock, all wired to the same two physical pins, provided each has a distinct address.

Section 5.3

SPI: faster, more wires, one device at a time (per line)

SPI (Serial Peripheral Interface) uses four signal lines: MOSI (Master Out Slave In), MISO (Master In Slave Out), SCK (shared clock), and CS/SS (Chip Select — one per device, used to indicate which specific device the current communication is addressed to).

#include <SPI.h>

void setup() {
    SPI.begin();
    pinMode(csPin, OUTPUT);
    digitalWrite(csPin, HIGH);   // CS idles HIGH; pulling it LOW selects that specific device
}

void sendByte(byte data) {
    digitalWrite(csPin, LOW);      // select this device
    SPI.transfer(data);              // send (and simultaneously receive) one byte
    digitalWrite(csPin, HIGH);         // deselect
}
Why SPI is generally faster than I2C, and what that speed costs

SPI's separate dedicated MOSI and MISO lines allow simultaneous full-duplex communication (sending and receiving at the same instant), and its clock rates typically run far higher than I2C's — making it the standard choice for higher-bandwidth peripherals like SD cards and displays. The cost is more wires overall (a dedicated CS line per device, rather than I2C's shared-address scheme), which makes SPI comparatively wire-hungry as more devices are added — a genuine, practical trade-off between speed and pin count that shows up constantly in real hardware design decisions.

Section 5.4

Choosing a protocol: a quick comparison

ProtocolWiresSpeedTypical use
UART2 (TX/RX), point-to-pointModerateDebug output, GPS modules, computer-to-board link
I2C2 (shared bus, many devices)ModerateMultiple sensors, RTCs, small displays
SPI4+ (dedicated CS per device)FastSD cards, high-speed displays, high-bandwidth sensors
A useful default heuristic for a first project

If you just need to see debug output or send simple commands from a computer, UART is the obvious default. If you're wiring up several simple sensors and want to conserve pins, reach for I2C. If a specific component's datasheet only supports SPI (common for displays and SD cards), you don't really have a choice — SPI it is. This chapter's job is to make these three names and their rough shapes familiar enough to read a datasheet's wiring diagram and know roughly what you're looking at; the Serial Protocols topic later will cover the actual bit-level framing, addressing conflicts, and multi-device bus management in full depth.

Section 5.5

Worked problem — a simple serial command interface

Problem

Build a sketch that reads a single-character command over Serial from the computer ('1' to turn an LED on, '0' to turn it off) and echoes back a confirmation.

const int ledPin = 13;

void setup() {
    Serial.begin(9600);
    pinMode(ledPin, OUTPUT);
}

void loop() {
    if (Serial.available() > 0) {
        char command = Serial.read();

        if (command == '1') {
            digitalWrite(ledPin, HIGH);
            Serial.println("LED ON");
        } else if (command == '0') {
            digitalWrite(ledPin, LOW);
            Serial.println("LED OFF");
        }
        // any other character is simply ignored
    }
}

Why `Serial.available() > 0` is checked first: this mirrors exactly the non-blocking philosophy from Chapter 4 — Serial.read() would return -1 (no data) if called when nothing has arrived yet, so checking availability first avoids acting on a meaningless "no data" read, and lets loop() continue freely doing other work whenever no serial command happens to be waiting, rather than blocking to wait for one.

Why this is a "preview" rather than a complete communication implementation: real command interfaces typically need to handle multi-character commands, parsing errors, and timing between bytes far more robustly than this single-character example — exactly the kind of protocol-design depth the dedicated Serial Protocols topic will cover, once the conceptual foundation from this chapter is in place.

Wrap-up

Recap

  1. UART: two dedicated wires (TX/RX), point-to-point, requires both sides to agree on a baud rate in advance since there's no shared clock. The Serial Monitor is UART from the computer's side — not a special debug-only mechanism.
  2. I2C: two shared wires (SDA/SCL) support many devices at once, each with a unique address — the shared clock (SCL) avoids UART's baud-rate agreement problem.
  3. SPI: faster, full-duplex, but needs a dedicated Chip Select line per device — the standard trade-off is speed and wire count against pin conservation.
  4. A practical default: UART for simple debug/command output, I2C for several simple sensors sharing pins, SPI when a component's datasheet requires it (displays, SD cards) or speed genuinely matters.
  5. This chapter is intentionally conceptual — full protocol timing, addressing details, and multi-device bus management are covered in depth in the later Serial Protocols topic.
Check yourself

Quick check

Question 1

Why does a mismatched baud rate between two UART devices produce garbled characters instead of a clear error?

UART has no shared clock signal -- both sides must independently agree in advance on the timing (baud rate) at which bits are sent and sampled. If the rates don't match, the receiver samples each incoming bit at the wrong moment relative to when it was actually sent, producing meaningless, garbled data rather than a detectable error condition.
Question 2

Why can multiple I2C devices share just two wires, while SPI needs a separate Chip Select line per device?

I2C devices each have a unique address, so a message on the shared SDA/SCL wires can specify exactly which device it's meant for -- every device hears it, but only the addressed one responds. SPI has no addressing scheme; instead, a dedicated Chip Select line per device is used to physically indicate which single device is active for the current transfer.
Question 3

In the serial command worked problem, why check Serial.available() before calling Serial.read()?

Serial.read() returns -1 if no data has arrived yet. Checking Serial.available() first avoids acting on this meaningless "no data" value, and lets loop() continue freely with other work when no command is currently waiting -- the same non-blocking philosophy as millis()-based timing from Chapter 4, rather than blocking until a command arrives.

Putting It Together

Six chapters have covered GPIO, analog I/O, timing, interrupts, communication, and power management as separate ideas. Real projects need all of them working together in one coherent piece of code. This closing chapter covers libraries and project structure — the practical skills for managing that complexity — introduces ESP32 WiFi/Bluetooth at a conceptual level, and finishes with a capstone project that deliberately uses nearly everything from this entire topic in one design.

Section 7.1

Using libraries

A library is pre-written code, packaged for reuse, that handles a specific component or task — a display driver, a sensor's communication protocol, a WiFi connection helper — so you don't need to implement low-level details (often I2C/SPI byte-level protocol handling, exactly the depth Chapter 5 deliberately deferred) yourself for every project.

#include <DHT.h>          // a library for DHT-series temperature/humidity sensors

DHT dht(2, DHT22);          // create a DHT object, tell it which pin and sensor model

void setup() {
    dht.begin();
}

void loop() {
    float temp = dht.readTemperature();   // the library handles the actual sensor
                                             // protocol internally -- you just get a number
}
A library is exactly C Programming's header/implementation separation, applied at scale

C Programming Chapter 8 covered splitting code into a header (declaring what's available) and an implementation file (the actual logic) so other code can use a function without needing to understand or even see how it works internally. A library is precisely this idea, packaged for distribution and reuse across many different projects and people — #include <DHT.h> gives you the declared interface (dht.begin(), dht.readTemperature()), while the actual bit-banging protocol details live in files you never need to open.

Not all libraries are equally reliable — check before committing a project to one

Community-contributed libraries vary enormously in code quality, maintenance status, and correctness — some genuinely have bugs, memory leaks, or blocking delays hidden inside seemingly simple function calls. Before relying heavily on an unfamiliar library (especially for a hackathon or coursework project with a deadline), it's worth briefly checking its documentation, recent update history, and open issues — the cost of discovering a critical bug in a third-party library the night before a deadline is far higher than the few minutes spent vetting it up front.

Section 7.2

Structuring a larger project

A one-file sketch works fine for a simple demo, but a real project (sensor node, robot controller, hackathon-style hardware system) quickly benefits from splitting code across multiple files, exactly as C Programming Chapter 8 recommended for larger C programs.

my_project/
  my_project.ino      -- setup()/loop(), high-level orchestration only
  sensors.h / sensors.cpp    -- all sensor-reading logic
  display.h / display.cpp     -- all display-update logic
  config.h                      -- pin number definitions, constants, in one place
Why a shared config.h for pin numbers is worth the discipline

Hardcoding pin numbers directly throughout a codebase (digitalWrite(13, HIGH) scattered across many files) makes rewiring a project — or adapting it to a different board — require hunting down every scattered reference. Centralizing every pin assignment as a named constant in one file (#define LED_PIN 13) means a hardware change is a one-line edit, and the rest of the code reads far more clearly (digitalWrite(LED_PIN, HIGH) documents its own intent) — directly the same "meaningful names over magic numbers" discipline from C Programming's earliest chapters.

This is also exactly why Chapter 6 (Git/Linux) matters for embedded projects specifically

A multi-file embedded project, developed collaboratively for something like a hackathon build, benefits from version control precisely the way any other software project does — branching to try a new sensor integration without breaking a working demo, tracking exactly which firmware version was flashed onto which physical board during testing, and coordinating changes across team members working on different subsystems (sensors vs. communication vs. power management) simultaneously.

Section 7.3

ESP32 WiFi and Bluetooth: a conceptual overview

#include <WiFi.h>

void setup() {
    WiFi.begin("network_name", "password");
    while (WiFi.status() != WL_CONNECTED) {
        delay(500);              // acceptable here -- one-time setup, not the main loop
    }
    Serial.println("Connected!");
    Serial.println(WiFi.localIP());   // the ESP32's assigned IP address on the network
}
Why WiFi connection uses delay() in setup() despite Chapter 4's warning

Chapter 4 flagged delay() as blocking and generally undesirable inside loop() — but a one-time connection step in setup(), before the device has any other ongoing responsibilities, is a reasonable, common exception: there's genuinely nothing else the program needs to be doing while it waits for a network connection to establish. The distinction is not "delay() is always bad," but "delay() is bad specifically when it would block other work loop() needs to keep doing" — context matters more than a blanket rule.

Once connected, an ESP32 can make HTTP requests to send sensor data to a server, host its own small web server to serve live sensor readings to a browser, or communicate over Bluetooth Low Energy (BLE) to a phone app — the exact mechanics of each involve library-specific APIs beyond this chapter's scope, but the conceptual shape is the same "connect, then send/receive data" pattern as the UART/I2C/SPI communication ideas from Chapter 5, just over a wireless network instead of physical wires.

WiFi/Bluetooth radios are a major power draw — directly relevant to Chapter 6

An active WiFi connection can draw significantly more current than the MCU's own processing — for a battery-powered project, this makes Chapter 6's power management directly relevant: connecting, sending data, then explicitly disconnecting or entering modem-sleep between transmissions (rather than holding a WiFi connection open continuously) is a standard, deliberate design pattern for battery-powered IoT nodes specifically because of this power cost.

Section 7.4

Capstone worked project — a self-adjusting light-monitoring node

Project spec

Build a device that reads ambient light via a photoresistor voltage divider, automatically adjusts an LED's brightness inversely to ambient light (dimmer room → brighter LED) using PWM, allows a debounced button press to toggle between this automatic mode and a fixed manual brightness, reports the current light level over Serial for monitoring, and — since this would realistically run on battery power — sleeps between readings to conserve power.

// config.h
#define LDR_PIN A0
#define LED_PIN 9          // must be PWM-capable
#define BUTTON_PIN 2
#define SLEEP_SECONDS 30

// main sketch
#include "config.h"

volatile bool modeButtonPressed = false;
bool autoMode = true;
unsigned long lastDebounceTime = 0;
const unsigned long debounceDelay = 50;
bool lastButtonReading = HIGH;

void handleButtonInterrupt() {
    modeButtonPressed = true;   // short ISR -- Chapter 4's pattern
}

void setup() {
    Serial.begin(9600);
    pinMode(LED_PIN, OUTPUT);
    pinMode(BUTTON_PIN, INPUT_PULLUP);
    attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), handleButtonInterrupt, FALLING);

    // --- Debounced mode-toggle check (Chapter 2's technique) ---
    bool reading = digitalRead(BUTTON_PIN);
    if (reading != lastButtonReading) lastDebounceTime = millis();
    if (millis() - lastDebounceTime > debounceDelay && modeButtonPressed) {
        autoMode = !autoMode;
        modeButtonPressed = false;
    }
    lastButtonReading = reading;

    // --- Read light level and set LED brightness (Chapter 3's ADC + PWM) ---
    int lightLevel = analogRead(LDR_PIN);                 // 0 (dark) to 1023 (bright)
    int brightness;
    if (autoMode) {
        brightness = map(lightLevel, 0, 1023, 255, 0);      // INVERSE: darker room -> brighter LED
    } else {
        brightness = 128;                                     // fixed manual brightness
    }
    analogWrite(LED_PIN, brightness);

    // --- Report over Serial (Chapter 5) ---
    Serial.print("Light: "); Serial.print(lightLevel);
    Serial.print(" | Mode: "); Serial.print(autoMode ? "AUTO" : "MANUAL");
    Serial.print(" | Brightness: "); Serial.println(brightness);

    // --- Sleep to conserve power (Chapter 6) ---
    esp_sleep_enable_timer_wakeup(SLEEP_SECONDS * 1000000ULL);
    esp_deep_sleep_start();   // execution restarts from the top of setup() on wake
}

void loop() {
    // intentionally empty -- deep sleep design keeps all logic in setup() (Chapter 6)
}

Why the debounce and mode-check logic sits inside setup(), unusually: because this design uses deep sleep (Chapter 6), the entire program restarts from setup() every wake cycle rather than looping continuously — so all logic that would normally live in loop() has to live here instead. This is a direct, concrete illustration of Chapter 6's "deep sleep restructures your whole program around setup()" point, not just an abstract warning.

Why the interrupt-based button check still matters despite the device spending most of its time asleep: an external interrupt (Chapter 4) can itself be configured as a wake source alongside the timer — meaning a real, more complete version of this project would also wake immediately on a button press, not just after the full 30-second timer, letting the mode toggle feel responsive even though the device is normally asleep. This capstone keeps the button check simpler (only evaluated during the brief awake window) to keep the example focused, but recognizing this extension is itself a demonstration of genuinely understanding how the pieces fit together, not just copying the pattern.

Every chapter in this topic, present in one design: Chapter 1's setup()/toolchain structure, Chapter 2's debouncing, Chapter 3's ADC reading and PWM output (plus the inverse map() relationship), Chapter 4's interrupt-driven button and short-ISR discipline, Chapter 5's Serial reporting, and Chapter 6's deep-sleep power management — this is precisely why "Putting It Together" is the right closing chapter for the topic, rather than introducing anything new.

Wrap-up

Recap

  1. A library packages reusable code behind a simple interface — the same header/implementation separation idea from C Programming, applied at the scale of sharing code across projects and people. Vet third-party libraries before depending on them for a deadline-driven project.
  2. Larger projects benefit from splitting code across multiple files and centralizing pin/constant definitions in one config file — both directly reduce the cost of later hardware or design changes, and both are exactly why version control (the Git/Linux topic) matters for real embedded projects.
  3. WiFi/Bluetooth follow the same "connect, then send/receive" shape as Chapter 5's wired protocols, just wireless — and carry a real power cost, making Chapter 6's sleep/disconnect discipline directly relevant for battery-powered networked devices.
  4. A blanket "delay() is bad" rule is an oversimplification — delay() in a one-time setup() step, before other ongoing responsibilities exist, is a reasonable, common exception to Chapter 4's general non-blocking-loop() guidance.
  5. A real embedded project is rarely one isolated concept — it's GPIO, analog I/O, timing, interrupts, communication, and power management all working together, exactly as the capstone project demonstrates.
Check yourself

Quick check

Question 1

How is using a library conceptually similar to C Programming's header/implementation file separation?

A library exposes a declared interface (function names you call, like dht.readTemperature()) while hiding the actual implementation details inside files you don't need to read or understand -- exactly the same separation as a .h header declaring what's available and a .c/.cpp file containing the real logic, just packaged for reuse across many different projects.
Question 2

Why is using delay() inside setup() to wait for a WiFi connection considered acceptable, even though Chapter 4 warned against blocking delays?

Chapter 4's warning specifically applies when delay() would block other ongoing work that loop() needs to keep doing. During a one-time setup() step, before the device has any other ongoing responsibilities to juggle, there's genuinely nothing else the program needs to be doing while it waits -- so the blocking behavior causes no practical harm in that specific context.
Question 3

In the capstone project, why does all the logic live in setup() instead of loop()?

The project uses ESP32 deep sleep, which (as covered in Chapter 6) restarts program execution from the very beginning of setup() on every wake cycle, rather than resuming loop() from where it left off. Since the device does its work, then goes back to sleep, then repeats, all the actual logic has to live in setup() -- loop() is never meaningfully reached in this design.

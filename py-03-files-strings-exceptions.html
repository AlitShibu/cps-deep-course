Files, Strings & Exceptions

C Chapter 11 made you manage FILE* pointers and check every return value by hand; C Chapter 5 made C strings a minefield of null terminators and buffer overflows. Python removes almost all of that ceremony — this chapter shows you the idiomatic, safe way to do both, plus exception handling, Python's real replacement for C's "check every return value" discipline.

Section 3.1

Strings — a real type, no null terminators

Recall C Chapter 5, Section 5.3 in full: a C string is just a char array with a '\0' convention, and half that section was pitfalls (buffer overflows, strcmp's surprising return value). Python strings are a genuine, built-in, immutable type — no manual memory, no terminator convention, and comparison works exactly the way you'd intuitively expect.

s = "Hello, World!"
print(len(s))            # 13 -- length is ALWAYS available, no strlen() needed
print(s[0])                # 'H' -- indexing works like a list
print(s[-1])                # '!' -- negative indexing, same as Chapter 2's lists
print(s[7:12])               # "World" -- slicing, same syntax as lists

a = "hello"
b = "hello"
print(a == b)                 # True -- normal == comparison, no strcmp() needed at all!

s2 = s.upper()                  # "HELLO, WORLD!" -- returns a NEW string; s itself is unchanged
print(s)                          # still "Hello, World!" -- strings are IMMUTABLE
Why strings are immutable, and what that means practically

Every string "modification" method (.upper(), .replace(), string concatenation with +) actually creates and returns a brand-new string, leaving the original completely untouched — directly analogous to Chapter 2's tuples. This eliminates an entire category of C bugs: there's no way to accidentally write past a string's "allocated size" (Chapter 5's buffer overflow pitfall) because Python manages a string's memory internally and a string is never resized in place — a new one is created instead whenever a "changed" version is needed.

Common string methods

s = "  Sensor Reading: 23.5  "
print(s.strip())                     # "Sensor Reading: 23.5" -- removes leading/trailing whitespace
print(s.lower())                      # "  sensor reading: 23.5  "
print(s.split(":"))                    # ["  Sensor Reading", " 23.5  "] -- split into a LIST
print(",".join(["a", "b", "c"]))        # "a,b,c" -- the REVERSE of split -- join a list into one string
print("Reading" in s)                    # True -- substring check, no strstr() needed

parts = s.strip().split(":")
value = float(parts[1].strip())            # "23.5" (a string) -> 23.5 (a float)
print(value)                                 # 23.5
Why this last pattern matters

Parsing a line of text into a usable number — reading a value out of a log line or a config file — is an extremely common real task, and this exact chain (strip → split → index → strip → float()) is the idiomatic Python way to do it, replacing what would be a much longer, pointer-and-buffer-heavy exercise using C's Chapter 5 string functions (strtok, manual character scanning, atof) by hand.

Section 3.2

File I/O — the "with" statement replaces manual cleanup

# Writing
with open("readings.txt", "w") as f:      # 'with' -- Python's answer to C's fopen/fclose discipline
    f.write("23.5\n")
    f.write("24.1\n")
# f is AUTOMATICALLY closed here, the instant the 'with' block ends -- guaranteed,
# even if an error happens partway through writing

# Reading, line by line
with open("readings.txt", "r") as f:
    for line in f:                          # iterate directly over a file's lines
        print(line.strip())                    # .strip() removes the trailing '\n'

# Reading the whole file at once
with open("readings.txt", "r") as f:
    contents = f.read()
    print(contents)
What the "with" statement is actually doing, and why it matters so much

Recall C Chapter 11's hard rule: every fopen needs exactly one matching fclose, and forgetting it risks losing buffered, unflushed data. Python's with statement (working with any "context manager," a broader Python concept this course won't need beyond files) guarantees the file gets closed when the block ends — including if an exception (Section 3.3) is raised partway through the block, which a plain open()/close() pair would not protect against without extra, easy-to-forget error-handling code. This is a structural, language-level solution to exactly the problem C Chapter 11 could only solve through programmer discipline.

Appending, and checking whether a file exists

with open("log.txt", "a") as f:    # "a" -- append mode, same meaning as C Chapter 11
    f.write("New log entry\n")

import os
if os.path.exists("readings.txt"):
    print("File found")
else:
    print("File not found")
Section 3.3

Exceptions — Python's replacement for checking every return value

Nearly every C chapter in this course included some version of the same warning: check malloc's return for NULL (C Ch.7), check fopen's return for NULL (C Ch.11), check fscanf's return count (C Ch.11) — C has no built-in error-signaling mechanism beyond "return a special value and hope the caller checks it." Python uses exceptions instead: when something goes wrong, Python immediately stops normal execution and jumps to the nearest matching error-handling code, rather than returning a value that's easy to silently ignore.

try:
    value = 10 / 0                # this will fail
except ZeroDivisionError:
    print("Cannot divide by zero!")

print("Program continues normally")   # this line still runs -- the exception was HANDLED
An exception immediately interrupts normal flow and jumps to matching error-handling code — it can't be silently ignored the way an unchecked return value can.

Catching specific exception types, and accessing error details

def safe_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError as e:
        print(f"Error: {e}")
        return None

def load_config(filename):
    try:
        with open(filename, "r") as f:
            return f.read()
    except FileNotFoundError:
        print(f"Config file {filename} not found -- using defaults")
        return ""

print(safe_divide(10, 2))    # 5.0
print(safe_divide(10, 0))    # "Error: division by zero" printed, then None returned
Why exceptions are a genuine structural improvement, not just different syntax

In C, a function signaling failure via a return value (like NULL from malloc/fopen) relies entirely on the caller remembering to check it — nothing in the language forces this, and every C chapter's pitfall boxes exist because it's so easy to forget. In Python, an unhandled exception doesn't get silently ignored — it propagates upward, interrupting the program with a clear error message (a "traceback") showing exactly where it happened, unless some surrounding code explicitly catches and handles it. This flips the default: in C, silence is the default and you must opt in to safety by remembering every check; in Python, loud failure is the default, and you explicitly opt in to graceful handling only where you've actually thought about what should happen.

raise — signaling your own errors

def set_temperature(value):
    if value < -273.15:                       # below absolute zero -- physically impossible
        raise ValueError(f"Temperature {value} is below absolute zero")
    return value

try:
    set_temperature(-300)
except ValueError as e:
    print(f"Invalid input: {e}")

raise lets your own functions signal a problem the same structural way built-in operations do — a direct replacement for C's convention of returning a special sentinel value (like -1 or NULL) to mean "something went wrong," which the caller has to know about and remember to check.

Section 3.4

Worked problem — a robust sensor log parser

Combining files, strings, and exceptions: parse a log file where some lines might be malformed, skipping bad lines instead of crashing the whole program.

# sensor_log.txt might contain:
# 23.5
# 24.1
# CORRUPTED
# 22.8

def parse_log(filename):
    readings = []
    try:
        with open(filename, "r") as f:
            for line_num, line in enumerate(f, start=1):   # enumerate: get index AND value together
                line = line.strip()
                if not line:                                  # skip blank lines
                    continue
                try:
                    value = float(line)
                    readings.append(value)
                except ValueError:
                    print(f"Skipping malformed line {line_num}: {line!r}")
    except FileNotFoundError:
        print(f"Log file {filename} not found")
        return []
    return readings

readings = parse_log("sensor_log.txt")
print(f"Successfully parsed {len(readings)} readings")
print(f"Average: {sum(readings)/len(readings):.2f}" if readings else "No valid readings")

What's happening structurally: two try blocks are nested — the outer one handles the file simply not existing at all (a total failure, nothing to parse), while the inner one handles one specific bad line at a time, letting the loop continue to the next line instead of aborting the entire parse over one corrupted entry. enumerate(f, start=1) gives both the line's content and its line number simultaneously, useful for the diagnostic message. This nested try structure — fail gracefully at the smallest possible scope, not the whole operation — is a genuinely idiomatic pattern worth internalizing.

Wrap-up

Recap

  1. Python strings are a real, immutable built-in type — no null terminators, no manual buffer sizing, and == compares content directly (no strcmp needed).
  2. The with statement guarantees a file gets closed when its block ends, even if an error occurs inside — a structural solution to C Chapter 11's "always remember fclose" discipline.
  3. Exceptions replace C's return-value-checking convention: an error interrupts execution immediately and loudly by default, rather than silently returning a value the caller might forget to check.
  4. try/except catches specific exception types; raise lets your own code signal errors the same structural way built-in operations do.
  5. Nested try blocks let you fail gracefully at the smallest useful scope (one bad line) rather than aborting an entire operation (the whole file) over one bad piece of data.
Check yourself

Quick check

Question 1

Why does Python's "with open(...) as f:" pattern solve a problem that C's fopen/fclose discipline (Chapter 11 of the C course) cannot fully solve through programmer discipline alone?

The with statement guarantees the file is closed when the block ends, even if an exception is raised partway through — this is enforced by the language itself, not by the programmer remembering to call close() in every possible code path, including error paths that are easy to overlook.
Question 2

In C, a failed malloc or fopen call returns NULL, which the caller must remember to check. What's the equivalent Python behavior, and how is the DEFAULT different?

Python raises an exception instead of returning a special sentinel value. The key difference in defaults: in C, an unchecked NULL is silently ignored if the programmer forgets to check it. In Python, an unhandled exception is loud by default — it interrupts the program with a visible error — unless the programmer explicitly writes a try/except to catch and handle it.
Question 3

In the worked log-parsing problem, why are there two separate try blocks instead of one large one wrapping everything?

The outer try handles a total failure (the file doesn't exist at all — nothing can be parsed). The inner try handles one malformed line at a time, allowing the loop to skip just that bad line and continue processing the rest of the file, rather than one bad line aborting the entire parse.

Writing Clean, Reusable Python

Every chapter so far has been one script at a time. Real projects — including the capstone that closes this course — span multiple files, need isolated dependencies per project, and get read by other people (or by you, months later). This chapter covers the organizational habits that make that possible: modules, virtual environments, and a few conventions worth adopting from day one.

Section 9.1

Modules — Python's answer to C's header files

Recall C Chapter 9's whole reason for existing: splitting code across files needs a way to share declarations. Python's answer is far simpler — any .py file is automatically a module, importable by name, no header file or prototype needed at all.

# sensor_utils.py
def celsius_to_fahrenheit(c):
    return c * 9/5 + 32

def is_valid_reading(value, min_val=-50, max_val=150):
    return min_val <= value <= max_val
# main.py
import sensor_utils

temp_f = sensor_utils.celsius_to_fahrenheit(23.5)
print(temp_f)                                        # 74.3

from sensor_utils import is_valid_reading             # import ONE specific name directly
print(is_valid_reading(200))                            # False
Why this is so much simpler than C's Chapter 9

There's no separate declaration/definition split (C Chapter 4's whole distinction), no header file, no include guards (C Chapter 9, Section 9.4) — Python reads the entire module and knows every function's signature directly from its one definition. The cost of this simplicity: Python re-parses and re-executes the whole module file at import time (once per program run, cached after that), rather than C's separate, faster compile-once-link-later model — another instance of Chapter 1's fundamental interpreted-vs-compiled tradeoff.

The `if __name__ == "__main__":` idiom

# sensor_utils.py
def celsius_to_fahrenheit(c):
    return c * 9/5 + 32

if __name__ == "__main__":
    # This code ONLY runs when sensor_utils.py is executed directly,
    # NOT when it's imported by another file
    print(celsius_to_fahrenheit(100))   # a quick self-test, e.g. `python sensor_utils.py`
What __name__ actually is

Python sets a special variable __name__ to "__main__" only when a file is run directly, and to the module's own name when it's imported elsewhere. This idiom lets a single file serve two purposes at once — a reusable library of functions and a runnable script with its own quick test/demo code — without the test code accidentally running every time someone else imports it. This pattern appears in nearly every real-world Python file with any standalone functionality, and it's worth adopting as a default habit.

Section 9.2

Virtual environments — isolating a project's dependencies

Every library this course has used (numpy, matplotlib, pandas, scipy) gets installed via pip install. Installing everything globally on your machine, across every project, is a recipe for real problems: two different projects might need incompatible versions of the same library, and it becomes impossible to know which packages a given project actually needs versus what's just globally present.

# Create a virtual environment (a self-contained, isolated Python install) named "venv"
python -m venv venv

# Activate it (Windows):
venv\\Scripts\\activate

# Activate it (Mac/Linux):
source venv/bin/activate

# Now pip install only affects THIS environment, not your whole system
pip install numpy matplotlib pandas scipy

# When you're done working on this project:
deactivate
A virtual environment is a private, disposable Python install per project — delete the venv folder, and every trace of that project's packages is gone, with zero effect on anything else.

requirements.txt — recording exactly what a project needs

# Save your project's exact dependencies to a file:
pip freeze > requirements.txt

# Someone else (or future you, on a new machine) can then recreate
# the exact same environment with one command:
pip install -r requirements.txt
Why this matters for sharing engineering code

A requirements.txt file is the practical answer to "what do I need installed to run this," and it's standard practice for any real Python project you'd share with a teammate (a hackathon project, for instance) or even just revisit yourself after months away. Without it, someone else's attempt to run your code fails with cryptic ModuleNotFoundErrors (Python Chapter 3's exception type) until they've manually guessed and installed every dependency one at a time.

Section 9.3

A sensible small-project structure

my_telemetry_project/
├── venv/                    # the virtual environment -- never share/commit this (Git track, .gitignore)
├── requirements.txt          # exact dependency list
├── data/
│   └── lap1.csv                # raw data files
├── sensor_utils.py             # reusable functions -- a module, Section 9.1
├── analysis.py                  # the main script that imports sensor_utils and does the actual work
└── README.md                     # a short explanation of what this project does and how to run it
Why separate "utility functions" from "the script that uses them"

This mirrors exactly the separation C Chapter 4 introduced between small, well-named functions and a main that orchestrates them — sensor_utils.py holds reusable, individually-testable logic; analysis.py reads like a short summary of what actually happens, calling into that logic. This separation also makes reuse genuinely easy: a second script analyzing different data can import sensor_utils too, without copy-pasting any code — directly solving the exact "don't repeat logic" motivation from the very first section of the C course.

A few naming and style conventions worth adopting now

  • snake_case for variables and functions (sensor_reading, not sensorReading) — the overwhelming Python convention, distinct from Java's camelCase.
  • Docstrings — a string literal right after a function's definition line, describing what it does. Tools and IDEs display these automatically when you hover over a function call.
  • Constants in ALL_CAPS at the top of a module — Python has no true const (C Chapter 2's keyword), but this naming convention signals "don't reassign this" to any reader, even though it's not compiler-enforced.
MAX_SENSOR_READING = 150.0    # a constant, by convention (not enforced by Python itself)

def celsius_to_fahrenheit(c):
    """Convert a Celsius temperature to Fahrenheit."""
    return c * 9/5 + 32
Wrap-up

Recap

  1. Any .py file is automatically an importable module — no header file, prototype, or include guard needed, unlike C's Chapter 9 machinery.
  2. The if __name__ == "__main__": idiom lets a file work both as a reusable library and a standalone runnable script, without its test/demo code running on import.
  3. Virtual environments (python -m venv) isolate each project's package versions from every other project and from your system Python — preventing version conflicts entirely.
  4. requirements.txt (via pip freeze) records a project's exact dependencies, so anyone else (or future you) can recreate the same environment with one command.
  5. Separating reusable logic (a module) from the script that orchestrates it mirrors C Chapter 4's function/main separation, and makes real reuse across multiple scripts genuinely easy.
  6. Adopt snake_case naming, docstrings, and ALL_CAPS constants as defaults — conventions, not compiler-enforced rules, but strongly expected in real Python code.
Check yourself

Quick check

Question 1

Why doesn't Python need anything equivalent to C's header files and include guards to share functions between files?

Any .py file is automatically an importable module -- Python reads the whole file and directly knows every function's full signature and body from its one definition, with no separate declaration step needed. There's also no risk of "including" the same file twice causing redefinition errors the way C headers can, since Python's import system only executes a module once per program run regardless of how many times it's imported.
Question 2

What problem do virtual environments solve, specifically?

They isolate each project's installed package versions from every other project and from the system-wide Python install, preventing situations where two projects need incompatible versions of the same library, and keeping it clear exactly which packages a given project actually depends on.
Question 3

What does the if __name__ == "__main__": idiom actually check, and why is it useful?

It checks whether the current file is being run directly (in which case __name__ equals "__main__") versus being imported by another file (in which case __name__ equals the module's own name). It's useful because it lets a file contain both reusable functions AND a quick self-test or demo script, without that demo code accidentally running every time some other file imports the reusable functions.

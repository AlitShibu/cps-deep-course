Section 10.1

The problem: a realistic telemetry analysis pipeline

The scenario: a vehicle's onboard logger recorded raw accelerometer and speed data during a test run, at 100Hz, with the usual real-world mess — sensor glitches, a bit of noise, and a need to answer concrete engineering questions from the cleaned result. This is deliberately the same kind of task your Motorsport track's Data Acquisition & Telemetry topic will have you doing with real hardware.

The pipeline has five stages, and each one is a direct callback to a specific earlier chapter:

StageChapter used
1. Load raw data from a fileChapter 7 — Pandas read_csv
2. Clean it (remove glitches/outliers)Chapters 4/7 — NumPy & Pandas boolean masking
3. Filter out noiseChapter 8 — SciPy's butter/filtfilt
4. Compute summary statisticsChapters 4/7 — NumPy/Pandas aggregation
5. Visualize before/afterChapter 6 — Matplotlib subplots
Why building this as one pipeline matters, not just five separate exercises

Real engineering data analysis is never one isolated operation — it's always a chain, where each stage's output feeds the next, and a mistake early (say, not removing an outlier before filtering) quietly corrupts everything downstream. Seeing all five stages connected in one script, with each stage's output feeding visibly into the next, is what actually builds the instinct for "what order do these operations need to happen in, and why" — a skill that reading the chapters in isolation doesn't fully deliver on its own.

Section 10.2

The full pipeline, built the way a real project should be

Following Chapter 9's project structure exactly: reusable logic lives in a module, and a separate script orchestrates it — directly mirroring C Chapter 4's function/main separation, one topic and one language removed.

# telemetry_utils.py -- the reusable module (Chapter 9, Section 9.1)
import numpy as np
import pandas as pd
from scipy.signal import butter, filtfilt

SENTINEL_VALUE = -999.0      # ALL_CAPS constant, Chapter 9's convention
OUTLIER_THRESHOLD_STD = 2.5    # how many standard deviations counts as an outlier

def load_telemetry(filepath):
    """Load raw telemetry from a CSV file into a DataFrame."""
    return pd.read_csv(filepath)

def remove_sentinels(series):
    """Remove sensor 'no data' sentinel values -- Chapter 4's masking idiom."""
    return series[series != SENTINEL_VALUE]

def remove_outliers(series, n_std=OUTLIER_THRESHOLD_STD):
    """Remove statistical outliers beyond n_std standard deviations from the mean."""
    mean, std = series.mean(), series.std()
    return series[np.abs(series - mean) < n_std * std]

def clean_signal(series):
    """Full cleaning pipeline: sentinels, then outliers -- Chapter 4/7's combined pattern."""
    return remove_outliers(remove_sentinels(series))

def filter_signal(series, fs, cutoff_hz, order=4):
    """Low-pass filter a signal -- Chapter 8's SciPy filtering."""
    b, a = butter(N=order, Wn=cutoff_hz, fs=fs, btype='low')
    return filtfilt(b, a, series.values)

def summarize(series, label):
    """Print a quick summary -- Chapter 4/7's aggregation methods."""
    print(f"{label}: n={len(series)}, mean={series.mean():.2f}, "
          f"std={series.std():.2f}, min={series.min():.2f}, max={series.max():.2f}")

if __name__ == "__main__":
    # Chapter 9's self-test idiom -- a quick sanity check when running this file directly
    test_data = pd.Series([1.0, 2.0, -999.0, 3.0, 100.0, 2.5])
    print(clean_signal(test_data).tolist())   # [1.0, 2.0, 3.0, 2.5] -- sentinel and outlier gone
# analysis.py -- the script that orchestrates the pipeline (Chapter 9, Section 9.3)
import numpy as np
import matplotlib.pyplot as plt
import telemetry_utils as tu

FS = 100   # sampling rate, Hz

# Stage 1: Load (Chapter 7)
np.random.seed(0)
t = np.arange(0, 5, 1/FS)
raw_accel = np.sin(2*np.pi*1.5*t) + np.random.randn(len(t))*0.4
raw_accel[100] = -999.0     # simulate a sentinel glitch
raw_accel[250] = 50.0        # simulate an outlier spike

import pandas as pd
raw_series = pd.Series(raw_accel)

# Stage 2: Clean (Chapters 4/7)
cleaned = tu.clean_signal(raw_series)
tu.summarize(raw_series, "Raw")
tu.summarize(cleaned, "Cleaned")

# Stage 3: Filter (Chapter 8)
filtered = tu.filter_signal(cleaned, fs=FS, cutoff_hz=5)

# Stage 4: Summarize the final result (Chapters 4/7)
print(f"Final filtered mean: {filtered.mean():.3f}, std: {filtered.std():.3f}")

# Stage 5: Visualize (Chapter 6)
fig, axes = plt.subplots(3, 1, figsize=(9, 7))
axes[0].plot(raw_series, alpha=0.6, color='red')
axes[0].set_title(f"Raw (n={len(raw_series)}) -- glitches visible")

axes[1].plot(cleaned.values, alpha=0.6, color='orange')
axes[1].set_title(f"Cleaned (n={len(cleaned)}) -- glitches removed")

axes[2].plot(filtered, color='green')
axes[2].set_title("Filtered -- noise smoothed out")

plt.tight_layout()
plt.savefig("pipeline_result.png")
plt.show()
What to notice about this split

telemetry_utils.py contains nothing that depends on this specific dataset — every function is general-purpose and reusable on any future telemetry file. analysis.py is the only place that knows about this particular run's data and parameters. If tomorrow you need to analyze a completely different sensor's data, telemetry_utils.py doesn't change at all — you write a new, short analysis script that imports the same reusable module. This is precisely the payoff Chapter 9 promised, now demonstrated on a genuinely complete, realistic task rather than a toy example.

Check yourself

Quick check — final review across the whole Python course

Question 1

In the capstone pipeline, why does cleaning (removing sentinels/outliers) happen BEFORE filtering, rather than after?

A filter processes the signal as a whole, and a large outlier (like the simulated 50.0 spike) would distort the filter's output across a wide surrounding region of the signal, not just at that one point. Removing outliers first ensures the filter only has to smooth genuine noise, not react to values that shouldn't be in the dataset at all.
Question 2

Why does telemetry_utils.py contain no code specific to the particular dataset being analyzed in analysis.py?

Keeping the module fully general-purpose means it can be reused, unchanged, for any future dataset or analysis script -- exactly Chapter 9's module/script separation. If dataset-specific details were mixed into the module, reusing it elsewhere would require editing it each time, defeating the purpose of factoring it out as a reusable module in the first place.

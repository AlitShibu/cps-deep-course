Putting It Together

Six chapters gave you four protocols, a decision framework, and a debugging method. This closing chapter shows they are one connected story rather than four separate facts to memorize: every protocol is a different answer to the same five questions, and each answer has a cost you can calculate in advance. Then it runs the whole story once, start to finish, on one realistic design — a greenhouse monitoring node that uses I2C, SPI, UART, and CAN together — choosing each link, budgeting pins and bus time with real arithmetic, structuring the firmware so nothing blocks, and bringing the system up in an order that makes every failure easy to localize.

Section 7.1

The whole topic in one picture

Here is the whole topic as one chain of reasoning, each link forged in an earlier chapter:

Ch.1  Bits must travel one at a time over few wires. The receiver
      must know WHEN each bit is valid (clock) and WHERE a frame
      starts and ends (framing). Either share a clock wire
      (synchronous) or agree on one in advance (asynchronous).
         │
Ch.2  UART: asynchronous. Start bit + stop bit frame each byte;
      both sides must agree on the baud rate, and the clocks may
      differ only by a few percent over one frame. Point-to-point.
         │
Ch.3  SPI: synchronous. A shared clock removes the tolerance
      problem and allows tens of MHz, but every extra slave costs
      a dedicated chip-select pin.
         │
Ch.4  I2C: synchronous, two wires, open-drain + pull-ups. Devices
      are chosen by address instead of by a wire, every byte is
      acknowledged, and several masters may share the bus.
         │
Ch.5  Differential signaling survives long, noisy cables. RS-485
      is UART-style framing carried that way; CAN adds dominant/
      recessive bits, ID-based arbitration, CRC, and ACK.
         │
Ch.6  No protocol is best. Match device count, distance, speed,
      noise, and pin budget to each protocol's known cost — then
      debug physical layer first, configuration second.
One sentence per chapter, memorized

1: a serial link needs a clock and a way to find frame boundaries. 2: UART agrees on the clock in advance and pays in speed. 3: SPI shares the clock and pays in pins. 4: I2C shares the wires and pays in speed and pull-up care. 5: CAN/RS-485 spend extra hardware to survive distance and noise. 6: choose by trade-off, debug from the wire upward.

The protocol is not the whole stack

Everything in this topic describes how bytes get from one chip to another. What those bytes mean is a separate layer on top: an I2C sensor's register map, the text of a GPS module's sentences, the 9-byte command format of a gas sensor, or an industrial scheme like Modbus RTU that defines meaning for bytes carried over RS-485. When a link "doesn't work," first decide which layer is broken: wires and signaling (Ch. 6's checklist), the protocol configuration (baud, mode, address), or the meaning of the bytes (the datasheet's register or message format). Debugging gets fast the moment you stop mixing the three.

Section 7.2

Five questions every protocol must answer

Strip away the details and every serial protocol in this course is an answer to the same five design questions. Seeing them side by side is what turns four protocols into one idea.

QuestionUARTSPII2CCAN
1. Who may talk, and when?Either end, any time (only two ends exist)Only the master starts; a slave speaks only while the master clocks itMaster starts; several masters allowed, conflicts settled by arbitrationAny node, any time; conflicts settled by identifier arbitration
2. Where do bits and frames start and end?Start/stop bits against a pre-agreed baud rateChip select goes low, clock pulses runSTART and STOP conditions, clock on SCLStart-of-frame bit, length code, bit-stuffing keeps edges coming
3. Who is the message for?The one other deviceWhichever slave has CS assertedThe device whose 7-bit address matchesEveryone receives; each node filters by identifier
4. How is a failure noticed?Optional parity, framing-error flagNot at allACK or NACK on every byteCRC, ACK, bit monitoring, automatic retransmission
5. What is physically on the wire?Single-ended push-pullSingle-ended push-pull, plus a clockOpen-drain with pull-up resistorsDifferential pair, dominant/recessive
Each stronger guarantee costs something you can name

Row 4 is the clearest example. SPI has no failure detection, so it needs no extra bits and runs fastest. I2C adds one ACK bit per byte, so a byte costs 9 clocks instead of 8. CAN adds a 15-bit CRC, an ACK slot, and stuff bits, so an 8-byte payload costs roughly 111 bit-times on the wire. Reliability is never free; it is paid for in overhead, in wires, or in hardware, and the table in Section 6.1 simply listed those bills.

Five back-of-envelope formulas worth keeping

Most protocol decisions need only these, applied before you write any code:

Raw bit rate is not data rate

A 400 kHz I2C bus never moves 400 kbit/s of payload: every 8 data bits cost 9 clocks, and every transaction also pays for a START, an address byte, and a STOP. A UART at 115200 baud carries at most 80% of that as payload. CAN at 250 kbit/s carries at most 64 payload bits per 111 on the wire, about 58%. Compare protocols on payload bytes per second and on latency, not on the headline clock number.

Section 7.3

Capstone — a greenhouse monitoring node, start to finish

The specification

A greenhouse controller built around an ESP32 must (1) read a temperature/humidity/pressure sensor and an ambient-light sensor, both mounted on the controller PCB; (2) show live readings on a 320×240, 16-bit-color TFT on the same PCB, redrawn five times a second; (3) read a CO₂ sensor module that talks UART at 9600 baud, answering a 9-byte request with a 9-byte reply; and (4) collect soil-moisture readings once per second from four small remote nodes spread along a 40 m greenhouse, next to pump motors and mains wiring, while also being able to send an urgent "stop all pumps" command that must never be delayed behind routine traffic.

Step 1 — choose a protocol for each link (Ch. 6)

LinkConstraintsChoiceWhy
Temperature/pressure + light sensors2 devices, a few cm away, slow dataI2CTwo shared wires however many sensors are added; two different fixed addresses (0x76 and 0x23), so no collision (Ch. 4)
TFT display1 device, a few cm away, about 1.2 Mbit per frameSPIOnly SPI offers the throughput; the display is write-only, so no MISO wire is needed (Ch. 3)
CO₂ moduleThe module only speaks UARTUARTNo decision to make; the device dictates it. 9600 baud, 8N1 (Ch. 2)
Four soil nodes + pump command40 m, motors and mains nearby, one message must preempt the restCANDifferential signaling for the noise, built-in arbitration so a low identifier always wins, CRC and ACK so a lost frame is retransmitted automatically (Ch. 5)

RS-485 would also span 40 m and reject the noise. CAN wins here only because of the last constraint: with RS-485 you would have to invent your own addressing, polling order, and collision rules, while CAN's identifier arbitration provides "this message always goes first" in hardware. If no message needed priority and a single master polled each node in turn, RS-485 would be the simpler, cheaper choice.

Four links, four protocols, each chosen for a different reason. Termination sits at the two physical ends of the CAN bus only.

Step 2 — count the pins (Ch. 3–5)

LinkGPIO pinsWhich signals
I2C2SDA, SCL
SPI to TFT5SCLK, MOSI, CS, plus the display's own data/command (DC) and reset (RST) lines — no MISO, since the display is never read

Notice that the display, a single device, costs more pins than the two I2C sensors and the entire CAN network combined. Had the two sensors been wired over SPI instead, they would have added a MISO line and two chip-select lines — three more pins — and a third sensor would add yet another. On I2C, the bus stays at two pins however many sensors share it.

Step 3 — budget the bus time (this section's key calculation)

Before writing any firmware, calculate how busy each link will actually be. Every number below uses the formulas from Section 7.2.

I2C (400 kHz, 2.5 µs per clock), sensors polled 10 times per second:
  BME280 burst read: address+W, register, restart, address+R, 8 data bytes
      = 11 bytes on the wire × 9 clocks = 99 clocks, plus about 3 for
        START / repeated START / STOP  → ~102 clocks ≈ 255 µs
  BH1750 read: address+R, 2 data bytes = 3 × 9 = 27 clocks (+ about 2)
      → ~29 clocks ≈ 73 µs
  One poll of both ≈ 0.33 ms;  10 polls/s ≈ 3.3 ms of every 1000 ms
  → bus busy ≈ 0.33 %

SPI to the TFT (20 MHz), full-frame redraw 5 times per second:
  One frame = 320 × 240 pixels × 16 bits = 1,228,800 bits
  Time per frame = 1,228,800 ÷ 20,000,000 = 61.44 ms
  5 frames/s = 307.2 ms of every 1000 ms
  → bus busy ≈ 30.7 %    (theoretical ceiling ≈ 16 fps)

UART to the CO₂ module (9600 baud, 8N1), one exchange every 2 s:
  9 bytes × 10 bit-times = 90 bits = 9.375 ms for the request,
  and another 9.375 ms for the reply  → 18.75 ms per exchange
  18.75 ms every 2 s = 9.375 ms of every 1000 ms
  → line busy ≈ 0.94 %

CAN (250 kbit/s, 4 µs per bit), four soil nodes at 1 frame/s each:
  Worst case ≈ 135 bit-times per 8-byte frame = 540 µs
  4 frames/s × 540 µs = 2.16 ms of every 1000 ms
  → bus busy ≈ 0.22 %
What the budget tells you

Three of the four links are almost idle. The sensor bus uses a third of one percent of its capacity, so I2C could carry dozens more devices before bandwidth mattered — the real limit on that bus is the number of distinct addresses and the total bus capacitance, not speed. The CAN bus is used for 0.22% of its time, which shows that CAN was chosen for reach, noise immunity, and priority, never for bandwidth. Only the display link is genuinely busy, at about 31%, and that is the one link where it matters how the transfer is performed.

The same display over I2C would not work

One frame is 1,228,800 bits = 153,600 bytes. On a 400 kHz I2C bus each byte costs 9 clocks = 22.5 µs, so a single frame would take 153,600 × 22.5 µs ≈ 3.46 seconds — about 56 times slower than SPI at 20 MHz, and nowhere near five frames per second. The protocol was not a matter of taste; a one-line calculation rules I2C out.

Step 4 — structure the firmware so nothing blocks

The budget shows that the CPU must juggle four links at once, and the worst thing it can do is wait on any of them. Three habits from earlier chapters combine here: the UART FIFO and driver buffer absorb bytes while the main loop is busy (Ch. 2); the SPI transfer for a whole frame is handed to DMA, so the CPU is free during those 61 ms; and the CAN peripheral's receive queue holds frames until the code drains it (Ch. 5). The loop below only starts things and collects results — no call waits more than a fraction of a millisecond.

#include <Wire.h>
#include "driver/twai.h"

uint32_t t_i2c = 0, t_co2 = 0, t_lcd = 0;
uint8_t  co2_buf[9];
uint8_t  co2_have = 0;
bool     co2_waiting = false;
uint32_t co2_timeouts = 0;

void loop() {
    uint32_t now = millis();

    // 1. I2C sensors: every 100 ms, about 0.33 ms of bus time
    if (now - t_i2c >= 100) {
        t_i2c = now;
        readBme280();                 // burst read from register 0xF7 (Ch. 4, Sec. 4.5 pattern)
        readBh1750();
    }

    // 2. UART CO2 module: request every 2 s, collect the reply later
    if (!co2_waiting && now - t_co2 >= 2000) {
        t_co2 = now;
        sendCo2Request();             // writes 9 bytes to the TX buffer and returns
        co2_have = 0;
        co2_waiting = true;
    }
    while (co2_waiting && Serial2.available() > 0 && co2_have < 9) {
        co2_buf[co2_have++] = Serial2.read();
    }
    if (co2_waiting && co2_have == 9) {
        handleCo2Reply(co2_buf);
        co2_waiting = false;
    } else if (co2_waiting && now - t_co2 > 100) {
        co2_waiting = false;          // no reply: give up, retry next cycle
        co2_timeouts++;
    }

    // 3. CAN: drain whatever has arrived; a wait time of 0 never blocks
    twai_message_t msg;
    while (twai_receive(&msg, 0) == ESP_OK) {
        handleCanFrame(msg.identifier, msg.data, msg.data_length_code);
    }

    // 4. Display: 5 fps; the push is DMA, so this call returns at once
    if (now - t_lcd >= 200) {
        t_lcd = now;
        startFramePushDma();          // helper from your display library
    }
}

This is a structural sketch, not a drop-in driver: readBme280, sendCo2Request, handleCanFrame, and startFramePushDma stand for the register-level code from Chapters 2–5 and your display library. The point is the shape. The CO₂ reply is collected in several passes through the loop instead of waiting 18.75 ms for it, and the timeout branch means a dead sensor costs one counter increment rather than freezing the whole node. The next topics on the roadmap (RTOS) replace this hand-rolled scheduler with proper tasks, but the underlying idea — never wait on a slow link — is identical.

The I2C bus that is stuck low after a reset

If the ESP32 resets in the middle of an I2C transaction, a sensor may be halfway through sending a byte and still holding SDA low, waiting for the master to supply the remaining clock pulses. The master wakes up, sees SDA stuck low, and concludes the bus is busy forever; a bus scan finds nothing even though wiring and pull-ups are fine. The standard recovery is to take control of the SCL pin, pulse it up to 9 times (8 data bits plus the ACK slot are enough to let any slave finish its byte) until SDA is released high, then generate a STOP condition and re-initialize the peripheral. This is the one failure in the chapter that the Ch. 6 checklist would not find by measuring pull-ups, because the symptom looks like a wiring fault and is actually a protocol-state fault.

Step 5 — bring it up one link at a time

A system with four buses fails in confusing ways if you power everything on at once. The disciplined order is to prove each link alone, using the cheapest check first, so that when something breaks you know exactly which link and which layer is responsible.

LinkFirst test, in isolationWhat a pass looks likeIf it fails, go to
UARTShort TX to RX on the ESP32 itself (loopback), then connect the moduleBytes sent are bytes received; logic analyzer decodes 9600 8N1 cleanlyCrossed TX/RX, baud mismatch (Ch. 2, 6)
I2CBus scan with only the two sensors connectedExactly two ACKs, at 0x23 and 0x76Pull-ups, wiring, address collision (Ch. 4, 6)
SPIRead the display controller's ID register, then fill the screen one solid colorCorrect ID; solid color with no wrong-colored or shifted pixelsSPI mode, DC line, bit order, logic levels (Ch. 3, 6)
CANFirst, the controller in self-test (no-ack) mode on a bench; then two nodes with a short cable and both terminatorsFrames sent are received; error counters stay at zeroMissing transceiver, termination, bit-rate mismatch (Ch. 5, 6)

The CAN row contains a lesson that comes straight from Chapter 5. A single CAN node alone on a bus will transmit a frame, see no node assert the ACK slot, flag an ACK error, and retransmit forever; its error counter climbs steadily although nothing is wrong with the node. That is why the first test uses a no-acknowledge self-test mode or a second node: the bus is behaving exactly as the protocol specifies, and the test must supply the missing ACK.

What "mastery" of this topic actually looks like

Not memorizing the frame diagrams. It is being handed a new sensor, display, or remote device and immediately asking the right sequence of questions: How many devices, how far, how fast, in what noise? Which of the five questions does this protocol answer cheaply, and which does it leave to me? How many pins and how much bus time will it cost, calculated in advance? What is the first test that proves this link alone? Section 7.3 was one worked answer to that sequence; the sequence itself is the transferable skill.

Wrap-up

Recap

  1. The whole topic is one chain: serial links need a clock and framing (Ch. 1) → UART agrees on the clock in advance (Ch. 2) → SPI shares the clock and spends pins (Ch. 3) → I2C shares the wires and uses addresses and ACKs (Ch. 4) → CAN/RS-485 spend extra hardware on distance and noise (Ch. 5) → the choice is a trade-off, and debugging starts at the wire (Ch. 6).
  2. Every protocol answers five questions — who talks when, where frames start and end, who a message is for, how failures are noticed, what is on the wire — and every stronger answer costs overhead, pins, or hardware.
  3. Compare links on payload throughput, not headline clock rate: UART carries 8 payload bits per 10 on the wire, I2C 8 per 9 plus per-transaction overhead, SPI nearly all, and an 8-byte CAN frame about 64 of roughly 111 bits.
  4. A bus-time budget (time busy per second) calculated before coding shows which links are idle and which are genuinely loaded; in the capstone only the display link, at about 31%, was busy, and the same display over I2C would have needed about 3.5 seconds per frame.
  5. Firmware for several links must never wait on a slow one: start transfers, collect results on later passes, use FIFOs, queues, and DMA, and give every wait a timeout.
  6. Bring a multi-bus system up one link at a time, using the cheapest isolating test for each (loopback, bus scan, ID read, self-test mode), and keep the three layers separate when debugging: wires, protocol configuration, and the meaning of the bytes.
Check yourself

Quick check

Question 1

A 128×64 monochrome OLED (1 bit per pixel, so 1,024 bytes per frame) can be driven over I2C at 400 kHz or over SPI at 8 MHz. Estimate the time to send one full frame over each, ignoring addressing overhead, and say whether the I2C version is acceptable.

I2C: 1,024 bytes × 9 clocks = 9,216 clocks ÷ 400,000 Hz = 23.04 ms per frame, about 43 frames per second. SPI: 1,024 × 8 = 8,192 bits ÷ 8,000,000 Hz = 1.024 ms per frame. SPI is about 22.5 times faster, but 23 ms per frame is easily fast enough for a small status display, so I2C is perfectly acceptable and saves pins. The comparison shows the decision depends on the actual data volume: the same two protocols that were wildly mismatched for the 320×240 color TFT are both fine for this much smaller screen.
Question 2

Six CAN nodes each send one 8-byte standard frame 20 times per second on a 125 kbit/s bus. Using the worst-case figure of 135 bit-times per frame, what fraction of the bus is used, and what does the result suggest about the design?

Total frames = 6 × 20 = 120 per second. Bits per second = 120 × 135 = 16,200. Utilization = 16,200 ÷ 125,000 ≈ 12.96%, about 13%. This is a comfortably light load, leaving large headroom for bursts and for lower-priority traffic, and it means the bus is nowhere near the point at which low-priority messages would be starved or delayed noticeably; the 125 kbit/s rate is more than adequate and also permits a longer cable than a faster rate would.
Question 3

After a reset in the middle of a transaction, an I2C bus scan finds nothing, pull-ups measure correctly at the supply voltage when idle, but SDA is being held low. Why does pulsing SCL up to 9 times fix it, and what must follow?

A slave that was mid-byte when the master reset is still waiting for the remaining clock pulses to finish shifting out its bits, and it holds SDA low while it does so. Each pulse on SCL lets it advance one bit; 8 data bits plus the ACK slot make 9 clocks, after which any slave has completed its byte and releases SDA. Once SDA reads high, the master should generate a STOP condition to put every device back in the idle state, then re-initialize its I2C peripheral. The fault was a stuck protocol state, not wiring, which is why measuring pull-ups alone does not reveal it.
Question 4

Using the five-questions table, which protocol gives the least help with question 4 (noticing a failure), and what silent symptom does that produce if an SPI slave is unpowered or disconnected?

SPI. It has no acknowledgment, no CRC, and no framing check: the master simply clocks bits out and reads whatever is on MISO. If the slave is absent or unpowered, nothing in the protocol signals an error; the master typically reads back a constant, meaningless value (often all 1s or all 0s, depending on whether MISO floats high or is pulled) and proceeds as though the transfer succeeded. This is why SPI bring-up should include reading a known identification register, whose expected value proves the slave is really there and responding.
Question 5

You power up one CAN node with a transceiver and a correctly configured controller, on a bench with no other node connected, and its transmit error counter climbs continuously. The node's code and wiring are correct. What is happening, and how do you test the node properly?

With no other node on the bus, no receiver asserts the dominant ACK bit in the ACK slot (Chapter 5, Section 5.3), so the transmitter detects an acknowledgment error on every frame, retransmits automatically, and its error counter rises — this is the protocol working exactly as designed. To test the node alone, switch the controller into a self-test (no-acknowledge) mode so it does not require an ACK, or connect a second node (with termination at both physical ends of the bus) that will acknowledge the frames.
